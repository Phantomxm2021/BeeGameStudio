# BeeGame Frontend Deployment

BeeGame is deployed as a Web SaaS frontend plus a BeeGame runtime host.

## Responsibilities

### Frontend

- Static React/Vite application.
- Uses Supabase Auth in the browser.
- Sends Supabase access tokens to the runtime host.
- Shows only the UI allowed by the current user's returned permissions.

### Supabase

- Owns Auth, RLS policies, account metadata, roles, credits, and durable SaaS records.
- Stores only data that should be durable and queryable.
- Does not expose service-role credentials to the frontend or local runtime host.

### Runtime Host

- Runs BeeGame sessions.
- Manages workspace filesystem access.
- Starts and stops previews.
- Streams transcripts and tool events.
- Calls Supabase using the current user's JWT and RLS/RPC, not service-role credentials.

## Required Production Environment

Frontend:

```env
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-supabase-anon-key
VITE_API_BASE_URL=https://runtime.your-domain.com
VITE_WS_BASE_URL=wss://runtime.your-domain.com
```

Runtime host:

```env
BEEGAME_SUPABASE_URL=https://your-project.supabase.co
BEEGAME_SUPABASE_ANON_KEY=your-supabase-anon-key
BEEGAME_SUPABASE_AVATAR_BUCKET=avatars
BEEGAME_SUPABASE_ASSET_BUCKET=beegame-assets
BEEGAME_WORKSPACE_ROOT=/srv/beegame/projects
BEEGAME_PREVIEW_PUBLIC_BASE_URL=https://runtime.your-domain.com/previews
```

Do not configure Supabase service-role keys in the frontend or runtime host for SaaS mode.

## Build

```bash
cd apps/frontend
bun install
bun run build
```

Deploy the generated `dist/` folder to your static hosting provider.

## Docker Compose

BeeGame can also run as two containers:

- `beegame-frontend`: Nginx serving the built React/Vite app.
- `beegame-runtime`: Bun runtime host for sessions, workspace files, previews,
  transcripts, and permission events.

Prepare the production env file:

```bash
cd docker
cp .env.production.example .env.production
```

Fill these required values:

```env
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-supabase-anon-key
VITE_API_BASE_URL=https://runtime.your-domain.com
VITE_WS_BASE_URL=wss://runtime.your-domain.com

BEEGAME_SUPABASE_URL=https://your-project.supabase.co
BEEGAME_SUPABASE_ANON_KEY=your-supabase-anon-key
BEEGAME_SUPABASE_AVATAR_BUCKET=avatars
BEEGAME_SUPABASE_ASSET_BUCKET=beegame-assets
BEEGAME_PREVIEW_PUBLIC_BASE_URL=https://runtime.your-domain.com/previews
```

Start the stack:

```bash
docker compose -f docker/docker-compose.yml --env-file docker/.env.production up -d --build
```

Default local ports:

- Frontend: `http://127.0.0.1:18080`
- Runtime host: `http://127.0.0.1:62174`

For production, put a TLS reverse proxy in front of those services:

- `https://app.your-domain.com` -> `beegame-frontend:80`
- `https://runtime.your-domain.com` -> `beegame-runtime:62174`

The runtime domain must proxy WebSocket upgrade headers.

Live previews use the runtime host under `/previews/*`. Route that path to
`beegame-runtime:62174` and keep `BEEGAME_PREVIEW_PUBLIC_BASE_URL` aligned with
the public URL, for example `https://runtime.your-domain.com/previews`.

## Runtime Host

Run the BeeGame runtime host separately from the static frontend. It should be deployed on a port/domain that does not conflict with generated game previews.

The host should use a managed workspace root generated by the platform. In server mode, users should not provide arbitrary workspace paths.

In Docker, generated projects are stored in the `beegame-projects` volume mounted
at `/srv/beegame/projects`. Do not mount the source repository itself as the
generated project workspace.

The runtime image seeds checked-in BeeGame skills into the `beegame-config`
volume on first start. If you later replace platform skills, update the volume
or recreate it intentionally.

## Authentication

Production authentication must use Supabase Auth. `VITE_API_AUTH_TOKEN` is only for dev/offline diagnostics and is ignored in production unless `VITE_BEEGAME_ALLOW_DEV_AUTH_TOKEN=1` is explicitly enabled.

## Protected managed previews

Managed preview URLs require a short-lived authenticated browser access session.
`/previews/*` is not a public sharing URL. Deploy the dashboard and runtime on
the same site so the runtime can use its scoped HttpOnly preview cookie.

## Admin Settings

Admin-only configuration includes:

- Model providers and API keys.
- Web search credentials.
- Runtime capability toggles.
- MCP server configuration.
- Workspace deployment policy.
- Credit policy and audit views.

Normal users should only see personal settings such as language and account profile.

## Production Checklist

Use the full preflight checklist in [BeeGame SaaS Preflight Checklist](../../docs/beegame-saas-preflight.md).

- Supabase Auth providers configured.
- RLS policies applied and verified.
- Storage buckets and policies applied for `avatars` and `beegame-assets`.
- Credit RPCs applied and tested.
- Runtime host uses anon key plus user JWT only.
- Static frontend uses Supabase anon key only.
- Generated project workspace is outside the repo.
- `.env.local` and generated `Projects/` data are not committed.
- Preview ports are isolated from frontend and runtime host ports.
- Docker runtime host does not contain Supabase service-role credentials.
