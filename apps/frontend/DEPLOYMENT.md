# BeeGame Frontend Deployment

BeeGame is deployed as a Web SaaS frontend plus a BeeGame runtime host.

## Responsibilities

### Frontend

- Static React/Vite application.
- Uses Supabase Auth in the browser.
- Uses refresh-capable HttpOnly sessions with the runtime host.
- Shows only the UI allowed by the current user's returned permissions.

### Supabase

- Owns Auth, RLS policies, account metadata, roles, credits, and durable SaaS records.
- Stores only data that should be durable and queryable.
- Does not expose service-role credentials to the frontend, distributed clients, or native model processes.

### Runtime Host

- Runs BeeGame sessions.
- Manages workspace filesystem access.
- Starts and stops previews.
- Streams transcripts and tool events.
- Uses the current user's JWT and RLS/RPC for user requests.
- The trusted V3 persistence host additionally uses a server-only service-role key for host workflow RPCs.

## Required Production Environment

Frontend:

```env
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-supabase-anon-key
VITE_API_BASE_URL=https://runtime.your-domain.com
```

Runtime host:

```env
BEEGAME_SUPABASE_URL=https://your-project.supabase.co
BEEGAME_SUPABASE_ANON_KEY=your-supabase-anon-key
BEEGAME_SUPABASE_AVATAR_BUCKET=avatars
BEEGAME_SUPABASE_ASSET_BUCKET=beegame-assets
AGENT_WORKFLOW_WORKSPACE_PATH=/srv/beegame/projects
BEEGAME_PREVIEW_PUBLIC_BASE_URL=https://runtime.your-domain.com/previews
```

Configure `BEEGAME_SUPABASE_SERVICE_ROLE_KEY` only on the trusted V3 persistence host. Never pass it to frontend build variables, distributed clients, or native model processes. In Compose, supply it through a runtime-only environment override; `.env.production` is shared with other services.

## Build

```bash
# From the repository root, using the same lockfile as CI and Docker:
bun install --frozen-lockfile --ignore-scripts
bun run --cwd apps/frontend build
```

Deploy the generated `apps/frontend/dist/` folder to your static hosting provider.
The frontend depends on workspace packages; a standalone npm install and local
`package-lock.json` are no longer supported.

To build only its Docker image, use the repository root as the context:

```bash
docker build -f docker/Dockerfile.frontend -t beegame-frontend .
```

`apps/frontend/Dockerfile` aliases the same recipe and also requires the root
context. This build does not compile or copy `vendor/bgs`.

## Docker Compose

The Compose stack has five services: `beegame-frontend`, `beegame-runtime`,
`beegame-billing`, `beegame-skills`, and `beegame-resources`.

From the repository root, prepare the environment files with:

```bash
bun run docker:init
```

Fill `docker/.env.production`, `docker/.env.billing`, and
`docker/.env.resource` as described in [Docker deployment](../../docker/README.md).
Keep billing and resource credentials in their dedicated files, and inject the
V3 host credential only into `beegame-runtime`.

Apply the database migrations, including
`supabase/migrations/20261022010000_single_runtime_model.sql`, before deploying
the single-model runtime. Saved model configurations keep their selected
`models.balanced` database value; the API and UI expose one `model` field.

Start the stack:

```bash
bun run docker:up
```

Default local ports:

- Frontend: `http://127.0.0.1:18080`
- Runtime host: `http://127.0.0.1:62174`

For production, put a TLS reverse proxy in front of those services:

- `https://app.your-domain.com` -> `beegame-frontend:80`
- `https://runtime.your-domain.com` -> `beegame-runtime:62174`

Project chat events use authenticated SSE; keep streaming responses unbuffered. Development preview proxies may also require WebSocket upgrade headers.

Live previews use the runtime host under `/previews/*`. Route that path to
`beegame-runtime:62174` and keep `BEEGAME_PREVIEW_PUBLIC_BASE_URL` aligned with
the public URL, for example `https://runtime.your-domain.com/previews`.

## Runtime Host

Run the BeeGame runtime host separately from the static frontend. It should be deployed on a port/domain that does not conflict with generated game previews.

The host should use a managed workspace root generated by the platform. In server mode, users should not provide arbitrary workspace paths.

In Docker, `../.beegame/projects` is bind-mounted at `/srv/beegame/projects`.
Keep generated project data out of version control and separate from source files.

The `beegame-config` volume persists host configuration. Enabled user skills
are materialized from the Skills service for runtime turns; startup does not
seed bundled Skills into that volume.

## Authentication

Production authentication must use Supabase Auth. `VITE_API_AUTH_TOKEN` is only for dev/offline diagnostics and is ignored in production.

## Admin Settings

Admin-only configuration includes:

- Model providers and API keys.
- Web search credentials.
- Runtime capability toggles.
- MCP server configuration.
- Workspace deployment policy.
- Credit policy and audit views.

Normal users should only see personal settings such as language and account profile.

## Production Checklist

Use the full preflight checklist in [BeeGame SaaS Preflight Checklist](../../docs/beegame-saas-preflight.md).

- Supabase Auth providers configured.
- RLS policies applied and verified.
- Storage buckets and policies applied for `avatars` and `beegame-assets`.
- Credit RPCs applied and tested.
- User requests use anon key plus user JWT; trusted V3 host RPCs use the host-only service-role key.
- Static frontend uses Supabase anon key only.
- Generated project workspace is separate from source files and excluded from version control.
- `.env.local` and generated `Projects/` data are not committed.
- Preview ports are isolated from frontend and runtime host ports.
- Native/model environments and frontend build arguments exclude service-role credentials.
