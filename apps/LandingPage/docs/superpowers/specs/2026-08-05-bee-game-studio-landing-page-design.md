# Bee Game Studio 产品展示落地页设计规格

日期：2026-08-05

## 1. 目标

为尚未正式上线的 Bee Game Studio 设计并实现一页式产品展示落地页。页面主要打动三类访客：

1. 没有开发经验，但一直有游戏想法的人；
2. 希望更自由地完成个人作品的独立游戏创作者；
3. 关注新一代游戏创作方式的投资人和合作伙伴。

页面的首要业务目标是收集候补名单，而不是直接引导用户使用尚未上线的产品。

## 2. 品牌表达原则

Bee Game Studio 不被描述为 AI 编程工具、游戏模板生成器或智能体集合，而被表达为一种新的游戏创作方式。

所有文案遵循以下顺序：

1. 先说用户一直想实现、却难以实现的愿望；
2. 展示具体使用场景和用户感受到的变化；
3. 用作品的持续成长、所有权和发布可能性建立信任；
4. 最后再提出 Bee Game Studio 对游戏创作未来的判断。

页面不展示模型名称、智能体数量、Token、技术架构、性能参数或功能清单。技术只在确有必要时作为可信度依据出现，不作为主要销售语言。

## 3. 核心主张

主标题：

> 让想象，真正发生。

首屏说明：

> 从一个念头，到一款可以亲手体验、继续改变的游戏。Bee Game Studio，让更多人参与游戏创作。

主要行动按钮：

> 加入候补名单

## 4. 页面叙事

### 4.1 首屏：想象开始发生

首屏表现一张纸上的游戏构想逐渐成为真实、可体验场景。文字不是从功能开始，而是直接承诺创作方式的改变。

辅助表达：

> 不是从一张功能清单开始，而是从你最想亲手体验的那一刻开始。

### 4.2 一直存在的遗憾

主标题：

> 每个人心里，都有一款还没被做出来的游戏。

正文讲述普通人反复想象的冒险、只想与朋友探索的地方，以及从未有人做过的玩法。结尾只表达 Bee Game Studio 想改变“只有掌握完整制作流程才能开始”的现状。

### 4.3 打破旧规则

使用“深夜便利店”作为叙事样例，先提出一个行业长期忽略的事实：

> 最好的游戏，往往还不存在。

它只存在于某个人的想象里。过去，这些想法只能停在脑海里；现在，它们可以成为真正的游戏。这里不解释产品如何工作，只展示 Bee Game Studio 让哪些体验第一次拥有了存在的可能。

### 4.4 产品价值

主标题：

> 游戏，不该只被别人做出来。

三句文案不再描述操作步骤，而是呈现“只有你会想到”的体验：

- 雨夜，按照你记得的样子下起来。
- 沉默的客人，说出只有你知道的秘密。
- 每个选择，都留下你的回声。

正文强调这不是更多功能，而是让想法、感受和选择第一次属于同一个人。

### 4.5 身份改变

主标题：

> 玩游戏的人，也可以创造游戏。

四列从时间线改为创作者的四个判断：你的感觉、你的选择、真实的体验、你的名字。结尾确认作品所有权：它可以被更多人看见，但始终属于你。

### 4.6 品牌愿景

主标题：

> 创作游戏，不该只是少数人的特权。

这一屏面向创作者、投资人和行业伙伴，提出 Bee Game Studio 是新的创作方式，而不是对旧工具的局部提效。

### 4.7 候补名单

结尾重新回到访客自己的想法：

> 你的游戏，会从哪里开始？

候补名单收集：

- 称呼；
- 邮箱；
- 身份：有游戏想法的人、独立游戏创作者、投资人或合作伙伴；
- 提交时间；
- 页面来源；
- 提交时的语言。

## 5. 视觉方向

视觉不采用常见 AI 产品的渐变、粒子、发光网络、仪表盘、功能卡片、蜂巢符号或 Prompt 输入框中心构图。

核心视觉语言是：

> 一张纸上的构想，逐渐成为可亲手体验的场景。

首屏采用克制的电影式摄影：黑色工作台、象牙色纸张、铅笔痕迹、逐渐立体化的微缩游戏场景。中段通过暖白、雨夜深绿和低饱和浅绿切换情绪，结尾回到深色愿景，再以暖白候补名单结束。

图像生成可用于制作叙事插图，但所有插图必须满足：

- 共同使用“草图到可玩场景”的物质变化；
- 不包含生成器水印、伪造的产品截图或虚构用户案例；
- 不出现通用 AI 视觉元素；
- 为页面文字预留明确的负空间；
- 保持统一的摄影、微缩模型、材质和光线语言。

## 6. 多语言

页面支持四种语言：

- 简体中文：`zh-CN`；
- 英文：`en`；
- 日文：`ja`；
- 韩文：`ko`。

### 6.1 自动选择

首次访问时读取 `navigator.languages`，按顺序匹配支持语言。匹配规则：

- 所有中文地区代码先回退到 `zh-CN`；
- 英文地区代码回退到 `en`；
- 日文地区代码回退到 `ja`；
- 韩文地区代码回退到 `ko`；
- 其他语言默认显示英文。

### 6.2 手动选择

导航栏提供语言选择器，显示语言原名：简体中文、English、日本語、한국어。用户选择后立即切换页面内容，并把选择保存到 `localStorage`。后续访问优先使用已保存选择，不再覆盖为浏览器语言。

页面根元素的 `lang` 属性必须同步更新。语言选择器可以用键盘完整操作，并具有清晰的可访问名称和焦点状态。

### 6.3 本地化与排版

四种语言使用独立、人工确认的文案文件。不得将中文断行、句长或标点位置直接复用到其他语言。

- 中文：中文字体优先、严格行首行尾禁则、正文约 28–32 个汉字行长，不压缩汉字字距；
- 英文：采用西文显示字体与正文体，允许适度负字距用于超大标题，按英文短语平衡断行；
- 日文：使用日文字体优先栈、日文标点与禁则处理，避免把助词孤立在行首；
- 韩文：使用韩文字体优先栈，按韩语词组断行，正文不使用中文式强制断行。

品牌名 Bee Game Studio 保持英文，不翻译。

## 7. 技术边界

- 前端：Vite、React、TypeScript；
- 不保留当前工作区已有的页面实现，从干净的前端结构重新搭建；
- 国际化采用项目内静态字典，不引入重量级国际化框架；
- 候补名单由 Supabase 持久化；
- 前端只使用 Supabase 匿名公钥，不包含服务角色密钥；
- 提供建表、约束、索引和 RLS 策略 SQL；
- 表单需要客户端校验、重复邮箱友好提示、提交中状态、成功状态和失败重试；
- 页面不需要登录、账户系统、后台管理界面、博客、价格表或产品编辑器。

## 8. 候补名单数据与安全

建议表名：`waitlist_signups`。

最低字段：

- `id`：UUID 主键；
- `name`：称呼；
- `email`：规范化后的邮箱，唯一；
- `persona`：枚举或受约束文本；
- `locale`：提交语言；
- `source`：来源；
- `created_at`：服务端提交时间。

匿名用户只能插入，不允许读取、更新或删除。重复邮箱由数据库唯一约束保证。前端错误信息不得泄露数据库内部细节。

## 9. 响应式与可访问性

- 首屏在桌面、平板和手机上都保持标题、插图和主要按钮清晰；
- 小屏幕允许插图裁切，但不得遮挡文字；
- 正文不使用过小字号，交互控件满足触控尺寸；
- 所有插图提供对应语言的替代文本；
- 支持键盘导航、可见焦点、减少动态效果偏好和足够色彩对比度；
- 动画只用于表现“构想逐渐成形”，不得妨碍阅读。

## 10. 验收标准

1. 首次访问能根据浏览器语言显示中文、英文、日文或韩文；
2. 用户能通过导航栏切换语言，刷新后保持选择；
3. 四种语言的页面标题、正文、按钮、表单和状态信息均完整本地化；
4. 不同语言使用各自的字体、断行和排版规则；
5. 候补名单成功写入 Supabase，并记录称呼、邮箱、身份、来源、语言和时间；
6. 重复邮箱、无效输入、网络错误和成功提交都有清晰反馈；
7. 页面视觉与已确认的“草图成为可玩场景”方向一致；
8. 页面不出现技术功能堆砌、虚构案例或通用 AI 视觉模板；
9. 桌面与移动端构建通过，无明显溢出、遮挡或不可操作内容。
