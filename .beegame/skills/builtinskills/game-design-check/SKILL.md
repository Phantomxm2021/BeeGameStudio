# Game Design Check

Check whether the assigned design can be used by its downstream team without guessing necessary product decisions. Take the original confirmed requirements, current responsibility prompt and delivery stage as inputs. This Skill supplies checking methods, not a second definition of ownership, release scope or phase authority.

## Select the applicable checks

Use the relevant sections of [document checks](references/document-checks.md). Native BGS loads the assigned sections directly from this reference with the reviewer task; reuse those bytes rather than rereading them. Otherwise read the needed sections, including an additional dependency discipline when required. In joint inspection, cover all assigned saved drafts and their actual dependencies; in revision verification, read the affected clauses and consumers. Do not load unrelated discipline guidance.

Apply checks only to the confirmed game and current assignment. A check does not require adding its subject to the game, creating a new chapter, matrix or report, or executing a new review stage. An explicitly pending later-stage decision is not an omission in an early baseline unless the present deliverable needs it. Conversely, a decision needed now is not optional simply because another stage follows.

## Common checks

- **Requirements and scope:** Trace consequential decisions to the confirmed brief or a legitimate design choice. Check required, optional and excluded content; platform, orientation, input and language constraints apply to relevant tables, examples and visible wording as well as main prose.
- **Implementer walkthrough:** For the next consumer's actual task, follow the source conditions, permitted actions, resulting state and feedback. Ask what must be built, which owner supplies each required input and what observable result would distinguish a correct implementation. Compare the producer's actual output with what its consumer needs, not just their matching IDs. Exercise the normal path and applicable interruption, repetition, simultaneous events and recovery; a necessary answer the implementer still has to guess is a finding. Check existing requirements, not hypothetical systems.
- **Consistency:** Compare statements about the same decision in prose, tables, examples and dependent clauses, including exclusions and global policies. Check conditions, ordering, units, reference bases and lifetime. Apply broad words such as all, none, always and never to the actual members of that category, then compare them with specific exceptions and pending decisions. Evaluate competing clauses against the same source-supported situation: fix the state before the event, the event/order, and the resulting state, then apply both the local rule and global policy. If they require different outcomes for that situation, record the conflicting clauses. Compatible vocabulary or a shared citation is not agreement. Use existing tables or prose; no additional scenario report is required.
- **Dependencies and assumptions:** Inspect the actual current source decision, not just a filename, valid link or completion summary. Compare what the producer supplies with what the consumer requires. Separate delivered facts, permitted alternatives, proposals and unresolved inputs; do not invent missing facts to close a dependency.
- **Responsibility:** Compare consequential choices, exclusions and fallback rules with the assigned responsibilities; a prohibition also decides behavior. Check that a clause claiming to leave a choice to another owner has not already constrained that choice elsewhere. Identify unauthorized choices and necessary decisions wrongly deferred using the current prompt, including examples and choices labelled as tuning. This Skill grants no additional edit authority.
- **Evidence:** Match conclusions to the available source and the check actually performed. File presence, a valid link and a successful calculation establish different properties; none proves the finished experience. For a consequential platform assumption, inspect the supplied contract, authoritative documentation or proportionate capability evidence and its preconditions. For an existing numerical calculation, inspect what it actually counts or executes and preserve its scope. Require the smallest missing check only when a concrete feasibility or numerical question blocks production; do not require temporary Scene/UI, simulation, previews or appendices for each document. Rendered layout, interaction, sound and game quality are checked using formal Content and the actual runtime.
- **Delivery expectations:** Inspect whether owned release-critical decisions have usable conditions/actions and observable expected results in their existing prose. Where the handoff provides acceptance pointers, check their meaning and coverage against the confirmed scope, not merely that their headings exist. Deterministic tests can establish rules; rendering, control and audio require target-runtime observation; direct resource/provenance inspection establishes only the inspected property. A successful design review cannot prove these future results. Keep uncertain feel/balance/appearance as scoped validation hypotheses, not missing product rules or guaranteed experience quality. Reference the owner expectation rather than create another independently maintained answer.

## Findings and corrections

Describe material findings through the source section, missing or conflicting decision, downstream consequence and what would close the finding. To judge impact, name the next consumer's concrete task and the decision it would otherwise have to guess. Distinguish a contradiction, an underspecified necessary decision, a valid pending dependency and an assumption needing later runtime evidence. Optional polish or an equally valid professional preference is not a necessary correction. A deferred item needs an owner and needed-by point; check whether that point precedes its first use. Use existing notes or the handoff; there is no prescribed severity scale or separate report.

Use the current assignment's step and permissions. In **inspect**, read saved drafts and relevant sources without changing them. In **revise**, group corrections in the recorded affected scope and preserve findings for verification. In **verify**, inspect changed definitions, exceptions, affected consumers and affected existing evidence without editing or reopening unrelated prose. These methods do not authorize extra review stages or release documents.

Replay the situation that exposed the finding against the corrected clauses, affected consumers and observable delivery expectations, including category membership and interruption/recovery where relevant. Check that the correction closes the implementation ambiguity rather than only changing vocabulary. These are lightweight reasoning checks, not a required simulator or scenario report. Retain unchanged evidence where valid. An unavailable source decision, disputed fact or scope change needs the authorized owner/user input; do not supply a non-owner default.

Keep tool work proportional to the findings. Collect independent source reads together and group related corrections. A structural correction must repair an actual violation of the supplied contract; it must not invent a new producer or owner decision. Use existing host checks for current saved inputs and rerun only invalidated relevant checks. A tool failure needs its actual diagnostic, not speculative edit/check loops. Reuse unchanged evidence and respect the assigned correction limit.

For BGS, handoff indexes point to authoritative prose and necessary acceptance expectations; they do not duplicate the full design. Use supplied host results for the inspected saved versions. For a concrete outstanding structural question, use the assignment's `--design-handoff N` and `--design-references --author-batch N` scope; consult `--design-handoff-help` only if needed. The host maintains version/hash metadata. Matching IDs or headings do not establish correct behavior, and different professional names do not establish a conflict. Inspect the source conditions and actual producer/consumer meaning. A retained hash binds its declared source identity, not authority or truth. Do not populate irrelevant tables or infer platform absence from a tool-scope rejection.

For assigned Art/UI samples, use native image reading or the supplied static-sample capture entry to inspect rendered appearance alongside the source clauses. The trusted capture writes only a private tool cache and disables project scripts and external dependencies; it is not runtime verification. In revise, edit only authorized sample sources and reconcile affected prose. Inspect the changed render before closing a visual inconsistency; a previous capture is not evidence for a revised source. Missing required visual observation remains a disclosed limitation, not a fabricated aesthetic PASS.

Report what was checked and what remains unresolved using the assigned receipt format. Each material finding needs actual source locations, downstream impact, closure condition and responsible owner. A necessary deferred decision has a real needed-by point; an optional improvement is not allowed to block work. Account for earlier recorded findings rather than silently dropping or downgrading them. Reading a saved draft is evidence of inspection, not proof of semantic correctness. Neither invoking this Skill nor a structural check releases documents: the host combines finite review results, deterministic checks, evidence and any explicit owner decisions.

For an assigned UI geometry check, read the actual UI-linked content/ui files and use the supplied `--review-layouts` command. These files are continued in Content, not copied from a separate test layout. Compare their screen/expanded-state coverage, active nodes, supported targets and declared clearance with the actual prose. Trace coexisting layers in the same state: a separate overlay uses root.data.layoutUnderlay to link its actual retained source and its explicit preserve/allow-cover policy. Inspect that policy against both general requirements and state-specific clauses; neither a permitted data policy nor independently fitting files proves prose agreement. Omitted links, markers or disabled content provide no combined clearance evidence. Missing future bindings do not invalidate planning geometry or prove full resource/package completion. In authorized revision, correct these same UI files and affected prose, then recalculate. Keep agreed control minima and required content; a layout result does not choose a new overlay policy or certify text fit, appearance or interaction. Reuse unchanged host diagnostics, but never substitute sample screenshots or matching numbers for this calculation.
