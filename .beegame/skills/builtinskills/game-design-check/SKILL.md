# Game Design Check

Check whether the assigned design can be used by its downstream team without guessing necessary product decisions. Take the original confirmed requirements, current assignment and actual consumer dependencies as inputs. This Skill supplies checking methods, not a second definition of ownership, release scope or phase authority.

## Select the applicable checks

Use the relevant sections of [document checks](references/document-checks.md). Its filenames identify disciplines, not required separate files; use the corresponding actual sections when records are merged. If the assignment already includes those reference sections, reuse them rather than rereading. Otherwise read the needed sections, including a dependency discipline when required. In joint inspection, cover all assigned saved drafts and their actual dependencies; in revision verification, read the affected clauses and consumers. Do not load unrelated discipline guidance.

Apply checks only to the confirmed game and current assignment. A check does not require adding its subject to the game, creating a new chapter, matrix or report, or executing a new review stage. A pending decision is not an omission while no current consumer needs it. A decision needed now is not optional merely because more work remains.

## Common checks

- **Requirements and scope:** Trace consequential decisions to the confirmed brief or a legitimate design choice. Check required, optional and excluded content; platform, orientation, input and language constraints apply to relevant tables, examples and visible wording as well as main prose.
- **Implementer walkthrough:** For the next consumer's actual task, follow the source conditions, permitted actions, resulting state and feedback. Ask what must be built, which owner supplies each required input and what observable result would distinguish a correct implementation. Compare the producer's actual output with what its consumer needs, not just their matching IDs. Exercise the normal path and applicable interruption, repetition, simultaneous events and recovery; a necessary answer the implementer still has to guess is a finding. Check existing requirements, not hypothetical systems.
- **Consistency:** Compare statements about the same decision in prose, tables, examples and dependent clauses, including exclusions and global policies. Check conditions, ordering, units, reference bases and lifetime. Apply broad words such as all, none, always and never to the actual members of that category, then compare them with specific exceptions and pending decisions. Evaluate competing clauses against the same source-supported situation: fix the state before the event, the event/order, and the resulting state, then apply both the local rule and global policy. If they require different outcomes for that situation, record the conflicting clauses. Compatible vocabulary or a shared citation is not agreement. Use existing tables or prose; no additional scenario report is required.
- **Dependencies and assumptions:** Inspect the actual current source decision, not just a filename, valid link or completion summary. Compare what the producer supplies with what the consumer requires. Separate delivered facts, permitted alternatives, proposals and unresolved inputs; do not invent missing facts to close a dependency.
- **Responsibility:** Compare consequential choices, exclusions and fallback rules with the assigned responsibilities; a prohibition also decides behavior. Check that a clause claiming to leave a choice to another owner has not already constrained that choice elsewhere. Identify unauthorized choices and necessary decisions wrongly deferred using the current prompt, including examples and choices labelled as tuning. This Skill grants no additional edit authority.
- **Evidence:** Match conclusions to the available source and the check actually performed. File presence, a valid link and a successful calculation establish different properties; none proves the finished experience. For a consequential platform assumption, inspect the supplied contract, authoritative documentation or proportionate capability evidence and its preconditions. For an existing numerical calculation, inspect what it actually counts or executes and preserve its scope. Require the smallest missing check only when a concrete feasibility or numerical question blocks production; do not require temporary Scene/UI, simulation, previews or appendices for each document. Rendered layout, interaction, sound and game quality need the project's actual content and runtime, whether BGS data, native engine assets or framework source.
- **Delivery expectations:** Compare the original confirmed requirements with the actual design before checking the declared outputs: authors may omit the same requirement from both prose and index. Inspect owned conditions/actions and observable results, then trace them to implementable tasks and their data inputs, prerequisites and verification methods. A task may be a foundational capability or an integration result; it need not encompass a whole player journey. Matching references do not prove meaningful coverage. Distinguish implemented from verified outcomes. Keep uncertain feel/balance/appearance as scoped validation hypotheses, not guaranteed quality. Reference the owner expectation rather than create another independently maintained answer.

## Findings and corrections

Describe material findings through the source section, missing or conflicting decision, downstream consequence and what would close the finding. To judge impact, name the next consumer's concrete task and the decision it would otherwise have to guess. Distinguish a contradiction, an underspecified necessary decision, a valid pending dependency and an assumption needing later runtime evidence. Repeated background, stylistic polish, stale production labels and equally valid preferences are not blockers by themselves; identify a concrete incompatible execution requirement before asking for cross-document revision. A deferred item needs an owner and needed-by point; check whether that point precedes its first use. Use existing notes or the handoff; there is no prescribed severity scale or separate report.

Use the current assignment's permissions. Read-only review inspects saved sources without changing them. Authorized revision groups corrections in the affected scope; follow-up checks changed definitions, exceptions, consumers and existing evidence without reopening unrelated prose. These are methods, not a required inspect/revise/verify task chain. Preserve findings until their actual closing evidence exists.

Replay the situation that exposed the finding against the corrected clauses, affected consumers and observable delivery expectations, including category membership and interruption/recovery where relevant. Check that the correction closes the implementation ambiguity rather than only changing vocabulary. These are lightweight reasoning checks, not a required simulator or scenario report. Retain unchanged evidence where valid. An unavailable source decision, disputed fact or scope change needs the authorized owner/user input; do not supply a non-owner default.

Keep tool work proportional to the findings. Collect independent source reads together and group related corrections. Inspect the recorded problem clauses, actual changes and source-backed consumers; sharing a filename is not a reason to reread all its requirements. A structural correction must repair an actual violation of the supplied contract; it must not invent a new producer or owner decision. Use existing host checks for current saved inputs and rerun only invalidated relevant checks. A tool failure needs its actual diagnostic, not speculative edit/check loops. A request to finish reading remains inside the assigned step, not a transition to independent verification. Reuse unchanged evidence; honor actual authorization and user budgets without inventing a correction limit.

For a supplied BGS Scene/UI geometry check or legacy handoff question, read only the applicable [saved-content checks](references/saved-content-checks.md). Use actual current sources and the supplied entry; do not create legacy indexes, batches, receipts or BGS data for a native-engine/DOM task. A hash binds source identity, not authority or semantic truth. Compare meanings and required behavior, not only matching IDs or headings.

For supplied or previously retained visual references, compare their relevant treatment with the source clauses. Inspect the actual reference when available; source markup alone does not establish appearance. Preserve the distinction between reference inspection and produced Scene/UI or runtime verification. In revise, correct only authorized existing sources; a previous capture is not evidence for a revised source. Missing required visual observation remains a disclosed limitation, not a fabricated aesthetic PASS.

Report what was checked and what remains unresolved in the project's existing review record; use a receipt format only if the current assignment supplies one. Each material finding needs actual source locations, downstream impact, closure condition and responsible owner. A necessary deferred decision has a real needed-by point; an optional improvement is not allowed to block work. Account for earlier recorded findings rather than silently dropping or downgrading them. Reading a saved draft is evidence of inspection, not proof of semantic correctness. Neither invoking this Skill nor a structural check certifies the design or game. Keep source checks, professional judgment, actual runtime evidence and unresolved decisions distinct.
