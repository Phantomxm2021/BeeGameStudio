# Game Design Check

Check whether the assigned design can be used by its downstream team without guessing necessary product decisions. Take the original confirmed requirements, current assignment and actual consumer dependencies as inputs. This Skill supplies checking methods, not a second definition of ownership, release scope or phase authority.

## Select the applicable checks

Use the relevant sections of [document checks](references/document-checks.md); its filenames label disciplines, not required separate files. Reuse reference sections already present in the assignment. Joint inspection covers all assigned drafts and actual dependencies; revision verification follows affected clauses and consumers, not unrelated disciplines. For consequential semantic/ownership conflicts, read its [cross-discipline reasoning](references/document-checks.md#cross-discipline-reasoning).

Apply checks only to the confirmed game and current assignment. A check does not require adding its subject to the game, creating a new chapter, matrix or report, or executing a new review stage. A pending decision is not an omission while no current consumer needs it. A decision needed now is not optional merely because more work remains.

## Common checks

- **Scope:** Trace required, optional and excluded content to the confirmed brief or a legitimate choice, including constraints in tables/examples rather than prose alone.
- **Implementability:** Walk the next consumer's actual task from source conditions through permitted action, outcome and feedback. Compare producer output with consumer needs, including relevant interruption/recovery; necessary guesses are findings.
- **Consistency:** Apply local/global clauses to the same actual situation, checking conditions, ordering, units, category membership, lifetime and exceptions. Shared IDs, terminology or citations are not semantic agreement.
- **Dependencies/ownership:** Read current decisions, distinguish facts, alternatives and pending inputs, and check consequential choices/prohibitions against actual responsibilities. Do not close a missing dependency with a non-owner default.
- **Evidence/delivery:** Compare original requirements with source decisions and implementable tasks before trusting output indexes. Match claims to actual checks and their preconditions; foundational tasks need not each cover a whole journey. Uncertain appearance, feel and balance remain hypotheses, not guaranteed quality.

## Findings and corrections

Record each material finding once in the existing review record: source locations, missing/conflicting decision, next consumer's concrete task/impact, responsible owner and closing evidence. Distinguish contradiction, necessary underspecification, valid pending dependency and later runtime hypothesis. A deferred decision needs an owner and a needed-by point before first use. Repeated background, polish, stale labels and equally valid preferences are not blockers without a concrete execution conflict.

Read-only review does not edit. Authorized revision groups related corrections in scope, then checks changed definitions, exceptions and consumers. Replay the situation exposing the finding to confirm the implementation ambiguity closed, not just the wording changed. Retain unchanged valid evidence and prior findings until actually closed; do not reopen unrelated prose or invent a mandatory review chain, severity scale or report.

Collect independent source reads together. Inspect recorded clauses, actual changes and affected consumers; sharing a filename does not require rereading all requirements. Use complete retained reports before rerunning to recover output, and rerun relevant checks when inputs/coverage or host freshness require it. A structural correction repairs an actual contract violation; a tool failure needs its diagnostic, not speculative loops. Missing/disputed decisions or scope changes need their authorized owner. Honor budgets without inventing correction limits; finishing reading does not authorize another verification task.

For supplied BGS geometry or legacy handoff inputs, use the applicable [saved-content checks](references/saved-content-checks.md), actual current sources and supplied entry. Do not create legacy indexes/batches/receipts or BGS data for native-engine/DOM tasks.

Inspect supplied visual references and compare relevant treatment with source clauses; markup alone does not establish appearance. Reference inspection differs from produced Scene/UI or runtime observation, and an old capture does not verify a changed source. Missing required observation remains unverified.

Report checked scope and unresolved findings using a receipt only when supplied. Reading, hashes, structural checks and Skill invocation do not certify semantics, authority or game quality. Keep source checks, professional judgment, runtime evidence and unresolved decisions distinct; optional improvements cannot block work.
