# Game Plan Execution

Use when a project already has an implementation plan. Implement its confirmed behavior and selected visual/content inputs without dropping scope, restyling or duplicating authored layouts. Local code organization and algorithms remain implementation choices. Preserve completed work and current user authorization; a plan cannot override its authoritative sources or a newer user instruction.

## Start or resume

1. Read the existing task directory, dependencies and source locations. BGS technical design and tasks are completed in the eight-document stage; before execution, reconcile affected task inputs with actual visual/resource/UI/Scene outputs in that same plan, preserving unaffected task IDs. A missing technical plan is an incomplete design handoff, not work intentionally deferred to implementation. In BGS use ReadDesignHandoff `{}` for current input issues and ReadImplementationTask `{}` for the existing task directory, then `{"id":"actual-task-id"}` for task prose and referenced owner decision/acceptance pointers. Use native Read for additional content/code and selected pictures. Reading tasks never locks the design or starts implementation; use the existing --design implementation entry only when entering authorized implementation. Do not copy another task document. Inspect current code and partial work before editing. If handoff reports missing inputs, repair the named owner/content only; preserve other valid work. Host version diagnostics use the existing explicit finalize entry before the lock, not manual version edits; a locked design still requires the existing authorized revision path.
2. Keep original task IDs in the existing execution list. Retain concise progress, result paths and the mandatory points each result covers there; do not create another ledger or append logs to finalized design records. Resume from actual partial code and current evidence, not ticks or remembered completion. If progress is missing or stale, recover it from retained files/results and check only unresolved points. Missing observations remain unverified.
3. Before consuming a dependency, inspect its needed output and interface: actual action/state names, types/units, resource IDs and exports as applicable. A ticked task or existing file/name does not prove the capability works. Missing or conflicting outputs block their consumer, not unrelated work. Correct within current authority; a locked or out-of-scope design needs the existing authorized revision path.

## Execute one coherent slice

For each task:

1. Read the task's mandatory points, original source/acceptance sections and expected results, following its source pointers rather than relying on the summary. Invoke the applicable professional Skill before the relevant specialist decisions; reuse guidance still available instead of reloading all Skills per task. A historical load does not establish retained guidance or application after compaction/focused continuation. Missing or conflicting inputs need their exact source/gap and affected task identified; use existing authority for corrections without inventing or simplifying product behavior. Continue independent work when possible.
2. Implement the behavior in the owning code or content. For scene/UI delivery, consume the project's actual authored sources and resources without a second layout copy. Use native engine or framework sources when those are authoritative; no separate BGS JSON is required.
3. Compare actual results against each mandatory point's expected conditions and outcome. Use focused rule/interface checks for deterministic behavior and actual observations for presentation/interaction, including the relevant connections and boundaries. Reuse current evidence covering multiple points/tasks; do not rerun unchanged checks or launch a whole game per task. Retain the result path, covered points and observed differences in the existing progress record. Do not weaken the expectation to fit a passing command; unobserved or pending integration stays unverified.
4. If the check fails, decide whether the code, the test, or the plan is wrong. Trace the cause; do not repeat the same failed command without changing the relevant condition. Identify the responsible source and apply a correction only within the current task's editing scope, then rerun the affected check. If the source is outside that scope, report the evidence, impact and needed correction rather than changing it or working around it.
5. Complete the same-ID execution item only when all its mandatory points have applicable evidence. Code may be finished while verification remains pending: keep the task unfinished and note that partial progress. Missing, failed or stale evidence cannot be replaced by a tick, loaded JSON or a green build. The recorded results must support the claimed scope; do not claim visual, audible or experience quality from unrelated checks. Continue dependency-ready work without routine per-task approval.

Keep narration and repeated source reading economical. Independent work may be delegated or parallelized when authorized and it truly has separate files and interfaces; neither per-task subagents nor per-task reviews are required. Choose the working context from the task's actual dependencies, not a requirement to carry the whole project history. A fresh or delegated context needs the goal, affected sources, current partial work, dependency outputs and relevant evidence/limitations, not copied documents or an acceptance verdict. Integrate returned work before accepting it.

## Read retained results before new execution

In BGS, ReadVerificationResults `{}` reads the newest saved host result, including failed or unfinished records; `{"measurementId":"actual-id"}` selects one record. `{"previewReceipt":".beegame/tmp/preview-test-.../execution.json"}` reads an existing preview receipt. Optional `details:true` expands retained details. These reads never execute checks; missing, changed or interrupted evidence is not a pass. Use CheckResourcesAndBindings `{}` for current saved resource/file/member/frame checks, with `detailsFor` to inspect a UI/Scene binding source. Runtime action/state wiring still needs observations.

Group independent reads and corrections for the same established cause without mixing unrelated changes or hiding a failing operation. If tool output is truncated or a final filter returns no matches, read the saved result and the actual process status before treating it as a test failure or executing again. Do not rerun merely to count checks or retrieve a missing field.

For BGS Preview, resolve the current supplied entry and its help. `--run` retains an `execution.json`, `stdoutPath` and `stderrPath`; `--inspect <execution.json>` reads that receipt and current boundary identity without running the test. Read the relevant saved output for assertion meaning: exit zero and unchanged identity do not prove correct coverage. Changed inputs or a host freshness rejection still require the appropriate new check; do not relabel old evidence. Expired access needs current authorized capability, not a copied URL or relaxed permissions.

For saved BGS UI geometry, call CheckUiLayouts with `{}` or `{"detailsFor":"content/ui/<actual-source>.json"}`; it checks all saved UI, reports effective variants and spatial observations, and expands the selected source's container constraints, position ownership and coordinates. Use native Edit for layout relationships, then recheck; edit the owning container for flow-controlled positions, and inspect variant selection when an override has no effect. Overlap candidates require design interpretation. For saved BGS Scenes, use CheckSceneLayouts `{}` or `{"detailsFor":"content/scenes/<actual-source>.json"}` for structure/static 2D reference framing and coordinate context. Adjust source transforms/cells/Camera with native Edit, then recheck. CheckUiLayouts remains authoritative for linked UI game-view allocation; missing geometry, 3D/XR space and traversal stay unverified. Use existing measurement inspection for runtime evidence. Keep a concise status, decisive diagnostics and actual coverage in the handoff; do not copy entire logs or Skill bodies into project guides. Saving request roundtrips is useful, but not a reason to skip necessary source reading or observations. Context caching and history recovery are host concerns, not repaired by another Skill rule.

## Finish the implementation

Reconcile completed task results with the original confirmed scope and applicable design records, including requirements not adequately represented by the task list. Run relevant integrated checks and the required player paths, reusing valid results. Read selected designs and captured views at matching sizes; compare the planned presentation, rules/actions, Scene/resource/audio use and relevant boundaries/recovery. Captures do not establish motion or interaction. Report actual implementation, observed agreement with design and unverified experience/quality separately; pending observations remain gaps even when layout checks or task items pass. Cover agreed conditions without inventing an exhaustive matrix. Use `evidence-before-completion` for the final claim.

This Skill gives the Agent a repeatable execution loop. It does not require a new worktree, fixed task duration, mandatory commits, or BeeGameStudio intervention in task choices.
