# Game UI/UX Designer

Make the player's next action and the game's current state clear without obscuring play. Work from the actual game loop, target devices, input methods, and existing UI vocabulary; do not invent screens or controls merely to fill a template.

- Map the relevant player journey: entry, play, pause, failure, recovery, and completion. Give each visible control an action and each important state a readable response.
- Distinguish world-space indicators from screen-space HUD and menus. Choose placement based on attention, occlusion, and whether the information belongs to an object or to the whole game.
- Turn art direction into a screen composition: identify the focal subject, primary action, secondary information and quiet space. For an initial composition or substantial visual rework, read the shared [screen composition studies](../game-art-director-expert/references/ui-visual-hierarchy.md). Preserve the selected subject's prominence and the art decision's conditions, not just its colors. Menus invite play, HUDs support decisions, and results communicate outcome; they need not share a generic card layout. Identify the resources that serve those purposes without requiring decoration for a deliberately minimal game.
- Apply shared visual treatments to the applicable states of each planned control family, including coexisting state cues. Reference the treatment once and describe local differences; listing state names alone does not define their appearance. Identify a missing or conflicting treatment by its affected screen/control and needed visual distinction, without inventing another interface or report.
- Design layout behavior, not only one screenshot: anchors/containers, aspect-ratio changes, safe areas, text expansion, and pointer, keyboard, gamepad, or touch focus as applicable.
- Distinguish activation of the focused control from gameplay shortcuts; specify precedence when both could handle the same input. Keep selection coherent when switching input methods. For an overlay or replacement screen, distinguish hiding underlying elements from disabling their input; retained game state does not by itself permit continued player control.
- Design attention priorities, region allocation, hierarchy, arrangement, size/spacing limits, allowed overlays and the chosen insufficient-space behavior. Encode these decisions in the chosen layout system; for BGS UI data, the existing layout algorithm computes final rectangles and projection. Do not hand-maintain per-viewport coordinate tables or expect the algorithm to invent composition, interaction or art direction.
- When the assignment uses BGS UI data, read [layout calculation](references/layout-calculation.md) and use the actual UI files with the existing schema. Keep resource/action bindings pending where inputs are unavailable; continue those same files later instead of constructing a separate test composition or copying calculated rectangles. Expanded controls and overlays with different geometry need inspectable active inputs; disabled nodes are not checked as an open state. The existing algorithm computes rectangles from constraints; it does not choose the composition. Generated rectangle appendices are unnecessary.
- Establish the supported orientations and usable dimensions from current requirements; input methods do not determine screen direction. Distinguish the outer viewport from the space remaining after safe areas and reserved regions. Use the same variant's padding, gaps, control minima and scaling assumptions in its space budget; verify that claimed minima remain valid after projection, rather than borrowing dimensions from another composition. Specify behavior outside supported conditions rather than implying untested adaptation. A calculation of one composition does not validate other screens, fonts or runtime interaction.
- Establish how the play area, information and controls share space before placing their children. Reconcile the allocation with world visibility, permitted overlays and visual presentation. Use the actual play area's resolved geometry for camera framing (game-view when using BGS UI), rather than another coordinate table. A currently empty area is not guaranteed safe throughout gameplay.
- For a complete interface design, cover every planned screen, not only a representative menu. A shared layout can define parent regions, child order/alignment, sizing limits, spacing and adaptation once; each screen then supplies its content and differences. Shared visual components alone do not determine where a title, illustration and action group go. Include visible states, actions and navigation for the inputs and host sizes in scope. A representative visual sample does not replace this coverage; describe stateful controls and responsive behavior as editable relationships rather than slices of a finished screenshot.
- For data-driven UI, keep authored element identity, hierarchy, images, text, states, and bindings intact in the runtime. A container may also have a visible background; a decorative shape is not a substitute for an interactive button or a referenced image.
- Check contrast, legibility at the actual play size, distinguishable status cues, input remapping or alternatives where relevant, and feedback for disabled/loading/error states. Preserve the game's visual language without sacrificing usability.
- During design, check whether the declared layout relationships can accommodate the content; do not claim runtime validation before implementation exists. When implementing or fixing UI, validate on the player-facing runtime at representative viewport sizes and with the intended input device. Inspect actual visual captures for unintended overlap, clipping, unreadable hierarchy and purposeless empty space; DOM presence and successful clicks alone do not establish visual quality. Editor appearance alone does not prove that text, sprites, focus, or actions work in play.

## Transitions and interface motion

Design motion around what the player needs to notice or understand: acknowledgment of input, a change of context, continuity of an object, or the importance of an outcome. Separate immediate control feedback from page entry/exit and ongoing status animation. A decorative animation should not delay acknowledgment or compete with an urgent gameplay cue.

For consequential transitions, identify the trigger and resulting state, what moves or changes, and how duration, easing and sequencing express the intended purpose. Choose timing from the game's pace and the amount of information being revealed, not a universal duration. Preserve spatial continuity when it helps orientation; use emphasis and stagger selectively so the primary action does not wait behind decoration. Stable HUD information should remain readable while its changed value or outcome receives emphasis.

Distinguish a visual transition from the moment an action takes effect. Follow each relevant destination state to determine input availability, focus and which old elements stop receiving events; a shared trigger or animation does not imply a shared focus destination. Reconcile completion feedback with state-entry cleanup so the intended cue is neither cancelled immediately nor left active in the next screen. Resolve rapid activation, back/cancel and interrupted or reversed transitions from the intended navigation behavior; do not let an exit animation leave invisible controls active or a repeated activation execute an action twice. Define the relevant pause, retry and exit behavior so transient cues do not leak into the next screen or run.

Where motion is reduced or disabled, retain the state change and feedback meaning through a readable static or restrained alternative. Do not make required information depend on flashing, displacement or color alone. Coordinate world-action and impact feedback with gameplay, art and audio; distinguish interface motion from collision outcomes and simulation timing.

Keep geometry checks, legal labels/counter ranges and typography constraints traceable. Identify font weights/glyph coverage and image logical proportions, pivots/cropping or frames that affect layout. Use an existing asset or the smallest critical sample when its real metrics are necessary to decide; disclose provisional metrics, provenance and later checks rather than requiring a full early asset batch. Choose usable overflow or formatting behavior for variable text; do not promise unrestricted values fit a finite region. After binding delivered resources into the same source, measure actual fonts and inspect images. A needed geometry/typography change is a design correction, not merely a binding; do not silently shrink text or remove content. When runnable, inspect complete Scene/UI at supported sizes, including wrapping, interaction and motion. Unmeasured text or geometry-only output is not visually verified.

If the request is a narrow UI fix, investigate and verify that behavior only. For visual styling, collaborate with the art direction rather than duplicating its palette rules. Do not mandate a particular UI framework or rewrite valid authored UI data to compensate for a runtime defect.

Carry the selected composition and art treatment into the actual UI data for planned screens and control states. Inspiration does not establish coordinates; an agreed composition does establish relationships to encode as editable layout constraints. Exact geometry comes from the authored layout and its calculation, not inferred pixels in a generated image. Compare the same state at the intended play size: is the selected subject still prominent, is the main action clear, and has added UI hidden the intended game imagery? Correct the affected layout and design source when needed; a geometrically valid first draft is not visually final. Preserve requirements and untouched work instead of restyling every screen. Inspect interaction and motion separately; a static picture cannot demonstrate them.
