# Producing and reconciling visual designs

Use when producing or revising screen concepts. A document-only assignment stops before production; a reference-only assignment does not authorize runtime implementation.

## Design the player situation

Use the confirmed brief, applicable GDD definitions and retained references for the current visual question. Choose reference study, a targeted concept or a target-engine sample according to what is unresolved; complete-game implementation does not require a separate screen atlas. For a screen-concept commission, carry the requested definitions into the visual brief: when the state occurs, what the player needs to understand, and which actions are available. Include required conditional notices, overlays and loading/recovery/error states. Internal rules, entity actions and transitions do not by themselves call for new screens, messages or buttons; preserve their required visible feedback within the scene or existing interface. Required state coverage is distinct from panel count. Copy, value and control-visibility variants may share a selected composition when the GDD defines their conditions and content and no new layout or artwork is needed. Identify the shared composition and those definitions in the existing handoff; a distinct composition or an unrepresented key element/action still needs a visual representation. Carry the GDD’s chosen composition, information grouping and art direction into the brief alongside explicit user requirements. State which visual details remain open for image design. Camera constraints belong to states retaining the gameplay view; title and standalone results follow their own compositions.

For an open composition or concrete interpretation of a broad style label, use the applicable [finished-game pictures and visual contrasts](ui-visual-hierarchy.md). Compare actual subjects, proportions, layers, materials and world/UI relationships in relevant viewing conditions, explaining the adopted relationship and what does not fit this game. With an established project design, use its selected pictures for production and comparison rather than reopen style research; a local repair can reuse that evidence.

Use the GDD’s shared artistic direction and each state’s player-facing purpose to guide the images. Preserve chosen focal subjects, scene/interface relationships and information hierarchy while developing typography, shape, color, materials and spacing. Resolve open choices coherently; when the image exposes a weakness, reconcile only the affected presentation decision rather than treating novelty or departure from the GDD as success. Each panel depicts one complete player-visible state with only its available information and actions. Character actions may appear in the scene; pose sheets and animation instructions belong to resource production.

Reuse suitable supplied designs. When image generation is useful for an unresolved appearance question, use the system `imagegen` Skill under the selected source’s authorization and cost guidance; group the requested screen compositions into an atlas when appropriate. Keep shared art direction separate from each player situation, necessary information/actions, chosen composition and applicable constraints in the image brief. Include relevant visible detail rather than copying whole GDD sections or hidden implementation rules. Image design develops the appearance within this design without adding or removing functionality. Depict one actual state per panel; conditional variants may reuse its composition as described above. Use meaningful working copy; only user-fixed wording is verbatim. Request the project target aspect ratio and choose atlas layout from required representations and the viewport. A blank layout guide constrains input, not measured output. Do not replace AI concepts with HTML/CSS, SVG or Canvas drawings. A new composition needs an authorized design reason, not a fixed number of alternatives.

During authorized implementation, use a target-engine scene to resolve camera, spatial scale, occlusion, input or timing questions. For 3D, inspect the actual scene from the relevant views; concepts guide style and subject/material treatment rather than certify navigable space. Bring representative models, materials and UI into a coherent playable situation as it develops. Compare against confirmed visual intent and any selected references. Static pictures cannot establish interaction or feel.

## Inspect the concept at its intended fidelity

Compare actual images and their mapped conditional definitions with the GDD's player-visible scope. Establish screen/state coverage, recognizable key game subjects/UI elements, readable necessary information and primary actions, retained functionality, major layout/hierarchy and the required visual style. Shared compositions can cover defined variants; missing required compositions, key elements or actions remain gaps even when every requested panel was generated. A concept does not prove interaction, motion or runtime correctness.

Repair omissions or contradictions that prevent the agreed screens, necessary information/actions, key subjects or intended visual direction from being represented. Retain usable compositions; resolve production details in the affected resource or runtime work rather than resubmitting a concept atlas. Request the target aspect ratio and accept usable concepts despite ratio deviation.

## Record and hand off the selection

When adopting image targets, use the current task’s source record to identify the selected images and panels, the corresponding existing GDD requirement sections, any editable source and consequential downstream adaptations. Keep the GDD unchanged when realizing its agreed design; concrete appearance alone does not require a document update. Revise affected GDD definitions only to correct an actual design contradiction within the assignment or carry out a user-authorized design change. A selected picture does not authorize new functionality or revised gameplay rules.

Retain the viewing conditions needed to locate a state, such as player situation, camera/view and display size, in the existing handoff. Distinguish inspiration, selected design, implementation starting points and actual runtime assets. Do not require consumers to choose among intermediate captures. Requested proportions remain targets; report actual image dimensions only from existing decoded metadata, otherwise leave them unspecified. A flattened screen board does not provide independently controlled runtime parts.

For authorized runtime/resource production, preserve the selected subjects, proportions, material/light relationships and state distinctions while separating independently controlled parts. For modular families preserve scale, pivots, coordinates and assembly transforms. Check provenance, use, compatibility and download/runtime cost of sourced assets. Missing required artwork remains a dependency.

## Observe an existing implementation or interaction prototype

When observing an existing HTML implementation or an authorized interaction prototype, use available project preview/capture tooling. Select the viewport/state and input environment relevant to the target; changing viewport alone does not emulate touch. Capture after the required state, fonts and images have settled. Inspect the pictures and retained report for actual environment and errors. A screenshot does not validate touch behavior, motion, audio or runtime fidelity; those need the existing runtime capture/playtest path when implementation is in scope.
