# Producing and reconciling visual designs

Use when producing or revising actual visual designs or modular assets.

Use the relevant requirements across the applicable professional chapters in `docs/GDD.md` to create one overview board covering all game screens and key states in the current assignment. Keep each complete Scene, subjects and HUD together in its panel. Share the board across UI/Scene responsibilities. Identify supplied images as inspiration, selected designs or runtime captures. A selected design supplies composition and appearance decisions for implementation; inspiration only informs those decisions. A reference-image assignment covers the board, not additional component explanation boards or runtime production.

For a consequential correction, revise the affected complete screen using the existing image as a reference and describe the intended change while preserving established composition and identity. With BGS assets.mjs, use referenceImagePath with prompt or uiReference; seeing an image in chat does not pass it to the image provider. Check the available quote and authorized budget; a revision need not become a new set of alternatives.

Inspect composition, hierarchy, subject appearance and key-state coverage. When several images warrant an authorized independent comparison, a short-context read-only sub-agent can receive the image paths and relevant GDD sections, then return consequential mismatches with image locations and implementation impact. The parent reconciles those findings; this is optional and does not authorize regeneration or GDD edits. Correct consequential omissions or contradictions; minor text, grid-count or pixel deviations need not trigger whole-image regeneration. Exact values remain in the GDD and implementation. Deliver image paths and consequential unresolved deviations in the completion message. Keep `docs/GDD.md` unchanged during reference generation unless the user explicitly requests a design change; do not adopt image imperfections as new requirements. A document-only assignment stops before production. Runtime production preserves the selected design's subjects, proportions, material/light relationships and state distinctions while separating independently controlled parts; a flattened screen board is not runtime UI.

For modular families preserve scale, pivots, coordinates, materials and assembly transforms. Check provenance, use, compatibility and download/runtime cost of sourced assets. Inspect the smallest useful complete screen/scene before propagating an uncertain treatment; use available renders or authorized image tools. This is not another mandatory review stage.

When the selected design is project HTML, use the current `preview.mjs --design-snapshot` entry instead of finding or launching Chrome or rewriting CDP capture code. Read `--help` for its `{path,views}` input; include only the required viewport/state queries and a ready selector when the page needs one. The command waits for load and fonts/images, retains screenshots and complete observations, and returns compact paths and errors. Read the saved report for details and inspect the actual pictures at player scale. Re-render affected views after a source change; retain coverage of required states. A screenshot or successful capture is not evidence of motion, interaction, audible feedback or runtime fidelity. Use the existing runtime capture/playtest path for those outcomes.
