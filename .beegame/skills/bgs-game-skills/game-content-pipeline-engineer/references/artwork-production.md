# Artwork production

Use confirmed user source requirements and the owning GDD appearance definitions: shapes, proportions, materials and spatial relationships. Resource production proceeds from these definitions without requiring a selected design image. Separate independently controlled game objects, backgrounds/layers and decorative UI parts from live text, values and interaction. UI artwork remains a resource dependency when controls are implemented in code; a UI framework does not supply the required skins.

Choose the required silhouettes, proportions, materials, lighting and action/state changes at gameplay size before settling on a representation. For the first concrete realization of a broad style, or a consequential unresolved appearance choice, use the shared [finished-picture comparisons](../../game-art-director-expert/references/ui-visual-hierarchy.md#finished-game-references); reuse the adopted project sources once established.

For new 2D characters, environment subjects, props and decorative UI artwork, follow the source order in [resource selection](resource-selection.md): reuse and inspect candidates before choosing a production method. A rejected generation prompt needs its input corrected; a prompt-check outage is not evidence that the image provider cannot produce the artwork. SVG or other programmatic drawings are the final fallback when the preceding sources cannot supply the required result, or the user explicitly requests that representation. Preserve the limiting facts with the existing production decision. A fallback that loses required appearance or actions remains an unmet dependency.

Before writing image prompts or per-object output paths, determine the required image deliverables: group compatible static UI artwork into a transparent UI atlas and static game parts into a separate game-element atlas. Each atlas is one deliverable passed to the system `imagegen` Skill, with all its required parts listed together in one prompt; its named parts become runtime regions, not individual generation jobs. Backgrounds/layers with incompatible opacity or scale can remain separate, and a family containing only one required element can remain a single image. Pose sequences use the character-animation method.

Generate these deliverables from the confirmed appearance definitions using the system `imagegen` Skill and current tool help. Describe the required elements and visual states, silhouettes, relative proportions, materials and lighting; let the image model arrange complete elements with transparent separation at their intended display scale. Static atlas generation needs neither predetermined extraction coordinates nor equal cells. Keep live labels, counters, progress and hit areas out of UI skins. Inspect a representative atlas or independent image in its intended composition before extending an uncertain treatment across further deliverables.

After generation, locate each static element in the actual image and record its source-pixel bounds for import, or crop complete, separable parts with the existing media tools. Named regions allow independently controlled elements to share one image; separate controls do not require separate generation requests or files. Retain suitable source files and register actual output paths and provenance. Cropping cannot remove an occluding object, recover hidden artwork or create transparency from painted background pixels; a flat concept is not a layered source or a ready runtime atlas.

Code handles processing, assembly, layout, live text, interaction, simple geometric controls and runtime effects. Procedural noise, emission, trails and shader composition are effect techniques; their use does not make complex painted shapes or changing material silhouettes unnecessary. When producing or importing effect textures or flipbooks, use [effect textures and sequences](../../game-technical-artist/references/vfx-craft.md#effect-textures-and-sequences) for representation, extraction and blend choices. These roles do not replace character, environment, prop or decorative UI artwork with newly coded shapes outside the fallback conditions above. For 3D/XR, use compatible models, materials and rigs to realize the selected design; an image derivative supplies only an applicable texture, not missing geometry or animation.

Inspect delivered parts against the owning appearance definitions for shape, material, proportions and required states; a shared style label is insufficient. Register actual files and provenance, then bind them in the target's native scene/UI implementation when in scope. Registration verifies file facts, not agreement with the design. If a required part cannot be produced within authorization, retain the specific dependency rather than relabel a substitute as final.

## Transparent output in use

Judge transparent artwork composited over its intended surface and a contrasting
light or dark surface with the intended filtering. An image viewer's backdrop is
not a painted pixel; alpha metadata establishes the channel, not edge quality.
Repair visible baked halos in that composition without clipping soft edges or
glow. Preserve atlas separation for the consumer's filtering.
