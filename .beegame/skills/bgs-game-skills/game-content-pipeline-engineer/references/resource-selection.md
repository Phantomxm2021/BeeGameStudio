# Resource Matching and Small Samples

Use for an unresolved source or representation choice. Preserve explicit user source choices, suitable supplied assets and adopted project sources. For each remaining resource family, search the self-hosted resource library first, then suitable Web sources, then use authorized AI generation; programmatic drawing is the final fallback. Move on when the preceding source cannot provide a usable, licensed match, and stop once a suitable source is found. Keep searches relevant and bounded rather than browsing whole catalogs. Unavailable access is an access failure, not an empty library.

For game subjects, environments and UI artwork, use [artwork production](artwork-production.md) to assess usability against GDD appearance definitions and any selected pictures. Match actual shapes, proportions, viewing angle, materials and actions rather than category/style labels. Respect explicit user budgets and source exclusions.

Select candidates within the chosen production method by required actions, states, readable cues, runtime format and quality. Keep unresolved appearance choices with their owning design decisions. Preserve required actions when matching files. For 2D character actions, use [sprite animation](../../game-technical-artist/references/ai-sprite-animation.md): retain suitable source sequences or generate ordered poses from the corresponding static character reference when AI generation is selected, then prepare and play the frames in the target engine. For 3D animation, acquire compatible models, rigs and clips; generated images can supply textures for those assets. Keep unavailable required inputs explicit.

The catalog returns `items`, `total`, `facets` and optional `nextCursor`. Use returned facets for structured filters and paginate only as needed. `readyElementCount` counts technically browsable files, not proven game-role matches. Empty `usageTags` means unclassified, not unavailable: inspect or audition the candidate. An access error is not an empty result, and semantic `no-match` is not proof that no files exist. An explicit `fetch` resolves and downloads the selected element's complete declared dependency closure, preserving each dependency's parent key, reference path and local path for one registration input. Keep actual delivered-file facts in the Manifest and concise query/download evidence and material rejection reasons in existing implementation progress, without inventing a sourcing history or requiring a report for every discarded candidate.

| Family | What to inspect in a relevant sample | Why existence alone is insufficient |
|---|---|---|
| Modular environment | Scale, edge treatment, pivots, tile joins, lighting/material and required variants in the scene | Attractive isolated tiles can fail to assemble coherently or omit a needed corner/transition |
| UI/font family | Render actual title, counter and label strings at display size; compare glyph shapes/weight, proportions, control states and stretch regions | Coverage alone does not establish matching letterforms. If subsetting is needed, derive coverage from player-visible copy, dynamic alphabets and confirmed languages, not the technical GDD prose |
| Repeated feedback sound | Event meaning, attack/tail, variation, mix space and loading/playback constraints | A valid file can be wrong in tone, mask another cue or fail in its actual playback path |

Compare only consequential candidates, without downloading whole catalogs or creating another procurement report. Keep source choices, fallback constraints and material rejection reasons with existing production decisions; delivered-file metadata and licenses belong in the Manifest. The GDD retains appearance goals, product constraints and explicit user source requirements. Revise it for an actual design conflict or authorized change, rather than recording routine sourcing facts or preselecting a drawing method. Verify the actual source and asset license when importing; repository code licensing does not automatically license its fonts or sounds.

Examples of concrete reference material: [Unciv's UI skins](https://github.com/yairm210/Unciv/blob/master/docs/Modders/Creating-a-UI-skin.md) show reusable shapes and nine-patch behavior; [Veloren's models](https://book.veloren.net/contributors/artists/voxel-models.html) place assets in a shared style/scale context; [OpenRA's mod guide](https://github.com/OpenRA/OpenRA/wiki/Modding-Guide) separates authored rules/maps/UI and resources. These illustrate matching and integration, not mandatory file formats or a reason to copy their look.

A fallback must preserve the required function and selected treatment. If it would replace a required visual/audio identity, change geometry or remove a state, identify the actual dependency and obtain the necessary decision rather than silently treating a placeholder as final. Resource presence, binding resolution and runtime consumption establish different things.

## Spend on the required use

For a loading or runtime-memory question, compare actual display/playback use, not file counts alone:

- Choose image resolution/detail for supported display size, crop, zoom and state variants. Reuse a compatible family or module while preserving identity, scale, pivots and required facing/animation. A smaller file is not a win if critical features stop reading; more variants are not automatically needed.
- Preserve padding/frame semantics. One whole-game atlas may force optional content into startup memory and prevent independent unloading; many separate files may add requests/uploads. Compare the relevant loading/lifetime pattern rather than mandate either extreme.
- Distinguish transfer size, decoded memory and GPU allocation. Compression can reduce download without proportionately reducing runtime memory. Existing metadata/import reports can establish dimensions or duration; those facts do not prove an asset is wasteful or unused.
- Load the resources needed for first interaction and prepare later resources near their actual use when beneficial. Loading/decode/upload are separate costs. Cache/release according to real ownership; deleting a shared asset to reduce a memory number can break another state.
- For audio, compare a finite prerendered cue, decoded loop, supported streamed format and live synthesis against duration, event rate, loading, CPU and audible needs. Existing PCM generation suits some short cues; neither long PCM music nor runtime synthesis is universally cheaper. Respect runtime codec support and audition any quality-changing conversion.

Keep consequential production choices and unresolved runtime constraints in the existing plan, updating affected decisions within current authorization; do not add an inventory/budget framework. Rendering choices can use the relevant [runtime cost tradeoffs](../../game-technical-artist/references/runtime-cost-tradeoffs.md); resource sourcing alone does not require that reference or a full profiler pass.
