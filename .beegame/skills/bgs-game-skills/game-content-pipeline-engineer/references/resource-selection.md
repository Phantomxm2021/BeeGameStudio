# Resource Matching and Small Samples

Use for an uncertain asset family, production route or compatibility question, not every resolved binding. Start from its actual visual/audio purpose and runtime needs. Honor explicit user source choices. For common sounds, icons and environment assets, first consider suitable supplied or built-in licensed resources. Prefer existing complete animations when suitable; a generated sheet does not guarantee temporal continuity. Consider AI generation for distinctive artwork when existing candidates do not fit, not as the default for all core art. Use focused web sourcing for a concrete gap, verifying rights and download/format feasibility; stop when a suitable candidate is found. This is not a mandatory source-by-source tour. Procedural replacement of required core art remains a fallback requiring a concrete blocker and user authorization; simple controls, geometric effects and an explicitly chosen procedural aesthetic are different.

The catalog returns `items`, `total`, `facets` and optional `nextCursor`. Use returned facets for structured filters and paginate only as needed. `readyElementCount` counts technically browsable files, not proven game-role matches. Empty `usageTags` means unclassified, not unavailable: inspect or audition the candidate. An access error is not an empty result, and semantic `no-match` is not proof that no files exist. A single-file `fetch` does not download its dependencies; inspect the returned dependency metadata and retrieve required files before claiming a usable bundle. Keep actual delivered-file facts in the Manifest and concise query/download evidence and material rejection reasons in existing implementation progress, without inventing a sourcing history or requiring a report for every discarded candidate.

| Family | What to inspect in a relevant sample | Why existence alone is insufficient |
|---|---|---|
| Modular environment | Scale, edge treatment, pivots, tile joins, lighting/material and required variants in the scene | Attractive isolated tiles can fail to assemble coherently or omit a needed corner/transition |
| UI/font family | Real glyph coverage, proportions, meaningful control states, stretch/crop behavior and legibility in the layout | An attractive preview can lack Chinese glyphs, readable counters or usable stretch regions |
| Repeated feedback sound | Event meaning, attack/tail, variation, mix space and loading/playback constraints | A valid file can be wrong in tone, mask another cue or fail in its actual playback path |

Compare only consequential candidates, without downloading whole catalogs or creating another procurement report. Record selected source/production choices in ASSET_PLAN.md before locking. During implementation, keep delivered-file metadata and licenses in the Manifest and unresolved choices in existing progress; do not reopen the plan for routine sourcing facts. Verify the actual source and asset license when importing; repository code licensing does not automatically license its fonts or sounds.

Examples of concrete reference material: [Unciv's UI skins](https://github.com/yairm210/Unciv/blob/master/docs/Modders/Creating-a-UI-skin.md) show reusable shapes and nine-patch behavior; [Veloren's models](https://book.veloren.net/contributors/artists/voxel-models.html) place assets in a shared style/scale context; [OpenRA's mod guide](https://github.com/OpenRA/OpenRA/wiki/Modding-Guide) separates authored rules/maps/UI and resources. These illustrate matching and integration, not mandatory file formats or a reason to copy their look.

A fallback must preserve the required function and selected treatment. If it would replace a required visual/audio identity, change geometry or remove a state, identify the actual dependency and obtain the necessary decision rather than silently treating a placeholder as final. Resource presence, binding resolution and runtime consumption establish different things.

## Spend on the required use

For a consequential resource-cost choice, compare actual display/playback use, not file counts alone:

- Choose image resolution/detail for supported display size, crop, zoom and state variants. Reuse a compatible family or module while preserving identity, scale, pivots and required facing/animation. A smaller file is not a win if critical features stop reading; more variants are not automatically needed.
- Group compatible small generated assets into a sheet before buying separate images, then publish inspected frames with the existing atlas tools. Packing separately generated images later does not save their generation cost. Preserve padding/frame semantics. One whole-game atlas may force optional content into startup memory and prevent independent unloading; many separate files may add requests/uploads. Compare the relevant loading/lifetime pattern rather than mandate either extreme.
- Distinguish transfer size, decoded memory, GPU allocation and generation cost. Compression can reduce download without proportionately reducing runtime memory. Existing metadata/import reports can establish dimensions or duration; those facts do not prove an asset is wasteful or unused.
- Include model implementation effort when comparing production cost. A spending cap is not a request for zero image charges; do not trade away required core art to save a quoted image fee while writing a custom drawing program.
- Load the resources needed for first interaction and prepare later resources near their actual use when beneficial. Loading/decode/upload are separate costs. Cache/release according to real ownership; deleting a shared asset to reduce a memory number can break another state.
- For audio, compare a finite prerendered cue, decoded loop, supported streamed format and live synthesis against duration, event rate, loading, CPU and audible needs. Existing PCM generation suits some short cues; neither long PCM music nor runtime synthesis is universally cheaper. Respect runtime codec support and audition any quality-changing conversion.

Keep consequential production choices and unresolved costs in the existing plan before locking or existing implementation progress afterward; do not add an inventory/budget framework. Inspect a critical sample before propagating an uncertain family, without deleting required production work. Rendering choices can use the relevant [runtime cost tradeoffs](../../game-technical-artist/references/runtime-cost-tradeoffs.md); resource sourcing alone does not require that reference or a full profiler pass.
