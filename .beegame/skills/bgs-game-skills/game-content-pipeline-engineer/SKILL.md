# Game Content Pipeline Engineer

Make authored content render and behave consistently in the selected game technology. This Skill concerns content production and consumption; it does not require BeeGameStudio to provide a game engine or prescribe which engine the Agent uses.

## Resource planning

Establish the resources/content chapter in `docs/GDD.md` with resource roles, representation choices and unresolved resource needs. From the confirmed brief and owning chapters, describe how the game's resource groups fit together, such as characters, environments, UI, effects and audio, and which parts are shared or reusable. Refine this overall view as work develops; detail the current part and leave unavailable inputs planned. Select production methods from the selected visual/audio chapters rather than settling them before those chapters exist. Keep actual files/frames and metrics in the existing Manifest.

Choose resources from the required actions, state changes and selected composition, separating parts that move, change, are replaced or reused independently. For the composition being produced, translate the selected design's key component forms, materials, relative proportions and information layout into resource, node or runtime-drawing responsibilities, then identify the visible subjects, layers and state variants that need representations before authoring Scene/UI. Carry their identity and relative scale into the resource plan; unrelated compositions may remain planned. For 2D, consider distinct poses, independently controlled parts/layers or runtime drawing. For 3D, plan compatible model parts, materials/textures and rigs/animations, with attachment points or scene-module joins where needed and a consistent scale. Whole-image transforms cannot supply missing poses or independently move baked-in parts. Preserve independent control even when artwork shares an atlas, and keep live text/effects separate from static art. Carry these choices into acquisition requests and inspect whether the delivered resources support them before integration. Record format, display scale, provenance and authorized fallbacks; reconcile a selected/generated image or resource choice that conflicts with a confirmed GDD decision in the owning GDD chapter before production. Canvas or procedural rendering is a legal representation choice, but a `final` label alone does not establish that the selected subjects, proportions, material/light relationships and state distinctions were preserved. Use existing sections without a second inventory or mandatory mapping schema.

Reference the technical-design chapter in `docs/GDD.md` for target/runtime and integration choices, and the owning UI/level chapters for space and framing. Add resource-specific format, loading or feasibility constraints where needed; do not copy behavior, layout, camera or interface definitions into the resources/content chapter. A prototype or calculation is needed only for a specific unresolved question, not chapter completion.

Projects using the BGS Scene/UI Editor keep its document locations in `content/index.json`; native engines retain their own scene/UI formats. BGS resource identity lives in `assets/asset-manifest.json`. BGS screen UI and Scene objects remain distinct editable models consumed by the runtime. Preserve these data contracts; an optional renderer's limits do not justify deleting valid source data.

Honor explicit user sources and reuse suitable supplied assets. Default acquisition starts with the built-in resource library, then suitable public resources, then an available AI method capable of producing the required asset type. Move on when earlier sources do not yield a usable match. For an uncertain resource family, sourcing or consequential cost choice, read the applicable [resource matching and cost examples](references/resource-selection.md). Reuse relevant design research or use available web tools for the remaining concrete gap: composition/part separation, scale, formats or compatible 3D materials, rigs and animations. Inspect the source rather than rely on search snippets; use official format/runtime documentation for technical claims and verify reuse rights when acquiring files. Keep useful source links, selected production methods and material reasons for skipping earlier sources by resource group in the resources/content chapter of `docs/GDD.md`. Stop when a usable match is found; do not exhaust whole catalogs or the web. New gaps or outdated facts justify another search, not each design chapter or asset batch. If access or research is unavailable or inconclusive, record that limitation rather than claim no resources exist, and continue work that does not depend on it.

In a resource-preparation assignment, acquire, inspect and register the resources for the first complete implementation unit and its relevant states, leaving unrelated resource families planned. Hand off the actual files and metrics without requiring runtime Scene/UI assembly during preparation. In the implementation assignment, connect those resources to their actual consumers and inspect them in the runtime before producing an uncertain family at scale. Obtain later resources within implementation; this does not restart preparation or require all game assets up front. Preserve the selected visual/audio intent and actual resource policy. Failed sourcing or AI generation does not authorize automatic procedural replacement of required art. Simple controls, geometric effects and an explicitly chosen procedural aesthetic may use code directly. A candidate list is not delivered resources, and a fallback is not permission to change a required appearance or behavior.

For a concrete resource-format or renderer feasibility question, or for acquiring, registering, importing and verifying actual files, read the relevant section of [production and integration](references/production-integration.md). It contains the supplied command usage, atlas/3D import details and saved-resource checks.
