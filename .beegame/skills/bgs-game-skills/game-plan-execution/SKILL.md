# Game Plan Execution

Use when a project already has an implementation plan. Implement its confirmed behavior and selected visual/content inputs without dropping scope, restyling or duplicating authored layouts. Local code organization and algorithms remain implementation choices. Preserve completed work and current user authorization; a plan cannot override its authoritative sources or a newer user instruction.

Scene/UI assembly, runtime consumption and gameplay code are implementation. In BGS, carry them out in the current implementation Goal; a bounded design or resource task hands off before entering it. Integrate validation with implementation, and repair affected design or obtain later resources within that same Goal. Do not add a final-only testing phase or restart the full production sequence.

## Start or resume

1. For work likely to span a context reset or handoff, start or resume from the ordinary project task file and any available handoff or compaction summary to locate the next action; if the task file is absent, save current tasks in docs/TASKS.md before continuing. Continue its remaining work, checking actual files and evidence rather than trusting task ticks or remembered completion. Local fixes need no task file. Preserve existing IDs when applicable. Missing observations remain unverified.
2. For that action, reuse available technical/design text and inspect missing or changed original GDD sections, selected pictures, resources, code and UI/Scene data needed to implement or verify it. For a new game, start with one coherent player situation from the confirmed brief: implement and check its basic behavior before expanding the same treatment; unavailable inputs remain planned. Reconcile required inputs with actual files before consuming them, preserving valid work. Choose task organization appropriate to the work; no index or coverage graph is required. ReadDesignHandoff locates GDD chapters/sections; ReadImplementationTask exposes optional existing task pointers and GDD section navigation; select the relevant chapters with ReadDesignHandoff. Use native reads for additional code, content and pictures. Use --design implementation to inspect current implementation sources within the authorized assignment; it does not freeze the GDD. A plain GDD needs no finalize command. Existing indexed projects can finalize metadata after authorized changes; revalidate affected evidence against the updated inputs.
3. Before consuming a dependency, inspect its needed output and interface: actual action/state names, types/units, resource IDs and exports as applicable. A ticked task or existing file/name does not prove the capability works. Missing or conflicting outputs block their consumer, not unrelated work. Correct within current authority; an out-of-scope design change needs user authorization through the existing task change path.

## Execute one coherent slice

Update the existing ordinary task file alongside meaningful implementation or verification progress, even while the task remains unfinished. Keep a concise record of implemented behavior, verified results and evidence paths, unverified or failed work, the next action and pending user-playtest questions. Do not edit the GDD merely to record progress or claim game acceptance.

For each task:

1. Use the task's mandatory points, original source/acceptance sections and expected results already available; follow its source pointers to read missing or changed sections rather than substitute a summary for them. Derive those expected results from the confirmed brief/design, not by reverse-engineering the current implementation or its tests. Invoke the applicable professional Skill before the relevant specialist decisions; reuse guidance still available instead of reloading all Skills per task. A historical load does not establish retained guidance or application after compaction/focused continuation. Missing or conflicting inputs need their exact source/gap and affected task identified; use existing authority for corrections without inventing or simplifying product behavior. Continue independent work when possible.
2. Implement the behavior in the owning code or content, connecting the confirmed action/state to its required visual/audio response and resulting appearance. Use the design's chosen representation, including resource states/frames/layers or runtime drawing as applicable; for scene/UI delivery, preserve the selected composition's key component forms, materials, relative proportions and information layout through the authoritative sources and resources, without a second layout copy. Naming or loading assets does not implement their selection or playback. Native engine/framework sources need no separate BGS JSON. Resolve presentation lifetime with gameplay before screen changes or removal can cancel required feedback; use the existing lifecycle facilities.
3. Check the affected behavior against its source requirements through focused rule/interface tests and ordinary controls across the relevant input lifecycle, from the action through state transition and required feedback cleanup. For editable UI/Scene sources, trace each changed field to its actual runtime consumer. For an affected visual or state presentation, reuse an existing Preview/capture at the selected design's corresponding state, viewport and relevant input, and compare the actual screen/scene with that source. Record behavior/input/state mismatches separately from visual/composition/material mismatches in the existing progress or evidence record. Observe the required presentation in that composition: meaningful moments and the passage between them for motion, actual output for audio. Reuse the existing Preview/capture or target-runtime tools; a still, loaded file or playback call does not establish the corresponding dynamic result. Hooks isolate rules but do not verify delivered input. Retain coverage, result paths and failures in existing progress, rerunning only affected checks. Missing required presentation is unfinished; unobserved behavior stays unverified. Judgments of appeal, difficulty and feel belong to user playtesting.
4. If the check fails, decide whether the code, the test, or the plan is wrong. Trace the cause; do not repeat the same failed command without changing the relevant condition. Identify the responsible source and apply a correction only within the current task's editing scope, then rerun the affected check. If the source is outside that scope, report the evidence, impact and needed correction rather than changing it or working around it.
5. Complete the same-ID implementation item when its mandatory behavior and applicable basic checks are supported. Missing, failed or stale technical evidence remains unresolved; pending user experience feedback alone does not keep technical implementation unfinished. An explicitly requested playtest still needs its own evidence or an honest pending result. Continue dependency-ready work within current authorization.

Keep narration and repeated source reading economical. Follow the current BGS limited-parallel contract when native children can complete independent work while the parent advances the player situation. Use the existing task record for file owners and settled interfaces; shared design, manifests, dependencies and application wiring remain with the parent. Do not create a delegation registry or require a child/review for each task. Children return actual paths, checks and gaps. Wait for writers to stop before integrating or reviewing their outputs. Check the combined input → rule/state → visual/audio response, motion lifecycle and recovery against the original design; isolated module success or a child summary cannot complete that player situation. After a failed/interrupted child, inspect its actual partial changes before assigning the affected work again.

## Read retained results before new execution

When implementation or a rerun depends on retained BGS evidence, use [Retained BGS evidence](references/retained-evidence.md) to inspect saved verification results, Preview receipts and relevant source/resource details. These reads never execute checks; missing, changed or interrupted evidence is not a pass. Runtime action/state wiring still needs observations.

Group independent reads and corrections for the same established cause without mixing unrelated changes or hiding a failing operation. If a source or Preview result is truncated, read the saved source/result and actual process status until the relevant instructions or observation are present; do not treat the visible fragment as the complete input or rerun merely to retrieve missing text. Do not rerun merely to count checks or retrieve a missing field. Keep a concise status, decisive diagnostics and actual coverage in the handoff; do not copy entire logs or Skill bodies into project guides. Context caching and history recovery are host concerns, not repaired by another Skill rule.

## Finish the implementation

Reconcile implementation with the full confirmed scope and design, including behavior absent from the task list. Finish applicable basic checks and hand off implemented behavior, observed results, unresolved technical issues and user-playtest questions. Use `game-playtest-performance` for a concrete runtime/performance investigation or an explicitly requested playtest; full-game bot navigation is not a default completion task. Reuse valid evidence. Waiting for subjective user feedback does not require further implementation iterations. Tool coverage boundaries belong in coverageLimitations, subjective post-handoff questions in outsideScope; missing required observations remain unverified and actual defects remain knownIssues. When no further authorized progress is possible without an external dependency or user decision, retain the blocker and remaining scope in a delivery-scoped blocked/failed acceptance report and submit it through the existing BgsFinishDelivery entry. This stops execution as blocked; it does not claim acceptance or require another test. Use `evidence-before-completion` for the final claim.

This Skill gives the Agent a repeatable execution loop. It does not require a new worktree, fixed task duration, mandatory commits, or BeeGameStudio intervention in task choices.
