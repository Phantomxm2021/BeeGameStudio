# Game Plan Execution

Use when a project already has an implementation plan. Implement its confirmed behavior and selected visual/content inputs without dropping scope, restyling or duplicating authored layouts. Local code organization and algorithms remain implementation choices. Preserve completed work and current user authorization; a plan cannot override its authoritative sources or a newer user instruction.

## Start or resume

1. Read the technical plan and relevant original design sources, selected pictures, produced resources and UI/Scene data. For a new game, start with one coherent player situation from the confirmed brief: prepare its inputs, implement it and check its basic behavior before expanding the same treatment; unrelated inputs may remain planned. Reconcile required inputs with actual files before consuming them, preserving valid work. Choose task organization appropriate to the work; no index or coverage graph is required. ReadDesignHandoff locates documents/sections; ReadImplementationTask exposes existing indexed tasks or the technical source. Use native reads for additional code, content and pictures. Use --design implementation to inspect current implementation sources within the authorized assignment; it does not freeze the documents. Plain documents need no finalize command. Existing indexed projects can finalize metadata after authorized changes; revalidate affected evidence against the updated inputs.
2. Resume from actual saved work and evidence, not task ticks or remembered completion. Reuse an existing task list when useful; do not create another ledger merely for BGS. Preserve existing IDs when applicable. Missing observations remain unverified.
3. Before consuming a dependency, inspect its needed output and interface: actual action/state names, types/units, resource IDs and exports as applicable. A ticked task or existing file/name does not prove the capability works. Missing or conflicting outputs block their consumer, not unrelated work. Correct within current authority; an out-of-scope design change needs user authorization through the existing task change path.

## Execute one coherent slice

For each task:

1. Read the task's mandatory points, original source/acceptance sections and expected results, following its source pointers rather than relying on the summary. Derive those expected results from the confirmed brief/design, not by reverse-engineering the current implementation or its tests. Invoke the applicable professional Skill before the relevant specialist decisions; reuse guidance still available instead of reloading all Skills per task. A historical load does not establish retained guidance or application after compaction/focused continuation. Missing or conflicting inputs need their exact source/gap and affected task identified; use existing authority for corrections without inventing or simplifying product behavior. Continue independent work when possible.
2. Implement the behavior in the owning code or content, connecting the confirmed action/state to its required visual/audio response and resulting appearance. Use the design's chosen representation, including resource states/frames/layers or runtime drawing as applicable; naming or loading assets does not implement their selection or playback. For scene/UI delivery, preserve the selected composition through the authoritative sources and resources, without a second layout copy. Native engine/framework sources need no separate BGS JSON. Resolve presentation lifetime with gameplay before screen changes or removal can cancel required feedback; use the existing lifecycle facilities.
3. Check the affected behavior against its source requirements through focused rule/interface tests and ordinary controls. Observe the required presentation in the actual composition: meaningful moments and the passage between them for motion, actual output for audio. Reuse the existing Preview/capture or target-runtime tools; a still, loaded file or playback call does not establish the corresponding dynamic result. Hooks isolate rules but do not verify delivered input. Retain coverage, result paths and failures in existing progress, rerunning only affected checks. Missing required presentation is unfinished; unobserved behavior stays unverified. Judgments of appeal, difficulty and feel belong to user playtesting.
4. If the check fails, decide whether the code, the test, or the plan is wrong. Trace the cause; do not repeat the same failed command without changing the relevant condition. Identify the responsible source and apply a correction only within the current task's editing scope, then rerun the affected check. If the source is outside that scope, report the evidence, impact and needed correction rather than changing it or working around it.
5. Complete the same-ID implementation item when its mandatory behavior and applicable basic checks are supported. Missing, failed or stale technical evidence remains unresolved; pending user experience feedback alone does not keep technical implementation unfinished. An explicitly requested playtest still needs its own evidence or an honest pending result. Keep verified behavior, known technical issues and user-playtest questions distinct in the existing record, without claiming game acceptance. Continue dependency-ready work within current authorization.

Keep narration and repeated source reading economical. When authorized, delegate bounded independent work such as a module, local investigation or visual comparison when its output justifies the extra call; neither per-task subagents nor per-task reviews are required. Give concurrent writers separate files/interfaces, and avoid reviewing files while another agent changes them. For a self-contained assignment, use native `spawn_agent` with `fork_context:false`; carry full history only when the actual dependencies require it. The handoff needs the goal, allowed scope, exact source/image paths and relevant sections, current partial work, dependency interfaces, necessary tool entries and evidence gaps. The child reads those sources; do not copy whole documents, Skills or logs, or preload an acceptance verdict. Return changed/result paths, decisive findings and unverified limits; the parent integrates the result and checks affected interfaces before accepting it.

## Read retained results before new execution

When implementation or a rerun depends on retained BGS evidence, use [Retained BGS evidence](references/retained-evidence.md) to inspect saved verification results, Preview receipts and relevant source/resource details. These reads never execute checks; missing, changed or interrupted evidence is not a pass. Runtime action/state wiring still needs observations.

Group independent reads and corrections for the same established cause without mixing unrelated changes or hiding a failing operation. If output is truncated or a final filter returns no matches, read the saved result and the actual process status before treating it as a test failure or executing again. Do not rerun merely to count checks or retrieve a missing field. Keep a concise status, decisive diagnostics and actual coverage in the handoff; do not copy entire logs or Skill bodies into project guides. Context caching and history recovery are host concerns, not repaired by another Skill rule.

## Finish the implementation

Reconcile implementation with the full confirmed scope and design, including behavior absent from the task list. Finish applicable basic checks and hand off implemented behavior, observed results, unresolved technical issues and user-playtest questions. Use `game-playtest-performance` for a concrete runtime/performance investigation or an explicitly requested playtest; full-game bot navigation is not a default completion task. Reuse valid evidence. Waiting for subjective user feedback does not require further implementation iterations. Use `evidence-before-completion` for the final claim.

This Skill gives the Agent a repeatable execution loop. It does not require a new worktree, fixed task duration, mandatory commits, or BeeGameStudio intervention in task choices.
