# Game Plan Execution

Use when a project already has an implementation plan. Implement its confirmed behavior and selected visual/content inputs without dropping scope, restyling or duplicating authored layouts. Local code organization and algorithms remain implementation choices. Preserve completed work and current user authorization; a plan cannot override its authoritative sources or a newer user instruction.

## Start or resume

1. Read the technical plan and relevant original design sources, selected pictures, produced resources and UI/Scene data. Reconcile the current part's required inputs with actual files before consuming them, preserving valid work; unrelated planned resources/content may remain pending while that part is implemented and observed. Choose task organization appropriate to the work; no index or coverage graph is required. ReadDesignHandoff locates documents/sections; ReadImplementationTask exposes existing indexed tasks or the technical source. Use native reads for additional code, content and pictures. Use --design implementation to inspect current implementation sources within the authorized assignment; it does not freeze the documents. Plain documents need no finalize command. Existing indexed projects can finalize metadata after authorized changes; revalidate affected evidence against the updated inputs.
2. Resume from actual saved work and evidence, not task ticks or remembered completion. Reuse an existing task list when useful; do not create another ledger merely for BGS. Preserve existing IDs when applicable. Missing observations remain unverified.
3. Before consuming a dependency, inspect its needed output and interface: actual action/state names, types/units, resource IDs and exports as applicable. A ticked task or existing file/name does not prove the capability works. Missing or conflicting outputs block their consumer, not unrelated work. Correct within current authority; an out-of-scope design change needs user authorization through the existing task change path.

## Execute one coherent slice

For each task:

1. Read the task's mandatory points, original source/acceptance sections and expected results, following its source pointers rather than relying on the summary. Invoke the applicable professional Skill before the relevant specialist decisions; reuse guidance still available instead of reloading all Skills per task. A historical load does not establish retained guidance or application after compaction/focused continuation. Missing or conflicting inputs need their exact source/gap and affected task identified; use existing authority for corrections without inventing or simplifying product behavior. Continue independent work when possible.
2. Implement the behavior in the owning code or content. For scene/UI delivery, consume the project's actual authored sources and resources without a second layout copy. Use native engine or framework sources when those are authoritative; no separate BGS JSON is required.
3. Compare actual results against each mandatory point's expected conditions and outcome. Use focused rule/interface checks for deterministic behavior and actual observations for presentation/interaction, including the relevant connections and boundaries. Reuse current evidence covering multiple points/tasks; do not rerun unchanged checks or launch a whole game per task. Retain the result path, covered points and observed differences in the existing progress record. Do not weaken the expectation to fit a passing command; unobserved or pending integration stays unverified.
4. If the check fails, decide whether the code, the test, or the plan is wrong. Trace the cause; do not repeat the same failed command without changing the relevant condition. Identify the responsible source and apply a correction only within the current task's editing scope, then rerun the affected check. If the source is outside that scope, report the evidence, impact and needed correction rather than changing it or working around it.
5. Complete the same-ID execution item only when all its mandatory points have applicable evidence. Code may be finished while verification remains pending: keep the task unfinished and note that partial progress. Missing, failed or stale evidence cannot be replaced by a tick, loaded JSON or a green build. The recorded results must support the claimed scope; do not claim visual, audible or experience quality from unrelated checks. Continue dependency-ready work without routine per-task approval.

Keep narration and repeated source reading economical. When authorized, delegate bounded independent work such as a module, local investigation or visual comparison when its output justifies the extra call; neither per-task subagents nor per-task reviews are required. Give concurrent writers separate files/interfaces, and avoid reviewing files while another agent changes them. For a self-contained assignment, use native `spawn_agent` with `fork_context:false`; carry full history only when the actual dependencies require it. The handoff needs the goal, allowed scope, exact source/image paths and relevant sections, current partial work, dependency interfaces, necessary tool entries and evidence gaps. The child reads those sources; do not copy whole documents, Skills or logs, or preload an acceptance verdict. Return changed/result paths, decisive findings and unverified limits; the parent integrates the result and checks affected interfaces before accepting it.

## Read retained results before new execution

When implementation or a rerun depends on retained BGS evidence, use [Retained BGS evidence](references/retained-evidence.md) to inspect saved verification results, Preview receipts and relevant source/resource details. These reads never execute checks; missing, changed or interrupted evidence is not a pass. Runtime action/state wiring still needs observations.

Group independent reads and corrections for the same established cause without mixing unrelated changes or hiding a failing operation. If output is truncated or a final filter returns no matches, read the saved result and the actual process status before treating it as a test failure or executing again. Do not rerun merely to count checks or retrieve a missing field. Keep a concise status, decisive diagnostics and actual coverage in the handoff; do not copy entire logs or Skill bodies into project guides. Context caching and history recovery are host concerns, not repaired by another Skill rule.

## Finish the implementation

Reconcile completed task results with the original confirmed scope and applicable design records, including requirements not adequately represented by the task list. Use `game-playtest-performance` for relevant integrated checks and the required player paths, reusing valid results. Read selected designs and captured views at matching sizes; compare the planned presentation, rules/actions, Scene/resource/audio use and relevant boundaries/recovery. Captures do not establish motion or interaction. Distinguish actual implementation, observed agreement with design and unverified experience/quality in the existing progress record; pending observations remain gaps even when layout checks or task items pass. Cover agreed conditions without inventing an exhaustive matrix. Use `evidence-before-completion` for the final claim.

This Skill gives the Agent a repeatable execution loop. It does not require a new worktree, fixed task duration, mandatory commits, or BeeGameStudio intervention in task choices.
