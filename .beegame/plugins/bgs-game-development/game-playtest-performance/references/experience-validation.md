# Requested gameplay-experience validation

Use when experience validation or an evidence-driven design revision is authorized, not as an extra stage before every delivery. Inputs are the actual runnable target/source version, the relevant design intent, one uncertainty and existing evidence. If the target is unavailable, report not-run and the missing prerequisite; inspect static material only within its limits.

Choose a scenario that could refute the intended behavior. State starting knowledge, normal controls, build, viewport/device and relevant seed/save. Derive the expected outcome from the authorized design, not the implementation's current behavior. Use the existing Preview/browser/test/capture facilities; a shortcut, state injection or solver path is an isolated-rule check, not ordinary player input or novice discovery.

Observe the target state through relevant controls and retain the outcome plus necessary timing/recovery. For a transition, keep the actual normal-speed passage and relevant interruption in an existing clip or timestamped frame sequence; endpoint stills do not establish continuity, and sparse frames leave intervening behavior unverified. Reuse sufficient evidence rather than recording every state again. Attribute a failed run to game, driver or environment before changing product code. No assumed input-to-photon measurement from bot timestamps or headless frame intervals.

Keep the small record in existing project test output or verification notes: scenario and intent; falsifiable hypothesis; version/conditions and input path; observed facts with screenshot/log/trace references; competing explanations/inferences; unresolved human questions; the concrete issue, authorized patch and same-situation retest result. These are record meanings, not a new mandatory schema, file or database. Mark severity by affected player outcome (blocks the required action, misleads, or remains an optional preference), never a weighted fun score.

Cite original execution and media evidence, and keep missing required observations separate from tool coverage limits and out-of-scope subjective questions. Do not map unrelated experience questions onto existing technical checks. A report does not itself establish a passed observation.

Give the supported issue to its existing owner. Creative resolves a cross-domain promise/tradeoff question; Systems/Balance rule, choice and parameter causes; Level spatial guidance/progression; Art composition/framing; UI interface; Feel action response; Audio audible event/mix/lifecycle; programming the actual control/state path. Use Creative’s [runtime diagnosis](../../game-creative-director-expert/references/runtime-critique.md) only for the assigned cross-domain judgment, not another mandatory review. Select the cause-specific guidance, use the existing authorized source correction and verification flow, then repeat the affected situation. Reuse unaffected design/resources/evidence; do not restart all phases or retry on a subjective score. If unresolved, retain the finding and needed action instead of an automatic repair loop.

A supplied screenshot can support a layout/cue inference, not actual action, motion or learning. Automation can establish tested transitions and observed feedback, not representative enjoyment. For real-player studies use [Player observation](player-observation.md); without participants retain that gap and do not simulate their reactions as facts.
