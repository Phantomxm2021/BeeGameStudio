## 5. Agent 自身问题的处理原则

以下事实需要改善能力可用性与证据质量，但不能变成 BGS 对 Agent 的执行管制：

| 现象 | 系统应提供 | 不应采用 |
| --- | --- | --- |
| 重复追查 404、只为看输出再次跑全程 | 现有测试记录一次保存、多次读取，区分应用网络错误与浏览器噪声 | 固定重试次数、强制新审核阶段、替 Agent 宣告 favicon 无害 |
| 同步 tick 查询 React DOM造成假失败、错误测试点对 | 可保存的测试条件/观察结果；结论明确测量方式 | BGS 自动修游戏，或以脚本 exit 0 判定需求完成 |
| 路径拼错、解释器误用、数组长度错误 | 明确 cwd、工具响应和可用能力 | 全部归因权限；放开跨项目路径或改写 shell 命令 |
| 无静音或浏览器遗留 | 现有受控浏览器默认静音、所属资源可回收 | 关闭用户浏览器，或删除游戏音频 |
| 模板/模拟替代真实需求 | 原始需求及能力缺口在交付中可见，必要时请用户决定 | 擅自降低需求，或由 BGS 接管游戏后端实现 |

## 6. 执行与验收规则

每个任务包遵循同一轻量步骤，不建立新状态机：

1. 复现日志事实并核对当前代码/运行版本；已有修复先验证，不能重复堆补丁。
2. 记录一个明确根因，在所属模块做最小修改，清理被替代逻辑；不改测试项目。
3. 用临时夹具与本地假模型做无费用验证；验收断言来自目标行为，不来自旧流程。
4. 涉及后端或 CLI 的修复，获得重启授权并确认实际加载后，才做真实页面/接口无费用检查。
5. 记录已通过、未通过、未测项与证据。新项目付费生成、既有项目内容修复均需另行授权。

完成定义：根因已修、必要回归通过、实际版本生效且目标行为验收通过。仅代码通过则标“已改待生效/验收”；原因不足则标“待定位”，不得伪装完成。
