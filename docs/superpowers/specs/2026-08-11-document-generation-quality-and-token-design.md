# Idea 到完整游戏文档的质量与 Token 优化设计

## 目标

保持现有八份 Foundation 文档及其专业深度，重构文档结构、上下文投影、生成顺序与验收方式，使真实用户从 Idea 出发能够通过 Bee Game Studio 生成可供人类团队和开发 Agent 使用的完整游戏文档，同时显著减少重复上下文、重复章节和无效模型轮次。

首轮工程目标是将完整流程总 Token 从本次基线的 14,696,571 降至 4,000,000 以内，并在不删减必要专业内容的前提下，将八份 Markdown 正文从 467,610 字符收敛到 300,000–350,000 字符。长期优化目标为 2,500,000–3,000,000 总 Token。

## 不改变的产品边界

- 文档集合保持为 `GDD.md`、`LEVEL_SCENE_DESIGN.md`、`BALANCE_DESIGN.md`、`TECHNICAL_DESIGN.md`、`ART_DIRECTION.md`、`UI_UX_SPEC.md`、`AUDIO_DESIGN.md`、`ASSET_PLAN.md`。
- 不增加第九份 Foundation 文档，不引入 MVP、骨架文档或简化交付。
- 不把任何测试游戏、项目名称、日志文本或示例 Idea 写入产品逻辑。
- 不用关键词、词组或正则表达式推断随机用户内容的语义和章节归属。
- 用户在设置界面确认的模型、平台、引擎、权限和资源策略保持最高权威。
- 不绑定某一个平台；文档只遵从当前项目已经确认的生产设置。

## BGS 与 Claude Code 的职责边界

Bee Game Studio 负责工作流编排，不负责控制 Claude Code 的思考与写作过程。BGS 只提供：当前 Confirmed Brief、当前文档职责契约、被职责契约允许的上游权威投影、目标路径、用户确认设置和完成标准。BGS 保存状态、固定服务端口、显示原始 API 错误并在文件落盘后执行确定性校验。

Claude Code 负责理解文档职责、完成专业正文和生产资料、使用正常思考能力、调用原生工具并将完整文件落盘。BGS 不禁用 Thinking，不注入整段历史会话，不为每份文档重复发送全部上游全文，不以 Watchdog 或业务层工具规则干预正常写作，也不通过多轮 Reviewer 代替首次正确生成。

## 八份文档的统一信息架构

每份文档保留其现有 canonical section marker 和职责章节，但呈现结构从“每章五段”改为四个文档级层次：

1. **执行摘要**：职责、关键决定、主要生产结论与完成定义，目标为五分钟内读完。
2. **专业正文**：按 canonical section 顺序呈现该学科拥有的设计事实、理由、参数和实现约束。
3. **生产资料**：按学科生成表格、流程图、线框图、参数表、状态图、矩阵或引用登记。资料必须服务实现与验收，不得为了满足格式而制造装饰性图表。
4. **审计附录**：统一汇总上游引用、风险、开放决策和验收标准。

不再要求每个 canonical section 重复 `Authoritative Decisions`、`Production Details`、`Upstream Authority`、`Risks`、`Open Decisions`。没有风险、引用或开放决策时不输出空段，也不输出 `No unresolved section decisions.` 等占位句。

## 学科专属生产资料

- GDD：产品与玩法总览、核心循环图、状态流图、范围和完成定义。
- Level/Scene：世界或关卡结构图、路线与选择图、节拍图、出生/恢复及场景转换示意。
- Balance：变量和参数表、权威公式、边界算例、经济流和调优验证矩阵。
- Technical：架构、数据流、状态生命周期、存档恢复、构建与验证图表。
- Art：视觉支柱板、色板、剪影与比例表、材质规则、动画/VFX 状态样例；输出必须使用可落盘的原创 SVG、表格或已登记参考，不制造不可追溯外部素材。
- UI/UX：信息架构、用户流程、屏幕与状态清单、低保真线框、HUD 布局、焦点和无障碍矩阵。
- Audio：事件到 Cue 矩阵、音乐状态图、总线与 Ducking 图、响度/格式交付表、可追溯声音参考登记。
- Asset Plan：资源主表、责任矩阵、依赖与集成顺序、许可表、里程碑与成熟度表。

## 上下文投影与生成顺序

生成顺序仍按职责依赖执行：GDD → Level/Scene → Balance → Technical → Art → UI/UX → Audio → Asset Plan。顺序本身不要求把此前所有正文注入后续 Agent。

每次文档生成只投影：

- Confirmed Brief 中当前职责需要的结构化字段；
- 当前 `GameDocumentContract`；
- 合法上游文档中由稳定 section identity 选择出的相关 section；
- 用户确认的生产设置；
- 当前目标路径和 deterministic completion contract。

上游选择必须来自显式 section contract 和稳定 ID，不得通过用户文本关键词、正则或 LLM 摘要猜测。投影结果只在内存或工作流请求中存在，不落盘为第二事实源。文档 Agent 不获得其他项目路径的通用读取权限，也不携带上一位文档 Agent 的模型对话。

## 生成和修订策略

每份文档默认一次完整生成。服务端在落盘后执行确定性校验；只有校验报告包含明确的结构、缺失资料、非法引用或落盘错误时，才允许一次定向修订。内容品味和跨文档冲突不通过反复自动 Reviewer 在首次生成阶段处理。

最终八份文件全部落盘后暂停文档 Agent，再执行一次综合评审。综合评审结合实际文档与代码路径，分别评价职责完整性、生产可执行性、人类可读性、Agent 可消费性、冗余、Token、轮次和耗时。内容冲突属于独立维度，不应掩盖文档自身质量结论。

## 确定性校验

服务端校验以下可机械判定的事实：

- 八份目标文件全部存在且为非空 canonical Markdown；
- front matter、canonical section marker、章节顺序和文档职责匹配；
- 执行摘要、专业正文、必要生产资料和审计附录结构完整；
- 没有空模板、占位句、重复实质段落、虚假文件路径或未登记引用；
- 学科专属生产资料符合当前文档合同；
- 文档大小、生成轮次、Token 和耗时被完整记录；
- 任何 API 或落盘错误以原始 provider 信息和工作流上下文展示。

确定性校验不判断文档主题内容，不通过正则或关键词给设计打分，也不要求模型为格式检查重复阅读文档。

## Chrome 验收

最终验收必须从固定端口启动真实 BGS 服务，使用 Chrome 操作设置界面和 Idea 输入流程。测试使用运行时提供的用户 Idea，不在产品逻辑或测试工具中硬编码某一游戏案例。测试验证：

1. 用户设置被完整采用；
2. Idea 到八份文档生成可以完成；
3. 每份文档及时落盘，错误可见；
4. 文档完成后 Agent 暂停；
5. 八份文档通过职责、结构和生产资料审计；
6. 总 Token ≤ 4,000,000，模型轮次 50–70；
7. 若未达 Token 目标，日志能按文档区分 fresh input、cache read 和 output，能够定位剩余浪费。

## 成功标准

- 八份文档数量和职责不变，完整度不降低。
- 机械模板不再占据每个章节，空开放决策段为零。
- 需要视觉、空间或交互表达的文档具有实际图表或可追溯生产资料。
- 人类可以先读摘要，再进入专业正文；Agent 可以按 section identity 获取局部权威，不需反复读取整包文档。
- 首轮总 Token 不超过 4,000,000；若完整度相同而文档字符低于 300,000，需要人工确认没有以压缩为名删除生产信息。
- 完整 Chrome 测试和最终产物审计同时通过后，才能宣称 Idea → 完整文档调整完成。
