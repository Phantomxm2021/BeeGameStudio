## 0. 不再摇摆的设计结论

**不是旧六阶段的迁移版，不是八文档改名成八种 Task，也不是放弃专业能力后完全相信 LLM。**

- 固定的是产品入口、用户承诺和八领域专业覆盖：idea → 三选一 → 游戏设置 → 提交完整目标；玩法、技术、美术、音频、UI／UX、场景／关卡、数值／平衡、资源规划默认完整考虑，相关决定与验证依据可追踪。
- 动态的是生产路径：Claude Code 决定计划、实际依赖、原型、工具、相关 Skills、必要委派、检查和修订。
- 复用的是旧流程的专业知识、编辑／制作工具、数据契约和真实验证能力，不复刻其阶段顺序。
- BGS 负责授权、实际身份／项目／会话、Question、事件、恢复、版本和用量，并保存其可核实的检查事实；不替 Agent 安排技术方案。
- 结果仍要满足确认需求。动态规划不授予降低范围、跳过必要验证、改已确认引擎或伪造完成的自由。
- 不先删模块，也不先承诺所有旧代码必须保留；按实际消费者拆开“有用能力”和“固定调度依赖”。
- 不新增 Planner 服务、通用 DAG 执行器、引擎分流框架、统一 Scene 模型或全量语义验收系统。

八领域规划默认完整覆盖，八文档默认组织，Agent 动态安排执行，实际游戏结果接受验收。八文档、Review／Revision、UI／Scene 和资源能力继续复用；默认文档组织不等于八个阶段、八名作者或八轮审查。简单项目可按 §3.6 合并记录，但不能省掉领域责任。八份文档全部完成不是开工前置条件；影响下一项工作的决定须在被依赖前明确，探索原型可以先行。

**自主的是执行方法，不是可以随意取消交付能力。** 文档统一组织、足以指导制作的专业决定、承诺的可编辑数据与实际资源消费属于交付要求；不能因为工具标为可选或 Agent 选了另一渲染库就静默省略。也不为让检查器通过而补一套运行时不消费的影子数据。

本次纠偏针对已证实的落地缺口：此前接单指令只笼统要求使用 Skills 和自行选择设计／检查，真实测试证明部分功能，未证明专业设计与品质覆盖完整。1.39 已接入共享专业责任、修正方法的旧流程前提；1.40 将可核对的报告指纹、实际执行与静态 Web 构建关联，并接通独立 debug 的已测候选／工程导出。这些不等于专业执行已经可靠，报告中的语义与体验结论仍须实际核对。BGS 能检查来源、版本、执行与引用事实，不能程序化证明任意玩法有趣或画面有品味。

## 2. 主线：完整目标交给 Claude Code，不交给另一个调度器

### 2.1 接单输入

沿用现有产品入口和确认记录，生产输入包含：

- 用户原始 idea、附件来源、选中方案及确认设置，尤其引擎／技术、目标平台、输入、语言、资源策略和首发要求；
- 当前工程、已有成果与已知问题的真实位置，当前授权及明确限制；
- 可用专业 Skills 与能力入口的简短说明，以及当前环境实际限制。

只消费选中方案；未选方案保留历史，不默认全部注入。已有项目的局部修改直接承接当前工程与新要求，不重新走三选一。

提交包含当前目标与一段简短专业交付责任，明确八领域默认覆盖、八文档默认组织及简单项目的合并方式；详细方法和现有来源通过真实路径按需读取。不要预载八文档正文、全资源字节、所有 Skill 正文、后台日志或本文全文。接单与变更指令复用同一职责定义；局部变更只要求处理受影响的专业内容，不重新编写全项目设计。

### 2.2 谁决定什么

| 主体 | 决定／承担什么 | 边界 |
|---|---|---|
| 用户 | 确认目标、设置、范围与重要变更，授予必要权限 | 不必批准每个 Todo、普通实现细节或审美微调 |
| Claude Code 主 Agent | 计划、专业设计决定及必要记录、工具／Skills、委派、实现与整合、品质检查和修复 | 覆盖当前目标与 §3.1 八领域责任；可以选择方法、顺序和有理由的文档合并，不能悄悄降低承诺或仅以自身判断证明合格 |
| 原生 subagent | 完成主 Agent 明确委派的专业工作／独立检查 | 来源、目标与修改范围明确；不是 BGS 固定作者名单 |
| BGS | 用户与项目归属、授权、正常执行传输、事件、Question、恢复、用量、实际版本与检查记录 | 不把默认文档组织变成文件数门禁或写作排程；不决定工具顺序、专业方案、修复路线或下一业务阶段 |
| Skills／能力工具 | 提供专业方法或可执行操作，准确说明输入、结果和限制 | 不扩大权限，不另定义业务职责，不把工具成功包装成游戏合格 |

专业职责由确认需求和任务指令明确；Skill 帮助做好工作。不要同时在 prompt、Skill 和宿主状态中维护三套职责。

### 2.3 动态规划的具体含义

Agent 根据当前依赖和不确定性选择下一项有价值工作，完成或发现新事实后调整计划。计划可用原生 Todo／计划和必要工程说明，不要求发布宿主 DAG。

- 核心机制不确定：先做标明探索用途的可玩原型，再根据实际结果收敛规则；不先写齐八文档。
- 机制明确、视觉组合有风险：可以先检查资源和界面／场景组合，避免完整制作后才发现不适配。
- 普通代码缺陷：依据现有设计直接修复并验证，不重开全部策划。
- 设计确有缺口：明确负责决策，修订实际来源及必要消费者；改变用户承诺才请求用户裁决。

这些是不同路径的示例，不是三个模板、项目分类器或新增阶段。必要依赖不能跳过，但不能从旧批次顺序推断全部工作必须串行。影响其他工作或玩家体验的决定，在消费者依赖它之前说明；尚需探索的部分可标为暂定并先做原型，不要求开工前写齐全部记录。

## 3. 专业能力如何介入，而不是八次必经作业

### 3.1 八领域默认完整覆盖，八文档默认组织

八领域都是规划覆盖项，不能由 Agent 随意挑选几个完成；覆盖深度按真实游戏复杂度决定。下面八文档是默认的持久组织方式，不是八次必经作业、八名作者或八轮审查。同一 Agent 可负责多领域，可先原型、交叉推进、按依赖补齐记录。简单工程的合并方式见 §3.6。

不要求所有游戏增加相同功能。某项子要求不适用时，简短说明与当前目标一致的理由；不能用“没写／没测”冒充不适用，也不能自行取消已承诺内容。没有经济系统仍需速度、时长、数量等数值决定；不使用外部图片仍需规划字体、程序化视觉、音频等实际资源，不能据此省掉数值或资源领域。

| 专业领域／默认文档 | 必要设计决定／目标 | 交付时观察什么 |
|---|---|---|
| 玩法与趣味／GDD.md | 玩家目标、动作和结果、核心循环、失败／结束／重开；挑战、选择、变化或其他持续投入来源；范围及最需验证的体验假设 | 实际经历开始、学习、主要挑战和结束／重玩；能说明哪些选择或技巧影响结果、节奏／挫败点如何；不凭可通关证明有趣，不强加排行榜、成长或随机性 |
| 技术／TECHNICAL_DESIGN.md | 用户所选路线、真实环境能力、关键接口、输入／加载／清理、保存与失败恢复中的必要决定 | 实际构建／启动、核心规则和集成；平台事实有来源或能力测试，性能结论有目标环境测量 |
| 美术方向／ART_DIRECTION.md | 主题与视觉语言、色彩／形状／材质或表现方式、文字与信息层级、关键对象辨识、界面／场景／资产一致性；适用的开始／结束画面 | 当前构建的代表画面与实际动态表现对照方向；检查可读性、焦点、统一性和完成度；资源昂贵或用了生图不等于美观 |
| 音频／AUDIO_DESIGN.md | 声音角色、所需事件、播放／停止／并发／音量与静音行为；是否需要音乐或有意静默及其理由 | 真实触发和状态切换；核对漏播、叠加、突变、重复疲劳与混音／听感。音频调度探针只证明调度；无可听证据或判断能力时保留听感未验证 |
| UI／UX／UI_UX_SPEC.md | 必要玩家界面与状态、导航、操作反馈、目标输入／适配、暂停／恢复及适用异常路径 | 实际操作而非只看截图；信息和控件可见可用，界面与美术方向一致；不把游戏界面简化成无主题的管理表单 |
| 场景／关卡／LEVEL_SCENE_DESIGN.md | 可构建空间、相机、目标／出生点／障碍、路线与教学／挑战安排；与玩法对应的空间规则 | 在实际场景完成必要路径，检查可达性、镜头、辨识与难度安排；几何检查只覆盖其可计算范围 |
| 数值／平衡／BALANCE_DESIGN.md | 速度、时长、数量、收益／代价等适用参数的初值、单位、关系和范围；难度／节奏与调优意图，关键计算依据及待实测假设；引用实际配置，不维护第二套值 | 确认运行时消费当前配置；关键数值计算与目标一致，试玩观察节奏与难度；初值可用不代表最终平衡优秀 |
| 资源规划／ASSET_PLAN.md | 必需图像、字体、音频、特效及程序化资产的用途、规格、来源／许可、制作或复用方式、绑定位置与可用回退；区分占位和正式内容，引用实际登记 | 当前构建中真实加载、显示或播放，风格／规格符合用途；已要求的正式内容不能用未批准占位替代，登记存在不等于实际可用 |

操作与状态反馈是跨领域要求，不是第九份文档或独立阶段。GDD 明确关键动作／事件及其结果；UI／美术负责可见响应，音频负责声音，技术负责接线与时序，相关数值决定节奏。对本项目关键事件记录适用的反馈方式并引用同一事件含义，不在多份正文重复定义规则。验收时实际触发响应、成功、拒绝／失败、奖励和状态变化，观察及时性、可理解性和可区分性；静音时关键状态仍可理解，不把特效数量当品质。

对“高品质”的判断需要项目内可比较的方向和实际结果。主 Agent 在必要设计记录中说明期望体验、表现方向与最重要的品质风险；有参考时记录参考及采用的特征，没有外部参考可用实际原型／局部表现确定方向。不强制先生图，不要求用户逐屏投票，不以增加内容规模代替打磨。

GDD 对玩法和范围有权威，其他文档承担各自专业决定，不重复定义玩法或替别的领域选方案。新工程八文档统一放在 `docs/`，使用上表文件名；领域标签不是路径，不再生成 gameplay/、art/ 等每文档一个目录。既存工程先保留真实路径和引用，归并须由项目 Agent 在授权修改内同步链接，系统开发者不得人工搬迁验收产物。简单工程仍可明确合并，不补空文件。文档保存设计依据，配置／Content／资源登记保存实际消费数据，运行证据证明已测结果；写齐文件不等于设计完整或游戏合格。

设计深度按“下游能否据此制作，下一次修改能否知道理由”衡量，而非字数或与旧稿对比。§3.1 的决定需要当前游戏的具体答案、必要理由、实际数据位置及待验证假设；仅复述“精美／有趣／有反馈”不足。美术与 UI 至少能说明构图焦点、关键对象语言、文字层级、主要屏幕与状态表现，并用同一真实游戏的代表画面／动态片段核对；不另做只供审计的假预览。数值／关卡不复制两套表，必要计算有可复核依据。来源冲突、未观察到的效果须保留问题，不能因八稿齐全宣布完成。上述审美与语义仍需实际判断，不宣称可由程序保证。

### 3.2 Skills 需要明确介入

正常接单与生产续作指令明确要求：开始相关专业工作或审查前，通过原生 Skill 工具加载适用且尚未加载的方法；Agent 选择相关方法，不把“按需”理解为可以完全忽略专业方法。不可用时准确报告，使用实际可用依据继续允许的工作，不能伪称已调用。复用 native-skill-plugins.ts 的标准 plugin 提供方式，不修改 Claude Code loader、不预载全部方法、不按固定阶段挑 Skill。记录调用不等于判断正确，也不为补调用单独开付费回合。

策划、UI、美术、音频、场景、数值、资源、实现和审查可复用已有专业方法；具体名称和可用性以运行配置中实际可见目录为准。处理专业问题时选择相关方法，已加载且仍适用的方法无需为每次 Edit 或复核重复加载。八领域覆盖不等于必须加载八个 Skills 或建立八个子代理；缺少某一专用 Skill 不免除该领域的设计责任。

接单／变更指令定义职责，Skills 只提供怎么设计、检查与取证的方法。1.39 已核对策划、技术、美术、UI、音频、场景、数值、资源和 game-design-check 等相关方法；修正了 8 个 Skill 入口和审查参考的适用范围，保留专业内容及八文档写作支持。旧批次／回执／固定 delivery 路径仅在当前任务实际提供时使用，BGS 数据专用要求不套到 DOM 或引擎原生工程；不要求写齐八稿或只凭正文判断结果。通用方法同时接受八文档或明确合并的实际来源与运行观察；有效数据契约保留，不另建平行品质 Skill。Skill 成功加载只证明方法进入上下文，不能证明运用正确。当前 skillEvidence 主要记录 Skill 工具生命周期；不得把缺少此事件直接当作所有方法均未使用，也不得把目录存在当作已使用。用户明确要求的调用缺证时应披露，不能伪造调用或用补调用刷通过。

### 3.3 UI／Scene：可编辑交付与技术路线分开

新建 BGS Web 游戏默认交付可编辑的 `content/scenes/*.json`、`content/ui/*.json`，按现有消费者需要维护 `content/index.json`，遵循既有 Schema、坐标、稳定 ID 与 Camera／game-view 关联。已有编辑器通过 game-content API 读取这些文件，只有 TS／DOM 代码不等于支持该编辑能力。React／Canvas 是实现选择，不是豁免数据交付的理由；除非用户明确取消 BGS 可视编辑要求，否则不静默改为源码限定工程。同一数据逐步补全，运行时真实消费；不得维护另一份独立硬编码坐标，或仅为检查生成不用的 JSON。

有实际可计算数据时即可用空间算法，不等到某个固定阶段。真实字体、图片／图集等输入改变后重查受影响部分；最终还需看实际游戏中的画面与交互。未知几何、3D／XR 及动态遮挡不能用矩形检查冒充通过。

Unity／Godot 使用各自原生 Scene／UI／资源工程，不额外复制为 BGS Web JSON；不由宿主指定引擎方案。明确要求仅源码交付的 Web 项目可按本身格式实现，但不能同时声称 BGS 编辑器可编辑。旧非 JSON 工程与本次暂停样本不能因规范升级自动改造；涉及交付结构迁移时先明确授权和影响。确定性检查验证格式、引用及可计算布局；另需通过当前构建中的真实数据变化验证消费，不能只看 JSON 存在。当前专项工具覆盖不足时标未验证，不回退为“无需数据”。

1.41 发现的 Task-only 保存依赖已在 1.42 解除：自主 Run 可通过原有 game-content API 与独立 debug，凭项目编辑权限保存已登记的 Scene／UI 数据；不创建 Task、原生回合或新数据库表。沿用 Run 版本／来源指纹、独占 writer、原稿归档和原子替换，保存记录与原生执行历史分开。暂停／占用／过期版本不可写；返回不确定时凭同一请求身份核对，不盲写、不自动重试。

成功保存是未测候选，不能复用之前的 Preview／导出；来源改回原字节也不复活旧测量。后续由用户明确发送正常同工程消息，Agent 核对实际改动、处理必要设计／消费者并重建测量；BGS 只提供上次原生回合后发生的文件路径／保存状态，不注入整份 JSON、不自动派发、不重开八文档。无变化的保存不使旧测量失效。保存中断或提交结果不明时，保留候选和记录；只有宿主确认操作退出后才能显式恢复 writer，不能凭缺失会话／超时解锁。

现阶段已在本地和真实 Supabase＋本机独立部署服务，用正常登录、真实 CLI／固定假模型验证上述闭环、实际浏览器数据消费与空闲服务重启。它不证明真实游戏品质、模型自主产出完整数据或新编辑跨进程故障组合全部通过。仅编辑现存登记数据，不自动迁移旧源码工程、新增文档或重写登记。完整 legacy index／package 的版本字段仍按真实来源处理，不伪造八文档审批或 Manifest 指纹来凑格式。

### 3.4 资源与数据消费

保留资源库、生成／下载／程序化制作、规格检查、登记、图集、批量绑定及来源／许可记录。资源使用策略来自确认设置；管理员开了工具不等于项目必须使用。

先依据专业表现目标判断需要什么、现有资源能否满足，再选择复用／生成／制作；资源策略 optional 只表示不强制使用资源库，不表示可以省掉资源设计与成品要求。程序化内容可以是正式资源，但须满足同样的视觉／声音目标，不能仅因下载方便与否作结论。无需为每个游戏强制付费生图，外部资源调用次数也不是品质指标。

付费验收必须复用正常本地启动器的资源、Skills、计费配置，再把资源配置传入正常 app；仅加载根 env 不等价于完整运行环境。复用现有配置生成函数，不另建服务发现框架；配置成功、鉴权可用、目录查询成功和实际资源消费分别举证。缺配置／服务错误不得当空目录或“没有合适资源”。收费生成保持现有显式授权、稳定请求身份和恢复规则，不自动重试。

需要早期资源试验时可以先做，不等八文档全部通过。占位可用于开发，不能冒充批准的最终资产；符合目标的程序化表现不天然等于占位。

并行工作由 Agent 决定，共享登记与同一文件写入需要协调。没有必要为每项资源建立宿主 Task。绑定／加载成功后仍需观察实际显示、播放或行为变化，不把“已经复制到工程”当成集成完成。

### 3.5 多技术路线

用户指定 Web／React，Agent 使用代码和正常开发工具；指定 Unity／Godot，Agent 操作真实引擎工程，使用可用且获授权的 CLI／MCP。不要求 Web 增加引擎接口，也不要求引擎同时具备两种控制方式。

不按 engine 名称禁止 Bun、浏览器等辅助工具；检查器只说明它实际检查哪个产物。Web 导出检查不证明原生工程编辑能力。工具缺失时核对环境、报告缺口，必要时 Question；不静默改引擎或安装。

### 3.6 必要设计记录：让下一次修改有依据

默认按 §3.1 的八文档组织持久设计，内容深度与工程相称，不为凑章节复述需求或扩写。简单项目中，若分文件只会重复同一批决定，Agent 可将相关领域合并到现有 README、GDD 或专项说明；在现有目录或正文中标清八领域各自在哪里及合并理由即可，不需另建第九份索引文件，也不逐份请求用户批准。合并不等于省掉数值、资源或其他领域；用户明确要求独立文档时遵从。

每份文档按依赖逐步形成，不等全部完稿才允许原型或实现，也不为满足默认文件名创建空稿。只记录影响玩家体验、后续实现／验收或需要持久解释的决定；不逐操作写日报，不新增文档字数／篇幅门槛、全量需求 Schema、Decision Taxonomy 或独立文档流水线。既有内容可直接引用，专业协作确有需要时再拆出相应文档。

记录应能找到：当前目标与范围的原始出处；相关设计决定及必要理由／假设；实际权威文件的位置；尚待验证的关键问题。内容可以是段落或短表；已有信息直接引用。临时探索标明用途，形成依赖或交付前补齐决定；不能先随意实现，再把代码行为倒写成用户需求。

| 确认 brief、设置、Question 答复与授权变更 | 用户承诺和范围；最新明确变更覆盖冲突的原选择，原始记录保留。BGS 已有 requirements／变更记录继续承担此事实 |
| 必要设计记录／既有专业文档 | 授权范围内的专业选择、体验目标、规则意图与接口；设计调整由负责该工作者修订并说明影响。不得以文档重写扩大用户授权 |
| 实际配置、代码、UI／Scene 与资源引用 | 被运行时消费的具体值、结构和绑定。文档链接其位置，避免复制第二套数值／坐标；发现实际行为与设计冲突时说明并修正，代码存在不能自行证明设计正确 |
| 测试、运行观察与交付说明 | 哪个版本在什么条件下验证了什么、限制是什么。执行回执、临时地址和大段日志留在已有证据位置，不塞进设计正文 |

首次依赖一项重要决定时留下可用记录；首次交付前能定位八领域的实际决定、适用理由与必要证据，不靠篇数证明覆盖。修改时同步受影响记录和消费者，维护已有工程版本／变更记录。只更新内容有变化的文档版本或修订说明，不将八份版本号统一升一遍；实现没改的设计理由无需重写，纯代码重构不重写设计。恢复时按当前保存内容继续，不把整个旧会话重新整理成文档。

委派只交接目标、必要决定、来源路径、允许修改范围和期望结果；子代理发现上游冲突时报告具体来源或在原授权内协调修订。用户承诺变化或关键输入缺失才 Question。主 Agent 负责整合，BGS 不为每个专业决定新建负责人注册表。

## 4. Review／Revision 与质量：方法动态，事实不能随意省略

### 4.1 审查由 Agent 组织，不是宿主固定循环

保留专业审查 Skill、原生独立 Reviewer、确定性检查、来源明确的问题和集中修订能力。Agent 根据当前风险安排审查：高影响规则在被大量消费前核对，视觉／反馈可用代表性可玩片段验证，局部修改核对真实影响。不把这些时机固化为游戏生产阶段，也不强制每个文件都派 Reviewer。默认八文档不产生八轮审查；首次交付核对八领域覆盖与必要跨领域依赖，复用已做的检查和真实来源，后续只重查变更及受影响部分，不按文件清单全量重读。

有独立检查价值时，Reviewer 从原始要求、当前决定和实际产物出发，检查作者可能漏掉的关键路径；不能只验证作者自己挑出的成功项。确定项用现有程序与运行证据，语义／体验用专业观察；不新增一个负责全项目语义认证的宿主 Agent。

审查问题需要具体依据、下游影响和可观察的关闭条件。未兑现承诺、影响核心体验的实际缺陷、关键验证缺失应处理；已有目标外的建议、无下游影响的整理或个人偏好列为可选改善，不因来自 Reviewer 就自动变成修复任务。严重影响辨识、操作或反馈的表现问题不能以“主观”降为可选。

Revision 可修正授权内的专业选择并同步必要消费者；用户承诺／范围改变才 Question。修复后的定向复核关注改动和真实影响，不因涉及一份文档就重读全部资料。问题关闭后，可选项不默认重开本轮；若 Agent 判断必须继续改善，应指出未满足的具体目标和新增验证必要性。停止依据是当前承诺与品质问题的处置，不是审查次数。

只读检查不能暗改来源再宣布通过；修订者不能用自己的“已关闭”代替必要复核。Agent 可委派独立检查，但另一个模型也可能漏检。去掉宿主固定 Review／Repair Task 链，不等于取消这些质量责任。

同条件反复失败且无新依据时，要说明原因和需要的行动，而不是宿主自动另开作者／Reviewer 重派。正常 Agent 修复不受隐藏硬轮数限制；用户预算、权限、取消和账户真实额度仍有效。

### 4.2 可核查事实与语义判断分开

| 检查对象 | 优先依据 | 不足与处理 |
|---|---|---|
| 格式、引用、几何、资源可解码等 | 既有确定性检查与真实输入 | 仅对实际覆盖有效；不检查的内容保持未知 |
| 构建、启动、规则与集成行为 | 项目测试、实际运行和必要操作／观察 | 测试可能遗漏或断言错误；不能用退出码证明所有玩法 |
| UI／Scene、字体、资源、音频消费 | 实际目标运行时中的结果与对应来源 | BGS 专项仅覆盖支持范围，不代表全部引擎／设备 |
| 规则冲突、需求误解、趣味、审美、听感 | 原始要求、专业设计方向、原型／试玩和实际画面／声音的具体观察 | 模型评价只是有依据的意见；没有实际材料／感知能力时不能声称已看／听／试玩，需要时由有权者判断，不以模型分数签字 |
| 缺环境、缺输入或过期证据 | 实际失败原因和当前版本 | 标未验证／阻断，不能伪造 PASS 或改为“不适用” |

不要求用户对每张画面投票，也不要求 BGS 拥有所有玩法的检查器才开工。无法可靠证明的品质结论须说明限制；不能以此隐瞒明显缺陷或省掉已确认的表现要求。

### 4.3 从原始要求核对覆盖，不从 Todo 反推完整

交付说明对照原始目标、最新变更、§3.1 八领域及实际必要玩家路径，数值与资源同样需要实际决定和来源；某项子要求不适用须有理由。专业检查不能只回答“文件存在”“构建成功”，也不要求在交付说明重新抄写八文档。开始／学习、核心循环、结果／重玩，以及目标要求的暂停、输入或异常路径，均按实际游戏判断适用性，避免强加无关功能。

复用已有 README／测试报告／交付说明，用简短对应关系即可：某项要求或设计目标 → 实际来源／运行位置 → 当前版本的检查或观察 → 结果与限制。无需逐代码行登记、为每条自然语言生成 ID 或另建全量质量账。测试命令输出保存在证据中，交付说明只引用关键结论。

责任和边界必须分清：

- 作者维护实际来源与验证材料；主 Agent 整合后核对原始要求，不能只汇总已完成 Todo。有必要时使用独立专业检查补查遗漏，不固定再跑一轮全项目 LLM。
- BGS 只用已有身份／文件／执行记录核对可以确定的事实：引用是否可读、关联项目和版本是否一致、调用是否实际发生、已知失败是否被略去。声明了不适用或写齐章节不代表语义正确。
- 当前自主入口已关联需求、源字节、构建及报告版本，并提供独立 debug 的读取／Preview／导出；1.48 同一当前输入核对可在原生回合内只读调用，收尾时由宿主再核对实际状态，不额外派模型。此关联仍不证明报告语义、专业覆盖或品质；不能解析一句 PASS 开放交付。
- 如果 Agent 漏写一个要求，程序不能从“已有条目全部通过”证明完整。独立核对仍应回到原始请求；缺少可靠判断的关键项保持未验证，必要时有权者处理。普通专业选择由 Agent 承担，不转成用户逐项审批。

最小接线只关联已有材料：在现有 Run／AgentTurn 或产物附件中可找到需求版本、相关源／构建身份、设计／报告位置和执行来源；已有字段优先复用，缺少关联才补少量元数据，不新建表或要求 Agent 回填第二套计划。结构提取不得猜测语义结论；找不到材料就呈现缺口，不让宿主再追加一个付费总结回合。具体字段在实施时按真实消费者核对，本文不预设新协议。

同一源码／构建、测试输入和环境下已有的有效证据可以引用。修改后按实际影响重新构建／检查：旧版本端到端通过不能接受新构建，未受影响模块的测试可注明版本与不受影响理由后保留；共享初始化、渲染、输入或音频等改变需扩大到相关运行路径。无法确定影响时说明原因并扩大必要检查，不默认全项目重审。

### 4.4 完成、可验收和发布不是同一件事

原生 turn 结束只证明执行结束。交付应能找到当前可运行游戏、可继续修改工程、启动方式、已核对的核心路径、实际证据和已知限制。

必需功能有明确缺陷或关键验证缺失，不能称“合格交付”；可保留候选预览和成果，但准确说明状态。通过构建／某项检查不等于整个游戏通过。

既有发布权限与有效证据约束保留；本文不解除当前 V3 关闭状态。源／构建 hash 只说明身份，不证明品质。收尾至少区分：实际可运行与已测功能、设计／表现的观察结论、未验证项、当前工程与构建位置。不能把“功能通过、品质未知”合并成“高品质游戏已交付”。

质量验收不要求用户反复选择好不好看。能依据目标和实际表现作出的专业决定由 Agent 做；真实试玩／听感等材料不足，或关键体验仍有争议时明确限制，必要时有权者裁决。自动流程的能力边界应诚实保留，不能靠再增加一个 LLM 投票补足。

### 4.5 品质检查怎样执行与留证

先围绕最有风险的体验选择代表性运行片段，再覆盖实际必要玩家路径；同一次运行可同时观察玩法、视觉层级、输入反馈和音频，避免按领域重复通关。录屏／截图／测试结果只保存有用途的材料，不逐帧制造审计文件。

| 检查方式 | 适用内容与产出 | 不能替代什么 |
|---|---|---|
| 确定性检查 | 规则、计算、引用、几何、构建、资源加载等；保存输入、当前版本和结果 | 不证明趣味、画面品味或完整语义覆盖 |
| 实际运行与专业观察 | 触发关键操作／结果／失败，观察可读性、反馈时序、风格一致与节奏；记录具体现象和对应画面／操作 | 静态截图不能替代交互，音频事件计数不能替代声音听感，使用作者同一算法作断言不算独立核算 |
| 必要独立核对／试玩 | 从原始要求与设计方向检查遗漏或高风险假设；指出依据、影响和关闭条件 | 不以 Reviewer 的身份、评分或 PASS 证明可靠，不把可选建议全部变成返工 |

验证驱动自身失败时先区分入口、测试脚本和游戏缺陷，保留实际错误；不能为了让脚本通过而修改本来正确的游戏。维护的回归脚本由作者保存到正常测试目录，有价值的临时探针可由作者整理为长期测试。检查者无需每次重造连接、定位和音频探针；源码、输入与环境适用性仍需核对。

## 5. BGS 怎样支持执行而不变成第二个 Agent

- 复用正常 native 提交、stream-json、plugin、session/resume、权限和原生 subagent；不改工具描述／结果、query loop、压缩、思考或最终回复。
- 原生计划是执行安排；BGS 可展示实际计划／Todo／事件，不把每个 Todo 转成必须领取的 Task／Attempt。
- 正常授权覆盖需求内的开发、检查和修复；新增权限、费用授权或实质承诺变化仍需原生确认。
- 能力从现有入口提供简短帮助：实际参数、结果、错误位置、覆盖与限制。无需另建 Capability Map 文档、引擎适配框架或动态规划服务。
- 子代理事件归到真实子代理，用量归实际请求；不把全部子日志注入主上下文，也不冒充主 Agent 消息。
- 平台状态来自真实事件与事实，不解析一句“进入下一阶段”来自动派发业务。原生空闲不等于后台操作完成，Agent 完成声明不等于质量验收。
- 原生 turn 结束后，BGS 不默认追加付费总结／下一阶段／修复请求。Agent 内部可在授权内继续用工具；需要后续提交时必须有用户授权或事先明确的持续执行依据，不能把普通完结当作无限续跑许可。

### 5.1 Question 与需求变更

真正发出原生 Question，并把实际答复送回正确会话／子任务。不要求先写宿主 finding JSON 才能提问；沉默、拒绝、过期答复不是批准。

新要求交给 Agent 当前工程、确认事实及变更，不由 BGS 生成详细修复路线。Agent 更新有变化的实际权威来源与消费者；不默认重开全部八文档或重造 UI／Scene。Agent 内部职业选择不应每次都推给用户。

### 5.2 中断与并发

用户暂停是持久意图，重启不解除。恢复先确认原生会话、子代理和实际后台／引擎操作状态；未知写者不因超时自动解锁，也不启动竞争写者。

原生子代理属于已授权协作，不应仅因没有独立 BGS Task 就认定非法；平台仍需区分真正竞争的项目会话。复用现有安全能力，具体接线需查证，不新增通用进程框架。

保留部分成果与历史，恢复按实际已保存状态继续，不盲目重做。外部收费请求响应丢失时用现有请求身份／outbox 核查，不盲重放。

### 5.3 Token 成本：先减少重复工作与不必要的长上下文请求

|---|---:|---:|
| 作者实现、首次测试编写及版本／README | 35 | 3,389,240 |
| 作者浏览器验证、测试工具返工与派发审查 | 17 | 1,990,230 |
| 独立审查 | 21 | 978,038 |

| 调整 | 具体落点与理由 | 验证与限制 |
|---|---|---|
| 修好跨回合测试入口 | preview-test-access 的默认帮助示例省略临时 apiUrl，使用 preview-test-client 已有当前能力解析；示例优先使用真实 gameFrame 做定位／evaluate，保留兼容接口 | 离线验证同一脚本换回合、过期权限、错误工作区和帧操作；不延长能力有效期、不自动重试收费操作 |
| 缩小一次具体工作的上下文 | 主会话保留同工程历史；Agent 可用现有原生普通子代理承担边界清楚的实现／检查，只交接目标、受影响来源和必要证据，避免不必要的全历史 fork | 不由 BGS 固定每次变更派子代理、清历史或修改原生压缩。委派也有启动／交接成本，按真实主子总量判断，不能保证模型总会选择最省路径 |
| 减少细碎往返 | 同一来源的相关修改尽量集中，独立读取／检查合理合并；使用已有 Write／Edit／Bash，不再造批量编辑框架 | 不把“少调用”当正确性；复杂依赖允许分步。仅提示集中执行不能证明收益已实现 |
| 复用验证与控制审后扩张 | 按 §4 复用维护的脚本和适用证据，关键独立检查保留；可选改善进入现有待办，不默认打开新修订链 | 改过的结果必须重验，不能为了省 Token 跳过品质责任。内置 verification 会要求独立构建／测试；如职责不匹配，可用正常原生委派明确实际任务，不修改其内置源码 |
| 控制输入与报告重复 | 职责短说明、方法按需读；按实际问题定位八文档的相关章节和权威配置，不预载全稿。完整日志保存后给紧凑结果；交接引用当前版本／路径与必要结论，不要求最终回复复制设计／报告 | 不截掉必要错误或为省成本省掉必要上下文，不伪造 tool.completed 或由 BGS 吞掉／替代原生最终回复；缓存命中仍计入用量 |

默认八文档不自动增加八个写作会话、八次审查、文档齐全回执或专门总结请求。相关决定和修改可在一次实际工作中集中保存；数值、坐标和资源绑定只维护实际权威数据，正文记录意图并引用。没有变化的领域保留原记录和仍有效的证据；一次必要运行可同时支持多领域观察。合并文件本身不等于省 Token，不能以减少篇数代替消除重复读取、抄写和长会话细碎往返。

1.39 已移除默认 Preview helper 示例中的临时 apiUrl，并用同一 Node 脚本在两个独立能力回合中验证；过期能力和错误工作区仍失败。接单／变更增加的是共享短职责说明，不预载八稿或全部 Skills，没有新增模型回合。该改动修正已知入口浪费，但尚无真实付费降耗数据；本机假模型的固定用量不能衡量收益。

后续成本验收按实际模型／配置报告主子请求数、缓存／非缓存输入、输出、重试与中断缺失项，并区分新增品质工作和可避免返工。价格未知不换算金额。历史样本只用于归因，不作为质量标准；新样本应有不同玩法或表现需求以暴露过拟合。没有付费测量前不承诺百分比或绝对额度，不设隐藏轮数／工具次数限制。

## 8. 独立验收标准与未解决风险

### 8.1 验收要证明什么

| 要求 | 有效证据 | 不算证据 |
|---|---|---|
| 用户目标完整进入 Agent | 原始输入、选中方案、设置与实际 native 提交一致 | 调试员重新手写的 Task |
| 路径由 Agent 组织 | 不同依赖下的原生计划／工具／委派与实际成果，不受宿主固定批次推进 | 把六阶段更名为六类任务 |
| 专业能力真正可用 | 相关 Skill／工具实际加载或执行；输入与结果可定位 | 目录存在或 Agent 说用过 |
| 修订正确而非只写回执 | 具体问题、实际来源变更、受影响行为复核与当前版本 | 模型自己标 resolved／passed |
| 八领域专业设计有依据 | 原始要求、§3.1 八领域的具体决定／子要求适用理由、现存权威来源及变更理由，明确数值与资源；默认八文档或合并位置可供下一次修改使用 | 只写“美观／有趣”、齐全八份空泛文档、根据现有代码倒推用户要求 |
| 游戏可运行、符合承诺、可继续修改 | 目标环境实际核心路径、UI／Scene／反馈／资源／音频中本项目必需项及工程入口 | 文件齐全、静态截图、单独构建成功 |
| 品质判断有实际材料 | 当前画面／动态反馈／声音／试玩观察对照专业方向，结论具体且承认覆盖限制 | 模型自行打分、音频调用计数代替听感、功能 PASS 代替品质 |
| 变更／恢复无无关返工 | 已有成果保留、影响可追踪、未改部分无无故重写，迟到／重复操作有真实处理 | restart 后状态看起来正常 |
| 成本确有改善 | 可比较的实际主子请求、缓存／非缓存输入／输出／失败用量及产出 | 少了阶段／代码行／测试数，或只看非缓存 Token |

不用新旧比较代替合格标准。比较成本只能解释改动效果，最终仍以本项目需求与实际产出判断。

### 8.2 必须保留的风险说明

- Agent 仍可能漏读、误解、错误规划或跳过必要检查。确定性工具覆盖有限，独立 LLM Review 不是保证。
- 趣味、手感、审美、音色不能靠 Schema 或模型投票保证；专业方法、原型／试玩改善判断，不承诺自动零缺陷。
- 取消宿主批次不必然降低成本：正常 Agent 也可能碎步探索和携带长历史。先消除宿主可证实的浪费，再用实际用量判断。
- 当前 Web／BGS 专项不能证明 Unity／Godot 实际运行或工程导出。常规目录／PATH 和旧工具配置检查仅是历史环境线索，不是可调用证明。
- 输入缺失、环境故障、模型误判与产品缺陷分别报告；不靠增加 prompt、付费重试或硬轮数限制掩盖。
- 如果最小自主闭环不成立，先重审接线和假设，不继续扩张专项或重新引入第二个调度器。

只使用合成资料／受控本机运行，验证接线与可确定事实；以下不要求新增通用语义检查器，也不把假模型表现当真实 Agent 品质。

| 新目标默认八文档组织 | 接单包含八领域与默认组织说明，但不生成宿主八批作者／八轮审查，也不因尚未写齐八稿禁止探索原型或独立工作 |
