## 0. 不再摇摆的设计结论

**不是旧六阶段的迁移版，不是八文档改名成八种 Task，也不是放弃专业能力后完全相信 LLM。**

- 固定的是产品入口与用户承诺：idea → 三选一 → 游戏设置 → 提交完整目标。
- 动态的是生产路径：Claude Code 决定计划、实际依赖、原型、工具、相关 Skills、必要委派、检查和修订。
- 复用的是旧流程的专业知识、编辑／制作工具、数据契约和真实验证能力，不复刻其阶段顺序。
- BGS 负责授权、实际身份／项目／会话、Question、事件、恢复、版本和用量，并保存其可核实的检查事实；不替 Agent 安排技术方案。
- 结果仍要满足确认需求。动态规划不授予降低范围、跳过必要验证、改已确认引擎或伪造完成的自由。
- 不先删模块，也不先承诺所有旧代码必须保留；按实际消费者拆开“有用能力”和“固定调度依赖”。
- 不新增 Planner 服务、通用 DAG 执行器、引擎分流框架、统一 Scene 模型或全量语义验收系统。

八文档、Review／Revision、UI／Scene 和资源等模块继续是可复用能力。是否调用、怎样组合由实际任务决定；选用后的契约和项目必需要求不能随意省略。

### 1.3 既有失败怎样影响本版，而不是变成案例专用补丁

## 2. 主线：完整目标交给 Claude Code，不交给另一个调度器

### 2.1 接单输入

沿用现有产品入口和确认记录，生产输入包含：

- 用户原始 idea、附件来源、选中方案及确认设置，尤其引擎／技术、目标平台、输入、语言、资源策略和首发要求；
- 当前工程、已有成果与已知问题的真实位置，当前授权及明确限制；
- 可用专业 Skills 与能力入口的简短说明，以及当前环境实际限制。

只消费选中方案；未选方案保留历史，不默认全部注入。已有项目的局部修改直接承接当前工程与新要求，不重新走三选一。

这是完整目标，不是完整上下文倾倒。不要预载八文档、全资源字节、所有 Skill 正文、后台日志或一份巨型执行 prompt。

### 2.2 谁决定什么

| 主体 | 决定／承担什么 | 边界 |
|---|---|---|
| 用户 | 确认目标、设置、范围与重要变更，授予必要权限 | 不必批准每个 Todo、普通实现细节或审美微调 |
| Claude Code 主 Agent | 计划、先验证哪个风险、设计产物形式、工具、相关 Skills、委派、实现、审查与修复 | 遵守确认承诺；对整合和交付说明负责，不以自身判断自证合格 |
| 原生 subagent | 完成主 Agent 明确委派的专业工作／独立检查 | 来源、目标与修改范围明确；不是 BGS 固定作者名单 |
| BGS | 用户与项目归属、授权、正常执行传输、事件、Question、恢复、用量、实际版本与检查记录 | 不决定工具顺序、文件结构、专业方案、修复路线或下一业务阶段 |
| Skills／能力工具 | 提供专业方法或可执行操作，准确说明输入、结果和限制 | 不扩大权限，不另定义业务职责，不把工具成功包装成游戏合格 |

专业职责由确认需求和任务指令明确；Skill 帮助做好工作。不要同时在 prompt、Skill 和宿主状态中维护三套职责。

### 2.3 动态规划的具体含义

Agent 根据当前依赖和不确定性选择下一项有价值工作，完成或发现新事实后调整计划。计划可用原生 Todo／计划和必要工程说明，不要求发布宿主 DAG。

- 核心机制不确定：先做标明探索用途的可玩原型，再根据实际结果收敛规则；不先写齐八文档。
- 机制明确、视觉组合有风险：可以先检查资源和界面／场景组合，避免完整制作后才发现不适配。
- 普通代码缺陷：依据现有设计直接修复并验证，不重开全部策划。
- 设计确有缺口：明确负责决策，修订实际来源及必要消费者；改变用户承诺才请求用户裁决。

这些是不同路径的示例，不是三个模板、项目分类器或新增阶段。必要依赖不能跳过，但不能从旧批次顺序推断全部工作必须串行。

## 3. 专业能力如何介入，而不是八次必经作业

### 3.1 设计完整性不能靠“文件数量”

| 专业领域 | 生产或交付所需要的事实 | 可用的实际载体 |
|---|---|---|
| 玩法 | 目标、动作与结果、核心循环、结束／重开、范围 | GDD、简短设计说明及实际规则／测试 |
| 技术 | 可行实现路线、关键接口、输入／加载／清理与风险 | 技术说明、项目配置、代码和必要能力测试 |
| 美术／反馈 | 视觉语言、辨识、层级、一致性与必要动态反馈 | Art Direction、参考和实际资产／运行画面 |
| 音频 | 项目所需事件、播放／停止／并发／静音行为 | Audio Design、资源及运行绑定 |
| UI／UX | 必要界面状态、信息、操作、适配和异常反馈 | UI 说明、BGS UI、DOM／React 或引擎原生界面 |
| 场景 | 可构建空间、相机、目标／出生点／障碍及相关规则 | 场景说明、BGS Scene 或引擎原生场景 |
| 数值 | 可运行初值、单位、关系和调优假设 | Balance Design、配置与必要计算／测试 |
| 资源 | 必需资产、规格、用途、来源与批准回退 | Asset Plan、资源登记或工程原生引用 |

同一 Agent 可承担多项专业责任，必要时委派；不要求八个作者。GDD 对核心玩法和范围有权威，不因此拥有所有专业选择。

八份文档继续可生成、读取、修改和审查；用户明确要求时必须交付。不把八份文档变成全部项目开工或交付前提，也不删除现有文档。需要持久解释的决定写清楚；实际数值、布局和绑定不在多处维护第二份。

### 3.2 Skills 需要明确介入

正常接单指令应明确要求使用与当前工作相关的专业 Skills，Agent 根据实际工作选择并加载。复用 native-skill-plugins.ts 的标准 plugin 提供方式，不修改 Claude Code loader、不预载全部方法、不按固定阶段挑 Skill。

策划、UI、美术、音频、场景、数值、实现和审查均有既有专业方法可用；具体名称以运行配置中实际可见目录为准。Skill 成功加载只证明方法进入上下文，不能证明运用正确。缺少必要方法／能力时如实说明，不伪造调用。

### 3.3 UI／Scene 的能力保留，格式不是通用命令

选用 BGS 内容能力时，继续用已有 Schema、坐标、稳定 ID、Camera／game-view 关联和批量绑定工具。同一来源逐步补全；资源绑定不另生成一套布局。

有实际可计算数据时即可用空间算法，不等到某个固定阶段。真实字体、图片／图集等输入改变后重查受影响部分；最终还需看实际游戏中的画面与交互。未知几何、3D／XR 及动态遮挡不能用矩形检查冒充通过。

React／DOM 或引擎原生 UI／Scene 按本身格式实现和验证，不为了宿主检查补第二套 BGS JSON。Agent 不必先证明某种工具不可用，才允许正常选择项目原生方式。

### 3.4 资源与数据消费

保留资源库、生成／下载／程序化制作、规格检查、登记、图集、批量绑定及来源／许可记录。资源使用策略来自确认设置；管理员开了工具不等于项目必须使用。

需要早期资源试验时可以先做，不等八文档全部通过。占位可用于开发，不能冒充批准的最终资产；符合目标的程序化表现不天然等于占位。

并行工作由 Agent 决定，共享登记与同一文件写入需要协调。没有必要为每项资源建立宿主 Task。绑定／加载成功后仍需观察实际显示、播放或行为变化，不把“已经复制到工程”当成集成完成。

### 3.5 多技术路线

用户指定 Web／React，Agent 使用代码和正常开发工具；指定 Unity／Godot，Agent 操作真实引擎工程，使用可用且获授权的 CLI／MCP。不要求 Web 增加引擎接口，也不要求引擎同时具备两种控制方式。

不按 engine 名称禁止 Bun、浏览器等辅助工具；检查器只说明它实际检查哪个产物。Web 导出检查不证明原生工程编辑能力。工具缺失时核对环境、报告缺口，必要时 Question；不静默改引擎或安装。

## 4. Review／Revision 与质量：方法动态，事实不能随意省略

### 4.1 审查由 Agent 组织，不是宿主固定循环

保留专业审查 Skill、原生独立 Reviewer、确定性检查、来源明确的问题和集中修订能力。Agent 根据当前风险安排在原型、设计、资源、实现或交付检查中使用，不强制先完成八文档再审查。

审查问题需要具体依据、下游影响和可观察的关闭条件。Revision 可修正授权内的专业选择并同步必要消费者；用户承诺／范围改变才 Question。修复后的定向复核关注改动和真实影响，不因涉及一份文档就重读全部资料。

只读检查不能暗改来源再宣布通过；修订者不能用自己的“已关闭”代替必要复核。Agent 可委派独立检查，但另一个模型也可能漏检。去掉宿主固定 Review／Repair Task 链，不等于取消这些质量责任。

同条件反复失败且无新依据时，要说明原因和需要的行动，而不是宿主自动另开作者／Reviewer 重派。正常 Agent 修复不受隐藏硬轮数限制；用户预算、权限、取消和账户真实额度仍有效。

### 4.2 可核查事实与语义判断分开

| 检查对象 | 优先依据 | 不足与处理 |
|---|---|---|
| 格式、引用、几何、资源可解码等 | 既有确定性检查与真实输入 | 仅对实际覆盖有效；不检查的内容保持未知 |
| 构建、启动、规则与集成行为 | 项目测试、实际运行和必要操作／观察 | 测试可能遗漏或断言错误；不能用退出码证明所有玩法 |
| UI／Scene、字体、资源、音频消费 | 实际目标运行时中的结果与对应来源 | BGS 专项仅覆盖支持范围，不代表全部引擎／设备 |
| 规则冲突、需求误解、趣味、审美、听感 | 专业 Review、原型／试玩和实际画面／声音 | 不能确定性保证；需要时有权者判断，不以模型分数签字 |
| 缺环境、缺输入或过期证据 | 实际失败原因和当前版本 | 标未验证／阻断，不能伪造 PASS 或改为“不适用” |

不要求用户对每张画面投票，也不要求 BGS 拥有所有玩法的检查器才开工。无法可靠证明的品质结论须说明限制；不能以此隐瞒明显缺陷或省掉已确认的表现要求。

### 4.3 如何防止“Agent 漏选检查却被当作完成”

Agent 可以选择验证方法，**不能决定哪些用户承诺可以不兑现**。

- 交付说明对照当前确认需求和实际必要玩家路径，而不只汇总它自己标记完成的 Todo。
- 对已有明确要求及可执行检查，保留覆盖与结果；无输入、跳过、失败或版本失效必须显露，不能因为没有报错就算通过。
- BGS 只核验自己能确定的身份、实际执行、版本和结构事实；它不能自动解释任意自然语言要求并证明覆盖完整。
- 对没有可靠自动覆盖的关键行为，采用实际运行／必要独立审查／有权者核对，或明确保留未验证状态。模型漏判风险仍存在，不承诺靠这几条消除。
- 复用已有任务／测试／报告的对应关系。没有合适记录时用简短可追溯说明，不新增另一份强制全量需求 Schema、DAG 或质量账。

### 4.4 完成、可验收和发布不是同一件事

原生 turn 结束只证明执行结束。交付应能找到当前可运行游戏、可继续修改工程、启动方式、已核对的核心路径、实际证据和已知限制。

必需功能有明确缺陷或关键验证缺失，不能称“合格交付”；可保留候选预览和成果，但准确说明状态。通过构建／某项检查不等于整个游戏通过。

既有发布权限与有效证据约束保留；本文不解除当前 V3 关闭状态。修改后重建／重测实际受影响对象，旧记录仍可读但不自动变成新版本通过。源／构建 hash 只说明身份，不证明品质。

## 5. BGS 怎样支持执行而不变成第二个 Agent

- 复用正常 native 提交、stream-json、plugin、session/resume、权限和原生 subagent；不改工具描述／结果、query loop、压缩、思考或最终回复。
- 原生计划是执行安排；BGS 可展示实际计划／Todo／事件，不把每个 Todo 转成必须领取的 Task／Attempt。
- 正常授权覆盖需求内的开发、检查和修复；新增权限、费用授权或实质承诺变化仍需原生确认。
- 能力从现有入口提供简短帮助：实际参数、结果、错误位置、覆盖与限制。无需另建 Capability Map 文档、引擎适配框架或动态规划服务。
- 子代理事件归到真实子代理，用量归实际请求；不把全部子日志注入主上下文，也不冒充主 Agent 消息。
- 平台状态来自真实事件与事实，不解析一句“进入下一阶段”来自动派发业务。原生空闲不等于后台操作完成，Agent 完成声明不等于质量验收。
- 原生 turn 结束后，BGS 不默认追加付费总结／下一阶段／修复请求。Agent 内部可在授权内继续用工具；需要后续提交时必须有用户授权或事先明确的持续执行依据，不能把普通完结当作无限续跑许可。

### 5.1 Question 与需求变更

真正发出原生 Question，并把实际答复送回正确会话／子任务。不要求先写宿主 finding JSON 才能提问；沉默、拒绝、过期答复不是批准。

新要求交给 Agent 当前工程、确认事实及变更，不由 BGS 生成详细修复路线。Agent 更新有变化的实际权威来源与消费者；不重开八文档或重造 UI／Scene。Agent 内部职业选择不应每次都推给用户。

### 5.2 中断与并发

用户暂停是持久意图，重启不解除。恢复先确认原生会话、子代理和实际后台／引擎操作状态；未知写者不因超时自动解锁，也不启动竞争写者。

原生子代理属于已授权协作，不应仅因没有独立 BGS Task 就认定非法；平台仍需区分真正竞争的项目会话。复用现有安全能力，具体接线需查证，不新增通用进程框架。

保留部分成果与历史，恢复按实际已保存状态继续，不盲目重做。外部收费请求响应丢失时用现有请求身份／outbox 核查，不盲重放。

## 6. 具体保留、解耦与退出清单

本表区分“模块能力”与“调用政策”。目标不是整目录删除；1.31 已接通自主接单并撤去按引擎名称的限制，1.32 提供按需资源／纯 Content 工具，1.33 接通同工程消息，1.34 复用实际按需 Preview；其余按消费者证据逐步处理。

| 对象／位置 | 处置 | 后续需要核对的消费者／影响 |
|---|---|---|
| 产品入口、原始 idea／确认简报、设置与语言／资源策略 | 保留 | 选中方案和设置能完整交给正常会话；不改正式 frontend |
| SessionManager、native-cli-process-runner、native-skill-plugins、权限／事件／用量／outbox | 复用必要能力 | 新目标接单、子代理归属、Question、取消／resume；不是改原生循环 |
| 八文档专业职责、写作方法、已保存正文／索引 | 保留能力和历史，退出固定产物门禁 | project-author／planning 的角色责任可用；AUTHOR_BATCHES 不能成为所有新任务的排程 |
| 专业 Review／Revision、问题来源、定向复核 | 保留并与固定派发解耦 | review-task-prompt／delivery review 当前由宿主指定步骤、范围、回执；不能原封不动塞给自主 Agent |
| UI／Scene Schema、编辑／渲染、空间算法、真实数据消费 | 保留专项能力 | 区分纯输入检查与 design-layout-check::checkReviewDesignLayouts 的文档发现逻辑；仅选用 BGS 数据时遵守契约 |
| 资源服务、media／resources CLI、Manifest、图集及批量绑定 | 保留，按需提供入口 | project-asset-command／resource-production／content-binding；共享登记安全和真实来源继续有效 |
| projectContentAuthority、buildSceneUiContentAuthoringAuthority | 解耦旧基线依赖后才能用于新主线 | 前者汇总八文档／索引，后者需要真实版本／Manifest；不能传空值或伪造八文档来绕过 |
| 专项构建／运行／已测 Preview／工程导出 | 保留准确覆盖，必要时解耦 Task-only 接线 | workflow-v3/checks／runtime-checks／measured-build／editable-project；目前主要是静态 Web，不是通用引擎支持 |
| project-conversation／app 自动阶段续轮、writing-workflow-runtime 固定作者批次 | 退出新自主接单路径；旧项目兼容保留待核对 | 不再由宿主决定下一领域／作者；只移除有实际调用证据的业务编排，不删正常 transport |
| workflow-v3 的人工 plan／逐 Task execute、强制每 Task expectedOutputs／CHECK_IDS | 不作为新开工协议 | routes／state／execution／context 可留历史和诊断；不能把旧六阶段包装成 Task DAG |
| 宿主 reviewOf／repairOf、Task-only session／导出资格、全局 deliveryEligible | 核查后收窄耦合，不直接删安全功能 | 明确是否有独立保护需求，再接到真实会话／版本；未有证据不得开放交付 |
| capability-scope.ts 及上轮接入的 engine 名称阻断 | 本轮已撤去名称阻断，只保留实际覆盖说明 | state／execution／checks／runtime／content-checks；对应回归改为核对真实输入与驱动，不动原权限与输入检查 |
| 数据库两张 V3 表、RPC、Run／Plan／Task／Attempt 历史 | 保留数据与必要并发／请求事实；用途待核对 | 不破坏已应用迁移，不继续要求 Agent 填一套第二计划；不另建数据库 |
| 新 Planner、统一知识库、跨引擎路由、通用审美／语义 Gate | 不新增 | 现有已证实问题无需先靠这些解决 |

**关键实现缺口**：工具存在不等于自主 Agent 可以调用。旧文档授权、阶段 materialize、Task writer/fence 与工具临时地址都可能是隐藏依赖。后续逐入口确认最小输入和生命周期，不另建整套协议，也不降低合法权限、来源和版本检查。

## 7. 后续实施顺序：工程变更顺序，不是游戏生产阶段

下表是工程变更顺序，不是 Agent 的游戏生产阶段。每轮仅按用户实际授权推进；历史实验不构成新的付费、SQL、安装、部署或正式 frontend 授权。

| 顺序 | 最小工作及原因 | 完成条件／回归范围 |
|---|---|---|
| 1. 核对接单与能力消费者 | 列清确认输入 → 当前入口／模式保护 → native 提交，以及 Skills、资源、布局、绑定、检查的真实调用。撤回已确认错误的 engine 阻断须另获实施授权 | 每项保留／解耦／退出有真实消费者；权限、暂停、并发和当前有效检查不退化。不能只删 assertLegacy 回旧固定流程 |
| 2. 完整目标最小闭环 | 用现有正常会话方式接目标，提供实际可用 Skills／必要工具；不靠手填 Task，也不靠所有专项先接齐 | 独立 debug／后端合成验证：目标完整、原生计划／工具、真实保存、失败反馈、Question 和结束；假模型只证明接线 |
| 3. 按调用需要复用专业能力 | 把上述闭环实际需要的纯能力从八文档／阶段／Task 前提中解耦，保留真实输入和安全契约；其余专项不阻塞接单 | 同一入口可在有真实输入时使用；布局／资源／绑定／检查不要求无关产物。无需先迁齐所有旧模块 |
| 4. 局部变更与中断闭环 | 给同一 Agent 实际变更／问题，复用 Question、暂停、恢复、版本和计费记录，不由宿主生成 repair plan | 局部修改不重做无关成果；新版本旧测量失效；未知写者不盲续作；原生子代理归属正确、费用不重复 |
| 5. 真实游戏与成本验收 | 另获付费授权后，用未见 idea 通过同一入口自主生产并检查实际游戏／工程；不同性质的目标用于暴露固定路径依赖 | 对照确认需求核对实际运行、表现与修改入口；逐请求主子用量完整。不得人工修补项目后宣称通过 |
| 6. 清理确认无用的编排 | 新主线有证据后，按消费者退出不必要宿主派发／强绑定，保留旧项目、数据和事实 | 删除范围可追踪，无效机制没有换名重建；正式 frontend／发布接线仍需单独授权 |

步骤 2 与 3 可在一个最小切片中完成必要接线，不要求先造抽象层。若无法在现有边界内安全复用，说明具体缺口后再决定最小改动。

回归按实际影响选：正常接单／身份／权限／Question／子代理／用量／恢复属于共享边界；某工具只验证自身和实际消费者。不修改 Claude Code、不假造 tool.completed、不靠全部旧测试通过证明新业务正确。

## 8. 独立验收标准与未解决风险

### 8.1 验收要证明什么

| 要求 | 有效证据 | 不算证据 |
|---|---|---|
| 用户目标完整进入 Agent | 原始输入、选中方案、设置与实际 native 提交一致 | 调试员重新手写的 Task |
| 路径由 Agent 组织 | 不同依赖下的原生计划／工具／委派与实际成果，不受宿主固定批次推进 | 把六阶段更名为六类任务 |
| 专业能力真正可用 | 相关 Skill／工具实际加载或执行；输入与结果可定位 | 目录存在或 Agent 说用过 |
| 修订正确而非只写回执 | 具体问题、实际来源变更、受影响行为复核与当前版本 | 模型自己标 resolved／passed |
| 游戏可运行、符合承诺、可继续修改 | 目标环境实际核心路径、UI／Scene／反馈／资源／音频中本项目必需项及工程入口 | 文件齐全、静态截图、单独构建成功 |
| 变更／恢复无无关返工 | 已有成果保留、影响可追踪、未改部分无无故重写，迟到／重复操作有真实处理 | restart 后状态看起来正常 |
| 成本确有改善 | 可比较的实际主子请求、缓存／非缓存输入／输出／失败用量及产出 | 少了阶段／代码行／测试数，或只看非缓存 Token |

不用新旧比较代替合格标准。比较成本只能解释改动效果，最终仍以本项目需求与实际产出判断。

### 8.2 必须保留的风险说明

- Agent 仍可能漏读、误解、错误规划或跳过必要检查。确定性工具覆盖有限，独立 LLM Review 不是保证。
- 趣味、手感、审美、音色不能靠 Schema 或模型投票保证；专业方法、原型／试玩改善判断，不承诺自动零缺陷。
- 取消宿主批次不必然降低成本：正常 Agent 也可能碎步探索和携带长历史。先消除宿主可证实的浪费，再用实际用量判断。
- 当前 Web／BGS 专项不能证明 Unity／Godot 实际运行或工程导出。常规目录／PATH 和旧工具配置检查仅是历史环境线索，不是可调用证明。
- 输入缺失、环境故障、模型误判与产品缺陷分别报告；不靠增加 prompt、付费重试或硬轮数限制掩盖。
- 如果最小自主闭环不成立，先重审接线和假设，不继续扩张专项或重新引入第二个调度器。

### 9.5 单组付费验收失败与恢复接线修复

- 正常用户、根环境、真实数据库与独立 debug 接完整「折光邮差」目标，实际模型沿用 `ark-code-latest`。Agent 自行调用策划 Skill、原生计划、文件和测试；无宿主 Task／阶段计划。保存了部分工程、规则、关卡、测试及音频，界面／完整运行尚未完成。

- 已证实根因：首次 Chat 有用户 `userDataRoot`，V3 executor 重建会话漏传，CLI 恢复根变成共享目录，而原生历史实际在用户目录。app／routes／executor 每轮保留当前用户数据根，不改原生 resume 或历史压缩机制。
