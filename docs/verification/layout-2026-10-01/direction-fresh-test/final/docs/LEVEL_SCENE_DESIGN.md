## 1. 关卡总览

首版仅 1 个关卡：**L1「首发之墙」**。无程序化生成、无可选路线——打砖块的空间是一个单屏封闭竞技场，"路线"体现为球在墙面间的弹道与玩家通过挡板进行的角度选择，而非角色在空间中的移动路径。

| 项目 | L1 |
|---|---|
| 目标 | 击碎全部 60 块砖（GDD §6.1） |
| 失败来源 | 球越过底部死亡边，3 条生命耗尽 |
| 空间形态 | 单屏矩形竞技场，静态固定布局 |
| 砖块规模 | 10 列 × 6 行；下 4 行为 1 命砖（40 块），上 2 行为 2 命砖（20 块） |
| 节奏意图 | 下半区快速清空建立正反馈 → 上半区 2 命砖延长交战、要求连续精准回球 → 清空收尾 |

## 2. 坐标系、单位与尺度

- 世界坐标：**左上原点，+X 向右，+Y 向下，单位为逻辑像素（logical pixels）**；与内容格式约定一致。
- 世界范围（设计坐标）：**960 × 540**。世界范围即玩法边界，不随宿主尺寸改变。
- `pixelsPerUnit = 1`（设计坐标直接作为世界数值，避免二次换算）。
- 所有节点位置以**中心点（pivot 0.5,0.5）**为节点 transform 基准；砖块碰撞盒 80×24、挡板 120×16、球半径 8 均为数据内尺寸。
- 世界范围 ≠ 显示范围：显示范围由相机取景与宿主容器决定（§4）。

### 3.2 砖块网格（结构化位置定义）

- 砖块尺寸 80×24，砖块间距 4。
- 网格总宽 = 10×80 + 9×4 = **836**；水平起始（第一块砖中心列）使网格整体居中：第一块砖左上角 x = **62**。
- 网格顶边 y = **80**；6 行总高 = 6×24 + 5×4 = 164，网格底边 y = **244**。
- 第 r 行第 c 列砖块中心（r 自下而上为 0–5，c 自左而右为 0–9）：

  `x = 62 + 40 + c·84 = 102 + c·84`
  `y = 80 + 12 + r·28 = 92 + r·28`

- 行属性：r=0–3 为 1 命砖；r=4–5 为 2 命砖。2 命砖位于顶部，交战距离更远、回球窗口更长但需要两次命中，构成首版的难度上限。
- 每块砖的 hp / score 写在场景节点 `data.behaviors` 配置中（数据归属 GDD §7），排布以本节公式为权威；正式场景文件保存于 content/scenes（后续批次）。

### 3.3 挡板与球的初始位置

- 挡板初始中心 **(480, 500)**；其水平活动范围：挡板中心 x ∈ [60, 900]（半宽 60，不越左右墙）。
- 球：发球准备时吸附于挡板正上方，初始中心 **(480, 484)**（距挡板顶面 0：挡板顶面 y=492，球底 y=492），随挡板水平移动，保持相对偏移 (0, −16)。
- 死亡边：y = 540；球整体越过（球心 y − 8 > 540）判出底，符合 GDD §5.2。

### 3.4 空间如何支撑引导、挑战与节奏

- **引导**：无文字教程。发球后球首先进入最近的第 0 行（发球点到砖底约 240px），玩家在第一次反弹前即可观察到"击球点改变角度"这一全部核心机制。
- **正反馈密度**：1 命砖占 2/3，前数次回球即可连续碎砖、分数快速上涨。
- **张力抬升**：进入顶部 2 命区后，首次命中只产生"受损"不消失（GDD §4.2），交火回合数增加；底部已经空旷，漏球风险随玩家注意力上移而升高。
- **安全纵深**：砖块底边（244）到挡板运动线（500）保留约 256px 自由区，给追球与角度修正留出空间；这是节奏的核心缓冲，不得被 UI 压缩（§5）。
- 无随机/过程化内容，故无连通性与安全出生问题：出生点即吸附点，保证球首次运动前不会接触任何砖块。

## 4. 相机取景与宽高比适应

- 相机：2D 正交相机，节点位于 (480, 270)，`orthographicSize = 270`（半高，世界单位=逻辑像素），参考视口 960×540，取景策略 **letterbox（等比留边）**。
- 设计意图：**世界参考视图 960×540 在任何横屏宿主中完整、等比可见，不裁剪、不拉伸、不移动世界**；多出的空间以留边/背景延伸处理（背景层可向留边区延伸以避免黑边，见美术文档）。

空间计算器验证结果（`.beegame/tmp/camera-draft-plain.json`，命令 `bun .beegame/delivery/check-content.mjs --camera-draft ... <w> <h>`）：

| 宿主逻辑像素 | 取景矩形（参考视图在宿主中的位置） | 结论 |
|---|---|---|
| 960×540 | x0=0, y0=0, 960×540 | 恰好铺满 |
| 1200×540（更宽） | x0=120, y0=0, 960×540 | 两侧各留 120px，无裁剪 |
| 960×600（更高） | x0=0, y0=30, 960×540 | 上下各留 30px，无裁剪 |

- 场景草案同构检查：`.beegame/tmp/scene-draft.json` 以 `--layout-draft 960 540` 检查，60 块砖 + 挡板 + 球全部启用、结构通过（静态几何检查，`ok:true`）。
- 上述均为**矩形/取景计算结果**，不是运行时验证；球体遮挡、实际渲染未检查。
- 坐标到屏幕的转换由技术设计按本节取景结果实现，不另建坐标表。

## 5. 必需可见区域与 UI 覆盖约束

- **必需可见游戏区：完整 960×540 世界**——四面边界、死亡边、全部砖块、自由交战区在进行中必须可见；这是硬性取景要求。
- 允许 UI 覆盖的区域：
  - **顶部 0–64 带状区**：HUD（分数、生命、暂停按钮）可覆盖，但必须半透明/不遮挡砖块（砖块顶边 y=80，留有 16px 净空）。
  - 四角的小范围按钮区（暂停）。
  - 开始/暂停/结算为整屏覆盖层，出现时游戏模拟已停止（GDD §3）。
- **禁止覆盖**：y=80–540 的游戏交战区在"进行中"状态下不得有任何持久性 UI 元素。
- 屏幕空间的最终分配、容器尺寸与具体布局由 UI_UX_SPEC（批次 3）拥有并保存为 content/ui 可编辑文档；本文件只提出上述游戏世界的可见性与覆盖约束。HUD 带高 64 为场景侧需求输入，最终以 UI 文档确认为准。

## 6. 本关卡与共享规则的差异点

- 首版只有一个关卡，无跨关卡差异；GDD 中的全部共享规则原样适用，本节无附加规则。
- 若评审决定调整砖块行数/尺寸，须同步更新本文件 §3.2 公式并重新运行取景/排布检查。
