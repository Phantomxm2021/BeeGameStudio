## 1. 场景规划

首发只有一个场景、一个关卡：**"棋盘"（单局街机棋盘）**。不存在关卡序列、难度分版或场景切换；开始/暂停/结束均为覆盖在同一棋盘之上的 UI 状态（见 GDD 第 6 节）。

- 关卡类型：固定布局的封闭网格竞技场。
- 关卡目标：吃到尽可能多的食物、争取高分；失败条件为撞墙或撞身；棋盘填满为特殊的胜利式结束（规则见 GDD 3.3、5.3）。
- 与"关卡"无关的元素（模式、道具、障碍）首发不存在，本文不预留位置。

## 2. 空间定义

### 2.1 世界坐标与尺度

- 坐标系：2D，原点左上，+X 向右、+Y 向下，单位为逻辑像素（logical pixels）。
- 网格：20 列 × 20 行正交方格，cellSize = 32×32，cellGap = 0。
- 游戏世界范围（世界 extent）：640×640 逻辑像素，即网格本身。
- 网格节点（grid）与背景/边框的作者态位置以 Scene JSON 表达；网格左上放在 (0,0) 时，格坐标 `(x, y)`（0–19）的中心像素为 `(32x + 16, 32y + 16)`。
- 边界墙是沿 640×640 四缘的视觉边框；墙体的"碰撞面"与网格最外缘一致——蛇头格坐标一旦离开 0–19 即死亡（GDD 5.3 第 4 步）。边框视觉可以略向外扩展但不得侵占可走格。

### 2.2 出生位置

- 初始蛇 3 节，水平排列于棋盘中央偏上：

| 节 | 格坐标 (x,y) | 像素中心 |
|---|---|---|
| 蛇头 | (10, 8) | (336, 272) |
| 身段 1 | (9, 8) | (304, 272) |
| 身段 2 | (8, 8) | (272, 272) |

- 初始朝向：右（+X）。蛇头前方到右墙有 9 格缓冲，上下各有 8 与 11 格空间，保证开局无需精确操作即可安全前行。
- 首个食物：在除蛇身 3 格外的任意空格中随机出现（约束见第 4 节）。

### 2.3 空间示意（N=蛇，·=空格，f=食物可能出现的区域）

```
y=0  ┌──────────────────────┐  ← 上墙（y=-1 即越界）
     │ ···················· │
     │ ···················· │
y=8  │ ········NNN→ ······· │   蛇身 (8,8)(9,8)，头 (10,8)
     │ ···················· │
     │ ················f··· │   食物示例位置，实际随机
     │ ···················· │
y=19 └──────────────────────┘  ← 下墙
     x=0                x=19
```

## 3. 取景与可见性

### 3.1 相机

- 正交相机；coordinateSpace = logical-pixels；orthographicSize = 320（参考半高）；参考 viewport 640×640；framing = **letterbox**。
- 设计结果：无论宿主什么形状，20×20 棋盘始终完整、等比、无变形地全部可见；不足的方向以安静的留白/letterbox 区域填补，不裁剪任何一行或一列。
- 相机适配只改变呈现，不改变作者态世界布局与碰撞（见 content-format 的 viewportAdaptation 约定）。

### 3.2 世界范围 vs 显示范围

- 世界 extent 恒定为 640×640。
- 显示 extent 由"游戏视图矩形"（宿主屏幕扣除 HUD 预留与安全边距后的区域）决定；棋盘在该矩形内取最大正方形居中。
- HUD 为屏幕空间 UI，不覆盖在棋盘格之上；游戏视图矩形的最终屏幕分配由 `UI_UX_SPEC` 拥有。本文提出需求并引用其结论：顶部 HUD 预留高度桌面约 64 逻辑像素、竖屏约 60 逻辑像素。

### 3.3 已计算的代表性构图（输入参考与结果）

使用 `bun .beegame/delivery/check-content.mjs --camera-draft` 对相机草稿（orthographicSize 320、viewport 640×640、letterbox）计算：

| 构图 | 宿主参考尺寸 | 游戏视图（扣除 HUD） | 棋盘正方形视图 | 在游戏视图中的偏移 |
|---|---|---|---|---|
| 桌面横屏 | 1280×720 | 1280×656 | 656×656 | x=312，y=0（两侧为留白） |
| 手机竖屏 | 390×844 | 390×784 | 390×390 | x=0，y=197（上下为留白） |

- 宽高比变化时：棋盘不拉伸、不滚动、无格被裁剪；多出的区域为背景延伸/留白，可作为氛围装饰区但不得放置任何影响判定的元素。
- 工具仅验证矩形取景：不验证对象投射、玩法遮挡或文字可读性（那些在后续 UI 文档与运行时验收中处理）；runtimeVerified = false，本阶段无运行时检查。

### 3.4 必需的可见游戏区域与覆盖规则

- 必需可见区：全部 400 个网格格，始终。
- 允许的 UI overlay：仅暂停遮罩与结算面板（半透明或居中面板，属于明确的状态切换）；游戏中除顶部 HUD 外，棋盘上方不允许任何悬浮提示遮挡格位。
- 竖屏时棋盘下方留白区可放置触控方向键（由 UI_UX_SPEC 定位置），方向键不覆盖棋盘。

## 4. 食物分布约束（程序化放置）

食物位置为运行时随机选择，但必须满足以下可验证约束，而非"任意随机"：

1. 候选集 = 当前未被蛇的任何一节占据的全部空格（400 − 当前蛇长）。
2. 从候选集中等概率选取；不使用固定序列、不偏向中心或边缘、不保证与蛇头保持距离。
3. 吃食物与新食物出现发生在同一步裁决内（GDD 5.3 第 5 步），玩家从不会看到"无食物"的中间帧。
4. 可达性：候选集中的每一格对一条合法移动的蛇理论上可达；本设计不放置内部障碍，因此任何空格在蛇身尚未封死路径时都可成为目标。系统不动态验证路径可达性（首发没有死局检测）；食物可能刷在蛇身盘绕形成的暂时封闭区内，由此产生的风险按 GDD 3.3 的既定规则处理。
5. 安全生成：食物永不生成在蛇身格、墙体外或非整数格。
6. 当候选集为空（蛇长 400，棋盘填满）：不生成食物，按 GDD 3.3 进入填满结束。

### 引导、挑战与节奏如何由空间安排支撑

- 无内部障碍意味着开局阶段空间开阔、挑战完全来自动作精度，符合"开箱即玩"。
- 难度不来自新元素，而来自同一空间中蛇身占用比例的上升：蛇长 20（占棋盘 5%）时仍宽松；蛇长 100（25%）以后路线规划成为主要挑战；具体节奏与占用率的关系见 `BALANCE_DESIGN.md`。
- 中央出生 + 朝右让玩家第一眼就看到完整的运动方向与前方余量，无需任何教学文字即可理解操作。

## 5. 场景数据约定

- 场景以作者态 Scene JSON 注册到 `content/index.json`（kind：scene-2d，loadPhase：startup），包含：coordinateSystem 设置（640×640、pixelsPerUnit）、grid 组件节点、相机节点、边框/背景节点；蛇与食物为运行时根据游戏状态驱动 transform 的节点（节点与初始 transform 仍作者态注册，不由代码发明层级）。
- 网格背景的棋盘格纹理/平铺表达在美术方向文档中定义视觉，具体 Tilemap/素材形式由内容管线与 ASSET_PLAN 决定；本文只规定格与世界的几何关系。
- 本文所有尺寸均为设计坐标；数值参数以 `BALANCE_DESIGN.md` 为权威，屏幕空间最终分配以 `UI_UX_SPEC` 为权威。
