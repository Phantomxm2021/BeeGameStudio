## 1. 设计基调与首发音乐决定

### 1.1 一句话执行标准

> **声音是这台夜色街机的机械确认音：平时近乎无声，只有"吃到、出事、荣耀"三个时刻出声；声音短、干、收尾干净，不做铺底氛围，不靠声音制造紧迫感。**

与美术方向对齐：静得下来、响得到位。6→14 步/秒的速度推进只由蛇的视觉传达，音频不随速度持续作响。

### 1.2 首发背景音乐决定：不做背景音乐

**首发不提供任何背景音乐（BGM），全部音频为一次性音效。** 理由：

1. 单局体量 30–60 秒量级（BALANCE_DESIGN 3.3），玩家在开始界面与局内高频进出，短小循环乐在反复重开后迅速变成听觉疲劳源。
2. 夜色、冷静、近乎安静的棋盘基调本身就是体验的一部分；廉价的短循环乐会拉低"精密街机"的品质感，而高品质循环乐的制作与授权成本对本项目体量不成立——不为做而做。
3. 无音乐意味着无需 ducking 链路、无需音乐循环点校准、无后台标签页音乐持续播放的风险，实现与验收都更薄。
4. 首发无音乐不影响任何 GDD 完成条件；关键事件全部由音效 + 视觉双通道承载。

"一首极轻的环境/芯片音乐循环"作为**可选增强**保留（见第 7 节），不在首发承诺内。

## 2. 必需音效（首发）

首发必需 5 个 cue，对应 AudioManager 订阅的 5 个事件。全部为单声道一次性短音（one-shot），干声、短包络、无长混响尾。

### 2.1 `ui-activate` —— 界面确认音

- **用途**：开始界面按"开始"；暂停/继续；游戏结束界面"重新开始"；暂停界面"退出本局"。一切界面确认共用同一 cue，不按按钮分化。
- **声音性格**：干净、轻、确定的电子"嘀"。三角波或软化方波质感（不要尖锐数字方波）；基频约 900–1200 Hz，音头在 2–5 ms 内到位，随后快速指数衰减，无拖尾。听感像街机面板按键的确认灯，不像旋律音。
- **触发时机**：按钮/按键被确认生效的同一刻（而非按下即响——被忽略的输入不响，见下）。
- **时长/循环**：约 40–70 ms，一次性，不循环。
- **停止条件**：自然放完，无需中断；切换状态不截断它（长度已足够短）。
- **重复触发行为**：可被快速重复触发（连点按钮），每次独立播放；但被规则忽略的操作不触发——例如非法转向输入、死亡过渡期的提前连点（GDD 5.4）、暂停期间的转向，一律不出声。

### 2.2 `eat` —— 吃食物

- **用途**：蛇头吃到食物、增长计分的即时确认；与美术的扩散环/爆开动效同步。
- **声音性格**：明亮、清脆、略带"啵"的颗粒感的上扬短音。可理解为一个高频小亮点：正弦/三角波为主，起始约 600–800 Hz，在 30–50 ms 内快速上滑到约 1200–1500 Hz 后立刻收住；音头可带极短噪声颗粒（对应食物"砰"地爆开），但不得有低频成分。
- **触发时机**：步进裁决确认吃到食物的同一刻（GDD 5.3 第 5 步），与视觉爆开同时。
- **时长/循环**：约 80–120 ms，一次性。
- **停止条件**：自然放完。
- **重复触发行为**：现实触发频率约每秒 1–2 次（受步进节奏与食物间距限制）。每次触发都完整播放、新实例不截断旧实例；因间隔远大于音长，正常情况下不会叠音。不得做逐次升调的连击音（首发无连击设计，避免暗示不存在的机制）。

### 2.3 `die` —— 死亡

- **用途**：撞墙或撞自身死亡瞬间，与红色叉形/星形闪、蛇身熄灭、屏震同步（ART_DIRECTION 第 7 节）。
- **声音性格**：一记干脆、坚硬、向下坠落的短"撞/断"音。中低频起手（约 200–300 Hz）在 100–150 ms 内快速下坠到约 60–100 Hz，可叠一层很短的噪声冲击（撞击感）；情绪是"收手、出事了"，**不是滑稽失败音，也不是长哀嚎**。收尾干净，与美术"不羞辱"的结算情绪一致。
- **触发时机**：碰撞判定成立的同一刻（GDD 5.3 第 4 步）。
- **时长/循环**：约 250–400 ms，一次性。
- **停止条件**：自然放完；本局内不被任何后续操作截断（结算界面出现后该音已结束）。
- **重复触发行为**：**每局至多一次，由规则保证**。死亡后的重开/退出输入在结算界面可交互后才生效（GDD 5.4），过渡期连点不产生任何声音。

### 2.4 `new-record` —— 破纪录

- **用途**：本局得分在结算时确认超过历史最高分（GDD 第 4 节、第 6 节）。
- **声音性格**：两枚或三枚上行的金色短音（琶音感），每个音 60–100 ms、间隔约 70–100 ms，总时长约 250–350 ms；三角波/正弦的明亮音色，音高落在高频区（首音约 880 Hz，整体上行约一个纯五度），听感"亮但轻"，像点亮一枚印章，不是凯旋号角。
- **触发时机**：进入游戏结束结算、纪录比较确认刷新时；与金色星标/印章出现同步（美术"一次性金色绽放"）。**不是在局内超过纪录的瞬间触发**——结算时才确认，避免局内打断注意力。
- **时长/循环**：约 250–350 ms，一次性序列。
- **停止条件**：序列自然放完；若玩家在序列期间触发重开（结算已可交互），允许序列被新音覆盖截断，不做特殊处理。
- **重复触发行为**：每次刷新纪录的结算至多播放一次。无本地纪录的首次开局不播放（GDD 第 4 节）。

### 2.5 `board-full` —— 棋盘填满（完美局）

- **用途**：蛇填满棋盘这一唯一非死亡结束方式（GDD 3.3）。必须与 `die` 明确可区分：这是荣耀式安静结局，不是事故。
- **声音性格**：柔和、通透的上行和弦式回响（两到三个和谐高频音轻轻叠入并缓慢散开），约 500–800 ms；无噪声冲击、无下坠、无低频，与死亡音的"硬、坠、短"完全对立。情绪对应美术的"金色、安静的满盘辉光，无震动"。
- **触发时机**：步进裁决确认新食物已无空格可放、进入填满结束的同一刻（GDD 5.3 第 6 步）。
- **时长/循环**：约 500–800 ms，一次性；具体时长与填满结算演出停留时间联动（未决项）。
- **停止条件**：自然放完。
- **重复触发行为**：理论极小概率事件，每次填满至多一次。

## 3. 优先级、并发与相对电平

### 3.1 事件层级（重要度从高到低）

1. **关键信息层**：`die`、`new-record`、`board-full` —— 承载本局结局信息，必须最突出。
2. **行为确认层**：`eat` —— 高频出现，明亮但必须让位于结局层。
3. **界面层**：`ui-activate` —— 最轻，存在即可。

### 3.2 并发规则

- 常态并发只可能来自"快速 UI 连点"与 eat 的零星重叠，均为短音，允许各自独立播放，不互相截断。
- **结局音对其他一切音效有优先权**：死亡/填满发生的那一步若同时产生 eat（规则上死亡与吃食物互斥，board-full 紧随最后一次进食之后），以结局音为准；必要时 AudioManager 可截断尚未播完的 eat，保证结局音从零电平干净起播。
- 同帧（同一步）最多起一个结局音；`new-record` 只在结算时出现，不与 eat 竞争。
- **吃食物的高频上扬音任何情况下不得掩盖死亡与破纪录**：靠电平差（见 3.3）与结局音优先权共同保证，而不是靠压低 eat 的亮度。

### 3.3 建议相对电平

以各 cue 自身混音后的峰值为基准（非文件原始电平），建议：

| Cue | 相对电平（建议） | 说明 |
|---|---|---|
| `die` | −3 dB | 全场最重，低频成分需在手机小喇叭上仍可感知 |
| `board-full` | −3 dB | 与死亡同级重要，但音色柔，不靠响度压人 |
| `new-record` | −4 dB | 略低于结局音，明亮感由高频而非响度承担 |
| `eat` | −9 dB | 显著低于结局层；高频在 −9 dB 下仍清脆，但每秒 1–2 次不疲劳 |
| `ui-activate` | −12 dB | 最轻一层，确认即可，不与玩法音争注意力 |

以上为混音目标量级，最终参数在 ASSET_PLAN 的"事件 → cue"映射与试玩中校准；校准验收点：把 eat 与 die 接续播放（模拟死亡紧衔接连进食），die 的起音必须清晰可辨、不被前一个 eat 的尾音糊住。

## 4. 状态转场中的音频行为

| 转场 | 音频行为 |
|---|---|
| 开始界面 → 游戏中 | "开始"确认时播放一次 `ui-activate`；开局后步进移动**默认无声**（`step` 移动音首发不加，TECHNICAL_DESIGN 第 11 节），直到首次吃食物才出 `eat`。 |
| 游戏中 → 暂停 | 触发即播一次 `ui-activate`；随后**一切音频静默**：无音乐可 duck（首发无 BGM），暂停期间不补播、不排队任何音效；暂停期间的转向输入无声且被丢弃（GDD 5.2）。 |
| 暂停 → 游戏中 | 播一次 `ui-activate`；步进继续，声音从当前状态正常起，不补发暂停期间的任何事件。 |
| 游戏中 → 死亡结算 | `die` 播放一次（唯一一次）；死亡演出与结算卡片上浮期间静默，无背景乐；结算可交互后重开/退出才再出声。 |
| 游戏中 → 填满结算 | `board-full` 播放一次；随后静默等待结算交互。 |
| 结算 → 游戏中（重开） | 播一次 `ui-activate`，新一局从静默起步，无开场音乐。 |
| 任意状态 → 开始界面（退出/返回） | 播一次 `ui-activate`；开始界面保持静默（标题母题不配音）。 |

由于首发无 BGM，**不存在 ducking（压音乐）需求**：暂停与死亡的处理是直接静默，而非压低某个音床。

## 5. 静音与音量

- **首发提供单一静音开关（mute on/off），不提供分级音量调节**：五个 cue 的混音电平（第 3.3 节）固定，不暴露给玩家。这与 GDD 1.3 首发不做设置项的取向一致，静音是可用性底线，音量滑块不是。
- 静音开关的入口位置（开始界面 / HUD 图标）归 UI_UX_SPEC 决定。
- **持久化**：静音状态写入 `localStorage`（建议键 `snake.muted`，值 `"1"`/`"0"`，最终键名归技术侧）。读取失败、损坏或不可用时按"未静音"处理，写失败静默降级（与最高分存储的降级策略一致）。
- 静音时仍正常创建/解锁 AudioContext（保证取消静音后即时有声），只是所有 cue 不出声；静音状态下解锁失败也不报错、不阻断。
- 若最终评审决定首发连静音开关也不做，则本节降级为"恒为出声、无任何音量设置"，但本文不推荐——浏览器静音场景应由产品自身提供出口。

## 6. 浏览器自动播放限制行为

- 首次用户手势（点击"开始"按钮 / 确认键 / 触摸）的事件处理器内创建或恢复 `AudioContext`（TECHNICAL_DESIGN 第 11 节）。
- **解锁之前**：AudioContext 不存在或处于 suspended，开始界面一切静默；此期间派发的任何音频事件直接丢弃，**不入队、不回补**（开始界面本就无玩法事件，实际无信息损失）。
- **解锁之后**：解锁手势对应的那次 `ui-activate` 在同一处理器内、context resume 成功后正常播放——即玩家进入游戏后听到的第一声，就是"开始"按钮自己的确认音；随后从游戏初始静默状态正常进行。
- 解锁失败（浏览器拒绝或异常）：整体静音降级，不报错、不阻断流程，游戏无声音可完整游玩；不做重试弹窗。
- 不做"解锁提示页"：开始按钮本身就是解锁入口，不增加额外交互层。

## 7. 必需音频 vs 可选增强

### 7.1 首发必需

- 5 个 cue：`ui-activate`、`eat`、`die`、`board-full`、`new-record`，按第 2 节性格与第 3 节电平实现。
- 静音开关及其 localStorage 持久化（第 5 节）。
- 首次手势解锁 AudioContext、解锁前静默丢弃、失败静音降级（第 6 节）。
- 结局事件对其他音效的优先权（3.2）。

### 7.2 可选增强（首发不做，评审后再议）

- **极轻背景音乐循环**：单一极简环境/芯片音色循环，须配暂停 ducking/停止与循环点校准；若做，必须默认音量极低（建议 −18 dB 以下）且可独立静音。
- `step` 步进移动音：默认不加；即便增强也应在达到较高速度后才以极轻音量（−20 dB 量级）淡入，低速完全无声，避免节拍机噪声。
- 转向确认音、非法输入（被忽略转向）提示音：需谨慎，易与高频操作叠加成噪声。
- 分级音量滑块替代纯静音开关。
- eat 随分数轻微变调：首发明确不做（见 2.2），仅作远期备选。

## 8. 视听双通道冗余（音频不得是唯一信息载体）

以下关键信息必须同时有明确视觉对应，关闭/失去声音时信息完整：

| 信息 | 音频 | 必须同时存在的视觉 |
|---|---|---|
| 死亡 | `die` | 蛇头处红色叉形/星形闪、蛇身逐节熄灭、屏震（ART_DIRECTION 第 7 节） |
| 破纪录 | `new-record` | 结算界面金色星标/印章 + 破纪录标识文案 + 光点粒子 |
| 棋盘填满 | `board-full` | 满盘金色辉光 + 区别于死亡的结算文案（无红色、无叉形） |
| 吃食物 | `eat` | 食物爆开扩散环、新食物弹出、分数跳变（GDD 2.3） |
| 界面确认 | `ui-activate` | 按钮按下/焦点态视觉反馈 |

## 9. 未决项

1. 五个 cue 的最终实现方式：程序化合成（WebAudio 振荡器/噪声）还是短音频文件——倾向优先程序化合成（零资源体积、参数可调、契合电子音性格），由 ASSET_PLAN 结合资源管线决定并给出资源 id 或合成参数表。
2. 各 cue 的最终音高、时长精确值与第 3.3 节电平的试玩校准，待可玩版本后以耳机与手机小喇叭两套设备复核。
3. `board-full` 的 500–800 ms 时长需与填满结算演出停留时长（ART_DIRECTION 未决项 4、GDD 未决项联动）对齐。
4. 死亡演出总时长（500–800 ms 区间）确定后，复核 `die` 时长与演出的配合，且不违反过渡期不吞输入规则（GDD 5.4）。
5. 静音开关的入口位置、图标与可见性矩阵，归 UI_UX_SPEC；localStorage 键名最终归技术侧确认。
6. 暂停与继续是否共用同一个 `ui-activate`（当前方案共用），试玩后若辨识度不足再分化。
