# UI 与 Scene 空间交接复测

本轮未全部达标。实际 Agent 已调用空间计算，并在正式评审中纠正 UI 与 Scene 的相机区域交接；但评审新增的收缩布局没有对应的 UI 草稿计算，最低空间仍算错。不能把 Agent 的通过结论当作空间布局已经闭合。

## 测试范围

新建隔离项目，输入为“我想做一个贪吃蛇游戏。”，使用真实 BGS Author 批次和一次 Review/Revision，模型为 ark-code-latest。确认设置为 Web、React、2D、Stylized、键鼠和触控。没有注入已知问题、复用旧稿或改动私人项目；只使用一个原生主会话。Agent 自主发起三次子任务调用，并调用五种 Skill。未启动资源、内容、实现或发布，也没有追加付费修复回合。

## 已验证的改进

- Agent 实际执行了布局和镜头计算，日志共有 13 次包含计算器调用的 Bash 工具记录。部分命令包含多次计算，也有命令错误，因此不是 13 次全部成功的断言。
- 菜单与结算生成了独立竖屏草稿，不再仅整体缩小横屏构图。
- 评审把竖屏相机输入从旧的 390×784 改为 UI 实际分配的 390×390，同步修订 UI、Scene 和技术文档。棋盘宿主偏移为 y=60，相机区域内部偏移为零。
- 对最终保留草稿免费复算，桌面和竖屏 HUD、菜单、暂停、竖屏结算及参考方向键区域没有活动节点越出分配区域。字体、审美和游戏运行表现未验证。

## 未解决的问题

| 问题 | 证据 | 对下游的影响 |
|---|---|---|
| 新收缩规则的最小高度算错 | UI 第 2 节分配方向键最小 190px；第 4.4 节三行按钮最低各 48px，两个间距各 8px，上下内边距 16/24px，合计至少 200px | 该最小值不能同时满足文档承诺；实现被迫重新决策 |
| 规则、草稿与验证没有一起更新 | Review 新增 375×667 的分配，只计算了 375×375 相机，没有生成或复算收缩后的方向键草稿。保留草稿在 375×232 区域复算时，最下一行越界 | 参考构图通过不证明新增变体成立；保留草稿不是最终收缩方案 |
| 最终文档仍有重复且冲突的声明 | UI 第 2 节先允许收缩，紧接着又写方向键固定不缩放；支持尺寸写 390×844，同时加入 375×667；桌面 HUD 第 4.2 与第 6 节的最高分位置不同 | 内容阶段仍需猜测该采用哪条规则 |

最小高度的 200px 结论直接来自最终文档，不依赖草稿是否更新。对保留草稿的越界结果仅证明它没有表达新增收缩规则，不冒充尚不存在的最终 Content 数据测试。

## 根因与下一步

入口和基础算法能用，但本轮仍将“设计规则”“局部计算草稿”“结果文字”作为三份分别维护的内容。评审能修改文字并计算相机，却遗漏了新 UI 规则对应的几何输入。相机计算不会验证方向键容器容量，这不是增加自审或更多 Reviewer 能直接解决的问题。

建议下一步只修交接：以同一份全屏布局草稿表达 HUD、game-view 和操作区；从计算出的 game-view 矩形取得相机输入，文档引用这些结果。设计变更同步更新该草稿，并计算受影响尺寸。不新增评审阶段、自动付费续跑、游戏引擎或规定子代理分工。本轮未实施这项后续调整。
