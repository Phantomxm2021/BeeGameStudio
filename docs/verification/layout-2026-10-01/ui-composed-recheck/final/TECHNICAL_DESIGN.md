## 1. 文档定位与范围

本文档规定：运行时技术选型、模块职责与信息流、完整生命周期时序、内容数据的装载与绑定、letterbox 坐标换算、资源与失败处理、性能约定、可行性风险及其验证手段。

本文档**不**做的事：

- 不复制 GDD 的规则、状态表与裁定口径；任何规则歧义以 GDD 为准。
- 不重复 `content-format.json` 的字段定义；本文只说明运行时**如何消费**这些字段。
- 不给出具体玩法数值（生命数、球速、角度、行列数、分值、容差等）——以数值平衡文档为准。
- 不建立屏幕矩形表或相机偏移表；几何数值由 `check-content.mjs` 从作者化数据推导，运行时按本文 §6 的公式换算。

**既定事实（全文必须一致）**：平台 Web；引擎 React；2D；风格化；输入为键盘/鼠标 + 触屏。单一关卡，设计坐标为逻辑像素，场地 480×672，原点左上，+X 向右、+Y 向下，`pixelsPerUnit=100`。正交相机 `orthographicSize=3.36`（世界单位半高）、参考 viewport 480×672、`framing=letterbox`。游戏视图 UI 节点以 `anchorMin [0.02,0.02]` / `anchorMax [0.98,0.98]` 拉伸留边。

## 2. 运行时技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 应用框架 | React（DOM） | 负责屏幕/HUD/菜单/结算等界面合成与生命周期；不承担逐帧世界模拟。 |
| 世界渲染 | **Canvas 2D**（单画布，置于 game-view 宿主内） | 见 2.1 选型理由。 |
| UI 渲染 | **DOM/CSS**（由 React 输出） | UI 文档天然是锚点/拉伸/容器模型，映射为绝对定位 + flex/grid DOM 最直接。 |
| 模拟时钟 | `requestAnimationFrame` + **固定时间步累加器**（步长 1/60 s） | 行为约定见 §7.3；算法可在不改变结果前提下调整。 |
| 输入 | 原生 DOM 事件（Pointer Events 为主，Keyboard Events 补发球/暂停键） | 统一归一化为内部指令，见 §3.2。 |
| 音频 | **Web Audio API 实时合成**（振荡器 + 增益包络，无音频文件；ASSET_PLAN §2.3 定为首版方案） | 由规则事件按 cue 触发，见 §3.6；`HTMLAudioElement`/音频文件 bank 仅为试玩后可备选 |
| 数据获取 | `fetch` JSON；图片 `Image`/`createImageBitmap` | 音频无文件，**不 fetch、不 decodeAudioData**；统一加载器只管 JSON 与图片，见 §7.1。 |
| 构建/包管理 | Bun（沿用仓库既有工具链） | 不引入额外引擎或重型框架。 |

### 2.1 世界渲染为何选 Canvas 2D 而非 DOM/CSS

1. **每帧重绘成本低且可控**：场上实体为挡板 1、球 1、砖墙数十块，总量小但球每帧位移；Canvas 一次清屏 + 数十次 `drawImage` 即可，不进入 React 协调与 DOM 样式/布局计算。
2. **坐标换算天然贴合相机模型**：通过 `ctx.setTransform` 一次写入"设计坐标→画布像素"的缩放与平移，所有绘制直接使用设计逻辑像素，世界代码与宿主像素完全解耦（§6）。
3. **图集消费直接**：图集帧 = 共享 `ImageBitmap` + 源矩形子区域视图，`drawImage(img, sx, sy, sw, sh, …)` 直接对应 `assetRef + frame` 绑定，不复制像素、不逐帧取图。
4. **不依赖目标浏览器布局语义**：碰撞与绘制使用同一套 AABB 数学，避免 DOM 盒模型、亚像素取整引入的视觉与判定偏差。

UI 仍用 DOM/CSS：文字排版、按钮焦点、触屏命中区、响应式变体（compact/portrait）与可访问性在 DOM 上是成熟能力，且 UI 文档的锚点/容器约定可直接映射 CSS，无需在 Canvas 内重造排版引擎。**世界坐标链与 UI 坐标链严格分离（§6.1）**。

## 3. 模块职责与信息流

### 3.1 模块清单

1. **Bootstrap（引导器）**：拉取并校验 `content/index.json`；按 `loadPhase` 组织装载顺序；实例化各模块；任何必需数据缺失即 fail-fast（§7.2），不得以默认布局继续。
2. **ContentLoader（内容加载器）**：按文档 id 读取/缓存 Scene/UI JSON；校验 schema、kind 与 index 一致性；构建**节点注册表**（按 `id` 索引，按 `semantic` 建组）；输出不可变的作者化快照。
3. **AssetStore（资源存储）**：读取 `assets/asset-manifest.json`，把 `assetRef`（+ member/frame）解析为实际 URL；负责图片/图集的加载、解码、按 URL 去重、在途请求复用与使用结束后的释放（§7.1）。首版无音频文件，AssetStore 不管理音频。
4. **InputLayer（输入层）**：订阅键盘与指针事件，做按键边沿检测、指针坐标反算（屏幕→设计坐标，§6.4）、触屏手势归一化；只产出**指令对象（intent/command）**，不直接改玩法状态。具体按键映射、手势口径与焦点导航以 UI_UX_SPEC §6 为准。
5. **GameStore（游戏状态）**：持有唯一的权威运行时状态（相位、分数、生命、球相位/速度、各实体运行时 Transform、砖块存活集）；对 UI 暴露只读视图模型；模拟数据置于 React 渲染周期之外（`ref`/外部 store），仅在分数、生命、相位等离散变化时通知 React。
6. **RuleEngine（规则求值）**：实现 GDD §3 的运动/反弹规则与 §5 的结算裁定；输入为固定步长 + 当前指令，输出为新状态与**规则事件**（击中墙/挡板/砖块、销毁砖块、失分、胜负、暂停切换）。碰撞算法可自选（扫掠或保守子步），但必须满足 §7.3 的行为结果。
7. **SceneRenderer（场景呈现器）**：消费作者化层级、Transform、sprite-renderer 与排序（`zIndex`/层级/文档顺序），结合相机换算把世界绘制到 Canvas；运行时只允许更新实体 Transform/存活状态，不改写作者化默认值。
8. **UiPresenter（UI 呈现器）**：按 UI 文档在实际视口解析布局（锚点/拉伸/容器/响应式变体），输出 React DOM；把视图模型绑定到对应节点（分数、生命、提示、各按钮可用性）；绘制顺序遵守 content-format 的 paintOrder。
9. **AudioController（音频）**：订阅规则事件，按 cue 名以 Web Audio **实时合成**可区分音效（合成参数集中于音频模块，对应 AUDIO_DESIGN 的 13 个 cue 命名）；管理 AudioContext 首手势解锁与静音（GDD 范围内唯一设置项）；上下文不可用时静默降级，不阻断玩法（§7.2）。无文件解码失败路径。
10. **ViewportAdapter（视口/相机适配器）**：从 UI 布局解析结果取得 game-view 宿主矩形，结合相机参数生成坐标换算函数；宿主尺寸变化（resize / 旋转 / 移动端 URL 栏伸缩）时重算，不触碰世界布局（§6）。

### 3.2 信息流（单向）

```
键盘/指针事件
   │ （InputLayer：归一化、边沿检测、坐标反算）
   ▼
指令队列 ──► GameStore（权威状态，固定步推进）
                   │
                   ├─ RuleEngine 求值（位移→碰撞裁定→胜负）
                   │        │
                   │        └─ 规则事件 ──► AudioController（音效）
                   │                    └─ SceneRenderer 反馈参数（碎裂等表现）
                   │
                   ├─ 视图模型变化 ──► React/UiPresenter（HUD、菜单、结算）
                   └─ 实体 Transform/存活集 ──► SceneRenderer
                                                   │
                          ViewportAdapter 换算矩阵 ─┘
                                                   ▼
                                              Canvas 2D 上屏
```

关键约束：

- **只有 GameStore 能改玩法状态**；输入层、UI 按钮、音频、渲染器都只发送指令或读取状态。
- UI 按钮（开始/暂停/继续/再来一局/退出）与物理按键发送**同构指令对象**，因此两条路径的裁定逻辑只有一份。
- 表现动画（砖块碎裂等）订阅规则事件异步播放，**不延迟、不参与**规则判定（GDD §5.6）。

## 4. 生命周期时序

所有时序以**显式步骤与指令处理点**表达，不依赖模块初始化顺序或事件监听器注册顺序。

### 4.1 启动序列（Bootstrap）

1. React 挂载根节点，渲染最小加载外壳（无任何玩法模拟）。
2. `fetch content/index.json`，校验根 schema 为 `beegame-content-package.v2`、`sceneModel=game-object-v2`、`dimension=2d`；解析 `documents` 注册表。
3. 并行拉取全部 `loadPhase=startup` 文档：进入首屏所需的 UI 文档（开始界面）与 `entryScene` 场景文档；校验文档 kind（场景必须为 `scene-2d`）、`rootId`、引用完整性。
4. 加载 `assets/asset-manifest.json`；解析 startup 文档 `assetRefs` 涉及的资源并解码首帧实际需要的图片/图集帧（开始界面即需要者）；音频可在首次用户手势后补解码（§7.1）。
5. ContentLoader 构建节点注册表；ViewportAdapter 测量实际视口并解析开始界面布局；实例化 GameStore（初始相位 = **开始界面**）、RuleEngine、输入层、渲染器。
6. 启动 rAF 循环。开始界面下 RuleEngine 不推进、不计时、无后台模拟；世界画布可呈现作者化静态背景（仅当 UI/场景文档如此要求），但不存在动态模拟。
7. 任一步骤失败：进入显式失败态（§7.2），不用代码内置布局/资源顶替。

### 4.2 帧循环与固定步

每一动画帧严格按下列顺序执行：

1. 读取 `timestamp`，计算与上帧差值；输入层在此前已把事件入队（事件随时入队，不在回调里改状态）。
2. ViewportAdapter 检查宿主尺寸是否变化，变化则重算换算（不重新装载世界）。
3. GameStore 把帧时间喂入累加器，按固定步长（1/60 s）执行**零到多个**模拟步；每一步内：
   1. 从指令队列取出截至本步的指令并裁定（暂停、发球等）；
   2. 若相位为"球运动中"：球先位移，再按 GDD §5.2 顺序（死亡边界 → 挡板 → 砖块 → 墙体）处理碰撞，处理砖块销毁/计分，再按 §5.4/§5.5 检查胜负与生命；
   3. 若相位为"待发球"：挡板移动生效，球贴附位置随挡板更新；
   4. 已暂停/结算/开始界面：不产生位移与碰撞。
4. 输出本帧状态：SceneRenderer 绘制一次世界；视图模型有离散变化时同步给 React。
5. 累加器设最大步数上限（防止后台切换回来后的"死亡螺旋"）；被丢弃的时间只表现为少模拟，**绝不在恢复后补发位移**——暂停规则同理（GDD §5.7）。

### 4.3 状态转换的实现对照（GDD T1–T10）

| GDD | 触发指令 | 运行时处理（效果细节以 GDD 原文为准） |
|---|---|---|
| T1 | `START`（开始界面按钮/确认键） | 调用唯一的 `createRun()`：从作者化场景快照构建新局——满生命（调值）、分数 0、全部砖块存活、挡板/球 Transform 复位、球贴附；相位→待发球。 |
| T2 | `SERVE`（发球键，**边沿触发**） | 仅在待发球相位生效；按调值写入恒定初速度，相位→球运动中；长按不连发，靠"按下沿 + 相位标记"保证一次。 |
| T3 | RuleEngine 内部事件 | 球触死亡边界且扣生命后仍有剩余：挡板/球复位为贴附，砖块与分数保留，相位→待发球。 |
| T4 | RuleEngine 内部事件 | 一步结算后存活砖块为 0：立即停止模拟、相位→胜利结算；该步后续任何朝向底边的轨迹不再判负（GDD §5.4）。 |
| T5 | RuleEngine 内部事件 | 死亡结算先扣生命，扣后为 0：相位→失败结算。T5 与 T3 在同一死亡处理函数内按生命余量二选一。 |
| T6 | `PAUSE_TOGGLE`（Esc/P/暂停按钮） | 仅在球运动中/待发球生效：记录来源相位，冻结模拟，相位→已暂停。 |
| T7 | `PAUSE_TOGGLE` 或 `RESUME` | 恢复到记录的来源相位，从冻结点继续；不补发暂停期间位移。 |
| T8 | `QUIT_RUN`（暂停菜单） | 执行当局清理（§4.4），相位→开始界面，分数不保留。 |
| T9 | `RESTART`（结算界面） | 复用同一个 `createRun()`，与 T1 完全相同的重置路径。 |
| T10 | `EXIT_TO_START`（结算界面） | 执行当局清理，相位→开始界面。 |

结算相位期间：场地移动/发球指令在 RuleEngine 入口直接丢弃；暂停切换与结算按钮指令始终可响应（GDD §5.6）。

### 4.4 Restart 与 Cleanup

- **再来一局（T9）/ 开始游戏（T1）走同一个 `createRun()`**：从不可变作者化快照重建运行时实体集合（砖块存活集、初始 Transform、球贴附状态），分数与生命重置；不重新拉取 JSON、不重新解码图片（缓存复用）。这样保证"固定关卡、相同初始布局"且不存在两套重置逻辑。
- **退出（T8/T10）**：移除当局运行时实体引用，停止规则事件订阅中的表现动画，停止任何在途音效；返回开始界面。共享的 AssetStore 缓存与内容快照保留。
- **应用卸载（React unmount）**：集中清理——取消 rAF、`AbortController` 注销全部输入监听、关闭/挂起 AudioContext、释放"无消费者"的已解码资源源、清空计时器。清理在 `useEffect` cleanup 中一次性完成，顺序显式，不依赖组件卸载先后。

### 4.5 页面失焦自动暂停

- 监听 `document` 的 `visibilitychange`：`visibilityState === "hidden"` 时，若相位为球运动中/待发球，派发自动暂停（T6 同路径，记录 `pausedReason=auto`）。
- 辅以 `window` 的 `blur`（以 `document.hasFocus()` 判定去抖，避免 DevTools、iframe 切换导致的误触发）。
- **恢复必须由玩家显式操作（T7）**，不在 `focus`/`visible` 时自动续球，避免玩家在无准备状态下漏球。
- 开始界面/结算相位下失焦不产生状态变化（无可冻结模拟）。

### 4.6 行为不依赖隐式执行顺序的保证

1. 所有外部刺激（键、指针、按钮、失焦）只入指令队列；状态变更只发生在模拟步的指令裁定点。
2. 指令按入队顺序、在单线程内同步排空；同一步内的指令按 GDD §5 裁定，不依赖监听器注册顺序。
3. 发球等一次性动作用"按下沿 + 当前相位 + 已消费标记"去重；暂停类指令幂等（已是暂停态再收到无效）。
4. `createRun()` 是重置的唯一入口；T1/T9 不分叉。

## 5. 内容装载与数据驱动绑定

### 5.1 `content/index.json` 与 loadPhase

- index 是运行时装载注册表：`documents` 中每个文档的 `id/path/kind/loadPhase` 与 `files` 一一对应。
- **startup**：进入第一个可交互帧所必需的文档（开始界面 UI 文档；`entryScene` 场景文档——T1 发生时必须立即可用）。startup 文档在启动序列中并行先取。
- **on-demand**：仅在流程进入或确有需要时拉取（如后续批次新增界面或 VFX 文档）；首版范围内不预取无关文档。
- 文档路径均相对 `content/`；不发明未注册的关卡文件种类，不使用 kind 占位。

### 5.2 Scene 文档的消费

运行时必须实际消费（解析而不用即违反 content-format 的 authority 约定）：

- **层级**：按 `parentId` 建树；Transform 为父节点局部坐标，按"父变换 × 平移 × 旋转 × 缩放"**只组合一次**；2D 使用 XY 平面。
- **坐标语义**：作者化位置即逻辑像素，`pixelsPerUnit` 仅在需要世界单位处（相机）换算，**禁止把作者化位置二次乘算**。精灵 pivot 只偏移渲染几何体，不偏移 GameObject/碰撞体。
- **组件**：`sprite-renderer`（含 `assetRef`/frame）驱动图像；`box-collider-2d` / `circle-collider-2d` 的 size/offset 驱动碰撞形状（球按圆、挡板与砖块按 AABB，具体以作者化组件为准）；`camera` 提供正交参数；组件以稳定 id 索引，不依赖数组顺序。
- **semantic**：`paddle`、`ball`、`brick`、`death-boundary`、`wall-left/right/top` 等玩法身份从节点 `semantic` 读取；节点名仅辅助调试。
- **行为配置**：球贴附偏移、发球朝向等运行时行为的作者化参数，落在 `node.data.behaviors`（稳定 id + kind + config）；kind 语义归运行时所有，但 config 是数据而非代码常量。
- **enabled**：禁用节点压制其子树（渲染与玩法均不实例化）。

### 5.3 UI 文档的消费

- 按 `rootId` 建树；固定尺寸控件用命名锚点 + position + size；拉伸区域（game-view、HUD 条带）用成对 `anchorMin/anchorMax + sizeDelta`；解析公式严格遵循 content-format 的 ui/stretch 约定（子节点 pivot 默认同锚点，绝不隐式 [0,0]）。
- 容器（row/column/grid）按文档顺序分配；响应式按 `responsive.compact`（宽 ≤ compactMaxWidth）与 `responsive.portrait`（高 > 宽，compact 之后覆盖）解析，未覆盖字段继承基线。
- 绘制顺序：每节点先背景/边框、再自身内容（文本/图像/控件）、再子节点；禁用节点整棵子树压制。
- UI 在**实际视口**解析；`referenceResolution` 只是设计参考，不被当作宿主窗口固定尺寸。

### 5.4 运行时状态到 authored 节点的绑定

启动时一次性建立绑定表（缺失必需绑定即 fail-fast）：

| 运行时角色 | 绑定方式 | 消费数据 |
|---|---|---|
| 挡板实体 | semantic 含 `paddle`（唯一） | 层级世界 Transform、box-collider-2d、sprite-renderer |
| 球实体 | semantic 含 `ball`（唯一） | Transform、circle-collider-2d、贴附/发球 behavior config |
| 砖块实体集 | semantic 含 `brick` 的全部启用节点 | 每个节点独立 Transform、碰撞体、精灵；数量即作者化数量 |
| 死亡边界 | semantic 含 `death-boundary` | 位置/几何；规则上**只触发失分，不反弹** |
| 三面墙 | semantic 含 `wall-*` | AABB/边界线，反弹面 |
| 分数/生命/提示/按钮 | UI 节点 id（如 `hud-score`、`hud-lives`、`pause-btn`、game-view） | 布局几何 + 文本/动作绑定 |

最终 id 与 semantic 取值以 `LEVEL_SCENE_DESIGN` / `UI_UX_SPEC` 作者化结果为准；代码按语义解析，不硬编码具体坐标、尺寸或行列数。**禁止第二份手写场景**：运行时不得出现与内容 JSON 平行的布局常量表、砖块排布表或尺寸常量；派生物（编译/缓存产物）可存在，但源改动经重建后必须传播。

### 5.5 重置数据来源

`createRun()` 的初始世界 = ContentLoader 输出的**不可变作者化快照**的深拷贝（砖块是否存活、各节点初始 Transform、enabled）。固定关卡不随机化；每局差异只来自玩家输入。

### 5.6 共享调值文件（项目自有，唯一）

- 位置：项目自有的一个 JSON（建议 `config/tuning.json`，位于 `content/` 之外）；不使用未受支持的 content 文档种类，不把共享值复制进每个场景。
- 承载：生命数、挡板速度、球恒定速度、发球初速度/朝向、挡板反弹最小/最大角度、砖块分值、挡板侧面/角落判定容差、砖块可接触数量上限、穿透保护容差/子步上限等——**最终字段清单与数值由数值平衡文档给出（依赖项，§9）**。
- 加载：startup 阶段一次加载、校验字段；缺字段/越界即 fail-fast，不静默猜测。
- 代码中除该文件与作者化内容外，不允许出现玩法调值的第三处来源。

### 5.7 资源清单

- 每个 `assetRef` 在所属文档 `assetRefs` 中出现一次，并解析为 `asset-manifest.json` 中 `status=verified` 的资源；精灵按资源 `root_path/file_paths` 与 member 解析，图集帧名大小写敏感且必须与实际 sidecar 一致，不做文件名猜测。
- 图集消费遵守 atlasLoading：帧是共享图片源的区域视图，不分别 fetch/解码；在途加载与已解码源按解析 URL 复用；无消费者后释放所属源；不预载无关图集群，不为同一用途同时加载打包图与原图。

### 5.8 data-driven 绑定验证方式

依据 content-format `runtimeConsumption.checks`，在**目标运行时**可被观察的前提下（当前不具备，见 §10），用以下方式验证，验证过程不改布局代码：

- **ui-layout**：临时改动某节点 `layout`（位置/尺寸，含父锚点与响应式变体），验证其实际运行时几何对应变化，并在目标视口确认控件/覆盖层完整在视野内；仅改文本不算布局验证。
- **scene-layout**：临时改动作者化 Transform，验证对应对象及子代在正确的 y-down 2D 空间变化（含旋转/缩放）。
- **resource-binding**：临时改动资源/帧引用，验证实际渲染或播放的资产改变，并确认映射被解析、资产被真实解码（HTTP 200 或文件名不构成验证）。

统一操作口径：在临时副本或拦截的测试响应中改动，比较改动前后目标运行时结果，随后恢复原始数据；无变化或错误变化即判定绑定失败；目标运行时无法观察时如实报"未验证"。

## 6. Letterbox 适配与坐标换算

### 6.1 两条独立坐标链

1. **UI 链（屏幕逻辑像素）**：UI 文档 → 实际视口解析 → DOM。开始界面、HUD、暂停/结算覆盖层走此链。
2. **世界链（设计逻辑像素）**：场景文档 → 模拟与碰撞始终在 480×672 设计坐标中进行 → 经相机换算到 Canvas 像素。

两条链只在 game-view 宿主节点处发生关系（UI 链提供宿主矩形，世界链在其内部取景）。**UI 适配不改世界，世界取景不改 UI。**

### 6.2 game-view 宿主矩形

- game-view 是 UI 文档中以 `[0.02,0.02]–[0.98,0.98]` 拉伸的节点；UiPresenter 在实际视口解析出其内容盒矩形（CSS 像素，左上角 + 宽高）。
- ViewportAdapter 每帧（或 ResizeObserver/尺寸变化事件时）读取该矩形的最新值作为取景输入；不在代码中记录任何设备的固定矩形。

### 6.3 设计坐标 → 画布像素（换算公式）

输入：game-view 内容盒宽高 `W、H`；相机参考视口 `vw=480、vh=672`；`framing=letterbox`（完整容纳参考视口、等比缩放、居中留边）。

```
scale    = min(W / vw, H / vh)                 # 统一缩放系数（CSS 像素 / 设计像素）
offX     = (W - vw * scale) / 2                # 留边偏移（相对 game-view 内容盒）
offY     = (H - vh * scale) / 2

screenX  = offX + designX * scale
screenY  = offY + designY * scale
```

世界单位侧只与相机参数有关：参考可见高（逻辑像素）= `2 × orthographicSize × pixelsPerUnit = 2 × 3.36 × 100 = 672`，与参考 viewport 一致；运行时不得再用 `pixelsPerUnit` 乘算作者化位置。

实现上 Canvas 的 CSS 尺寸 = game-view 内容盒尺寸；逐绘制可用等价的 `ctx.setTransform(...)` 一次写入缩放/平移，之后全部绘制语句直接使用设计坐标。`check-content.mjs` 推导的 letterbox 矩形（桌面与竖屏两例）与本公式一致；本文不另建矩形表——任何宿主尺寸都按上式实时计算。

### 6.4 输入反算（屏幕像素 → 设计坐标）

```
designX = (localX - offX) / scale
designY = (localY - offY) / scale
```

`localX/localY` 为指针相对 game-view 内容盒的 CSS 像素。落在留边区的指针：反算结果在场地外，挡板目标经场地夹取后自然无效；不把留边事件映射成场地内位置。鼠标横轴驱动挡板、触屏拖拽驱动挡板时，统一使用该反算结果，再按 BALANCE §1.2 的指针直接映射策略更新挡板。

### 6.5 设备像素比（DPR）

- Canvas 后备存储按 `devicePixelRatio` 放大（建议封顶 2，兼顾低端设备填充率，§7.4），CSS 尺寸保持 content-box 尺寸；上下文变换在 §6.3 基础上整体乘 DPR。
- 鼠标/触屏的 `clientX/clientY` 是 CSS 像素，反算不涉及 DPR。
- DPR 变化（跨窗口拖动到不同密度显示器）等同尺寸变化处理：重算换算，不重建世界。

### 6.6 禁止事项与引用

- 禁止为适配而缩放/重排作者化世界 Transform，禁止在代码里烘焙第二套布局；取景只改变呈现（content-format viewportAdaptation）。
- 取景范围与相机要求引用 `LEVEL_SCENE_DESIGN`；屏幕分区、安全区与响应式变体的最终口径引用后续 `UI_UX_SPEC`；本文不代其决策。

## 7. 加载、失败处理、存储与性能

### 7.1 资源加载与缓存

- **JSON**（index/场景/UI/调值/manifest/图集 sidecar）：经 fetch 加载，按路径缓存，失败可重试一次后进入失败处理。
- **图片/图集**：按解析 URL 合并在途请求；优先 `createImageBitmap` 解码，失败回退 `Image`；图集只解码共享源，帧为区域视图；引用计数归零后释放源；切换文档/退出当局时核对消费者。
- **音频（实时合成）**：首个用户手势后创建/恢复 `AudioContext`（浏览器自动播放策略）；音效在事件发生时以振荡器+包络实时合成，无文件加载/解码；上下文挂起期间事件静默跳过、不补发。
- 启动只装载首帧所需；on-demand 文档及其资源在进入对应流程时加载，加载期间展示作者化/中性加载态，不模拟玩法。

### 7.2 失败处理

| 失败类型 | 处理 |
|---|---|
| index/场景/UI/调值 JSON 拉取或解析失败 | 启动期：显式错误界面 + 重试入口；运行期必需文档：停留在当前安全相位（不进入新局），提示重试。**不使用内置默认场景/布局顶替。** |
| 必需绑定缺失（找不到 paddle/ball/brick/死亡边界等） | fail-fast，报错指明缺失 semantic/id；不进入可玩状态。 |
| 图片/图集解码失败 | 该图形标记不可用并上报；若为首帧必需资源则阻断进入对应界面；非必需时以占位/降级呈现继续，玩法不因纯视觉资源失败而停摆。 |
| 音频上下文失败/挂起 | 记录并降级为静默（实时合成无文件可失败）；音频从不阻断玩法。 |
| 资源引用与 manifest 不一致 | 加载期校验失败即报错，不猜测文件名或帧名。 |

### 7.3 时间步与防穿透（行为结果约定）

- 采用固定步长 1/60 s + 帧时间累加器（算法可替换为等价的帧驱动方案，但须满足下列结果）。
- **只规定行为结果**：60 fps 正常游玩时，球在任何一步都**不穿透**墙、挡板、砖块，**不漏掉**该步应发生的碰撞；同一步多对象接触按 GDD §5.2 顺序裁定；角部/跨多块按 GDD §5.3 处理。
- 低帧率下靠固定步多执行补齐判定，而非放大单步位移；最大步数上限触发时宁可短时减速呈现也不产生大步穿透。
- **高速度单步跨越（tunneling）是首要可行性风险（§8 R1）**：可选实现为线段扫掠（segment-vs-AABB/圆对 AABB 扫掠）或保守子步（按球径/容差细分单步）；具体算法在不改变 GDD 裁定结果的前提下自由选择。

### 7.4 性能与低端设备/触屏

- 实体规模小（数十块砖），Canvas 2D 全量重绘即可满足；避免每帧分配对象/闭包，碰撞用扁平数组遍历，砖块销毁后从活跃集移除。
- 合批倾向：共用图集源可在同一画布顺序绘制；不承诺也不强制 draw-call 批次数指标。
- DPR 封顶、必要时降低后备分辨率；监测长帧（连续帧超过预算）作为低端降级触发条件（降级只影响呈现精度，不影响模拟结果）。
- 触屏：game-view 设置 `touch-action: none` 并以非被动监听阻止滚动/缩放手势冲突；拖拽采样在帧内统一消费，避免每事件触发状态写入；按钮命中区满足 UI_UX_SPEC 最终尺寸。
- 后台标签页：rAF 自动挂起；回到前台按累加器上限处理并配合自动暂停（§4.5），不追算后台位移。

### 7.5 存储

无持久化（GDD §7）：不写 localStorage/IndexedDB 保存分数、设置或进度；刷新即回开始界面。静音状态仅内存有效。唯一"存储"是运行期内的内容快照与资源缓存。

## 8. 可行性风险与验证手段（不预先造框架）

原则：先以最小步行骨架（walking skeleton）验证高风险项，再横向填充；不为假设的未来需求（多关卡、道具等排除项）预留抽象。

| # | 风险 | 影响 | 验证手段（spike/验收） |
|---|---|---|---|
| R1 | **球高速单步穿透砖块/挡板**，或一步跨多砖时反弹/销块错误 | 玩法核心失效、计分错误 | 最小仿真 spike：以调值最大球速对最薄碰撞体做扫掠/子步验证；构造正对、角部、一步跨两块、贴边四类几何输入，断言不穿透、反弹面正确、销块数符合 GDD §5.3；在 30 fps 节流下复测。容差/上限依赖数值文档。 |
| R2 | 同帧死亡边界与挡板/砖块同时可触及时裁定错误 | 生命/胜负结果错误 | 针对 GDD §5.2 优先级与 §5.4"胜利即时生效"构造同帧用例（含击碎最后一砖后朝底边运动），断言死亡优先、胜利优先两条口径。 |
| R3 | letterbox 留边导致输入映射偏移（桌面/竖屏） | 挡板错位、误触 | 自动化在 960×540、390×844 及一个极端宽高比下，点击场地已知设计坐标点，反算误差为 0（亚像素容差内）；留边区点击不产生场内位移。 |
| R4 | 浏览器自动播放策略阻断音频 | 首局无声（可接受降级） | 验证首次手势后 AudioContext 恢复；解码失败时静默降级且无异常外泄。 |
| R5 | 触屏滚动/双击缩放与拖拽冲突 | 移动端无法操控 | 真机/移动模拟：拖拽挡板期间页面不滚动不缩放；点按发球边沿触发一次。 |
| R6 | 数据绑定漂移：代码出现第二份场景/调值，源 JSON 改动不生效 | 作者化流程失效 | 按 §5.8 三类 checks 做临时改动对照；代码审查定位任何布局常量并消除。 |
| R7 | 帧率波动导致累加器洪泛或卡顿 | 暂停恢复后跳变、低端掉碰撞 | 人工制造后台切换与长帧，验证步数上限、自动暂停与"不补发位移"。 |
| R8 | React 重渲染侵入逐帧循环造成掉帧 | 低端设备性能 | 将模拟状态与 React props 隔离，用渲染计数断言：运动中 React 仅在离散视图模型变化时重渲染。 |

算法与代码组织（碰撞实现、store 形态、文件切分）在不改变 GDD/T1–T10 既定可观察行为的前提下保持灵活；任何调整以回归上述行为用例为界。
