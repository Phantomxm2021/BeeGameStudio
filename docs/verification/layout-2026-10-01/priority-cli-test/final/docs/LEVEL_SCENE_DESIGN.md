## 1. 本文范围

- 负责：世界坐标系尺度、游戏场地/墙/死亡线、砖阵行列、挡板与球初始摆放、相机取景计算输入、世界侧 UI 叠加限制、交付下游的节点与组件数据需求。
- 不负责：HUD/菜单的具体屏幕几何与视觉（归 UI_UX_SPEC / ART_DIRECTION）、键位与触控热区（归交互契约）、分值/生命/球速/角度（归数值平衡文档，下称 BALANCE）、素材产出与图集划分（归资产计划）。
- 首版只有**一张固定布局的单屏关卡**，本文即该关卡的空间权威。

## 2. 世界坐标系与尺度

### 2.1 坐标约定（引用契约，不另建规则）

- 采用 `content-format.json` 的 `coordinates.scene2d`：**原点 top-left，+X 向右，+Y 向下，距离为逻辑像素（logical pixels）**；Z 仅用于深度/排序。
- Scene `data.settings.coordinateSystem` 本关填写：
  - `origin: "top-left"`
  - `units: "logical-pixels"`
  - `width: 960`，`height: 540`
  - `pixelsPerUnit: 100`（仅作像素↔世界单位换算；创作位置不被乘两次）
- 节点 transform 为父节点局部坐标；2D 平面使用 XY，旋转角为弧度。

### 2.2 设计参考场：960×540，兼容最小 800×450

- 本文全部几何在 **960×540 设计坐标**下创作（16:9），这是 GDD 第 7 节规定的横屏设计参考坐标。
- GDD 同时规定**最小可用尺寸 800×450**。960×540 与 800×450 同为 16:9，最小尺寸即参考场的等比缩小（比例 0.8333）：本文所有几何在该尺寸下**同比例缩小、不重排、不裁剪**。例如墙内可玩矩形在 800×450 宿主上呈现为约 666.7×333.3 宿主像素，信息结构与相对尺度完全一致。
- 低于 800×450 或非横屏时不做适配，由运行时显示"请旋转设备至横屏 / 窗口尺寸不足"提示页（GDD 第 7 节）。

### 2.3 "世界范围" vs "显示范围"

- **世界范围（world range）**：创作数据存在的坐标空间，即 960×540 逻辑像素。本关的玩法内容集中在 x∈[64,896]、y∈[64,480] 的带状区域；其余为留边，供背景与可能的 UI 使用。世界范围是固定的，不随宿主窗口变化——任何取景适配**不修改世界 transform、collider 与布局**。
- **显示范围（display range）**：运行时宿主容器的实际像素区域。相机以 `letterbox` 把 960×540 的参考视口等比嵌入显示范围：
  - 16:9 宿主（含 960×540 与 800×450）：参考视口铺满，无留黑；
  - 比 16:9 更宽的宿主：左右留黑，世界竖向范围（含顶墙与死亡线）完整；
  - 比 16:9 更高（更方）的横屏宿主：上下留黑，世界横向范围（含左右墙）完整。
- 即：**世界永远完整、不裁剪、不变形；变化的只是缩放与留黑**。具体计算见第 5 节。

### 3.4 砖位公式（供下游逐节点落数）

- 行、列编号均 **1-based**：row r∈[1,6]，col c∈[1,10]。
- 砖块**节点中心**（collider 中心 = transform position）：
  - x = 84 + (c−1) × (72+8) + 36 = 120 + (c−1) × 80
  - y = 104 + (r−1) × (24+10) + 12 = 116 + (r−1) × 34
- 例：r1c1 中心 (120,116)；r6c10 中心 (840,286)，右下角 (876,298)。
- 所有砖均为一次击碎，玩法等价；行间暖色递进（品红→玫红→橙→琥珀）只是视觉节奏，按 ART_DIRECTION 6.3 由素材侧实现，几何上砖与砖完全同构。


## 4. 目标、出生与结束条件，及球路可达性论证

### 4.1 条件引用 GDD（本空间如何支撑）

| 条件（GDD 权威） | 本空间的支撑 |
|---|---|
| 单局目标：生命耗尽前击碎全部砖块（GDD 2.1） | 砖阵 60 块全部位于墙内矩形上半部，每块砖均为独立节点、带独立 box-collider-2d，可被球从下、侧、上方向接触；无砖块位于墙外或 UI 覆盖区。 |
| Ready 出生：球静止吸附挡板上方随板移动（GDD 4.1/4.2） | 待发位 (480,427) 紧贴挡板上缘正中；挡板在该 Y 的全部可达 X 范围（中心 128–832）移动时，球与板始终在墙内，吸附点永不进入墙体。 |
| Playing：球与墙/挡板/砖弹性反弹（GDD 5.1） | 顶/左/右三墙封闭墙内矩形的三侧；挡板击球上缘 y=432 横贯砖阵宽度方向；碰撞组件见第 9 节。 |
| 漏接：球越过死亡线 → 扣命复位或 Game Over（GDD 4.2） | 死亡线 y=480 横贯墙内全宽（x80–880），挡板下缘距线 32，不存在挡板把死亡线局部挡住而形成歧义的几何情形。 |
| 胜负结算、暂停 | 世界在覆盖层期间冻结（TECHNICAL_DESIGN 2.3）；场地四角与顶带留出 UI 叠加区（第 6 节）。 |

### 4.2 球路可达性论证（几何层面）

反弹角度的具体范围由 BALANCE 规定；本文只论证空间几何不制造死区：

1. **砖阵下沿与挡板之间留有足够反应距离**：砖阵下沿 y=298 到挡板击球上缘 y=432 之间为 134px 高、800px 宽的完整开放矩形，内部无任何 collider 与装饰遮挡，球在该区域的轨迹全程可见、可拦截。
2. **不存在被墙体/边角封死的区域**：
   - 砖阵整体相对墙内场地水平居中，砖阵两侧与墙之间仅有 4px 间隙（小于球直径 10，球不会进入），所有砖都面向开放区；
   - 最下排边角砖（r6c1、r6c10）的底面向开放反应区敞开，可自下方直接击中；
   - 最上排边角砖（r1c1、r1c10）上方有 24px 走廊（y80–104）连通左右，球可经侧墙/顶墙反弹后进入，不存在三面围死的砖；
   - 砖缝（8）与行间距（10）均不大于球直径（10），球不会被夹入砖缝形成卡死结构。
3. **挡板活动宽度与砖阵宽度关系**：挡板宽 96，约为墙内宽度（800）的 12%、砖阵宽度（792）的 12.1%；挡板中心可达 x128–832，击球上缘覆盖范围随板移动可触及 x80–880 全宽——即挡板能移动到任意一列砖的正下方，每列砖都存在"竖直或近竖直一击直达"的几何路径，无需依赖极端倾斜角。
4. **水平速度非零保护**：GDD 5.3 要求反弹后水平速度分量不得为 0（量化下限归 BALANCE）。几何上砖阵横向铺满，球不会因布局被迫进入纯垂直往返；即便球暂时近垂直运动，玩家也能用挡板击球的水平偏移改变方向（GDD 5.1）。

### 4.3 明确依赖 BALANCE 的待验证项

- **反应时间够不够**：134px 反应距离是否充足取决于 BALANCE 给出的球速 v。球以斜向穿过该区时路径长于 134/v，但玩家还需横向移动挡板到位，键盘移动速度同样由 BALANCE 规定。**本文不声称反应时间已足够，须在 BALANCE 球速确定后于运行时验证**（见第 10 节）。
- 挡板反弹角度的具体 min/max、水平速度分量下限、是否随时间加速，均以 BALANCE 为准。几何上虽无死区，但"在 BALANCE 实际角度范围内 60 块砖是否均可在合理击球次数内被击中"（尤其最下排边角砖的单弧直达角较陡）属于运行时观察项，不由几何论证替代。


## 5. 相机与取景

### 5.1 相机草稿（计算输入）

相机参数以 workspace 相对草稿文件 `.beegame/tmp/breakout-camera.json` 表达，内容：

```json
{
  "orthographic": true,
  "orthographicSize": 2.7,
  "coordinateSpace": "logical-pixels",
  "pixelsPerUnit": 100,
  "viewport": { "width": 960, "height": 540 },
  "framing": "letterbox"
}
```

参数含义（契约 `sceneVocabulary.requiredData.camera`）：正交相机；`orthographicSize=2.7` 为世界单位半高，按 `2 × orthographicSize × pixelsPerUnit = 2 × 2.7 × 100 = 540` 得参考可视逻辑像素高度；viewport 960×540 声明参考宽高比 16:9；`framing: "letterbox"`。相机节点位置取世界中心 (480,270)（最终随 Scene JSON 落定；取景计算器只算矩形与跨度，不读相机位置）。

### 5.2 计算器实际运行结果

已实际运行（项目根下）：

```
bun .beegame/delivery/check-content.mjs --camera-draft .beegame/tmp/breakout-camera.json 960 540
bun .beegame/delivery/check-content.mjs --camera-draft .beegame/tmp/breakout-camera.json 800 450
```

另补跑两个非 16:9 宽高比用于说明留黑行为：

| 宿主尺寸（宽×高） | 宽高比 | 世界矩形 rect（宿主像素 x,y,w,h） | 留黑 | halfHeight / halfWidth（世界单位） |
|---|---|---|---|---|
| 960×540 | 16:9 | (0, 0, 960, 540) | 无 | 2.7 / 4.8 |
| 800×450 | 16:9 | (0, 0, 800, 450) | 无（整体等比缩小 0.8333） | 2.7 / 4.8 |
| 1024×768 | 4:3 | (0, 96, 1024, 576) | 上下各 96px | 2.7 / 4.8 |
| 1280×540 | 约 2.37:1 | (160, 0, 960, 540) | 左右各 160px | 2.7 / 4.8 |

四次结果均 `ok: true`、`projection: "orthographic"`、`aspect: 1.7778`。

### 5.3 结论

- **letterbox 下世界不裁剪**：任意横屏宽高比下，顶/左/右三墙与底部 y=480 死亡线**始终同时可见**——墙内矩形完整在屏；砖阵、挡板、球的相对构图不变。
- 16:9 宿主（含最小 800×450）无留黑；更方的横屏（如 4:3）世界上下方向完整、左右铺满，**上下区域留黑**；更宽的横屏（如超宽 2.37:1）世界竖向完整居中，**左右区域留黑**。留黑区由背景层深色填充（ART_DIRECTION 5.3），不得出现白边。
- 取景适配只改变呈现：世界 transform、collider、砖位不被缩放或移位；指针→世界坐标映射由运行时把上表的 rect 缩放与偏移计入逆变换（TECHNICAL_DESIGN 第 7 节）。
- **计算器能力声明（如实）**：`--camera-draft` 的输出 note 明确"Camera framing only; does not project objects, verify gameplay occlusion or establish XR comfort"。它只验证取景矩形与正交跨度，**不投影任何节点、不验证遮挡关系、不验证可玩性**；本文不据其结果声称遮挡或可玩性成立。


## 6. UI 叠加限制（世界侧要求）

屏幕空间的最终分配归 UI_UX_SPEC；本文只从世界可读性出发规定允许与禁止叠加的区域：

- **允许叠加带**：y∈[0,64]（顶墙之上的整宽留边）——HUD 分数/最高分/暂停/静音按钮放此带内；不得向下侵入顶墙（y=64）。
- **角部允许区**：场地四角的留边区（如左上角 x<64 区域）可放小型控件，但控件投影不得进入墙内可玩矩形（x≥80、y≥80）。
- **禁止叠加区**：墙内可玩矩形 x∈[80,880]、y∈[80,480] 全程不允许常驻 UI 遮挡；待发提示（Ready）是唯一例外，允许以居中、高透明、不覆盖球与挡板的形式短暂呈现，发球后消失。
- 暂停/结算覆盖层允许覆盖全屏（此时世界冻结，覆盖层自带深色半透明底），属状态既定行为，不受上述限制。
- 若 UI 文档需要世界空间的信息图形（如贴在场地内的提示），须以相机参考面（`cameraReferencePlane`）方式表达并在内容阶段投影；本空间不预留第二个世界矩形。

## 7. 程序化内容

首版无程序化内容：砖阵为固定 10×6 布局，所有 60 个砖节点在 Scene JSON 中显式存在（可由工具从第 3.4 节公式生成 JSON，但生成结果即创作数据，运行时不再做随机排布）。不规定、不需要连通性/随机出生约束。

## 8. 节奏与空间安排

- **上部高密度（砖阵区 y104–298）**：60 块砖密排成 6 行，是视觉与碰撞的密集带，球进入后短程连续反弹、碎音成片，形成对局高点。
- **下部开放（反应区 y298–432，高 134）**：刻意留出的安静矩形，是玩家的观察与操控空间；球每次离开砖阵进入该区，节奏从"连续碎击"切换为"一次判断 + 一次接球"，再接回上部——单局节奏由这两个区域的交替天然构成。
- **危险边界（y432–480，仅 48）**：挡板与死亡线之间距离很短，漏接发生在一个狭窄条带内，保证失误反馈明确但不提前给玩家压迫感（死亡线常态近乎不可见，ART_DIRECTION 6.5）。
- 无遭遇、无敌人、无强度事件编排；节奏完全由空间密度分区与球路决定。

## 9. 交付下游的 Scene 数据需求

Scene JSON（`scene-2d`，内容阶段创建于 `content/scenes/`）至少包含：

| 节点 | semantic | 组件 |
|---|---|---|
| `camera` | — | `camera`（参数同第 5.1 节草稿，终值随内容阶段） |
| `wall-top` / `wall-left` / `wall-right` | `wall` | `box-collider-2d`（尺寸/位置按第 3.1 节）+ `sprite-renderer` |
| `death-line` | `death-line` | `box-collider-2d`（isTrigger:true，厚 4，横贯 x80–880） |
| `paddle` | `paddle` | `box-collider-2d`（96×16）、`sprite-renderer`；`behaviors`：paddle 运动类（kind 终值按 TECHNICAL_DESIGN） |
| `ball` | `ball` | `circle-collider-2d`（radius 5）、`sprite-renderer`；`behaviors`：ball 运动类 |
| `brick-r{1..6}-c{1..10}`，共 60 个 | `brick` | `box-collider-2d`（72×24）+ `sprite-renderer`；位置按 3.4 公式 |

- 各节点 `enabled:true`；碎砖由运行时设置节点 enabled/disabled（销毁即禁用），重开时全部恢复。
- 砖块 sprite 可引用同一图集的不同 frame（行间暖色差异），但 frame 引用是素材决策（ASSET_PLAN / ART_DIRECTION），几何不随之变化。
- 节点层级建议：背景与墙为根级，砖阵可挂在一个空父节点 `bricks` 下（父节点仅组织层级，不加 collider），`paddle`/`ball`/`death-line` 为根级，便于运行时按 semantic 检索。
