## 2. 运行时总体选型

### 2.1 React 单页应用

- 交付形态为 React 单页应用（SPA），静态资源可直接部署到任意静态托管；构建工具建议 Vite（dev server 与打包基线），语言使用 TypeScript。该建议不构成对内容契约的偏离。
- 职责分层：
  - **React 层**：应用外壳、界面挂载与切换、标题/暂停/结算等屏幕、HUD 数据展示；
  - **模拟层（simulation）**：游戏循环、固定步推进、碰撞结算，放在不依赖 React 的独立模块中，**不把逐帧变化的球/挡板位置放进 React state / props**，避免每帧重渲染；
  - **内容层**：`content/index.json` 与各 Scene/UI/VFX 文档的解析、缓存与类型化访问；
  - **服务层**：输入、持久化、音频网关。
- React 与模拟层之间通过一个轻量 store / 事件订阅交换**低频状态快照**（分数、生命数、游戏状态、最高分），HUD 订阅快照更新；高频坐标只存在于模拟层并直接绘制。

### 2.2 2D 渲染方案：Canvas 2D（世界）+ DOM（UI）

**明确推荐：世界渲染使用 Canvas 2D（`CanvasRenderingContext2D`），屏幕 UI 使用 React 输出的 DOM。** 不使用 WebGL 作为首版基线。

理由：

1. **对象数量级极小**：一张满砖阵（几十块砖，量级 < 100）、单球、单挡板、少量静态墙。这是 Canvas 2D 在低端移动设备上也能稳定 60fps 的负载，无任何性能压力（见第 11 节）。
2. **与内容契约的消费直接对应**：契约的 atlas 加载规则要求"按共享图源的区域解码 frame、复用已解码源、不复制像素"。在 Canvas 2D 下这正是一次 `drawImage(atlasImage, sx, sy, sw, sh, dx, dy, dw, dh)` 区域绘制，frame 矩形到 API 参数为 1:1 映射，不需要构建 UV 缓冲、着色器与材质缓存，实现与验证都最简单。
3. **没有需要 WebGL 的表现需求**：无光照、无 3D、无大规模粒子；碎砖表现即使使用 `particle-system` 数据，也可作为少量带 atlas frame 的四边形/动画帧在 Canvas 2D 呈现。
4. WebGL 会引入着色器、上下文丢失（context loss）、更多移动兼容分支，对本项目零玩法收益。若后续美术/VFX 文档提出超出本基线的着色器或粒子需求，再按第 12 节的触发条件评估迁移，不在当前批次预埋复杂度。

UI 侧：运行时提供一个 UI 文档渲染器，消费 `ui-screen` / `ui-hud` / `ui-flow` 文档，按内容契约的 anchor / pivot / stretch / container 规则计算几何并输出 DOM 元素与 CSS。**CSS 只承担绘制外观（颜色、字体、圆角等 `style` 字段映射），不承担第二套布局**——几何必须来自契约公式与 `layout` 数据（契约 `runtimeConsumption.responsive` 明确禁止用第二套布局替换创作数据）。绘制顺序、disabled 子树抑制等同样遵循契约，不自造规则。

Canvas 的 backing store 按容器 CSS 尺寸 × `devicePixelRatio` 分配（DPR 设上限，见第 11 节），绘制坐标仍为设计逻辑像素。

### 2.3 游戏循环：帧率无关的固定时间步进

GDD 要求"结果不因帧率变化而改变销毁集合"。采用经典 **fixed timestep + accumulator** 方案：

1. 每一渲染帧由 `requestAnimationFrame` 驱动，取 `performance.now()` 时间戳；
2. 帧间隔先做钳制（clamp，建议上限约 100ms），防止切后台返回或卡顿后一次补发巨量步进（spiral of death）；
3. 帧间隔累加到 accumulator，模拟层按**固定步长 `dt`** 逐步推进，直到 accumulator 不足一个 `dt`；每帧步进数设置上限；
4. 所有积分式只使用固定 `dt`：`position += velocity * dt`。因此在 60Hz / 120Hz / 其他刷新率下，单位真实时间内的模拟结果一致——变化的只是每帧执行几个步进，玩家可观测结果（反弹、销毁集合、计分、死亡判定）不随帧率变化；
5. 渲染可在相邻两个物理状态之间按 accumulator 余数做插值，仅用于视觉平滑；插值不参与任何判定，不改变销毁集合。

`dt` 基线建议 1/120 秒，**最终值留待原型阶段结合数值平衡文档给出的球速确认**（需保证与第 12 节的隧穿对策共同满足判定精度）。任何加速曲线（若数值文档规定球随时间加速）也只改变速度参数，步进模型不变，保证规则对帧率一致可重复。

覆盖层（暂停、结算）显示期间模拟冻结，不推进 accumulator 的有效模拟时间；覆盖层关闭前的输入不排队、不补执行（与 GDD 5.2 一致）。

### 2.4 固定步内的碰撞结算顺序（以可观测结果描述）

模拟层实现自定义的确定性 2D 碰撞结算（不依赖外部物理引擎，见第 5 节对 collider 数据的消费）。**一次结算（一个固定步）必须产出下列可观测结果，实现细节可不同，结果必须稳定一致：**

1. 先按 `dt` 对球做运动积分；
2. 求本步内球与墙 / 挡板 / 砖块的接触：反弹方向按**最先接触的碰撞面**确定；挡板击球时按击中挡板的水平位置决定反弹角度（GDD 5.1）；
3. 本步接触到的砖块**全部予以销毁并逐块计分**——同一次结算多砖全部销毁，不得只销毁其中一部分；
4. **在该次结算的末尾**才检查球是否越过底部死亡线。因此同一结算内最后一块砖被击碎且球越过死亡线时，判定为**关卡完成**（消除优先于漏接，GDD 5.2）；
5. 生命、分数、砖块数量的变化在当次结算立即生效，HUD 即时反映；
6. 状态转移当刻起丢弃旧状态输入：暂停生效后该帧移动/发球输入丢弃；漏接判定后球立即停止受挡板影响。

接触次序的确定性排序规则属于实现细节（建议按扫描接触时刻排序、并列时刻使用固定的法线优先级 tie-break），但必须在原型中用角落同时接触用例验证其帧率无关性（第 12 节风险 2）。

## 3. 坐标系与数据契约（引用，不复制第二份规则表）

本节只声明本项目**使用哪些契约规定、由谁在数据里填实际值**。坐标、层级组合、旋转、pivot、stretch、绘制顺序等全部规则以内容契约原文为唯一权威：`.beegame/delivery/content-format.json` 中的 `coordinates`、`rectTransform`、`uiPaint`、`sceneVocabulary`、`uiLayoutContract` 等节。禁止在本文或代码中另建一份规则表。

### 3.1 2D Scene 坐标

- 采用契约 `coordinates.scene2d`：**top-left 原点，+X 向右，+Y 向下，距离为逻辑像素**；`pixelsPerUnit` 仅用于像素与引擎单位换算，创作位置绝不被乘两次。
- **Z 仅用于深度/排序**（结合 `zIndex` / `layer`），不是屏幕偏移；同级后绘制的节点覆盖先绘制的节点。
- Transform 为父节点局部坐标，按 `parent * translation * rotation * scale` 精确组合一次；所有持久化旋转角为弧度，2D 平面正角为顺时针。
- 场景 `data.settings.coordinateSystem`（`origin: "top-left"`、`units: "logical-pixels"`、`width`/`height`、`pixelsPerUnit`）的实际数值由场景文档填写。

### 3.2 正交相机

2D 相机必须为正交相机，相机组件按契约 `sceneVocabulary.requiredData.camera` 声明：

- `orthographic: true`；
- `coordinateSpace: "logical-pixels"`；
- `orthographicSize`：世界单位下的半高，与可视逻辑像素高度的关系遵循契约公式（`2 * orthographicSize * pixelsPerUnit`）；它是参考半高，不是场地高度；
- `viewport.width` / `viewport.height`：参考宽高比；
- `framing`：在 `keep-height | keep-width | expand | letterbox` 中选择，本项目基线推荐 **`letterbox`**，理由见第 10.1 节；
- `nearClip` / `farClip` 可选。

相机实际参数值由场景文档在相机节点上给出；运行时不把取景适配变成对世界变换的缩放或第二套布局。

### 3.3 UI 坐标

- 遵循契约 `coordinates.ui` 与 `uiLayoutContract`：屏幕 UI 使用 **top-left 逻辑像素**，与场景维度无关；根的 `referenceResolution` 是设计参考而非宿主窗口固定尺寸，屏幕根解析到实际 viewport。
- anchor / pivot 为 `[x,y]` 归一化坐标，`[0,0]` 左上、`[1,1]` 右下；`layout.position` 是相对 anchor 的父局部偏移；子节点 pivot 默认与 anchor 相同，`data.anchor` 仅覆盖 pivot；拉伸须成对提供 `anchorMin`/`anchorMax` + `sizeDelta`；嵌套 DOM 使用局部坐标，绝不使用已累加的世界坐标。
- 各 UI 文档的 `targetViewports`、`minimumControlSize`、响应式变体由 UI/UX 文档拥有并在数据中声明。

## 4. 内容加载架构

### 4.1 入口：content/index.json

- 运行时首先获取并解析 `content/index.json`，其 schema 为 **`beegame-content-package.v2`**，`dimension: "2d"`、`sceneModel: "game-object-v2"`、`entryScene` 指向入口场景文档。
- `documents` 是运行时加载注册表：每个文档以稳定 `id` + `path`（相对 `content/`）+ `kind` + `loadPhase` 登记，**文档 ID → 路径的解析只此一处**；运行时持有 ID→文档的缓存，后续一律按 ID 取用，不在代码里写死文件路径。
- 契约 `runtimeConsumption.authority`：解析字段却不在运行时使用，不满足契约；"解析了"不等于"消费了"。

### 4.2 startup 与 on-demand 阶段划分建议

首版文档数量少，划分建议如下（最终登记以内容批次产出的 index 为准）：

| loadPhase | 文档 | 理由 |
|---|---|---|
| `startup` | 入口游戏场景（`scene-2d`，`entryScene`）、标题界面（`ui-screen`）、游戏内 HUD（`ui-hud`） | 第一个可交互帧所必需：标题界面要展示最高分，进入对局即需要完整场景与 HUD |
| `startup`（可随主包） | 暂停菜单、关卡完成结算、游戏结束结算等覆盖层 UI | 体积极小且对局中随时可能进入；随主包可避免对局中出现网络等待，也简化状态机 |
| `on-demand` | VFX 文档（碎砖等特效） | 仅在实际需要时拉取；如需预热，可在 Title/Ready 阶段空闲时提前获取，但不预取无关特效组 |

契约要求 startup 文档优先获取，on-demand 文档只在游戏进入/需要时获取。旋转/尺寸提示页为应用必备界面（见第 10 节），其 UI 数据应随 startup 可用。

### 4.3 asset-manifest 与 atlas 加载

- **`assets/asset-manifest.json` 是所有资源的权威清单**；文档中的每个 `assetRef` 必须在 `assetRefs` 中列出一次并解析到已验证的 Manifest 资源；场景节点不直接持有资源路径，仅契约 `assetComponentTypes` 所列组件类型可持有 `component.assetRef`，多文件资源用 `data.member` 指定精确文件。
- Atlas 严格遵循契约 `runtimeConsumption.atlasLoading`：**frame 是共享图源上的区域，不单独 fetch / decode 成图片**；按解析 URL 复用在途加载与已解码源，使用期间由渲染器缓存持有，全部消费者用完后释放；不为同一用途同时加载打包图与原图，不预加载无关 atlas 组；区域视图可有独立 UV/裁剪状态而不复制像素。在 Canvas 2D 下即"解码一次图集大图，frame 按源矩形反复 `drawImage`"。
- 不保证 draw-call 合批（契约亦不要求）；禁止文件名猜测，frame 名大小写精确且必须实际存在于图集数据中。

### 4.4 数据消费的验证义务（义务声明，非已完成事项）

- 契约 `runtimeConsumption.verification` 与 `checks` 是运行时必须履行的验证义务：在临时副本或拦截的测试响应中改动创作数据（节点位置/尺寸、砖块 transform、资源/frame 引用、文本等），**不改动布局代码**，对比改动前后的目标运行时结果，再恢复原数据；无变化或错误变化即绑定失败；无法观测目标运行时必须报"未验证"。
- 对应到本项目至少覆盖：
  - `scene-layout`：改 Scene JSON 中砖块/挡板 transform（含层级），运行时对象实际位置随之改变；
  - `ui-layout`：改 UI 节点位置/尺寸（含父级 anchor 与适用的响应式变体），实际运行时几何改变；在各目标 viewport 下控件与覆盖层完整在屏；
  - `resource-binding`：改资源/frame 引用，实际绘制出的素材改变（真实解码，HTTP 200 或文件名不算数）。
- **本批次没有任何运行时实现，以上全部为未验证状态；本文不声称任何运行时检查已完成。**

## 5. 场景数据所有权与玩法行为

- GDD 第 6 节规定：砖块布局（行列、间距、场地位置）与挡板、球的初始摆放在 Scene JSON 中创作，运行时加载呈现，不在代码常量中固化。运行时必须消费节点层级、`enabled`、局部 transform 与渲染/碰撞组件，而不是把场景当成一张参数表后另建硬编码场景（契约 `runtimeConsumption.scene`）。
- 身份标记：玩法身份写入 **`node.semantic`**，首版使用 `paddle` / `ball` / `brick`，另需 `wall`（刚性墙）与 `death-line`（底部死亡线，建议为 trigger）语义；语义清单随场景批次定稿。
- 碰撞体组件：挡板、砖块、墙、死亡线使用 **`box-collider-2d`**（`size` / `offset` / `isTrigger`），球使用 **`circle-collider-2d`**（`radius` / `offset` / `isTrigger`）。运行时的自定义确定性模拟直接读取这些 collider 做结算；本规模下无需外部物理引擎，默认**不创作 `rigidbody-2d`**（若原型证明确有需要再引入，且不得与 2D collider 体系混用冲突）。
- 玩法行为一律写入 **`node.data.behaviors`**：每条含稳定 `id`、`kind` 与 `config`。`kind` 是由运行时拥有的开放玩法行为词汇（运行时维护 behavior registry 按 kind 装配行为，config 传入数据）；预计需要的最小集合（暂定，场景批次定稿）：挡板控制类（如 `paddle-motion`）、球运动类（如 `ball-motion`）；砖块/墙/死亡线以 semantic + collider 表达即可，不强行加行为。
- 遇到未注册 kind 属于数据/版本不匹配，**加载期显式报错（fail loud）**，不得静默忽略。
- **禁止添加 `script` / `MonoBehaviour` 类组件或 `scriptId` 字段**（契约明文规定）；行为逻辑只能存在于运行时代码 + `behaviors` 数据，创作数据不承载可执行脚本。

## 6. 共享调参

- 分值、初始生命数、球速、反弹角度约束、水平速度分量下限、加速曲线、死亡线判定容差等**全部可调数值由数值平衡文档唯一拥有**（GDD 2.3 / 5.3 / 第 9 节）；本文不维护参数表，代码中**不得硬编码**这些数值。
- 机器可读载体：使用一个**项目自有、位于 `content/` 之外的 JSON 文件**，基线路径建议 **`config/tuning.json`**（契约 `rules` 允许这种项目自有 JSON，且不允许发明未登记的 content 文档种类）。模拟层启动时加载该文件，注入行为与碰撞结算。
- 权责关系：数值平衡文档是数值权威，`config/tuning.json` 是它在工程中的**单一机器可读投影**（手工维护或由数值文档流程生成都可，但不得在场景/代码里出现第二份副本）；技术侧只定义加载与注入方式，不决定数值。加载失败或字段缺失时，启动期显式报错，不以代码默认值静默兜底。

## 7. 输入集成

三种输入方式在接入层归一化后交给模拟层；**具体按键清单、触控热区、焦点行为以交互契约文档为权威**（GDD 第 3 节），冲突时以该文档为准。

1. **鼠标 / 指针移动 → 挡板 X**：监听游戏区域的 `pointermove`，取 `clientX`，经画布 bounding rect 与**相机取景的逆变换**（letterbox 的缩放与留白必须计入）映射为世界逻辑像素 X，再按挡板半宽与场地左右边界钳制。鼠标与触控共用同一条"指针坐标 → 世界 X"路径，不各写一套映射。
2. **键盘按住**：`keydown` / `keyup` 维护按下状态集合；每个固定步内按 `速度 * dt` 持续移动挡板（左右取净值）。具体键位（方向键 / A/D / Esc / P / 空格 / 回车等）以交互契约为准；运行时只负责状态采集与固定步消费。
3. **触控拖动**：统一使用 Pointer Events；游戏区域容器设置 `touch-action: none`，对触摸相关事件（`touchstart`/`touchmove` 等按需，使用非 passive 监听）`preventDefault()` 以阻止页面滚动、缩放下拉等默认行为；触点 X 的映射与鼠标完全相同。
4. **指针捕获**：在游戏区域按下/开始拖动时对该元素调用 `setPointerCapture`，使指针移出区域甚至移出窗口后仍持续收到移动事件，`pointerup`/`pointercancel` 时释放；这样挡板不会因手指滑出边界而失控。
5. **发球：边沿触发一次**。发球只在 Ready 状态有效，按 GDD 4.2 在**输入释放边沿**触发，单次消费，长按不连发；状态非 Ready 时该输入直接忽略。暂停及覆盖层显示期间，移动与发球输入无效且不排队。
6. 界面按钮（暂停按钮、结算按钮等）由 UI DOM 层按 `actions` 数据响应点按；覆盖层上的点按是冻结期间唯一允许生效的输入类别（GDD 5.2）。

## 8. 持久化

- 首版唯一持久化内容为**本地最高分**（GDD 2.3），使用 `localStorage`。
- 键名（含命名空间与版本）：**`breakout:highscore:v1`**。
- 序列化格式：单个 JSON 对象，如 `{"version":1,"highScore":0}`；写入用单次 `setItem` 完成。
- 读取容错：
  - `try/catch` 包裹读取与 `JSON.parse`；键不存在、JSON 损坏、字段类型不符、数值为负 / 非有限数 / 非整数时，一律视为无记录，回退为 `0`，不阻断游戏启动；
  - 写入同样 `try/catch`（隐私模式、配额满、存储被禁用时可能抛错），写入失败只影响持久化、不影响当局流程。
- 更新时机遵循 GDD：仅在单局结束（胜利或失败）且当局得分超过已保存最高分时更新；清除浏览器数据导致丢失属预期行为。

## 9. 音频接入

- 音频方案为 **Web Audio API**：全局共享一个 `AudioContext`（懒创建），音效以 `AudioBuffer` 一次性解码后播放 one-shot，事件名、音源、音量与混音由音频设计文档拥有；本文只定义对接边界。
- **手势解锁**：浏览器 autoplay 策略禁止手势前发声。`AudioContext` 在首次用户手势（首次 pointerdown / keydown）时创建或调用 `resume()`，状态变为 `running` 前不调度任何声音；每次手势可幂等尝试 resume。iframe 承载时还可能受宿主 Permissions-Policy 约束（见第 12 节风险 4）。
- 与内容数据的边界：场景中 **`audio-source`** 组件（持有 `assetRef`，属于契约 `assetComponentTypes`）按 Manifest 解析音源；玩法代码不直接引用音频文件名。
- 与玩法的边界：模拟层只发出**领域事件**（暂定：`serve`、`bounce-wall`、`bounce-paddle`、`brick-destroyed`、`life-lost`、`win`、`lose`、界面类事件等，最终名称与映射以音频文档为准）；音频网关订阅事件总线，把事件映射为音源播放。事件总线不得反向影响玩法结果（无声/解码失败不改变游戏状态）。
- 并发注意：碎砖可能在一次结算中连续触发多个同音 one-shot，需设并发声部上限并对极短间隔内的同音事件做节流/声部回收（建议量级见第 11 节），避免瞬时创建大量 AudioNode。

## 10. 响应式与屏幕方向

### 10.1 取景策略：letterbox（相机）与 UI 适配（DOM）分离

- **世界相机推荐 `framing: "letterbox"`**：在任意横屏宽高比下完整呈现创作参考视口，超出比例的部分留黑边/装饰边，不裁剪任何一侧。理由：打砖块的顶/左/右刚性墙与底部死亡线必须**全部同时可见**，裁剪任何一侧都会直接改变玩法可读性；`keep-height` / `keep-width` 会在比例变化时裁掉场地，`expand` 会露出未经创作的世界区域（固定墙之外没有可看的内容）。因此以"完整、不裁、不变形"为最高优先级，代价（留白）由背景美术在安全区外吸收。
- 取景适配**只改变呈现**：世界 transform、collider、砖块布局不被缩放或移位（契约 `sceneVocabulary.viewportAdaptation`）。
- **屏幕 UI 适配是独立通道**：UI 根解析到实际宿主 viewport，按契约 anchor/pivot/stretch 与（由 UI 文档声明的）compact 等响应式变体适配；两条通道不混用，UI 不跟随相机缩放，相机也不读取 UI 布局。
- 首版仅横屏，不做竖屏重排（GDD 第 7 节）。

### 10.2 竖屏 / 尺寸不足：提示页

- 运行时持续检查容器方向与可用空间（`resize` / `orientationchange` / `matchMedia("(orientation: landscape)")`）。当设备为竖屏，或可用横屏空间低于最小可用尺寸时：显示"请旋转设备至横屏 / 窗口尺寸不足"**提示页**，游戏不开始、不强制重排；恢复到可用横屏空间后可继续进入游戏。
- 判定阈值的工程表达（如何把宿主 CSS 像素与 800×450 设计坐标对应、DPR 如何计入）属于 UI/UX 文档的 `targetViewports` 范畴，本文只规定行为：**提示页而非重排**；阈值最终值在 UI 文档产出后补入。

## 11. 性能与可行性硬约束（给设计师的约束）

以下为基线硬约束，场景/UI/音频创作必须在此之内：

1. **同屏对象数量级**：一张满砖阵——**几十块砖（量级 < 100，建议场景创作上限 120 块）+ 单球 + 单挡板 + 少量静态墙**。此规模下 Canvas 2D 无性能风险，不需要对象池之外的优化；不要引入移动砖、多球等超出 GDD 范围的内容。
2. **纹理与图集**：
   - 格式：风格化 sprite 优先 PNG（无损 + alpha）；确有体积收益时可用 WebP 但须保留 PNG 降级；不使用无广泛支持的格式；
   - 图集打包**不使用旋转帧、不使用 trim**（契约明文不支持 rotated/trimmed frame），frame 必须完整落在图源内；
   - 单张图集边长建议 ≤ 2048×2048（移动设备解码内存安全线），避免 4096；首版图集数量控制在个位数；
   - 建议按设计逻辑像素的 2 倍出图以保证 Retina 清晰，运行时按逻辑尺寸绘制；Canvas DPR 上限取 2（仅在实测内存/帧率允许后再考虑放宽到 3）。
3. **字体**：实际字体文件需在 Manifest 注册（建议 woff2）；HUD 数字必须按契约 `textFit` 用真实字体度量最大可能分值后再定文本框，不靠运行时缩字救场。
4. **音频并发**：`AudioContext` 全局唯一；建议同时发声声部上限 8（最多不超过 16），同音 one-shot 在约 30–50ms 内节流，超出上限时回收最旧/最轻的声部；所有 SFX 预解码为 `AudioBuffer`，不边播边 fetch。
5. **帧预算**：以 60fps 为目标（帧预算约 16.7ms）；当前负载远离瓶颈，任何新增表现需求必须先核对本节约束。

| # | 风险 | 对策方向 |
|---|---|---|
| 1 | **高速球隧穿（tunneling）**：球在一个步长内跨越薄砖，离散点检测漏判 | 使用连续碰撞检测：运动段（swept circle / segment）对 AABB 求本步精确进入时刻；必要时把单步运动再细分为子步（子步内移动量小于砖厚/球半径的固定比例）；不允许用"提高帧率"替代算法；原型验证销毁集合帧率无关 |
