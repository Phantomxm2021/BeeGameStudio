## 1. 目的与边界

本文档建立首版打砖块的技术基线：运行时栈、内容数据契约、加载能力、作者侧硬约束、输入与音频的统一消费方式。

基线来源**仅有**两类，本文档不超出它们：

1. 已确认平台：Web 浏览器、React、2D、仅横屏、键盘/鼠标 + 触屏；
2. `docs/GDD.md` 所确立的玩家可见行为。

本文档不重述、不修改 GDD 的玩法结论；不规定任何平衡数值（球速、挡板宽度、阵列规模、生命数、分值等一律以《数值平衡文档》为准）；不替代 Scene/UI 作者的摆位与布局决策。GDD 第 6 节声明"只定义玩家可观察的规则结果，不规定实现算法"，本文档给出实现取向，但任何实现结果若与 GDD 可观察规则冲突，以 GDD 为准。

本批次为初稿，运行时过渡细节、最终矩形等在最后一个作者批次补全（见第 9 节）。

## 2. 运行时栈与渲染

### 2.1 技术栈

- 宿主：现代 Web 浏览器；应用框架：React（用于应用装配、屏幕流转、UI 组件树与生命周期）。
- 无服务端玩法依赖；首版无联网、无跨会话持久化（GDD 2.2）。

### 2.2 2D 渲染方式的选择原则

游戏世界（挡板、球、砖块阵列、场地）与屏幕 UI 采用不同的渲染策略，按"谁最适合该职责"选择，而非全栈单一方案：

- **世界层：Canvas 2D（`<canvas>` + `CanvasRenderingContext2D`）为默认选择。** 理由：场上存在一颗每帧持续运动的球与可能整屏的砖块，命中后需要立即重绘；Canvas 逐帧绘制开销可预期，且不产生与运动对象数量同阶的 DOM 节点。世界层由一个（或按前后景分离的少量）画布承担，React 拥有画布节点与装配，绘制在 React 渲染之外的帧循环中进行，避免每帧走 React 协调。
- **屏幕 UI 层：DOM/React。** 菜单、HUD、暂停、结算、横屏/空间不足提示等以 DOM 呈现，天然获得文本排版、可聚焦性、键盘 Tab 顺序、按钮语义与无障碍基础。UI 的几何位置不由 CSS 自由排版发明，而由 UI JSON 的 `layout`（锚点/枢轴/拉伸/容器）解析得到（见第 4 节）。
- **例外原则：** 若某 UI 元素必须与世界逐帧同绘（如附着在球上的标识），才进入画布；反之，静态世界装饰也不因"在世界里"就必须进画布。判定标准是更新频率与坐标空间，不是视觉类别。首版内容简单，预计不触发例外。

### 2.3 帧循环与时间推进

- 以 `requestAnimationFrame` 驱动绘制与逻辑推进；标签页不可见时 RAF 自动暂停，恢复后按恢复时刻继续，不补发积压运动（与 GDD 6.3"不补发暂停期间积压输入"的取向一致）。
- 逻辑推进取向：**固定逻辑步长（fixed timestep）累加器 + 单帧内 0..N 次定步更新，渲染按累加器剩余量插值（或首版直接取最新逻辑态）**。选固定步长的理由：球的弹射与 GDD 6.2 的同帧多结果判定要求跨设备刷新率结果一致；按帧裸推进会使高刷屏球速翻倍、低刷屏穿透砖块。文档可见性改变（如某设备需要不同步长上限）时在末批次细化；本文档不给步长具体数值——步长是稳定性参数，但其上跑的速度/角度等调值归平衡文档。
- 暂停、结算进入瞬间冻结逻辑更新（GDD 5.2、6.3）；冻结期间不推进、不积分。
- 帧率目标为浏览器默认刷新率下"每帧一次更新+绘制"，不设独立的解锁帧率机制；不承诺 draw-call 批处理（内容契约亦说明图集是加载结果而非批处理保证）。

## 3. 坐标与相机

### 3.1 坐标系（遵循 content-format.json `coordinates`）

- 世界 2D：**原点左上角，+X 向右，+Y 向下，单位为逻辑像素**；`pixelsPerUnit` 仅用于逻辑像素与引擎单位的一次换算，作者摆位绝不被乘两次。
- Transform 位置为父节点局部坐标；父级变换只组合一次；精灵 pivot 只偏移渲染几何，不偏移 GameObject 或其碰撞体。
- 持久化旋转角为弧度；2D 平面内正向旋转为顺时针（y-down）。
- 深度即绘制先后：Z/`zIndex` 表示顺序，不是屏幕位移。

### 3.2 场景取景与屏幕 UI 适配分离

- Scene 的 `coordinateSystem.width/height` 是**作者参考框**，不是地图边界、更不是宿主窗口固定尺寸。
- 2D 相机为正交相机，须声明 `orthographic`、`coordinateSpace`、`orthographicSize`（参考半高，与参考框高度独立）、`viewport`（参考宽高比）与 `framing`（`keep-height | keep-width | expand | letterbox`，缺省 keep-height）。
- 运行时按所选 framing 对实际宿主容器取景：可改变呈现（含有意留黑边），**不改写世界 Transform、不在代码里烘焙第二套布局**。
- 屏幕 UI 走 UI 根的适配（见 3.3），与世界相机取景是两条独立管线；UI 不因世界缩放而被重排。

### 3.3 屏幕 UI 坐标

- 屏幕 UI 同样使用左上角逻辑像素。根 `data.referenceResolution` 是**设计参考分辨率，不是宿主/iframe 固定尺寸**；屏幕空间根解析到实际视口，世界空间 UI 才保留作者根尺寸。
- 锚点/枢轴为归一化 [x,y]：[0,0] 左上、[1,1] 右下；`layout.position` 是相对锚点的父局部偏移；子节点枢轴默认与锚点相同，`data.anchor` 仅覆盖枢轴。
- 拉伸须成对提供 `anchorMin/anchorMax` + `sizeDelta`；流程容器（row/column/grid）拥有子项几何，不与拉伸锚点混用。
- 运行时**不得用 CSS 布局替换作者布局**；作者数据表达不了的适配需求，回到 UI JSON / `uiLayoutContract.responsive`（compact / portrait 变体）解决。
- 根 `data.orientation` 为 Landscape；竖屏主机与低于最小尺寸的主机显示旋转/空间不足提示，而不是另做一套 HUD 排版（GDD 第 8 节）。

## 4. 内容数据契约

### 4.1 唯一可编辑来源

- 作者编写的 **Scene JSON / UI JSON** 是层级、摆位、布局、响应式变体与资源绑定的**唯一可编辑来源**（GDD 第 8 节）。运行时代码加载并消费这些数据，不以代码常量复制作者决策；编译/缓存产物是派生物，不是权威。
- `content/index.json`（schema：`beegame-content-package.v2`，`sceneModel: game-object-v2`，`dimension: 2d`，声明 `entryScene`）把文档 ID 解析到路径：
  - 每个 `files` 条目在 `documents` 中恰好登记一次：`id / path / kind / loadPhase`；
  - `loadPhase: startup` 只给 `entryScene` 与首个可交互帧所需的 UI 文档（预计：开始界面 UI + HUD）；
  - 其余界面与 VFX 标 `on-demand`，进入或需要时才获取。
- 文件路径相对 `content/`；每个被使用的 `assetRef` 在文档 `assetRefs` 中列一次并解析到已验证的 Manifest 资源。

### 4.2 Scene 文档消费要点

- 场景节点全部是 GameObject：禁止 `node.kind`；玩法身份（player/ball/brick/paddle/anchor 等）放 `node.semantic`；渲染、物理、音频、动画、相机能力放 `components`，类型只能取 `sceneVocabulary.componentTypes`，每个组件有与数组顺序无关的稳定 id。
- 运行时须真正消费：节点层级、`enabled`、局部 position/rotation/scale、渲染组件、相机与排序——场景不是一张玩法参数表。运行时可更新状态与 Transform（如挡板横移、球运动、砖块销毁），但不替换作者初始世界。

### 4.3 UI 文档消费要点

- `role` 为闭集，取 `uiVocabulary.roles`，根角色与文档 kind 对应（ui-screen → screen-root，ui-hud → hud-root，ui-flow → flow-root）。
- 资源型角色（image / sprite / nineSlicePanel）必须带 `node.assetRef`；其他角色不得带。
- 绘制顺序：每个启用节点先画背景/边框，再画自身内容，再按文档顺序画子节点；后画的兄弟覆盖先画者；禁用节点抑制整棵子树。
- `bindings/actions` 用于把节点接到游戏状态与意图（如分数文本绑定、发球按钮动作），具体绑定面在 UI 文档落地时确定。

### 4.4 项目自有调值文件

- 共享玩法调值放**项目自有的一个 JSON 文件**（位于 `content/` 之外，由游戏加载），其取值由《数值平衡文档》 authoritative 定义。
- 该文件**不属于 content 注册的文档种类**（注册处只接受 Scene/UI/VFX）；不得把同一批共享值复制进每个场景，也不得为它发明 content 文档类型。
- 本技术文档不预设该文件的最终路径与字段表；预计承载：球速与提速档位、挡板宽度与键盘移动速度、砖块阵列行列/尺寸/间距/边距、初始生命数、各行砖块分值、发球初始角度范围。

## 5. 加载与缓存

### 5.1 清单与图集

- 所有资源经 Manifest 解析，禁止文件名猜测；多文件资源用 `member` 精确定位，图集帧用 `frame` 命名（区分大小写、不带扩展名），以实际图集内容为准。
- **图集帧（atlas frame）是共享图源上的区域选取**，不为每帧单独 fetch/解码；区域视图可有独立 UV 状态而不复制像素。
- 按解析后的 URL **复用在途加载与已解码图源**（使用所选渲染器的缓存）；同一用途不得同时加载打包图与原图；不预载无关图集组。
- 资源**释放原则**：图源归加载器所有，在其全部消费者结束使用后释放；节点/文档卸载时解除引用，由缓存决定回收时机。首版体量小，主要风险是泄漏而非误释放，实现上以"每个解码图源对应可计数引用"为基准。

### 5.2 startup 与 on-demand 划分

- **startup（进入首个可交互帧前）**：`index` 中标记 startup 的文档、开始界面与 HUD 所需资源；完成后即应可进入开始界面（GDD 5.1：资源可用后首先进入 Menu）。
- **on-demand**：进入发球准备/游玩前再取得关卡场景所需剩余文档与资源；结算/暂停等覆盖层在进入相关流程前取得。划分原则：startup 只放"不可推迟否则首屏不成立"的内容，其余全部按需；不借 startup 预载整包。
- 加载失败、资源缺失按显式错误处理（重试或提示），不得以静默回退到代码内置图形的方式"成功"。

## 6. 给美术 / UI 作者的可行性硬约束

以下为本平台在首版**不可协商**的约束，作者数据须在此内成立：

1. **层级与顺序**：2D 无真实厚度；前后关系由节点树 + `zIndex`（及 UI 的文档顺序）决定。建议作者按固定带编排（如：背景 < 砖块 < 球 < 挡板 < 粒子反馈 < 屏幕 UI），具体数值由 Scene/UI 作者在文档中给出，运行时只读取不推断。
2. **碰撞组件可用类型**（取自 `sceneVocabulary`，2D 闭集）：
   - 球：`circle-collider-2d`（`radius`、`offset`、`isTrigger`）；
   - 挡板、砖块、矩形场地边界：`box-collider-2d`（`size`、`offset`、`isTrigger`）；
   - 首版不使用 capsule/polygon collider，不使用 3D collider，不在同一对象混用 2D/3D 刚体。
   - 碰撞体随 GameObject 局部空间定义，pivot 不影响碰撞体位置。
3. **行为配置方式**：玩法行为写 `node.data.behaviors`，每条为 `{ id（节点内稳定唯一）, kind（运行时拥有的开放行为种类）, config }`。**禁止脚本组件 / scriptId / MonoBehaviour 式组件**；作者不写代码，运行时按 kind 注册并执行行为。预计的 kind（命名在实现批次最终确定）只覆盖 GDD 已有角色：挡板横移跟随、球持续运动与弹射、砖块一击即碎、边界（左/右/上弹射、底部失误）、生命/分数记账。
4. **可见物必须有真渲染器**：2D 作者图形用 `sprite-renderer`（带已验证 assetRef）；纯色/标签如需走世界画布才用 canvas + image/text；碰撞体不可见，不能拿碰撞体充当表现。
5. **资源归属**：场景节点不直接持有 assetRef/frameRef；只有资源型组件类型可持 `component.assetRef`，多文件资源以 `data.member` 选定。
6. **触控目标**：可交互区域必须在 UI 文档中有真实节点/action 承载；散文里描述的"更大热区"不是受检几何。控件最小尺寸以根 `minimumControlSize`（最终宿主逻辑像素）为准，值由 UI 文档定义，不是本地 `minSize`、不是平台常量。
7. **调值来源**：作者不把数值散写进节点 config 之外的多处；跨对象共享的数值引用第 4.4 节的项目自有调值 JSON。

## 7. 输入层

GDD 第 4 节的操作表是权威，本节只规定运行时如何**消费**输入，不重定义操作。

### 7.1 意图归一

三类物理输入在输入层被归一为同一组意图，玩法状态机只消费意图、不感知设备：

- `movePaddle(targetX)`：挡板目标横坐标（场地逻辑坐标）；
- `serve()`：发球（仅在发球准备状态有效）；
- `pauseToggle()`：暂停/继续；
- UI 动作：`confirm`（聚焦按钮的确认）、`restart`、`exitToMenu`，由界面按钮/焦点派发。

归一方式：

- **键盘**：左右方向键/A/D 按住产生方向状态，由逻辑步长按平衡文档给的键盘移动速度积分出目标横坐标；空格 → serve（准备态）；P/Esc → pauseToggle；结算/暂停界面走可聚焦按钮的确认。
- **鼠标**：场地内指针横坐标（含挡板区域，不要求指针在挡板上）经"屏幕→世界"逆映射（经第 3.2 节同一相机取景）换算为场地逻辑 x，直接作为 `targetX`；点按发球提示区域 → serve；按钮点击走 DOM。
- **触屏**：触点横坐标同样逆映射为 `targetX`，拖动/按住拖动持续更新；点按场地 → serve；暂停等按钮点按走 DOM。触点与鼠标事件不重复派发同一意图（防止一次触碰产生双份）。

### 7.2 消费规则

- 多设备并存时以**最近一次产生有效输入的设备**为准（GDD 第 4 节），设备切换无额外状态；实现上不维护"当前设备"的玩法分支，只更新同一个 `targetX`。
- 挡板纵向位置固定，`targetX` 被夹到场地左右边界内（GDD 第 4 节）；发球准备态球随挡板摆位（GDD 6.3）。
- 状态门控在意图消费侧：暂停/结算态丢弃 `movePaddle/serve`；仅准备态接受 serve；仅游玩态接受进入暂停（GDD 5.2）。输入层不缓存被门控丢弃的意图，恢复后不补发（GDD 6.3）。
- 屏幕→世界映射必须与实际取景（含 letterbox 留边）一致；留边区域内的指针不映射为场地内移动。

## 8. 音频（技术约束简述）

- 实现可选 HTMLAudio（`Audio` 元素，适合少量一次性音效/背景音乐）或 WebAudio（适合需要程序控制、混音与精确触发时机的音效），由实现批次按 AUDIO_DESIGN 的事件密度选择；首版预计事件种类少（弹射、击碎、失误、过关/失败、界面操作），不预设复杂音频图。
- 技术上须提供：**全局静音开关与音量作用域**（主音量，必要时区分音乐/音效两条总线）；静音状态首版不要求跨会话持久化（与 GDD 无持久化一致）。
- 音频资源同样经 Manifest 注册与解析，遵循第 5 节的加载/缓存原则；浏览器自动播放策略下，首次音频由用户交互（开始操作）解锁。
- 触发时机、事件清单、混音与表现以《AUDIO_DESIGN》为准，本文档不定义其行为。

## 9. 本批次明确不做的事

1. 不发明最终的场景/UI 矩形：不给出挡板/球/砖块的最终坐标、尺寸、阵列边距、HUD 面板矩形——这些是 Scene/UI 作者与平衡文档的决策。
2. 不写死运行时过渡细节：界面切换、过关/失败过渡、发球释放的具体时长与动画曲线不在本批次定义；仅规定"进入暂停/结算即刻冻结"等 GDD 已要求的结果。
3. 不替代 Scene/UI 作者做层级、锚点、变体选择；不在代码中预设第二套布局或内置图形。
4. 不选择与 GDD 不同的玩法结果，不新增 GDD 排除项中的任何内容（道具、多关卡、持久化等）。
5. 不声称已执行任何运行时/视觉检查：本文档不含已验证结果；内容契约要求的数据绑定验证（改动作者数据→目标运行时结果改变）在实现批次按 `runtimeConsumption.verification` 执行，未观测到运行时时按"未验证"报告。
6. 本文档为 v0.1 初稿，**将在最后一个作者批次（5/5）补全**：随 Scene/UI/平衡/音频文档落地后回填最终文件路径、相机 framing 的最终选择、行为 kind 命名表、调值 JSON 的字段契约与加载时序细节。

  - 最小可用设计尺寸（GDD 第 8 节）、各界面节点/action 与焦点顺序。
- **数值平衡文档**：第 4.4 节项目自有调值 JSON 的字段与全部数值（球速/提速、挡板宽度与键盘速度、阵列参数、生命、分值、发球角度范围）。
- **美术文档 / 资源管线**：全部美术与音频资源在 Manifest（`assets/asset-manifest.json`）注册并可解析；图集与其帧名实际存在；文档 `assetRefs` 与之一致。
- **AUDIO_DESIGN**：音频事件、触发、混音方案，决定 HTMLAudio/WebAudio 的最终取舍。
