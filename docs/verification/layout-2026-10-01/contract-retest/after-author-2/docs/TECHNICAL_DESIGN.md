## 1. 文档目的、边界与批次状态

本文档说明运行时**如何消费** GDD 确立的玩法规则与作者编写的 Scene/UI 数据，建立必要的技术基线，使后续 Scene、UI/UX、Balance、Asset 批次有可对接的运行时约定。

边界纪律：

- **玩法规则只引用、不复述**：挡板/球/砖块行为、碰撞裁决、胜负与计分、状态流转等玩家可见规则一律以 GDD 相应章节（§3–§7）为权威；本文档不复制规则、不重复参数表，也不得选择与 GDD 不同的结果。
- **数值不决定**：速度、尺寸、行列数、生命数、角度范围等以 Balance 文档为权威；本文档只规定数值以何种单位、何种方式被运行时消费。
- **版面不决定**：场地与 UI 的具体矩形、节点布局以作者编写的 Scene/UI JSON 为唯一可编辑源（GDD §1.3）；运行时不得以代码常量或第二套布局取代。
- 本文档为批次 2/5 草稿，最终场景/UI 矩形、过渡时序、性能预算终值等待后续批次输入后，在末批次补完与签发。

本批次未执行任何运行时实现、性能测量或视觉检查；文中不含此类结果。

## 2. 平台基线与总体架构（运行时形态）

### 2.1 React Web 应用的组织

交付物为一个浏览器内运行的 React Web 应用，建议的逻辑分层如下（描述职责，不规定最终目录与构建工具）：

1. **引导层（Bootstrap）**：解析 `content/index.json`，按 loadPhase 加载文档与资源，驱动 GDD §7 的 Loading → Start 流程。
2. **内容层（Content Registry）**：持有解析后的 Scene/UI 文档与 Manifest 资源映射，提供按文档 ID / 节点 ID / assetRef 查询的只读接口；是作者化数据在运行时的唯一入口。
3. **资源层（Asset Cache）**：图片解码源、atlas 帧区域视图、音频解码缓冲的加载与缓存（见 §5）。
4. **游戏引擎层（Game Engine，框架无关的 TS/JS 模块）**：实体状态、运动模拟、碰撞检测、游戏状态机；由 `requestAnimationFrame` 循环驱动。
5. **输入层（Input Router）**：键盘、鼠标、触控统一抽象为意图，并按当前游戏状态做合法性路由（见 §6、§7）。
6. **表现层（React + Canvas）**：Canvas 承载场内世界；React 承载 HUD 与全部界面流程（见 §2.3）。

### 2.2 渲染循环与 React 的关系

- 高频的场内模拟与绘制运行在 React 渲染模型**之外**：引擎持有可变的世界状态（普通对象/类型化数据），每帧由 rAF 回调更新并重绘 Canvas。**不得**把球/挡板的逐帧位置放入 React state 或 props，避免每帧触发协调（reconciliation）。
- React 负责低频、离散的界面状态：当前游戏状态（GDD §7）、分数、剩余生命、最高分、"新纪录"标记、界面/弹层的显隐。引擎通过轻量订阅接口（观察者/store）在**离散事件点**（计分、扣命、状态转移）推送快照，React 据此重渲染 HUD 与界面。
- 数据流方向单一：作者化数据 → 引擎消费；引擎事件 → React 快照；界面操作 → 输入层动作 → 状态机。React 组件不直接修改场内实体。

### 2.3 2D 渲染方式：Canvas 2D（场内）+ DOM/React（界面）

基线选择：

- **场内世界（球、挡板、砖块、场地表现及场内特效）使用 Canvas 2D 绘制**。理由：对象位置逐帧变化、数量可控但更新连续，命令式绘制可避免 React 每帧协调；Canvas 2D 可直接按 atlas 帧矩形（源图像素区域）绘制缩放精灵，满足内容契约对资源绑定与帧消费的要求。
- **HUD、开始/暂停/结算界面与旋转提示页使用 DOM（React 组件）呈现**，由 UI 文档驱动。理由：文本、按钮、可访问性、焦点管理与触控命中区是 DOM 的固有能力；锚点/拉伸/流式布局按 `uiLayoutContract` 解析后映射为 DOM 几何。
- 合成顺序：Canvas 世界层在下，DOM 界面层在上；暂停/结算等弹层为覆盖 Canvas 的 DOM 层，并负责截留该层出现期间的指针事件。

美术方向纪律：选择 Canvas 2D 是**架构**选择，不是视觉风格选择。运行时必须支持美术文档定义的贴图精灵、atlas 帧动画与特效表现；不得以"纯色矩形便宜好画"为由把美术方向降格为几何色块。任何纯色块只能作为开发期占位，不得作为验收视觉。

本批次不排除实现阶段在有证据时改用 WebGL 渲染器；但切换不得改变 §2.2 的循环边界与上述消费契约。

## 3. 运动更新与碰撞检测原则

GDD 要求球发出后持续匀速运动、不加速（GDD §3.2），且任何情况下不得穿墙穿砖（GDD §5.2 规则 4）。本节规定更新原则，不规定最终碰撞算法。

### 3.1 模拟与渲染解耦：固定步长基线

- 运动模拟以**时间**驱动，不以帧数驱动：实体位移 = 速度 × 实际经过时间，速度单位为"设计逻辑像素/秒"（设计坐标见 §4.2）。渲染刷新率（30/60/120Hz 显示器）不得改变球的观察速度。
- 基线采用**固定时长模拟步长 + 时间累加器**：rAF 每帧获得真实帧时 `dt`，累加后以固定步长 `h` 推进若干次模拟；剩余时间不丢弃（可用于渲染插值，插值非首版强制）。
- 累加的帧时必须**设上限（clamp）**：标签页切回、调试断点、卡顿后的超大 `dt` 不得一次性推进大量步长，避免"死亡螺旋"与行为异常；该情形下宁可短暂时钟滞后（并参见 §3.4 的自动暂停基线）。
- 固定步长的具体取值（以及"固定步长累加"与"可变帧时直接积分"的最终取舍）在末批次结合碰撞测试确定；无论选哪种，必须满足 §3.2、§3.3 的结果要求。

### 3.2 匀速保证

- 球速为标量常量（方向可变、大小不变；取值由 Balance 定义），模拟中不得因帧率、剩余砖块数、对局时长改变。
- 挡板反弹（GDD §5.1）只改方向：由击中水平位置映射出射方向，出射速度大小与入射一致。
- Ready 期间球附着于挡板上方的偏移为固定设计偏移；发球以输入被接受的瞬间为界（GDD §5.3），此后挡板移动与球无关。

### 3.3 不漏碰撞：连续检测需求与 GDD §5 裁决顺序

离散地检测"终点位置是否重叠"在高速或低帧时会漏碰撞（隧道效应），不满足 GDD §5.2 规则 4。碰撞方案必须满足以下**结果要求**，最终算法（扫掠体/线段扫掠、保证步内位移小于最小特征尺寸的子步进、连续求交等）不在本批次裁定：

1. 碰撞判定必须覆盖球在**一次位移内的完整运动区间**（上一位置到当前位置），而非仅终点采样；最坏情形以可接受的最低帧率 + Balance 球速验证不穿墙、不穿砖。
2. 同一位移内的多对象裁决严格按 GDD §5.2 的可观察顺序落地：
   - 先判定该位移中球是否**整体越过底线**：成立则漏球，同一刻的砖块/挡板接触全部不计；
   - 未漏球时，所有接触砖块各承受一次击中、各自计分，多砖接触只呈现一次"使球离开砖阵区域"的反弹，不得叠加多次反弹造成抖动；
   - 该次碰撞销毁最后一块可击碎砖时，只要未漏球即判胜利；
   - 球同时接触挡板与侧墙时按挡板接球处理；
   - 任何裁决后球不得留在墙体或砖块内部（需要位置修正/回退策略）。
3. 反弹方向规则（墙反转、挡板按击中位置映射出射角且不出水平/朝下方向）引用 GDD §5.1，角度数值来自 Balance；模拟层负责把规则实现为确定性计算。

### 3.4 暂停与页面隐藏的时间处理

- Paused 期间模拟时钟冻结：不累加、不推进，恢复后从冻结瞬间继续，暂停时长不影响位置与速度（GDD §5.3）。
- 基线提议：Playing 中页面 `visibilitychange` 变为隐藏时自动进入 Paused；恢复时由玩家手动继续。此为技术基线，可在 UI/UX 或末批次调整，但不得违反 GDD 的暂停语义。

## 4. 坐标与数据契约

### 4.1 唯一作者化数据源与 index 解析

- Scene/UI JSON 是布局与关卡内容的唯一作者化数据源；`content/index.json`（schema `beegame-content-package.v2`）将文档 ID 解析为 `content/` 相对路径，并声明 `entryScene` 与各文档的 `loadPhase`。
- 运行时必须**实际消费**解析出的字段：节点层级、`enabled`、本地 position/rotation/scale、渲染组件与资源绑定、Camera、UI 的 layout/anchor 等；仅解析而不使用不满足契约（`runtimeConsumption.authority`）。
- 不允许在代码中维护第二份手写布局/关卡拷贝；构建产物（派生/编译内容）可以使用，但源数据变更后经重建必须传播到产物。

### 4.2 设计坐标语义（不是宿主像素）

- 场地：Scene 的 `coordinateSystem` 给出 width/height（逻辑像素）与 `pixelsPerUnit`；原点左上，+X 向右、+Y 向下。该宽高是**作者参考帧**，不是浏览器/画布尺寸，也不是地图硬边界。
- UI：根的 `referenceResolution` 为设计参考；锚点/枢轴为归一化 [x,y]（左上 [0,0]、右下 [1,1]）；`layout.position` 是相对锚点的父级本地偏移；子枢轴默认与锚点相同；拉伸须成对提供 `anchorMin/anchorMax` 与 `sizeDelta`。具体规则以 `content-format.json` 的 coordinates.ui 与 uiLayoutContract 为准，运行时不得隐式改写。
- 角度一律弧度；2D/UI 平面内正角为顺时针。图片/atlas 矩形一律使用图像左上像素坐标。
- 模拟全程在**设计逻辑像素空间**进行；到宿主像素的换算只发生在渲染与输入反投影环节，各恰好一次，不得对作者化位置重复乘缩放。

### 4.3 场地到实际视口的映射

- 基线取景原则：**等比缩放、完整呈现作者场地（contain/letterbox）**。缩放系数 `s = min(viewportW / designW, viewportH / designH)`，场地在容器内居中，不足方向留边（letterbox）。理由：砖阵的每一块砖都必须可玩可见，裁切式取景可能隐藏砖块或边界，与 GDD §8 的可见性条件冲突。
- 缩放只改呈现：不改写任何世界 Transform、不重排砖阵、不改变碰撞体积（与 `sceneVocabulary.viewportAdaptation` 一致）。运行时可将该基线表达为 Scene 中 Camera 的 framing/viewport 数据（由 Scene 批次作者化），代码只负责按作者化 Camera 计算投影。
- Canvas  backing store 按容器 CSS 像素 × `devicePixelRatio`（设上限，如 2–3）分配，绘制时计入 DPR 以保证清晰度；HUD 所在 DOM 由浏览器原生处理 DPR。
- 世界取景与屏幕 UI 适配是**两条独立通道**：场地 letterbox 时，UI 根仍解析到完整实际视口。

### 4.4 UI 到实际视口的映射

- 屏幕空间 UI 根解析到**实际视口**而非参考尺寸；按 uiLayoutContract 计算锚点、枢轴、偏移、拉伸与容器排版，未声明字段继承基线，`responsive.compact/portrait` 变体仅在适用条件下覆盖。
- 响应式不是"用第二套 CSS/引擎布局替换作者布局"的许可（`runtimeConsumption.responsive`）：若作者数据表达不了目标布局，应回到内容/契约层解决，不得静默忽略 layout 字段。

### 4.5 横版判定与旋转/尺寸提示页（技术判定原则）

- 以容器实际尺寸为判定输入（用 `ResizeObserver`/窗口尺寸事件 + `matchMedia("(orientation: landscape)")` 交叉验证），不以设备名称或输入类型推断。
- 不满足以下任一条件即进入"请旋转设备至横版 / 请扩大窗口"提示页：
  1. 方向不符（高 > 宽）；
  2. 横版可用空间小于**最小可用尺寸**。
- 最小可用尺寸的判定原则（引用 GDD §8 的可见性条件）：砖阵区、挡板活动区、球、HUD 同时完整可见且可辨认，挡板触控操作不被遮挡。**具体最小数值由 UI_UX_SPEC 与 Balance 给出**（GDD §11 已列此项），技术侧只提供判定钩子，并消费 UI 根的 `targetViewports` / `minimumControlSize` 等数据。
- 提示页不是错误布局：不做强制重排、不做无法游玩的缩小；当时若在局内，模拟按暂停方式冻结；条件恢复后自动返回此前界面（状态与场内内容保持不变）。

## 5. 加载能力与资源约束

### 5.1 文档与资源加载流程

- 启动时优先获取 index 中 `loadPhase: "startup"` 的文档（entryScene 与第一交互帧所需 UI）；`on-demand` 文档仅在进入相应界面/需要时获取。
- 资源经 Manifest（`assets/asset-manifest.json`）解析：文档中的 assetRef → 资源 → `file_paths` 中的实际文件；资源绑定变更必须导致实际解码/播放的资产变化，HTTP 200 或文件名本身不构成消费证据（`runtimeConsumption.checks.resource-binding`）。
- 加载进度可呈现；首版无强制加载动画以外的玩法（GDD §7 Loading）。

### 5.2 Atlas 帧加载

严格按 `runtimeConsumption.atlasLoading` 的结果要求：

- atlas 帧是共享图像源上的区域，**不得**作为独立图片分别 fetch/解码；绘制时以源区域（源矩形 + 独立 UV/区域视图）呈现，不复制像素。
- 按解析后的 URL 复用在途加载与已解码源（in-flight de-duplication + 渲染器缓存）；同一用途不得同时加载打包图与原图；不得预加载无关 atlas 组。
- 消费者全部释放后释放拥有的解码源；区域视图生命周期独立于源。
- 图集帧为平面矩形，不支持旋转/裁剪帧（Manifest 图集契约）；帧矩形必须全部落在图像实际尺寸内。

### 5.3 加载失败处理

- 数据获取失败、资源解码失败、超时均归入 GDD §7 Loading 的失败分支：显示**可重试**的中文错误提示，重试重新执行缺失项的加载；不得用未作者化的占位图/无声静默顶替已声明的资源绑定。
- 在途请求在重试或场景切换时应可中止（abort），避免旧响应晚到覆盖新状态。
- 运行中的局内按需加载失败（首版内容基本为 startup 加载，此条为通用基线）：不得破坏当前状态机一致性，给出重试入口而非崩溃白屏。

### 5.4 资源可行性硬约束（给美术/音效设计者的基线）

以下为**合理基线**，目的是保证 Web 端可加载、可解码、可流畅运行；具体资源清单、数量与终值由 ASSET_PLAN 结合真机测量确定。

图像：

- 格式基线：**PNG**（含 Alpha）作为图集与精灵交付格式；自定义字体以 **WOFF2** 为基线。WebP 等现代格式仅在确认目标浏览器基线后作为可选，不在首版强制双格式交付。
- 单张图集边长基线 ≤ **2048px**（解码后 RGBA 内存约 16MB/张，且兼容移动端 GPU/Canvas）；4096px 需在末批次经设备验证后特批。
- 所有游戏内图形通过作者化图集/精灵消费；不接受运行时按文件名猜图。

音频：

- 短音效以压缩格式（**MP3** 基线）交付，背景音乐 MP3 或 AAC(.m4a)；不以未压缩 WAV 作为常规交付（体积与解码浪费）。
- 播放基线为 Web Audio API（`decodeAudioData` 预解码 + 声源池），支持同类音效快速重叠播放；同时发声数基线按 ≤ **8 路**设计，超出时按优先级替换最旧同类声源。

体积/解码预算（**临时基线，待测量修订**）：

- startup 文档及其引用资源的传输总量基线 ≤ **5MB**；
- 单个音效文件基线 ≤ 200KB，单首背景音乐基线 ≤ 3MB；
- 解码后驻留图像内存基线 ≤ 64MB。

以上数值是约束设计的初始基线，不是验收终值；若 ASSET_PLAN 论证需要突破，须在末批次给出对应设备上的加载/内存证据后修订。

## 6. 输入统一抽象

GDD §3.1 要求键盘、鼠标、触控同一时刻任一可用、效果等价。输入层将三种物理输入归一化为统一意图，状态机只消费意图、不感知设备。

### 6.1 意图模型

- **连续意图——挡板水平意图**：两种表达并存于抽象层：相对速率（键盘：-1/0/+1，长按持续）与绝对目标 X（鼠标/触控：投影到场地设计坐标后的目标位置）。
- **离散意图——动作**：发球、暂停/继续、再来一局、返回开始界面，以及 UI 的确认/交互；一律**边沿触发**（按下到接受的一次跃迁），键盘自动重复（key repeat）不得重复触发动作。
- 所有客户端坐标经同一投影函数换算：容器像素 → 场地设计逻辑像素（§4.3 映射的逆变换），并夹取在场地左右边界内。

### 6.2 三种输入的适配基线

- **键盘**：监听 keydown/keyup，维护按键按下集合以支持长按持续移动；方向键为左/右方向键与 A/D；发球为 Space；暂停为 Esc/P（具体按键归属以交互契约/UI_UX 为权威，技术侧保证动作语义）；对游戏按键阻止默认行为（避免页面滚动）。
- **鼠标**：mousemove 将光标在场地内的投影作为挡板绝对目标 X（夹取边界）；点击/按下在 Ready 时为发球，在 UI 节点上时交 UI 处理；光标离窗时保留最后有效意图。
- **触控**：使用 **Pointer Events** 统一鼠标与触控；手指可在屏幕任意水平位置拖动（**不要求按在挡板上**，GDD §3.1），触点 X 经同一投影驱动挡板；Canvas 区域设置 `touch-action: none` 防止滚动/缩放手势；落在 UI 控件上的触点归控件，不驱动挡板。首个落在游戏区的有效触点驱动挡板，期间其他触点不改变挡板目标。

### 6.3 多输入并存、同时刻等价

- 三种输入可同时存在并产生同一意图模型；归一化后对状态机完全等价，实现 GDD §10.2 的"三者行为等价"验收。
- 冲突消解基线：指针（鼠标移动/触控拖动）在产生新事件时提供绝对目标，优先级高于键盘相对速率；指针停止活动后键盘重新生效。本质是"最近活跃的输入源在该帧生效"，不得出现两路输入互相拉扯导致挡板抖动。手感参数（键盘速率、鼠标/触控平滑）由 Balance 定义。

### 6.4 动作输入与状态可用性

- 各动作仅在 GDD §4/§7 所列状态下可用：如发球仅 Ready 生效（发出后发球输入无效果）；结算态仅接受再来一局/返回开始界面。可用性由状态机在分派时统一裁决（见 §7.2），输入层自身不做玩法判定。
- 暂停层、结算层等覆盖 DOM 负责截留指针事件，避免弹层下的 Canvas 触点驱动挡板。

## 7. 状态管理落地

### 7.1 状态机拥有权

- GDD §7 的状态机（Loading、Start、Ready、Playing、Paused、Win、Game Over）在游戏引擎层有**唯一实例与唯一拥有权**：React 不持有派生状态机，只订阅当前状态快照以选择界面；输入层不改变状态，只提交动作。
- 状态转移的触发源只有两类：玩家动作经路由分派（如发球、暂停、重试），以及模拟事件（漏球成立、最后一块砖销毁、生命归零）。转移函数以 GDD §7 表为权威实现为确定性 (state, event) → state 映射。

### 7.2 过渡期间的输入屏蔽

- 动作在分派瞬间按当前状态校验合法性；非法动作直接丢弃，**不排队、不缓存**到下一状态（GDD §5.3 的交互边界）。
- 状态转移与界面呈现之间到达的输入，以状态机的新状态为准裁决；弹层 DOM 同时提供物理截留。
- 漏球判定成立的瞬间起，球与挡板/砖块的后续交互一律无效（GDD §5.3）：模拟层在该帧即冻结相关交互，随后进入生命扣除结算；结算持续期间只接受规则允许的两个动作。

### 7.3 本机最高分持久化

- 使用 `localStorage`，单一命名空间键（如 `breakout.highScore.v1`，最终键名为实现细节），值为整数字符串或含整数的简单 JSON。
- 启动时读取；缺失、解析失败、非法值一律按 0 处理，不阻塞进入游戏。
- 写入时机严格遵循 GDD §6.3/§6.4：仅正常打完出现胜负结算、且本局分数超过历史最高分时写入；主动退出/放弃的局不参与比较。写入后界面呈现"新纪录"提示。
- 存储不可用（隐私模式、配额异常）时降级为仅当局内存有效，不报错、不影响玩法；清空浏览器数据导致最高分丢失是 GDD 确认的可接受行为，不做云端恢复。

### 7.4 新一局的数据重置

- "再来一局"/开始游戏必须从内容层持有的**作者化初始数据**重建场内实体（砖块耐久与分布、挡板与球初始位姿、分数 0、生命数初值），不得在上一局被修改过的实体状态上回滚修补，避免残留状态缺陷。
- 生命数初值等数值由 Balance 经共享玩法调参数据提供（项目自有 JSON，按 content-format 规则放在 `content/` 之外），运行时同样只消费、不硬编码。
