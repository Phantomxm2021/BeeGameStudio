# V3 代表性切片与视觉观察调整（2026-10-14）

## 依据

「萤石驿站」原生回合在启动后约 44 分钟累计 93 次请求、约 885 万总 Token；其中约 9 分钟等待一次工作区外临时脚本写入批准。先完成成批 Scene/UI 和运行时，接近第 40 分钟才读取可判断效果的截图；脚本断言通过时棋盘仍不可见。因此不能把该耗时称为「早期原型」，也不能把脚本通过当作视觉/玩法通过。缓存读取包含在总 Token 内，不能按非缓存输入计价。

## 本轮系统调整

- 替换现有 Agent 专业上下文中的执行顺序表述：合并文档不能只列领域标题，须有当前切片所需的具体决定；先观察一个真实可玩、可见的交互，再扩展同类场景、屏幕和资源。不增加宿主阶段、轮数上限或另一份 Review prompt；不指定 Web/React/Unity/Godot 技术路线。
- 保留八领域设计记录默认组织、相关专业 Skill 的现有调用要求，以及可选单文件 `CLAUDE.md` 导航。`CLAUDE.md` 不成为重复的强制计划或设计权威。
- 现有 AI 图片能力仍按实际可用性和费用使用。概念图可供美术/UI 对齐，不能自动当作可裁切的正式图集或 UI 资源；正式资源仍需独立选择、制作和登记。
- 现有 Web Preview 工具增加一次性 `--snapshot`：在项目绑定的隔离浏览器首载后保存唯一截图和运行时错误计数。它不用项目自写测试脚本，也不构建、不改游戏源码；只提供诊断，不证明玩法、美感、Scene/UI 消费、源版本新鲜度或交付合格。非 Web 项目继续用其原生运行与观察工具。

## 验证边界

离线回归：Agent 交接、Skill 插件、项目导航、预览权限和工具共 62 项通过（常规模式 1 项浏览器用例跳过）；另开启合成 Chromium 路径跑完整工具组，11 项通过，包括真实隔离 iframe 的首载截图与运行时错误计数。`git diff --check` 与 `node --check` 通过。仓库级 TypeScript 检查仍因大量现存的跨包模块解析与类型错误失败，本轮没有把它改称通过。

不运行付费模型、不修改测试项目。能否让真实 Agent 更早观察画面、减少 Token 与返工，以及游戏品质是否提升，仍须以后经单独授权的新项目验收；不能仅凭本轮离线回归宣称已解决。

## 后续视觉方案调整（同日）

在代表性切片要求之外，视觉类游戏默认先保存覆盖适用八领域的可执行设计初稿；在批量制作 UI、场景和资源前，基于这些决定保存一张同时呈现代表性玩法画面与主要 UI 的综合视觉方案，并实际查看。默认使用已有 AI 生图桥，先只读询价；用户明确排除或缺少付费授权时不得擅自生成。桥已开启不代表供应方可用；用现有 `assets.mjs cost` 核实，不能把不可用悄悄降级为文字或占位图。

选择视觉方向后，把被采纳的颜色、形状、层级、反馈和资源要求写回对应设计记录。概念图不代替玩法规则、精确文案、布局坐标或正式资产。制作后观察真实运行截图及交互，与视觉方案核对，记录明显差异和未验证的品位判断；构建、Schema 或几何检查通过都不等于视觉合格。此顺序属于 Agent 的专业交付方式，不新增宿主固定阶段、自动质量结论或强制 Review 循环。

本次仅调整 V3 稳定专业上下文及生图工具反馈，没有修改正式前端、Claude Code 源码或测试项目。假图片服务离线回归证明只读询价不会生成图片、`generate` 可将图片保存到项目供回读，桥开启时不会误报供应方已可用；目标 Agent 是否真的遵循上述顺序、视觉效果和成本是否改善，仍未经真实付费项目验收。

## 真实项目反例后的视觉交接修订（同日）

「潮汐灯塔」真实运行中，八文档和五次专业 Skill 调用已发生，但唯一视觉提案的生成指令明确排除了 UI；资源计划又规定提案不进入运行时，Agent 随后自行绘制所有画面和 UI。首屏截图与提案差异显著，并有布局溢出。停止时记录约 1,055.6 万总 Token（其中约 1,013.3 万缓存输入）、182.5001 Credit；游戏未交付。该结果否定了「在完整制作指令中写一句综合提案要求，就能约束视觉实现」的假设。

现在新项目的**首个原生任务被指派为设计与视觉方向交接**：适用八领域设计记录完成后，从中列出实际界面、关键状态、独特场景及物件；保存并查看 `assets/visual/ui-board.png` 与 `assets/visual/scene-board.png`，向用户展示实际图片和覆盖关系后结束本回合。前者覆盖封面、实际 UI 屏幕和游戏中 HUD；后者覆盖独特场景类型、重要状态及代表物件。过密的总览可加细图，不能缩成无法判断的小格子。窄范围技术可行性探针仍可先做，但不等于批量制作。后续制作需用户在同工程明确继续；BGS 不自动开启下一付费回合。此边界依赖 Agent 正确执行，宿主当前只在回合结束核验图片文件，并未拦截越界写入。

宿主在首回合结束时只读检查两张基础图片存在、位于工程内、PNG 可解码且不是相同字节；缺少时回报交接未完成。即使通过，也仅表示文件事实，不证明图片真的覆盖界面与场景、更不证明审美被确认。覆盖与视觉方向仍须查看图片；没有人工确认时不能宣称审美已获保障。首回合误做的测量也不能绕过此交接。制作时的独立资源和 UI/Scene 数据仍由 Agent 根据确认方向生产；BGS 已有图集打包能力，只处理经检查的独立源图，不把 AI 总览图的臆测坐标当成图集元数据。最终仍需逐屏、逐代表场景观察实际运行截图和玩家流程。

这是一个有意的产品行为变化：新项目不会在最初原生回合内直接交付完整游戏，需要一次视觉方向交接；旧项目的现有会话与文件不迁移，后续回合也不注入新的两张视觉稿要求。离线测试覆盖图片缺失／损坏／越界路径、首回合交接、同工程后续消息和原生 CLI 传递；没有追加真实付费运行，故 Agent 是否遵循以及成本是否改善仍未验证。

## 纸鸢邮差测试后的修订（同日）

上述“视觉稿后结束并等待再次授权”已被真实测试证明不符合一次启动游戏制作的用户预期，现已撤销，不再作为当前流程要求。新项目仍须基于设计记录制作并查看 UI 与场景视觉稿，但应在同一原生任务里继续资源、内容和可玩实现；视觉稿不再触发用户审批，也不代表审美合格。首回合回执仅报告图片文件事实及测量状态，不以视觉交接阻断生产。旧项目已结束的回合不会因系统改动自动付费重开。

生图不再逐张询问的前提是“开始构建”现有确认页明确告知平台生图另按实际价格扣 Credit，个人密钥由提供方收费；Agent 仍须只读询价并受已有预算与余额约束，费用或能力不可用时不能伪称成功。此轮只做离线回归，没有再运行付费项目；Agent 是否在真实新项目中连续完成制作、视觉和整体品质仍未证实。

## 资源落地与实际消费：审计后的修订（同日）

目标仅针对已证实的落差：有视觉板和提示词，但没有符合所选方向的运行时资源。当前 `content-resources` 已在无绑定时返回未验证，且只能核对声明过的引用／文件；`pixel-data-consumption` 只覆盖选定的静态图像／Tilemap，不能验证程序 Canvas、美感或全部状态。因此不新增一个“必须依次搜索网络／库／AI／程序”的来源流程，也不把空 `assetRefs` 一律判失败。

在现有专业交接文字中落地的简短规则：先从设计记录列出当前切片所需资源及风格；逐项选合适来源——内置库可能适用时先查，网络素材先核使用权，缺少合适成品时才选择 AI 制作或真正适合的程序绘制，无需走遍所有来源。简单按钮／几何特效可以程序绘制；风格关键的角色／背景不能以未经观察的通用占位物替代。文件型资源保留实际文件、来源与权利记录；程序型资源记录渲染代码路径，不伪造 `assetRefs`。对应资源先制成并检查，再定稿该切片 Scene/UI JSON；使用现有检查核对文件和引用，并在可进入的游戏状态中逐项观察所需资源的实际消费。未覆盖处标“未验证”，不从板图、Schema 或单张截图推断全部通过。

自审计后删除了不合适的绝对要求：不强迫每个图标查询资源库，不强迫程序图形落位图文件，不强迫 Web 素材优先，不要求整款游戏所有资源先于任何 Scene/UI 数据制作，也不增设固定宿主关卡／新资产 Schema。保留必要限制：外部素材有使用权证据；板图不是图集；声明的文件必须存在且被引用和实际使用。此修改能明确正确工作顺序，但仍依赖 Agent 选择检查对象；现有检查器不能证明遗漏了哪些本应制作的资源，真实品质需后续授权测试观察。

回归：允许本机临时监听的离线环境里，`agent-goal.test.ts` 全部 39 项、453 断言通过；包括来源选择不僵化、文件／程序路径与实际消费要求，以及既有工作流边界。`git diff --check` 无问题。本轮无新检查器、模型费用、部署或项目产物写入；根级类型检查仍有上节所记的两处独立测试类型错误，未把整体检查称为通过。

## 后续系统 Bug 修复与发布证据归因（同日）

- `content-resources` 原先遇到顶层 `assetRefs: []` 就返回“无资源绑定、未验证”，即使节点内部已有 `assetRef`。现复用已有声明一致性检查，让这种矛盾返回失败并指出节点中的未声明 ID。真正没有文件资源的程序绘制仍是“未验证”，不会被假判为失败或已消费。
- 旧测量后修改 `docs/IMPLEMENTATION_PLAN.md` 时，该文件属于可编辑工程的构建快照，旧测量与当前工程确实不再对应；Preview／发布／导出拒绝是正确边界，不能绕过。原诊断又把同一源文件变化报告成 `Saved check inputs or checker versions differ: build`，混淆了“源变了”和“检查器版本变了”。现分别计算并报告，只保留真实的源变更原因；最终定稿文档后仍须重新构建、测量。
- 离线回归：`context-content.test.ts` 与 `agent-measurement.test.ts` 共 37 项、519 断言通过，包括无声明但内部引用资源、文档变更后旧结果仍拒绝发布、真实检查输入／产物变化分别归因。没有改正式前端、Claude Code、生成项目；未付费重跑、未部署。此修复不证明所需美术资源完整，也不证明运行时已消费或游戏品质合格。

## 系统入口修复：已登记内容不再跳过现有检查（同日）

审视测量入口发现：静态 Web 的源拷贝构建与浏览器冒烟会运行，但即使工程有 `content/index.json`，已有的 Scene/UI 结构、空间布局和资源检查器也未进入该测量回执。只读对纸鸢邮差现存 JSON 调用同一布局检查器，得到四份 UI 的根方向缺失；原生测量不会报告。该差异是已证实的系统接线缺口，并非需要一个新 Review Agent。

现对**已登记 BGS Scene/UI 的静态 Web 工程**在一次测量内自动运行现有三项确定性检查。登记表损坏、结构／布局／资源检查确定失败时，旧式“构建和冒烟通过”不再允许交付或发布；Preview 仍可用于诊断。失败检查的 ID／状态也进入原生回合结束交接，不仅藏在测量明细里。未声明位图资源的内容保持“资源覆盖未验证”，不会仅因程序绘制而失败。回执还逐份列出已登记而没有任何通过的消费探针涉及的 Scene/UI 文档，避免把静态校验称作运行消费；即使某份文档被探针抽样，也不等于所有节点和状态通过。已保存的检查输入及检查器版本进入后续新鲜度比对；未登记 BGS 内容的旧／其他技术路线不会被擅自转成 BGS JSON。

同时修正一个上下文划分 Bug：此前“旧工程不强加两张新视觉板”的过滤，把同段通用资源决策规则一并滤掉。现仅过滤新项目的视觉板要求，保留适用于旧工程的逐项资源选择、实物落地、引用及运行观察规则。这是拆开既有要求，不增设额外 Prompt 阶段。

## Scene 节点实际消费探针（同日后续）
