# 贪吃蛇 技术设计（TECHNICAL_DESIGN）

- 版本：v0.1（作者草稿，待统一评审）
- 作者：Bee Game Studio 主 Agent
- 日期：2026-09-30
- 平台：Web；引擎/框架 React；2D；输入：键盘/鼠标 + 触屏。
- 上游：GDD（行为权威）、LEVEL_SCENE_DESIGN（空间）、BALANCE_DESIGN（数值）、ART_DIRECTION（视觉）。

---

## 1. 目标与总体原则

- 在不改变既定产品设计的前提下，让首版在桌面与移动端浏览器稳定运行 60fps、整盘完整可见、可随时重开。
- **数据所有权原则**：场景层级、transform、UI 布局、响应式变体、资源绑定以编写的 Scene/UI JSON 为唯一可编辑来源；代码只负责加载/解析这些数据与实现动态玩法，不维护替代性布局或用常量覆盖编写决策。
- 玩法数值（BALANCE_DESIGN 第 2 章）作为发布配置数据提供（可由平衡配置 JSON/TS 配置模块承载），不散落在组件代码里。

## 2. 运行时模块与职责

| 模块 | 职责 | 不做什么 |
|---|---|---|
| `App` / 页面壳 | 挂载、视口尺寸监听、页面可见性监听 | 不持有玩法规则 |
| 数据加载层 `sceneLoader` | 加载并校验 Scene/UI JSON、平衡配置；产出规范化的场景描述（节点树、格尺寸、绑定、响应式变体） | 不发明 JSON 中没有的节点 |
| 游戏状态层 `gameState`（建议 reducer/轻量 store） | 持有状态机当前态、蛇身格位数组、方向、缓存输入、食物格、分数、n（已吃数）、剩余节拍时间；唯一的状态变更入口 | 不直接接触 DOM |
| 规则求值层 `rules` | 纯函数：应用缓存方向、计算目标格、按 GDD 3.7 次序结算、生成新食物（候选空格均匀随机）、计算 T(n) | 不做渲染；不读取视口 |
| 节拍驱动 `tickScheduler` | 按当前 T(n) 调度步进；暂停时冻结剩余时间、恢复后续跑；失焦自动暂停 | 不决定节拍结果 |
| 输入层 `input` | 键盘映射、触屏滑动（24du 阈值）、鼠标按钮事件 → 动作/方向意图 | 不直接改蛇 |
| 场景呈现层 `SceneRenderer` | 依据场景描述 + 游戏状态把格位绑定到节点变换；绘制蛇/食物/棋盘；特效 | 不内建布局常量 |
| UI 层 `HUD/Menu` | 依据 UI JSON 渲染各状态界面、分数、按钮；回调动作 | 不重算玩法 |
| 持久化 `storage` | 最高分读写（localStorage，带异常兜底） | — |
| 音频 `audio`（预留） | 事件音效；首版无音频内容时为空实现接口 | — |

## 3. 信息流与关键时序

### 3.1 初始化

1. 页面加载 → `sceneLoader` 拉取 Scene/UI JSON 与平衡配置并校验（字段缺失按第 7 章失败处理）。
2. 规范化场景描述（世界原点、格尺寸 32du、棋盘 672du、节点 id、资源 URL、响应式变体）。
3. `gameState` 以就绪态初始化：蛇 [(10,10),(9,10),(8,10)]、朝右、分数 0、n=0；按 3.2 规则准备首食物（开局开始时才需要出现：在“开始”动作进入游玩时生成，满足 d₀≥5）。
4. `storage` 读取最高分（失败则视为无记录）。
5. 渲染就绪屏。

### 3.2 单局流转

- 「开始 / 再来一局」→ 重置为初始游玩态（同一初始化路径，保证行为一致）→ 生成首食物 → 调度器以 T(0)=160ms 启动。
- 输入意图进入状态层：转向写入缓存（容量 2，去多余/即时非法项的处理按 GDD 3.3：入缓存时不丢弃，应用时裁决反向作废）；暂停类动作立即触发状态转移。
- 每个节拍到期，状态层调用 `rules.step(state)`：严格执行 GDD 3.7 次序（合法缓存方向→目标格→胜负判定→进食/前进、食物重生、n 与后续 T(n)），产出新状态；调度器读取新 T(n) 安排下一节拍。
- 状态变化单向流向呈现层与 UI；呈现层只订阅、不回写。
- 失败/通关 → 停止调度器 → `storage` 按需写入最高分 → 渲染结算。
- 「返回主菜单」→ 停止调度器、清理当局数据 → 就绪态。

### 3.3 暂停/失焦

- 暂停：调度器记录当前节拍剩余时间并停止；继续时从该剩余时间恢复（GDD 3.8）。
- `visibilitychange` 切到隐藏且处于游玩 → 等同于暂停；回到页面不自动继续，由玩家手动恢复（避免后台标签页计时器堆积）。

### 3.4 重启与清理

- 重开/返回菜单必须：取消待执行节拍定时器、清空输入缓存与特效、取消未完成资源加载（若有）；新局不复用旧局定时器，避免多次 tick 叠加。

## 4. Scene/UI JSON 数据契约（与项目既有约定兼容）

- 采用项目既定的场景描述结构（节点树：`id/type/transform/children`；UI：布局 + 响应式变体 + 动作绑定）；不新造不兼容格式。实现时若平台有现成 schema/加载器，以其为准，本文以下为最小内容约定：
  - 棋盘根：世界原点、设计尺寸 672×672；棋盘节点含列/行元数据或对格尺寸 32du 的引用（供逻辑定位，具体行列数值以平衡配置为权威、由构建注入场景数据，避免两处手写）。
  - 蛇容器、蛇节模板节点、食物节点、边框节点；资源绑定（形状/颜色可由样式或轻量矢量资源表达，遵循美术方向）。
  - UI：HUD（分数/最高分/暂停按钮）、就绪、暂停、失败、通关各界面布局；响应式变体（断点与每格最小可读尺寸由 UI_UX_SPEC 定义）。
- 运行时逻辑格位 → 世界变换的绑定：`worldXY = origin + cell × s`，origin/s 来自场景数据。
- 静态布局与资源选择保留在数据侧；代码中不得出现“棋盘 672”“每格 32”等替代布局的硬编码常量（公式中的换算读取数据值）。

## 5. 取景与适配实现

- 监听容器尺寸；取 UI 占用后的可用矩形，计算等比缩放 `scale = min(availW/B_designW, availH/B_designH)`，其中 `B_designW/B_designH`（发布值 672/672）读取自 Scene JSON 的棋盘设计尺寸；棋盘居中。保证整盘可见、不裁剪、各向同性。
- 背景层独立覆盖容器（渐变/可平铺），不随棋盘缩放平移。
- 触屏坐标换算为设计坐标后再做 24du 滑动判定，保证不同 dpr 下阈值语义一致。
- dpr 处理：绘制按 `scale × devicePixelRatio` 设置，上限 2–3 以控开销。

## 6. 渲染与性能

- 蛇仅 3–441 个简单圆角节、单食物，每节拍仅一次状态更新；建议 DOM/React 元素或单一 Canvas 二选一，规模上二者均可：
  - Canvas：每帧重绘量极小（≤442 个形状），60fps 无压力；节拍间仅食物脉冲/特效需要重绘，可按需渲染。
  - DOM：节点数随蛇长线性增长，441 个节点在 React 下仍可接受，但终局反复重排风险略高；如采用，蛇节用 transform 定位避免布局抖动。
- 节拍调度用基于时间戳的累加（而非 `setInterval` 固定漂移），但**判定时机仍以离散节拍为准**，表现补间不得改变碰撞结果（GDD 3.2）。
- 内存：重开即释放节节点/特效对象；无位图资源时基本零加载体积。

## 7. 加载、存储与失败处理

- 首版以本地 JSON/打包数据为主，无远程加载依赖；如经 fetch 加载，失败时显示“资源加载失败，点击重试”，不进入黑屏。
- JSON schema 校验失败：开发环境抛出明确错误；生产环境显示加载失败并上报日志。
- localStorage 不可用（隐私模式/配额）：游戏正常可玩，仅最高分不保存，不弹错误。
- 最高分写入做防御：只接受数字、有限值；读取异常按无记录处理。

## 8. 可行性风险与验证方式

| 风险 | 验证方式（无需预建框架） |
|---|---|
| 441 节 DOM 在低端移动机掉帧 | 实现一个最小压力页面（渲染 441 圆角矩形）实测帧率；不达标则用 Canvas |
| 80ms 节拍下定时器在移动端后台/触摸时漂移 | 用时间戳累加并在真机游玩验收（playtest 阶段） |
| 等比适配 + UI 占用在小竖屏导致格位过小 | 按 UI_UX 断点表逐档检查最小格尺寸 |
| 滑动转向误触/延迟 | 真机触屏校准 24du 阈值与主轴判定 |
| 状态机因异步顺序产生非法转移 | 规则层保持纯函数、状态变更单入口；以状态转移表为用例做单元测试 |
