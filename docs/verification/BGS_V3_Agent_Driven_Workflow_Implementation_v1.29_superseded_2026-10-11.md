> 目标：idea 输入 → 三选一 → 游戏设置 → Claude Code Agent 接任务 → 动态规划、执行与调整 → 游戏交付。
> 状态：本版为重新审计后的规范，不是已实现声明。现有 V3 的主要证据仍是宿主 Task API／debug 合成闭环，尚未证明上述 Agent 主导业务完整贯通。正式 frontend 的 V3 接入已撤回，当前交付资格仍关闭。

## 0. 核心结论

**我们是在 Claude Code 上承接游戏业务，不是在 BGS 中再造一套 Agent 执行器。**

- 产品入口保持 idea、三选一和游戏设置；取消八文档生产门禁不等于取消这些入口。
- 设置确认后，将用户原始意图、选中的方案、确认设置和已有工程交给 Claude Code Agent。
- Agent 在授权内自行规划、使用 Skills、选择工具、必要委派、实现、验证、修复和调整计划。
- BGS 管用户授权、实际项目与会话归属、状态／事件、Question 答复、版本和用量，提供可选专业能力。
- 不要求先提交 BGS Task DAG 才能开工，不让用户逐任务点击 Execute 代替 Agent 生产。
- 不按 engine 名称禁止工具，不将 Web 专项或 BGS Scene/UI JSON 设为所有游戏的交付前提。
- 自主执行不等于结果可靠：实际游戏与证据仍须核对，不能凭作者／Reviewer 声明宣布合格。
- 不增新 Planner 服务、引擎分流框架、统一场景模型、通用验收框架或另一套计费账。

### 1.3 根因

1. 把“Claude Code 主导生产”误写成“BGS 制定任务协议，Claude Code 完成宿主分配步骤”。
2. 把“必要的真实验收”扩大成“BGS 必须先拥有每项游戏功能的检查器”，导致长期停留在字体、音频、Tilemap 等专项。
3. 把人工 plan／execute、受控假模型的成功当成总体推进证据，没有优先验证用户确认后 Agent 是否真正自主接单、规划和完成游戏。
4. 技术边界纠偏后又按 engine 增加判定，继续用规则替 Agent 选择工具；不是靠更换模型或叠加 prompt 能解决的方向问题。

这是系统规划和实施取舍的偏差，不应归咎于模型，也不能靠把旧流程照搬回来解决。

## 2. 业务主线及职责

### 2.1 用户入口固定，生产方式动态

| 环节 | 应做什么 | 不应做什么 |
|---|---|---|
| idea 输入 | 保存用户原始描述、附件和明确限制 | 只保留模型改写后的摘要，丢掉原意 |
| 三选一 | 给出三个可理解、可选择的游戏方向；保留用户选中项 | 将选项变成三次生产，或向生产 Agent 注入全部未选方案 |
| 游戏设置 | 确认玩法方向、技术／引擎、平台、输入、资源使用方式等已有设置 | 从发布 Web 推断必须 React；改变已确认引擎 |
| Agent 接任务 | 用正常 Claude Code 提交方式交付完整确认目标、工程位置、权限及可用能力 | 要用户填写 Task JSON 或先建固定生产阶段 |
| 动态生产 | Agent 按真实工作需要规划、执行、委派、验证、修订；进度来自实际事件 | 宿主按文档名／检查器／保存动作拆任务，决定逐工具顺序 |
| 游戏交付 | 指向当前实际游戏与可继续修改工程，说明运行方式、证据和限制 | 将 native complete、文件存在、绿勾或全八文档当成合格证明 |

这些是业务关系，不是六个强制生产阶段。新需求／局部修改承接当前工程和用户变更，不重新走一次三选一或重做全部策划。

### 2.2 决策所有权

| 主体 | 负责 | 不替谁做决定 |
|---|---|---|
| 用户 | 确认方向／设置，授权费用／范围及重要变更 | 不必裁决每个普通实现细节 |
| Claude Code 主 Agent | 动态计划、方法、工具、必要委派、实现、验证、修复及交付说明 | 不擅自改变用户已确认承诺或扩大权限 |
| 原生 subagent | 按主 Agent 委派完成相关工作，使用相关专业方法 | 不由 BGS 强制为每个领域建立一个作者 |
| BGS | 身份／项目归属、授权、事实保存、状态／事件、Question 路由、用量及可选能力 | 不决定工程结构、UI 格式、工具组合、每次修复步骤 |
| Skills | 帮助策划、UI、美术、音频、场景、数值、实现和试玩做得更好 | 不维护另一套业务职责，不授予额外权限 |

主 Agent 对交付负责，不代表它的判断不会出错。专业语义、手感、审美和听感的限制须如实报告；必要时依靠实测或有权者判断，不承诺纯 LLM 零缺陷。

### 2.3 多引擎是需求与工具能力，不是 BGS 分流架构

- 用户说“用 Web／React”，Agent 直接写代码并使用正常开发工具；不增加专用引擎 CLI／MCP 层。
- 用户说“用 Unity／Godot”，Agent 使用环境中可用且获授权的 CLI／MCP 操作原生工程；BGS 不预设必须同时有两种接口。
- 引擎项目可使用 Bun 脚本、浏览器或其他辅助工具；不能仅按 engine 字符串禁止。
- CLI／MCP 控制开发工程与发布到 Web／PC／移动端是不同事项；某个 Web 导出运行成功不证明原生工程可编辑。
- 环境缺工具／权限时报告实际缺口，必要时发 Question；不静默安装、改引擎或制造替代工程。
- 本轮不实现引擎适配器。已有工具是否可用是环境事实，不是新增宿主引擎路由协议的理由。

## 3. Agent 接单、规划与执行

### 3.1 一次交付确认事实，按需读工程

初始输入只需包含：

- 用户原始 idea／附件来源、选中方案与确认设置；
- 已有工程位置、用户当前授权和明确限制；
- 必要的专业职责及相关 Skill 入口；
- 实际可用的资源、构建、Preview 等能力入口与真实限制。

不要复制全部资源字节、八文档、未选方案和历史工具日志。当前工作事实保存在工程和必要记录中，Agent 按需读取；不能仅靠长会话摘要继续旧决策。

不新建巨型任务 prompt。职责由用户目标和授权界定，Skill 提供方法；BGS 说明能力，不用说明暗中要求固定工作步骤。

### 3.2 动态计划属于原生 Agent

Agent 可用原生计划／Todo、工具和必要 subagent 组织工作；是否拆任务、写多少设计、何时验证，取决于实际复杂度。计划变化不要求用户逐步骤批准，也不要求提交宿主 DAG 才能继续。

普通开发、检查和需求内修复由一次明确项目授权覆盖。范围／技术承诺、额外权限、用户设定预算或产品争议有实质变化时才请求确认；Agent 正常执行空间不等于关闭原生权限和安全约束。

BGS 可以展示真实计划／Todo／事件或保存薄指针，但它们不是第二份执行权威。不把观察到的每个 Todo 转换成必须领取的新 Task／Attempt，不为简单游戏开一组额外付费 Planner／Replanner。

### 3.3 正常运行与委派

沿用普通原生提交、stream-json、权限／Question、子代理事件和 session/resume。BGS 不修改工具描述／结果、query loop、压缩、思考或最终回复；不靠文件出现提前杀进程或伪造结束。

Agent 决定必要委派和上下文。BGS 保留父子归属、真实状态和所有执行用量，不把子代理工具／消息放进主会话冒充主 Agent 输出，不把所有子代理日志重新灌入主模型。

不按领域强制独立会话，也不强制所有工作复用同一长历史。宿主只提供必要事实和正常会话能力，不另实现原生压缩／切会话算法。

## 4. 设计、Review／Repair 和交付事实

### 4.1 保留专业设计，不要求八份稿

玩法、技术、美术、音频、UI／UX、场景、数值和资源责任仍存在；根据项目需要写在简短说明、代码／配置、原生场景或已采用的 BGS 内容中。同一决策只有一份权威，可读说明解释目标和修改入口，不复制整棵 UI 树或全部坐标。

用户明确要求文档则交付；不以“省 Token”删除需求。BGS 内容编辑／消费是可选能力，明确采用时遵守其 Schema／绑定契约；其他项目不补第二套 JSON 来满足检查器。

### 4.2 Review／Repair 是工作方法，不是宿主固定批次

Agent 在实际需要时组织 Review／Repair，使用相关专业 Skill、确定性工具和实际运行。检查问题应有具体来源、影响和关闭条件；修订回到有权者，不能为润色、偏好或新增需求反复返工。

审查和修复的任务形式由 Agent 决定，不强制所有游戏经历宿主 Review Task → Repair Task → Follow-up Task 三个独立会话。检查能在当前授权内直接完成，就不另开一轮机械模型请求。

这不意味着只相信自检或放弃独立 Review：关键争议可采用原生 subagent／实际测试／有权者判断。独立 Reviewer 也可能漏检，不能把它说“通过”当成事实。

有新依据可继续正常修复；相同条件反复失败、没有新证据时停止宿主自动重新派发，明确原因。既不隐藏硬轮数限制，也不承诺无限付费审查能收敛。

### 4.3 检查器提供能力，不指定技术方案

既有布局、资源、UI／Canvas／字体／音频、Bun 构建和 Chromium 检查可复用，但必须准确说明输入要求、实际观察、覆盖和限制。Agent 可选择合适工具或已有项目测试，不要求宿主先接齐所有功能驱动。

适用性依据是**调用的检查器和实际输入／运行条件**，不是项目 engine 名称。某驱动只检查静态 Web，就不能声称它验证了引擎工程；但不能因此禁止引擎 Agent 使用该驱动检查一个真实 Web 导出。

缺输入／缺观测是未验证，驱动失败不是游戏缺陷。绑定确切的源码／构建版本和证据；修改后旧证据仍可查，但不能作为新版本通过。

### 4.4 交付不能只靠一句“完成”

交付要能找到当前游戏／工程、实际启动入口、已核对行为、已知问题和证据。至少核对确认的核心循环、成功／失败／重开、关键 UI／反馈和项目要求的资源／音频；不用所有项目相同的一张专项检查清单。

Agent 的报告可以解释结果，原生事件／实际进程输出和游戏观察提供事实。摘要／hash／退出码各自只证明有限内容，不能自动证明好玩、美观或所有规则正确。

现有宿主观测不足时，允许明确的人工／设备验收或记录未验证；不伪造通过，也不为了未来所有情况新建复杂验收框架。正式发布仍遵守有效安全／权限约束，不能因改文档就解除当前关闭状态。

## 5. Question、修改和中断

- 需要用户决定时，真正发出原生 Question；BGS 将实际问题显示并把答复送回所属会话／子任务。用户沉默、拒绝、过期答复不是批准。
- 不要求先生成宿主 finding JSON 才允许普通业务提问；必要的版本／来源核对复用已有事实，不将 BGS 元数据塞进原生工具输入。
- 局部变更交给 Agent：当前确认需求、实际工程、用户新要求和相关失败证据。BGS 不替它生成详细修复路线，也不自动重做八领域。
- 暂停是用户意图，重启不解除；正常 session/resume 不等于后台操作已经完成。原生进程、subagent、引擎导入／构建和外部收费操作的活性分别核对。
- 不因超时、缺会话或人工“应该结束”解锁未知写者。保留已保存成果、权限边界与历史；不要新增通用进程框架追求绝对隔离。
- 来源／工程变更后重新核对受影响实际行为，旧测量不能继承为新版本合格。无关成果不删除、不要求为了新索引重写。
- 模型／资源请求响应丢失不盲重放；用现有操作身份、用量 outbox 和幂等事实核查，无法确认则保持未知。

| 对象 | 处置 | 必要边界 |

| SessionManager／正常 native 提交／权限／Question／子代理事件／resume | 保留 | 复用普通能力，不改 Claude Code 原生循环或 native 工具 |

## 8. 成本与质量约束

- Agent 默认不受隐藏 maxTurns／固定修复次数约束；执行用户明确预算、权限和账户真实额度。
- 不把每个机械保存、检查汇总或交接总结变成新模型请求；不重复注入正文、全资源和后台日志。
- Agent 本身可能碎步执行、漏检和反复探索；取消宿主调度不保证这些问题自动消失，真实请求记录才是改进证据。
- 按实际 native 会计 epoch／请求／主子代理归属统计非缓存输入、缓存读写、输出及失败／中断。计费仍由现有 billing／outbox 负责，金额缺失标未知。
- 专业质量靠实际游戏和必要证据判断，不以模型主观分、检查数量、切换模式或比旧版更好作为合格标准。
- 上次工具核对只说明常规目录／PATH 未找到可用 Editor／Godot，旧 Unity 登记失效且 Codex 的 unityMCP 配置禁用；不是本轮重验或全机器无安装的证明，更不证明 BGS Claude CLI 可调用 MCP。缺工具是具体环境问题，不是业务必须换一套引擎路由的理由。
