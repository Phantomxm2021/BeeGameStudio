### 保留的边界

资源创作内容、审美与音频听感仍有模型能力依赖；本轮解决的是已证实的传输、工具和上下文组织缺口，不承诺资源质量自动合格。字体下载的授权来源限制没有放宽，其他已授权来源仍可按原路径获取。资源任务可以修复不完整成果，但不能通过扩大设计范围或删掉必要资源降耗。

新增复杂度仅包括字体解析依赖、两个复用原生调度的资源分组、回执问题 ID 的小型诊断记录。分别用于解决无法区分系统字体回退、单任务历史膨胀、格式返工时问题被丢弃；没有新增业务审批、模型次数上限或新的设计权威。

目标是让资源生产与 Content 绑定承担必要的游戏制作工作，同时减少历史重传、机械编辑和验证工具探路。保持已确认的玩法、视觉与音频要求，以及现有八文档业务流程。质量依据是实际交付要求和检查覆盖，不是旧流程的通过结论。

## 一 资源和 Content 使用独立任务上下文

### 实施方式

复用现有原生 Agent 调度和结果交接机制。resources、content 各启动一个原生执行任务，由现有业务阶段发起；主会话负责展示与交接，不再亲自执行这两个阶段或追加一轮模型总结。不清空主会话，不修改原生通用压缩、缓存或历史恢复算法。

任务输入包括完整确认 brief、当前阶段目标、当前设计版本、必要源文件的位置、已有资源和数据的位置、用户裁决及未决项、当前可用工具入口。源文件仍是权威；不把模型摘要作为新权威，也不复制八文档全文或历史工具日志。输入缺失或版本过期时明确报告，不能自动发明默认值。

预加载负责方法的必要 Skills，采用现有作者调度方式；职责仍由角色及阶段任务定义。资源任务按实际产物选择资源生产相关 Skill，Content 使用内容管线方法，不预加载所有专业角色或新增固定并行岗位。任务内部是否委派由 Agent 决定，写同一文件的工作必须避免并发覆盖。

只复用分派、事件和结果等待，不复用 Reviewer 的只读命令限制或文档作者的文件范围。资源和 Content 继承当前项目已经授权的原生执行能力；从主任务变为子任务不能意外丢失工具、网络、Question 或文件权限。

### 生命周期与恢复

- 利用现有任务事件、agent ID、结果回执和项目交付状态记录任务对应关系。只有现有持久化字段不足以定位执行任务时，补充最小关联字段；不另建任务管理服务。
- 同一未完成任务的获准继续优先恢复原任务。先检查已保存成果及回执，不能每次继续都启动新作者、重新阅读和重做全部工作。
- 已交接到另一个阶段或已发生影响输入的设计修订，才使用新任务；旧任务结果保留为历史，不能冒充当前版本完成。
- 停止、权限询问、用户 Question、服务重启、子任务失败、工具进度和用量，都沿现有原生链路传播。任务未完成不能因调度结束而进入下一阶段。
- 旧项目不重做已完成阶段；正在执行的任务不中途切换。下一个正常获准的阶段入口采用新方式。

收益确定项：资源任务不接收作者及 Review 的原始对话，Content 不接收资源生成脚本和试错历史。实际还需读取多少专业资料，取决于任务本身，不能预先保证固定输入长度。

## 二 把明确的绑定交给批量工具

### 为什么需要工具

已有格式与引用校验器能检查结果，但不会替 Agent 批量填写绑定。仅要求模型把 Edit 合并，仍依赖它每次都采用高效操作。增加一个窄用途的 Content 绑定入口，让模型一次提交明确映射，程序执行重复赋值。保留原生 Write/Edit；该入口不是强制执行脚本或新的审批流程。

### 输入和行为

输入使用现有内容身份：文件、node ID、Scene component ID、当前文件哈希，以及明确要设置的资源、成员、帧、字体、动作或状态绑定。只接受已有格式中的合法绑定位置，不用数组下标、模糊名字或通配匹配推断目标。不新增游戏决策词典、另一份长期绑定权威或通用补丁语言。

程序先在内存中准备全部受影响文件，使用现有 schema、资源解析和设计指纹逻辑检查；全部前置校验通过后再写入。资源不存在、帧名不唯一、目标失效、格式不合法、修改了布局或其他设计字段，均返回具体文件和节点，不能自动选替代资源或缩放 UI。

复用设计与资源定位字段的同一实现，避免批量工具与基线校验各维护一套允许字段。自动更新受影响文档的资源引用集合时必须保留仍被其他节点、TileSet、嵌套引用或运行时声明使用的条目；无法确定的引用保留并报告，不做顺手清理。Content 索引中的设计及资源版本来自当前业务输入，不能由模型猜测。

执行由原生任务在项目沙箱内调用，权限和事件归属保持可见；BGS 后端不代写游戏内容。`check-content.mjs` 保持只读，绑定操作使用独立的薄入口，复用共享实现而非复制一个大 bundle 到项目。

### 失败和并发

提交前逐文件核对哈希，拒绝覆盖已经变化的文件；重复赋同值按无变更处理。采用单文件原子替换，不承诺普通文件系统无法保证的跨文件事务。中断或后续文件冲突时报告已写、未写及失败文件；下次根据实际文件继续，不能回滚覆盖其他作者的新修改。

输出包括修改数量、文件及节点、实际哈希、未完成项与后续检查范围。批量成功仅说明赋值和结构检查成功，不能证明动作语义、字体适配或最终画面合格。

哈希核对不等于文件锁。写入前再次核对并使用现有可用的文件并发保护；若原生写入链没有可共享的保护，不宣称支持同文件并行修改，也不为了批量绑定新建跨任务事务框架。

资源注册中的 SHA-256 等机器可算字段也应从文件生成；优先复用现有资源命令补一个计算能力。它不推断来源、许可证、用途或质量状态，不自动把条目设为 verified。以该小改动替代 Agent 抄写哈希及临时生成器，不扩展为资源制作框架。

## 三 让验证入口稳定且能够直接完成检查

### 入口不再依赖模型保存临时地址

扩展现有 `inspect-design.mjs` 及 Preview 能力，不新增浏览器服务。命令每次调用时，从服务维护的当前能力描述读取真实入口并申请浏览器连接。Agent 使用固定命令，不再复制带随机前缀的 URL、CDP 地址或浏览器启动参数。

能力描述通过现有任务访问机制授权读取单个文件；包含项目和会话归属、当前执行标识及必要连接信息，不包含账户凭据。不开放整个主机配置目录，不把能力写入游戏源码或交付包。阶段结束、停止和服务重启时撤销；新执行开始时刷新，清理旧执行时不能删除新执行的描述。

描述缺失或过期、浏览器启动失败、连接中断分别返回可识别的环境错误和恢复动作。入口不扫描端口、不猜 API、不后台无限重试，也不能自行恢复用户已停止的项目。压缩后再次调用同一命令仍能读取有效能力；能力失效时由系统生命周期处理。

### 自动处理已知的验证工作

| 工作 | 入口承担的确定性操作 | 仍需专业判断或其他证据 |
| --- | --- | --- |
| 资源可用性 | 按 Manifest 枚举，解析已支持的图片、图集、字体和音频；在托管浏览器解码，报告文件和错误类型 | 是否达到美术要求、音乐是否悦耳、混音是否合适 |
| 字体与布局 | 自动加载已注册实际字体，按已有 UI 源和声明视口批量测量；复用布局算法 | 合法动态文案和数值极值需源中已有明确值；缺失时不能假装已覆盖 |
| 完整 UI 静态呈现 | 接入与 Editor 共用的只读绘制路径，从保存的 JSON 与实际资源渲染，输出截图及遗漏项 | 审美判断、动态效果与实际游戏输入仍需后续检查 |
| 检查结果 | 返回完整问题列表、检查对象、源哈希、检查器版本及未覆盖项 | 一张截图或零格式错误不能代替交付判定 |

不得静默忽略不支持的资源类型、UI 状态、字体或节点。静态检查可以批量完成；完整场景动态合成、XR 和游戏运行时不扩展进本次工具，仍由现有对应验收负责。

FontFace 加载成功不等于所有字符都由该字体绘制。已知缺字应报告；无法可靠确定实际字形回退时保留未验证范围，不能把系统回退字体的测量包装成目标字体通过。

### 必须补齐的现有缺口

当前 `inspect-design.mjs` 要求 `--preview-api`，最终字体又依赖外部页面注册 `window.beegameDesignFontFaces`；无页面时只做候选字体与几何测量。`content-consumer.mjs` 也不渲染屏幕。因此只包一层命令不能解决 Agent 手写 HTML 和 Playwright 的问题。

先补资源解码和自动字体加载，再把 UI Editor 的只读节点绘制及其必要样式、资源解析抽为双方共用能力。不能复制 `renderUiNode` 拼另一套近似渲染器，也不能只导出函数却漏掉字体、响应式、图层与样式依赖。编辑工具、选中态及拖拽不进入只读画面；不具备覆盖的角色或展开态明确标记未验证。

该项需要实现投入，但直接替代本例重复出现的浏览器脚本与错误探路。完成之前只能声明解码、字体和几何入口可用，不能宣布完整 UI 验证已落地。

### 结果输出与复用

一次检查覆盖其已声明的相关文件和视口，直接输出完整诊断，详细几何另存可读文件，避免 Agent 为找字段连续重跑与过滤。没有问题也必须给出覆盖数量和未覆盖范围。

已有结果仅在实际输入、检查器版本及相关环境条件相同的情况下复用。浏览器环境不可用、字体变化、源变化或视口变化均不能复用原通过结论。本轮不另建缓存调度服务。

## 四 资源生产减少无效纠错

资源 Agent 在既有任务内先确认可用制作路线和最易失败的真实产物，再扩展同类资源。例如文字采用现有字体能力还是定制绘制，必须满足既定字符与样式要求；不把手工编码复杂字形视作所有项目的默认实现。具体选型不能硬编码为贪吃蛇、像素风或某种字体。

先使用实际文件、原生工具和现有授权回退。失败有明确原因且能局部修正时继续；相同原因反复出现时重新评估方法，必要的取舍走已有负责人决策或 Question。没有依据自动降级、按次数强制回退或无限追加尝试，都不属于本方案。

这一部分仍有模型判断，不承诺消除所有返工。确定性改善集中在注册、解码、路径和格式诊断，生产审美保留人工或后续实际观察的边界。

## 验收要求

### 离线与本地浏览器验收

1. 在主会话放入大段无关历史，资源及 Content 子任务的实际模型请求中不出现这些历史；确认 brief、用户裁决和责任源仍可访问。包括阶段转换、未完成任务恢复、旧项目继续及服务重启场景。
2. 多文件批量绑定覆盖不同 UI 角色、Scene 组件、多文件资源、图集帧、嵌套字体引用；与明确预期逐项对照。缺资源、歧义 ID、哈希变化、越界路径、设计字段变动必须有可定位结果，不能静默部分通过。
3. 运行中中断、并发文件变化和重复提交，不覆盖新数据、不重复启动作者、不错误推进阶段。完成与失败的工具事件在对应 subagent 面板可见，用量包含子任务和压缩但不重复计算。
4. 浏览器能力缺失、失效、重启、错误资源内容、字体缺失、错误 MIME 和错误相对路径均得到明确诊断；正常路径用固定入口完成。恢复入口不扩大权限或重开用户已停止的任务。
5. 用独立构造的响应式、嵌套布局、图集、字体、合法长文案及展开态验证 Editor 与检查入口一致；缺失对象必须表现为覆盖失败或未验证，不能只统计已成功对象。

### 真实流程与成本验证

本轮规划不启动付费运行。实施后的真实验证使用不同类型的新 idea，并采用相同模型配置、明确的相近交付范围，记录缓存条件。贪吃蛇只作历史成本参照，不反复调优成专用测试答案，也不人工修补原测试产物。

至少分别观察一个简单 2D 项目、一个多界面项目和一个资源种类不同的项目。每个项目报告各阶段请求数、平均及峰值上下文、非缓存输入、缓存输入、输出、失败与返工链、交付结果。三例只能证明样本表现，不证明所有项目稳定。

通过标准：已确认需求没有被减掉；可确定检查覆盖完整；资源和 Content 不携带无关主历史；重复赋值能批量完成；正常验证无需环境探路和手写通用驱动；发现的问题能进入既有修订处理。若 Token 下降但交付缺失或检查漏项，判定优化不合格。

不设强制 Token 或轮数上限。若请求数或上下文未下降，先用记录判断是在必要制作、重复探索还是工具缺口上，再决定是否继续修改；不默认追加 Reviewer 或扩大自动重试。
