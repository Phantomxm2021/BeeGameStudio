## 本轮落地记录（2026-10-08）

### v1.8 补齐记录

v1.7 的落地声明不充分：任务输入已取消首屏门槛，但原生作者系统提示仍保留；批量 UI 报告没有提供修正所需矩形，`--details` 也未返回批量节点；Scene 作者仍需拼单文件命令，规则结果复用缺少实际接入。本轮按真实调用链补齐，而不是追加 Review 角色或循环。

| 已证实缺口 | 本轮实现与边界 |
| --- | --- |
| 两处作者指令冲突 | 原生作者系统提示与文档局部任务一致：先保存必要批次；单源检查只用于具体疑问，不再是扩展批次前的强制门槛。回归检查真正生成的 Agent 系统提示，不只匹配任务字符串 |
| UI 批量报告需要猜字段、再次读取几何 | 默认 `diagnostics[]` 给出来源、节点、视口、关闭条件、实测边界和相关遮挡对象；父容器数据使用算法原有局部坐标，明确区别宿主坐标。跨文件遮挡及 Scene 裁切也提供实测数据。`--details` 返回 `measurements[].nodes`，帮助与作者任务同步说明该结构 |
| Scene 需要临时 shell 循环 | `check-content.mjs --scene-layouts WIDTH HEIGHT [WIDTH HEIGHT ...]` 程序遍历已保存 Scene，接受嵌套及含空格文件名，逐文件汇总结构与指定视口几何；单文件失败不跳过其余来源。不猜最终 UI 游戏视口，不声称验证玩法／可解性；3D／XR 几何和未声明必要可见对象明确未验证 |
| 求解输入与实际 Scene 可能分离，重复求解无依据 | 复用现有 `calculate-balance.mjs --scenes`，自动读取保存的 Scene 并传给模型，不新建求解平台。既有结果附录记录模型、规则读取来源、Scene 成员、工具与输出身份；`--check-result` 只读核对，不执行模型。宿主对已链接、带记录的附录检查过期输入，失效交原有修订路径。旧结果没有记录则不能宣称新鲜，但不强迫所有历史笔记迁移 |
| 工具存在但实际任务／权限未接通 | Scene 作者得到批量入口、真实数据接口和计算工具；UI 作者得到确认方向／维度参数和结果字段位置；Inspect／Verify 放行只读有效性检查，仍禁止执行项目求解脚本。Revision 重算仍限已授权的模型／输出路径，并保留原生执行权限 |

计算记录只证明已登记字节未变，不能证明模型真正使用了每项输入、导入依赖已全部登记、规则正确或覆盖充分。必要语义与规则边界仍需核对，不能把哈希当成可解性证明。没有增加自动缓存服务、额外摘要阶段、硬调用次数限制或通用规则求解器。

本轮没有重置单个作者长历史；通过直接报告、批量入口和只读复用减少无效调用，但净 Token／耗时改善尚无付费运行证据。`CouldntReadCurrentDirectory` 仍未复现，不列为已解决。

本方案把正常交付主线明确为设计收口后冻结，再生产和验收。冻结前调整 UI 空间问题的检查与修正路径，并处理 Scene 阶段已确认的路径混用、临时批量脚本错误、重复求解及检查输入与实际产物分离问题。程序报告直接交给 Revision，移除重复总结报告的空间 Review，保留修改后重算与 Verify。原有专业审查继续检查界面覆盖、交互完整性和美术一致性，不作为每次空间修正的中间步骤。

本次范围是减少无效执行和重复模型交互，不是删除必要的可解性、数据一致性或修改后验证。工作目录不可读的运行异常须先定位，不能假定增加提示词已经解决。

技术设计保留前期基线和冻结前接线补全两个工作时点，取消默认全文重读八文档与整篇重写。设计文档只保存版本、设计决定和真实依赖；评审与放行状态统一由现有交付记录维护，不要求模型在正文重复更新。

通用生产路径优先处理检查范围不一致、现有工具难以直接消费、无关历史持续进入后续任务三项问题。临时脚本、全文改写和底层请求异常分别处理，不将所有成本归为模型能力，也不靠模型次数上限、删除必要验收或追加审查角色降耗。

内部资源工具优先收拢图像处理和图集打包，再提供必要的基础音频导出；不把某次 Agent 自写的 SDF 和音频脚本直接升级成通用引擎。统一机械生产能力，保留每个游戏的创作、风格和专业取舍。

主要方向可保留，但 v1.5 尚不能直接作为无歧义的实施依据。本次修正以下缺口；严重程度针对方案可能引入的错误，不代表这些新路径已经运行过。

| 级别 | 原方案缺口与依据 | 本版修正 |

## 正常交付主线

**八文档及实际 UI Scene 布局完成 → 必要程序检查与一次专业 Review → 必要的集中 Revision 与 Verify → 冻结设计基线 → 资源制作 → Content 绑定 → 实现 → 交付验收。**

程序空间报告直接交给 Revision，不需要一个只总结报告的空间 Review。专业 Review 检查语义、遗漏和专业一致性，仍然保留。能在同一次合法 Revision 内集中关闭的问题不分成两套修订。

具体调度为：保存全部来源并做程序检查 → 既有专业 Inspect 对同一版本完成检查 → 合并程序诊断与语义问题进入一次 Revision → 修改后程序检查与定向 Verify → 接受基线。程序诊断不需要 Inspect 重新描述、定严重程度或伪造 finding 才能进入修订；专业 Inspect 不能被诊断通过替代，也不能与修改同一来源的 Revision 并发。输入损坏导致部分语义无法检查时，Inspect 明确缺口，修正后由 Verify 补查该部分，不能当作已检查。所有必要检查已完成且无须修订时，Inspect 后直接由宿主放行，不另派一次仅确认空报告的 Verify。

冻结前完成设计收口，冻结后以完成游戏交付为主，不因为新的偏好、润色意见或“可能更好”不断重开策划。资源后出现问题不自动返回设计 Review 或 Revision；先判断应修资源、绑定还是实现。

### 已确认的流程缺陷

| 缺陷 | 实施要求 |
| --- | --- |
| 不影响实质执行的文档状态清理，被设置成 Content 前必须关闭的事项 | 删除这类状态待办触发自动回审的行为。已有实际决策时，非阻断清理不承担生产放行条件 |
| 首次 Review 的已知必要问题被延期，资源完成后再检查和修订 | 必要设计问题在冻结前集中关闭；不能通过更换 follow-up 标签或截止阶段延迟处理 |
| 定向 Revision 或 Verify 在结束时被要求完整补读无关文档 | 任务范围与结束检查一致。初次专业审查需要全局覆盖，定向修订与复核只要求相关来源及关联影响 |
| 后续发现问题就自动回修文档，放大调度、历史上下文与返工 | 冻结后取消默认自动回修设计。必要设计变更由用户明确决定后，复用既有受影响变更入口 |
| 最终技术任务默认全文读取八文档，作者整份写入技术正文与索引 | 改为专业接口接线补全，按来源定位读取、局部编辑，并在已有联合 Review 核对实际改动 |
| 修订已保存且 Verify 声明关闭问题，正文仍写“草案、待联合评审” | 去掉正文中的动态流程状态；宿主依据当前版本的有效回执和检查结果放行，不能以正文措辞或模型声明判断 |

冻结不是保证设计零缺陷，也不是允许明知核心要求互相矛盾仍宣布合格。它表示生产按已接受的版本执行，允许已知非核心限制，不把交付验收变成第二次策划。

## 技术基线与接线补全

技术收口不是发现一个新技术故障，也不是重新规划游戏。前期技术基线让专业作者知道平台约束；后期接线补全让实现者知道怎样消费专业产物。两者仍写入同一份 `TECHNICAL_DESIGN.md`，不增加另一份技术权威文档。

### 两个工作时点

| 时点 | 必要输入 | 技术作者交付 | 不承担的工作 |
| --- | --- | --- | --- |
| GDD 完成后的技术基线 | 用户已确认的平台要求、GDD、现有平台能力与数据格式 | 运行框架、坐标及数据约定、规则与表现分工、生命周期底座、平台限制 | 猜测尚未确定的 UI、音频、资源决定，提前写一套替代答案 |
| 专业产物保存后、联合 Review 前的接线补全 | 当前技术基线、专业文档与已有索引、实际 UI Scene 及资源计划 | 缺失的消费接口、加载与事件连接、受影响条款、实现任务及完成条件 | 重新总结八文档、复制业务规则、重写仍有效章节或重新策划 |

接线任务保留独立上下文，不继承前期作者的完整排错历史。系统交接当前文件、已有索引和必要源位置，不默认要求第二次通读八份正文，也不新增一个模型先压缩或总结八文档。原文始终可按需读取；相关来源确实不足时扩大读取范围，并明确缺口，不能为节省 Token 跳过依赖。

### 接线必须补齐的内容

| 专业决定与产物 | 技术接线需要回答的问题 |
| --- | --- |
| UI 页面、操作及实际 JSON | 怎样加载并消费节点和布局，按钮怎样连接导航与游戏动作，哪些绑定由 Content 完成 |
| Scene 节点、坐标及实际 JSON | 怎样转换为游戏规则数据，怎样投影到画面和 UI 游戏区域，避免另造一份布局 |
| 音频事件及生命周期要求 | 游戏事件怎样触发声音，怎样处理手势解锁、状态切换、后台与清理 |
| 资源清单与规格 | 何时加载、共享与释放，怎样处理失败，哪些已授权回退可用 |
| 数值与规则 | 程序怎样读取和消费权威参数，不另定阈值或凭记忆复制数字 |
| 各专业必需交付要求 | 实现任务怎样引用所有者条款和实际产物，以什么证据判断完成 |

该表是任务交接范围，不是新增全量 Schema 或 Decision Taxonomy。项目不适用的事项可以说明不适用；已有完整接线不重复编写。专业引用和实际产物必须可定位，不能仅交接一句“按照文档实现”。

### 局部补全与实际差异检查

1. 先读取当前技术基线，再依据已有索引定位各专业的接口、约束、事件和交付要求。已经查明的源位置直接使用，不通过模型反复寻找或总结。
   必须核对全部已登记必要输出与实现任务的关联，而不是仅挑选少数接口。索引遗漏的要求仍由专业 Inspect 对照原始需求及正文发现；程序只能证明已登记项的覆盖，不能宣称需求语义完整。
2. 只新增缺失的接线与任务章节，修改确实受影响的旧条款；仍有效的规则、架构和解释保持原样。沿用现有编辑工具，不依赖一句“不要重写”的提示作为保障。
3. 技术作者不改变其他专业所有者的决定。无法同时实现的要求给出源条款、影响和缺少的决定，在冻结前由现有 Revision 或有权者处理，不悄悄选择一边。
4. 完成后沿用既有版本规则，并同步受影响索引。引用与索引检查使用宿主最终采用的现有入口，不由作者临时自写另一套检查替代。
5. 将实际改动范围及关联来源交给已有联合 Review。程序可确认文件、版本、引用和差异；是否遗漏接口、改了专业决定或存在无关语义改写，由专业审查判断，不伪装成确定性证明。
6. 整份文件写入不自动判错，也不等于所有设计已推倒重做。确需调整结构时说明原因和范围；没有必要的大量无关改写应删除或收回到局部修改，不为润色启动另一轮改写。

不增加独立的技术集成 Reviewer。已有联合 Review 仍覆盖专业一致性和实现任务来源；接线作者按需读取不能被误解成联合审查也只抽查几个章节。发现必要问题时并入同一次合法 Revision 与 Verify。

若联合 Revision 改变了专业接口，在同一次授权修订内同步受影响技术条款和任务引用，再由 Verify 检查关联影响；不在联合审查通过后额外调度一次全文技术集成。

## 文档内容与交付状态

本轮已核对到技术文档升至 v1.2，实际条款已修订，Verify 回执声明问题关闭，但正文仍保留“草案、待联合评审”等旧表述。现有放行逻辑保存交付状态和基线，不同步修改这些正文文字。这是状态重复维护造成的不一致，不等于整次修订没有保存，也不能仅凭 Verify 的声明认定宿主已经放行。

### 单一状态依据

| 内容 | 保存位置与使用方式 |
| --- | --- |
| 文档版本、设计决定、规格、来源及真实未决依赖 | 保留在专业文档和已有索引中，供下游实施 |
| 待审、修订中、Verify 结果、宿主是否放行及接受的基线 | 使用现有交付状态与有效回执，不在正文维护另一套动态标签 |
| 尚未完成的资源绑定、字体测量、TileSet 边界或运行验证 | 保留实际要求、责任和验证阶段，不因设计通过就写成已经完成 |

下游任务由系统提供当前适用基线和阶段状态。Agent 不通过标题中的“草案”或正文中的“待评审”猜测权限，也不通过作者的“已完成”声明决定是否进入生产。

### 更新与失败处理

1. 作者模板和任务要求不再写入会随流程变化的“待联合评审”“某文档待编写”等标签。需要引用的来源使用实际位置；来源真的缺失时仍需明确，不能只删掉词语掩盖缺口。
2. Revision 完成时保存实际改动和版本，进入 Verify；此时不能提前把基线标为通过。Verify 必须对应最终文件及有效证据。
3. 宿主接受有效结果、必要检查通过且必要问题关闭后，沿用现有状态保存入口记录基线与下一阶段。任一条件失败或状态保存失败，都不宣称正式放行；不新增第二套状态文件。
4. 放行后不再自动重写正文来添加“已通过”。这样避免为了更新标签改变刚审过的文件、使指纹失效并再触发审查。
5. 对冻结前正在收口的新项目，必要的过期文字清理并入已有授权编辑，不另开 Review 或付费任务；最终验证对应清理后的文件。纯流程文字不得设置 Content 前硬截止。
6. 对已经冻结的旧项目，不直接修改文档或历史回执。任务交接以已有正式基线为准，说明正文状态文字过期；只有实际设计问题或明确用户变更才按前述分流处理。

“正式基线已接受”只说明设计阶段放行，不证明资源、实现、手感或最终游戏已通过。状态统一不会解决语义漏检；真实缺少的设计决定仍需处理，不能归为文字清理后忽略。

## 通用生产问题与调整优先级

| 归因 | 已证实的问题 | 调整动作及实施位置 | 优先级 |
| --- | --- | --- | --- |
| BGS 流程设计 | 定向 Revision Verify 在结束时被要求补读整份文档 | 在任务生成、读取核对与放行检查统一范围；重点核对 `project-author.ts`、`project-conversation.ts`、`src/beegame/saved-draft-check.ts` 与 `design-review.ts` | P0 |
| BGS 材料设计 | 正文反复维护动态生产状态，制造跨文档同步修订 | 按前述“文档内容与交付状态”执行；清理生成要求，不改写旧项目证据 | P0 |
| BGS 执行接口 | 布局报告、回执和归档读取存在摸索或口径差异 | 复用宿主实际入口，直接返回完整问题和准确定位；回执提交校验与最终放行共用必要规则 | P0 |
| Agent 执行策略 | 自造检查工具、猜字段、全文重写 | 将已验证入口交到当前任务，按报告和来源局部修订；确有缺口才写最小任务脚本 | P1，与对应入口修复一起实施 |
| 上下文组织 | 地形、图标、音频、注册和收尾共用增长历史 | 在现有可独立交付的资源工作之间交接实际产物，后续任务不继承无关制作和排错历史 | P1 |
| 底层请求异常 | 一次流式失败及回退造成额外耗时 | 保留错误与原生恢复证据，核对重复执行和用量统计；不把偶发异常扩建为新的重试框架 | P2 |

P0 先消除确定的流程和接口返工；P1 随后处理生产工具复用与上下文隔离。P2 的基础错误记录并行保留，只有证据显示反复发生或影响恢复正确性时再扩大修复范围。本优先级是系统改动顺序，不是给游戏缺陷重新定级。

### 任务开始和结束使用同一检查范围

初次联合 Review 覆盖八文档的全局一致性；定向 Revision Verify 覆盖原问题、实际改动及必要关联。可写文件列表是权限边界，不等于其中每份文件都必须全文重读，也不等于读取一段就证明语义已经检查。

1. 派发任务时沿用现有 finding 的文件、源章节、影响和关闭条件，明确必要关联要求与程序检查。缺少关闭条件或关键来源时在开始阶段报告缺口，不把摸索留到最后交接。
2. 核对 `missingSavedDraftReads`、`stopHooks.ts` 及任务生成调用方：全局 Review 保留完整材料读取核对；定向任务以已有 finding 的源章节、实际修改范围及已知消费者引用为起点，而非由模型自由声明已读。复用原生读取记录核对当前版本覆盖；章节移动、来源缺失或关联范围不能可靠定位时，扩大到对应文件或明确未验证，不默认扩大到八文档。实现前核对原生记录能否表达所需范围，不承诺只改提示即可支持局部读取核验。
3. 实际修改后读取受影响条款及关联要求，必要时扩大到相邻章节或整份文档。扩大范围须由具体依赖或新发现问题支持，不因进入 Verify 就自动扩成八文档。
4. 引用、格式和来源指纹等廉价程序检查可以按正确性需要扫描更广范围；程序扫描不等于要求模型再次阅读同样的全部正文。有效检查结果仍按输入变化规则复用。
5. 原问题之外出现真实必要问题时，记录原文与影响并按已有权限处理；不能为维持窄范围隐藏它，也不自动重新开启全局 Review。来源无法定位或未完成必要读取时保持未验证，不删掉所有读取核对来换取低成本。

### 检查与读取入口直接可用

继续使用现有 `check-content.mjs`、`inspect-design.mjs`、资源检查和绑定入口，不新增包办生产的工具平台。

- 对当前任务直接给出适用命令、输入路径、参数和结果位置。算法诊断与宿主放行使用同一实现；前置条件不同造成的差异须明确，不能把草稿检查通过写成生产通过。
- 同次结果返回全部问题、覆盖和缺口。详细几何或大结果按需读取，不能只给一个文件路径后让 Agent 猜里面的字段。
- 大输出使用原生已支持的文件定位与读取能力；正文标明完整输出位置和实际读取方式。若归档搬移、读取权限或定位失效，应修输出到读取的连接，不让 Agent 改路径碰运气；不另造 BGS 专用归档层。
- 回执提交前暴露字段、路径和必要来源检查错误，提交校验与宿主最终检查共用规则。格式失败只修回执；实际输入已变或证据失效才重做对应检查。
- 连续同样的失败应定位输入、接口或能力缺口，不逐次切换模式、截取输出或重建检查器。错误文案和说明只是辅助，不能代替接口修复。

### 资源制作和上下文交接

资源生产保留完整美术和音频要求，允许作者选择专业制作方法；优化的是重复建设工具和传递历史，不是删掉 BGM、美术或必要质量检查。

1. 从实际日志逐项确认重复的机械操作及对应能力：参数校验、批量文件处理、资源注册、解码检查和格式转换。已有经过验证的能力直接复用；尚无能力且反复失败的操作，只补最小函数或脚本并做本地回归，不预建万能资源生成器。
2. 创建工具和验证工具分开说明。资源解码通过不代表风格、构图或听感合格；检查器也不能冒充生图、图集制作或音乐创作能力。
3. 非必要不让生产作者重新解析压缩加载器、检查器源码或重建浏览器驱动。现有入口不支持当前必要操作时，说明缺口，允许最小相关脚本；该脚本读取实际产物，不能复制一套权威数据或代替宿主检查。
4. 沿用现有资源任务能力，将能独立保存和验收的整组视觉与音频工作分离上下文。组内相关资源保留共同风格约束；不按每张图片、每个音效或每次工具调用拆出一个新 Agent。
5. 资源注册与最终交接读取已保存资源、已有索引、相关要求、有效检查结果和未关闭问题，不继续携带全部制作轨迹。已有有效注册和结果不再让另一个模型重抄或重算；未交付项仍明确保留。
6. 更换上下文只发生在产物与证据已保存、职责可明确交接的边界。不在未完成写入、未解决权限或原生工具正在运行时清空会话；不中断正常原生恢复来强制重启。
7. 后续任务收到的是当前版本的真实来源及必要约束，不只是模型摘要。原始日志留作审计，不删除；它们按需查阅，而不是默认注入每一次请求。
8. 同一批次已知且相互独立的读取、检查或修改可以合并执行，前置依赖不明的操作保持顺序。收尾由现有宿主保存状态和机械检查，不为确认文件存在、转述 PASS 或重写一份交接说明再调用模型；语义未决事项仍由负责角色处理。

保留一个现有 resources 阶段及其总任务、最终回执和恢复关联。若按视觉／音频分工，子任务只负责明确独立的产物；共享 `asset-manifest.json` 的写入与最终注册由一个现有负责人汇总，其他任务返回实际文件与来源，不各自重写整份清单。子任务完成不等于整个资源阶段完成。取消、权限等待、部分完成和服务重启均沿用原生任务恢复，不因换上下文重复生成或注册。是否采用分工取决于现有能力和净成本，不新增固定岗位。

任务拆分可能增加共同约束的重复读取和协调成本，所以先针对日志已确认的资源长历史路径实施，不把所有阶段机械拆碎。先测净成本和质量；如未改善，重审边界，不能宣称“独立上下文必然更便宜”。不新增固定轮数、Token 上限、自动摘要流水线或第二套任务数据库。

### 请求异常单独处理

核对原生请求日志中的失败、回退、最终结果与实际提交记录，区分模型请求重发和生产操作重做。已有恢复能力优先保留；BGS 不叠加新的静默重试，不把未完成输出计为正式完成，不因请求失败再次执行已经成功的资源写入或发布。恢复后检查当前实际输入和结果是否仍有效，而不是自动重跑整个阶段。

用量按已有请求身份及流式片段规则统计，失败请求有实际用量则单列，没有用量不凭空估计。原始异常与恢复时间单列；未查明原因保持待定位。本次偶发异常不是千万 Token 的主要原因，不以扩大它的修复代替 P0 P1 的工作。

## 标准内部资源工具

目标是让 Agent 调用已验证的机械能力，而不是每个游戏重新编写 PNG 编解码、图像变换、图集打包或基础音频合成。工具不负责决定游戏画风、生成审美判断、选择旋律或重新规划界面。它不承诺素材高品质；品质仍需遵守美术音频要求并实际观看、试听。

### 现有能力与缺口

| 已核对的基础 | 可以复用的部分 | 尚需完成的部分 |
| --- | --- | --- |
| 工作流服务已有图像处理依赖，静态预览使用同类处理能力 | 成熟图像解码、变换与编码，不由 Agent 重写 PNG 算法 | 面向作者的稳定批量生产入口、输入校验、实际输出与错误报告 |
| `sprite-sheet.ts` 已有帧解析与边界检查 | 现有图集元数据格式、帧名归一化规则和消费者校验 | 从实际图片生成兼容图集和准确帧坐标；生产侧不能自定另一套格式 |
| TileSet 格式、资源 Manifest 和资源验收已存在 | 图集成员引用、逻辑尺寸与资源注册、宿主检查 | 输出能直接进入这些现有入口，不让作者重新写注册或检查器 |
| `programmatic-audio-resource.ts` 已有音源、时序和包络参数格式 | 适用的基础音频描述和参数校验 | 核对现有渲染能力；缺失时补最小离线渲染与文件导出，再验证真实播放 |
| 原生生图与资源获取能力已存在 | 创作和来源获取渠道 | 与后处理工具清楚衔接，不把生图结果、检查器或设计参考图当作完整资源交付 |

上述基础不代表内部工具已经可用。尤其现有程序化音频 JSON 注册要求 `provisional`，不能仅清除该标记或修改状态就把它当作最终可播放资源。新能力应交付真实可消费输出并走现有资源注册与验证。

### 工具范围与条件项

| 能力 | 本批或条件项提供什么 | 不自动做什么 |
| --- | --- | --- |
| 图像处理 | 实际解码与信息读取、明确矩形裁切、按指定策略缩放、留边及已有图层合成、兼容文件导出 | 猜测元素语义边界、自动抠掉必要内容、改变配色风格、把 PNG 尺寸当作逻辑显示尺寸 |
| 图集打包 | 批量输入独立图片或已定位区域，固定输入顺序下可重复打包，输出图片及现有格式帧表，检查命名和边界 | 旋转帧、自动裁边帧、把所有资源放进一个大图集、改变动画或资源生命周期分组 |
| 基础音频导出（确认缺口后实施） | 仅在当前资源任务确需程序化音频且现有生成／导出渠道不能满足时，复用已有描述补最小文件导出，报告采样率、声道、时长和峰值 | 作曲、自动把哔声认定为合格 BGM、擅自归一化改变动态关系、替代目标浏览器解码试听 |
| SDF 或复杂绘图 | 不列为首批必需项；先用已有向量、基础图形或生图能力交付适用素材 | 建立通用绘图语言、渲染器或针对本案例的固定形状模板 |

SDF 是通过距离计算绘制形状的一类方法，不是所有游戏都需要的资源工具。只有不同项目重复出现现有能力确实无法完成的具体操作时，再补最小相关能力，不为复用某个脚本而要求后续游戏采用它。

图像裁切可用于明确选区；图集元数据仍不得声明消费者不支持的 `trimmed` 或 `rotated`。原图空白、逻辑显示尺寸、枢轴和动画对齐分别处理，不能把裁得更紧视为天然正确。首批音频输出格式依据现有资源与目标平台能力确定，不同时建设多种编码器。

### 最小实现与调用方式

1. 在现有工作流服务中实现小型生产函数，复用现有媒体库、解析器和资源检查；只增加一个薄的本地调用入口。优先接入现有项目工具部署方式，不新增服务、任务队列、MCP 平台或独立资源数据库。
2. 作者入口按“图像处理、图集打包、基础音频导出”列出操作；命名和部署路径在实施时与现有入口一致。新入口仍是待实现能力，不能在当前任务帮助里冒充已经安装成功。
3. 每个操作接受显式输入、输出路径及必要参数。图片按文件或命名区域批量输入；音频读取已有格式描述。较大批次允许使用输入文件，不让 Agent 在 Shell 中拆分长字符串、展开源码或拼凑宽高参数。
4. 工具安装与依赖属于 BGS 部署，不要求每个游戏临时安装一套媒体库。任务交接给出适用操作、最小完整调用示例、参数单位及结果格式；不得要求 Agent 阅读工具实现源码才会用。
5. 参数和原始文件校验后执行机械变换，再读取实际输出并调用相关现有校验。生产工具检查自己的输出不等于宿主放行；宿主复用相同解析和必要规则，专业质量与目标运行验证仍单独保留。
6. 支持批量处理和必要的同批连续操作，例如明确裁切后打包。只实现实际需要的组合，不建立任意处理图或通用流水线 DSL。

以下是接口必须表达的内容，不另建资源协议；复用现有文件、Manifest 和检查记录可表达的字段。

| 操作 | 必须明确的输入 | 必须返回的实际结果 |
| --- | --- | --- |
| 图像处理 | 源文件、裁切矩形及坐标单位、目标尺寸、保持比例或明确变形策略、输出格式及路径 | 实际输出路径、像素尺寸、格式及透明信息、已执行变换、诊断 |
| 图集打包 | 帧 ID 与源文件或源区域、实际加载分组、边距与过滤要求、输出图片和元数据路径 | 图集尺寸、全部帧名及矩形、边距策略、现有格式元数据、必要检查结果 |
| 基础音频导出 | 已有描述文件、cue ID、计划要求的采样率和声道、输出路径、明确的循环要求 | 可消费文件、实际时长和格式、峰值及削波诊断、循环验证结果或限制 |

默认结果精简但包含完整错误清单、输出文件和检查范围。大帧表或详细采样信息保存为实际文件并给出准确读取位置，不输出像素数组、PCM 数据或整段工具源码到模型上下文。参数错误给出准确字段、实际值和允许条件，不能仅报一个含糊的“生成失败”。

### 图像与图集的正确性要求

- 使用实际解码后的尺寸校验裁切区域；区域越界明确失败，不静默截断。已明确需要跨画布留边的操作必须单独说明，不伪装成合法裁切。
- 缩放策略明确。像素风使用适合其要求的采样方式，其他风格按已定要求选择；不能统一使用一种滤镜，也不自动拉伸满足尺寸检查。
- 图集帧 ID 来自调用输入或现有资源计划。按照消费者实际帧名归一化规则检测碰撞，例如带图片后缀与不带后缀的同名项，不以自动重命名破坏引用。
- 帧矩形由实际操作生成，不让模型手工计算后再复制；检查全部矩形在图片范围内且互不非法覆盖。当前消费者不支持旋转和裁边元数据，生产工具默认不产生此类输出。
- 首批采用已有可靠打包能力；若尚无可复用实现，使用固定顺序的简单行式布局即可，不为追求最高填充率建设复杂优化器。超出目标平台或计划允许的图片尺寸时明确失败并给出实际需求，不自动缩小素材、重分加载组或发明消费者不支持的多页格式。
- 同组资源具有兼容用途、过滤和加载生命周期。背景、字体、音频和无关关卡资源不为减少文件数强行合并；组的决定来自专业计划，不由打包工具猜测。
- 过滤边距或边缘扩展仅按明确要求执行，并验证帧选择不包含误采样区域。逻辑显示尺寸、枢轴和九宫格等设计信息沿用原要求，不能从图集矩形推导后擅自覆盖。
- 生图可能产生不规则共享图。工具接受已确认的命名矩形进行裁切和打包，但不能假设它天然等距或含有正确的分隔；若无法可靠选区，仍需检查实际图片或重新制作，不承诺全自动语义分割。
- 每个实际区域要能被现有消费者正确读取。校验数据再做至少一次真实导入和取帧检查，不能以图片存在或元数据合法替代。

### 音频导出的正确性要求

- 复用现有参数定义和单位。核对描述格式与实际采样率的可表达范围；格式能通过不代表任意采样率均能正确渲染，无法表达或实现的输入需明确失败。
- 噪声等随机生成使用明确输入的种子，在相同配置下可复现。种子属于生成输入，不据此新增玩法随机规则。
- 确认声部时序、包络、声道和最终时长，混音结果不得包含非有限采样值。削波必须报告；是否调整音量或动态关系由既定音频要求决定，不暗中修改听感来取得通过。
- 循环元数据必须与实际消费方式一致。只做了循环边界数值检查时不能宣称无接缝；试听及边界波形检查保留。格式无法承载的循环信息沿用现有资源使用方式，不另造隐式播放器规则。
- 导出文件必须可被目标运行环境解码，检查时长、声道和事件用途。工具报告不等于最终混音、音乐风格或信息反馈合格，实际试听不能删除。
- 基础合成适合某些音效或计划允许的程序化音色，不强制所有音频使用它。音乐需要完整结构、节奏和音色设计，仍可使用已授权的资源获取或生成渠道；不能为复用工具取消必需 BGM。

### 资源注册与修改安全

生产工具负责输出，不默认修改设计文档、UI Scene、玩法代码或冻结布局。资源阶段沿用现有资源注册入口，把实际文件和元数据写入已有 Manifest；Content 继续完成正式绑定，不因工具生成成功就宣布集成已通过。

工具返回可供注册使用的实际路径、尺寸和格式，不另建一个平行资源清单。来源、许可和 AI 程序化加工记录继承真实原始来源；加工第三方图片不能改记为原创，合成音频也不能伪造生成平台来源。

- 输入输出解析沿用项目工作区与权限边界，防止路径越界和符号链接绕过；不允许工具修改未授权区域。
- 输入文件默认保留；输出已存在时要求明确替换意图，不通过先删除失败产物启动新一轮权限申请。既有合法更新能力继续使用，不建立新的覆盖审批系统。
- 图集图片和元数据作为一组输出，复用已有安全写入或临时写入能力。失败时不得把半份产物登记为完成；报告实际留下的文件，不静默抹掉已完成成果或原始证据。
- 参数、解码、执行、输出校验和注册失败分开报告。前几步成功而注册失败时修注册，不默认重新生图或合成。
- 输出大小、解码资源占用及运行时支持范围按现有安全能力处理；这些是程序安全边界，不转化为新的模型次数或 Token 限制。

### 实施批次与交付物

| 批次 | 实施工作 | 必须交付的结果 |
| --- | --- | --- |
| 第一批 图像与图集 | 复用现有图像库，提供批量变换和非旋转非裁边打包；产物进入现有帧解析与资源验收 | 生产函数、薄调用入口、帮助示例、合成回归；图集可被真实消费者取帧 |
| 第二批 基础音频（有已证实缺口时） | 先核对已安装工具及导出渠道，确需补能力时才实现最小导出，不扩建作曲引擎 | 若实施则交付可消费文件与相应验证；现有能力足够时记录复用方式并跳过建设 |
| 第三批 生产接入 | 接入资源任务工具说明与既有注册检查，协调上下文交接，不改变已定风格与职责 | 作者拿到可用入口，宿主使用同一必要规则，真实运行可核对调用及制作结果 |

各批次是系统实施工作包，不增加游戏生产阶段。第一批本地回归通过后即可完成它在第三批中的接入，不等待第二批。基础音频导出是条件项，不作为主流程修复或图像工具可用的前提。SDF 及更多编码或打包优化只有明确缺口后再评估，不预排建设计划。

不把旧项目脚本直接复制为产品功能。可以只读分析其重复机械部分，但通用实现使用独立合成输入核对，不带入本案例形状、固定尺寸、箱子图案、配色、旋律、帧名或关卡规则。

## 冻结前的收口条件

1. 八文档及各自必要输出已保存，必要技术接线与实现任务已补齐；实际 UI Scene 布局与设计来源关系明确。已有索引和版本机制继续使用，不增加第二套权威文档。
2. 下游必须依赖的产品决定已明确；影响核心执行的规则、时序或责任冲突已关闭。当前仍缺的关键决定不能标为“Content 前再补”后进入资源制作。
3. 必要程序检查已执行，失败和缺口已如实处理；几何通过不代替语义、内容覆盖与专业一致性检查。
4. Review 发现的非阻断项明确保留为已知限制或可选待办，不再带有自动强制回审的期限。必要项不能仅靠改标签变成非阻断项。
5. 完成需要的 Revision 与 Verify 后，系统保存当前已接受基线及仍适用的证据。文档实质变化沿用已有升版本规则。
6. 资源尚未生成时，不要求提前证明最终字体、图像、TileSet 或音频导入已经通过。设计需明确规格、适用约束和已授权回退；生产后验证这些事实不是重新做设计决定。

对直接决定布局能否成立、且事后无法仅靠合法绑定解决的未知量，冻结前应使用已有字体／关键样本或最小能力检查确认，例如必要字形在最小支持视口能否容纳、所选 TileSet 几何能否表达设计。无需生成全部资源，也不增设固定原型阶段；检查确实不可得时，明确风险、受影响依赖和已授权回退，不能把这种必要可行性缺口当作普通后续观感调优放行。

未来必要的资源与运行验证仍在对应生产或验收环节执行，其期限不是可选事项；本方案只取消它们被误转换为设计回审的行为，不删除实际验证要求。

文档内容与交付状态按前述单一依据分工；必要的未知设计决定和真正依赖仍需明确，不能与过期状态文字混为一谈。基线放行后不再为了添加通过标签修改已审文件。

已知问题在冻结前就给出处理结论：必要问题集中修订，非阻断问题接受或登记，不能留下已知问题后再付费重复判断它是否成立。集中修订和 Verify 未完成必要关闭时停止该组自动工作，不重新换编号开启审查。

## 冻结后的问题分流

| 问题 | 处理主体与动作 | 是否允许自动修改设计 |
| --- | --- | --- |
| 实现没有遵守文档、遗漏反馈或错误消费 UI Scene | 实现阶段修代码与数据消费，按已有设计复验 | 不允许，不能改文档给错误实现洗白 |
| Content 绑定漏项、资源路径或动作引用错误 | Content 在已有绑定职责内修正并验证 | 不允许改变保护的文字、布局、交互或规则 |
| 资源不符合已定规格、尺寸、风格或播放要求 | 资源阶段修正产物，或使用文档已授权的回退 | 不允许临时降低设计要求 |
| 不影响核心交付的文字瑕疵、状态描述或可选优化 | 记录已知问题并继续生产，不改冻结文档来做无关清理 | 不自动修改，也不自动回审 |
| 必须改变已定布局、规则、范围或专业决定才能继续 | 说明具体矛盾、影响、可选处置及最小变更范围，由用户决定 | 仅在取得明确变更方向后处理 |
| 没有证据证明原设计可执行，或必要平台能力不支持 | 如实报告未验证或失败，继续不受影响的工作；核心交付不能假装通过 | 不自动发明默认值或缩减范围 |

资源绑定后的字体适配、图像裁切、TileSet 边界和音频导入检查仍然保留。检查发现错误时先修产物是否满足已定规格；只有确实需要改变冻结设计时才进入用户裁决，不直接自动分派设计 Revision。

“用户决定”沿用已有明确授权：使用既定回退、按已定规则计算响应式结果、在合法绑定槽选择符合规格的字体或资源，不需要再次询问。当前指纹保护的布局、字号、文字和规则也不能凭模型认为“只是小修”自动豁免；越出已有授权范围的设计变更才提出具体取舍。接口或运行环境故障应修系统并恢复原任务，不能包装成用户的设计决定。

判断依据必须是原要求、当前基线、实际输入和具体执行证据，而不是作者或 Reviewer 觉得“更正确”。影响无法确定时明确不确定性，不能以新增审查循环代替说明。

### 用户决定变更后的处理

用户可接受非核心限制、选择已有授权回退，或明确批准最小设计变更。已授权回退可正常执行，不因使用回退再询问一次。接受限制不能把必需但未实现的功能隐瞒为已完成，也不能伪造通过记录。

只有明确同意设计变更后，才复用现有受影响修订入口：指定来源、责任、可修改文件与影响范围，修订并升版本，重算必要结果，再由 Verify 核对关闭。用户同意不是事实验证，也不是允许重新策划全部八文档。

复核通过后更新受影响基线，恢复实际需要补做的工作，保留仍有效资源和实现；不能仅因文档版本提高就重做整个游戏。若变更仍无法闭环，明确停止及原因，不自动开启下一轮。

## UI 确认的流程

**全部 UI JSON 保存完成 → 批量检查报告保留 → 既有专业 Inspect 完成 → 必要时集中 Revision → 修改后重算 → 定向 Verify。**

不加入“先检查代表界面或共享结构，再补齐其他界面”的强制步骤。不禁止作者按需使用现有检查定位保存或格式错误，但局部通过不能替代全部输出后的覆盖检查。不新增独立的空间 Reviewer、修订角色或循环框架，复用现有 Revision、Verify、版本记录和空间算法。这里的专业 Inspect 就是正常主线已有的联合审查，不是新增一次 UI 审查。

这条自动修订流程适用于冻结前设计收口。冻结后仍可执行空间检查，但其结果按“冻结后的问题分流”处理，不能直接触发改设计；明确获准的设计变更才使用原 Revision 与 Verify 能力。

| 环节 | 职责 | 不应做的事 |
| --- | --- | --- |
| UI 作者 | 完成全部实际 UI JSON，保存适用视口、约束与关联布局 | 用临时样例或另一份布局替代实际输入 |
| 批量检查 | 对照既有页面／状态要求核对实际文件，检查适用视口及明确关联布局，统一汇总结果 | 把全部现存文件通过当作页面没有遗漏；只检查 Agent 临时挑选的文件 |
| Revision | 直接使用报告，在授权范围内集中修正问题 | 修改前重复计算未变输入；重新摸索报告字段；删内容或降低标准来过检查 |
| 修改后重算 | 验证修改及关联布局是否满足空间约束 | 只检查改动节点，忽略父子关系、共享组件、覆盖层与其他适用视口 |
| Verify | 核对原问题关闭及设计影响，确认报告对应最终输入 | 再次转述报告；重新计算相同输入；重审无关文档 |

## 报告要求

同一次批量检查返回一种稳定、可直接使用的结果格式，不要求 Agent 猜字段、切换检查模式或用截取输出的方式寻找问题。

- 列出已检查文件、视口、关联布局和检查范围；缺输入、格式错误、检查失败及未验证项目明确显示。不能以空问题列表表示检查通过。
- 每个问题给出文件、节点、视口、问题类型、原因、必要的实际几何数据及关闭条件；区分明确违反约束、重叠候选与无法检查。
- 有明确共同原因的连锁问题集中描述，例如父容器错误引起多个子节点溢出。没有依据时不强行归并，也不隐藏子节点影响。
- 能可靠计算的修正附推荐位置、尺寸或布局参数，说明坐标系与依据，并注明建议是否经过重新计算验证。无法确定唯一方案时明确需要设计取舍，不给出伪确定答案。
- 默认返回问题与必要依据，不展开全部节点几何或完整 JSON；现有定位入口保留按需读取能力。

“全部检查”指算法当前支持且输入齐备的检查，不承诺一次发现所有 UI 缺陷。某个文件无法继续计算时，继续检查其他文件，并记录该文件未检查的范围。

覆盖分两层核对：程序用已有 UI 输出索引和显式文档链接与实际文件双向比对，列出预期但缺失、未登记及未检查的来源；状态可由同一文件表达，不强制“一状态一文件”。专业 Inspect 再对照原始需求、UI 正文及状态组合检查遗漏，尤其是未登记的页面、展开态、覆盖关系与支持视口。现有几何算法只检查已提供的标记和组合，不能自动证明模型没有漏标。没有可靠预期来源时返回覆盖未验证，不要求另建一份手写页面数据库。

## 结果复用与修改验证

复用系统生成的实际结果，不复用 Agent 自称的“通过”。设计指纹只证明受保护设计字段未变，不能单独作为检查结果有效性的依据：当前指纹有意排除合法资源绑定，而新字体、图片及图集信息可能改变适配结果。

先区分“避免模型重复调用”和“避免宿主重新计算”。当前 `designCheck`、CLI 与回执边界多处直接执行检查，并无已经验证完备的跨阶段检查缓存。本轮优先将宿主本次实际结果交给任务，允许廉价检查在放行前重算；不得为了声称零重算新增缓存系统。

若复用跨步骤的既有结果，必须在原有记录中足以核对：实际读取的 UI／Scene／相关资源文件内容、检查文件与组合范围、视口及确认方向、draft／资源延期等模式、算法或构建版本；涉及字体或运行渲染时还包括相应环境。两处调用同一函数但输入选项不同，不是同一次检查。缺少这些依据时由宿主重算或标为未验证，不要求模型补写哈希证明。读取期间输入变化的结果不能用于放行。设计期资源延期结果不能复用为正式 Content 通过。

Revision 修改前使用仍适用的原报告；完成相关修改后统一重算。能可靠确定关联范围时检查该范围，不能确定时批量重算。Verify 消费宿主确认有效的最终结果，不额外发起相同模型工具往返；宿主为确保当前输入而做的廉价重算不算违规。

空间重算只能验证算法支持的约束。Verify 还需核对修改没有遗漏必要内容、降低控件标准、改变既定交互或破坏关联设计；不能用几何通过替代这些判断。

## 分支与停止规则

- 程序检查及既有专业 Inspect 已完成且没有需要修正的问题：宿主核对有效结果后放行，跳过 Revision 及单独 Verify；尚有未完成的专业检查时先完成它，不能仅凭几何通过放行。
- 冻结前有明确问题或需要判断的候选问题：报告直接交给 Revision，不加中间空间 Review。允许的重叠须有实际设计依据，不能仅凭模型宣称合理关闭。
- 冻结后发现空间问题：先按问题分流修产物或请求用户裁决，不自动返回设计 Revision。
- 冻结前原需求和既定职责内的取舍由授权 Revision 负责人处理；改变用户要求或超出权限时升级，不擅自选择。冻结后的设计取舍遵循上述用户变更规则。
- 输入或必要证据不足：保留未验证状态，说明责任与缺失内容，不宣布通过。
- Revision 修订、重算和 Verify 后仍有问题：保留未关闭项与具体原因，停止自动循环；后续处理需要明确方向，不能自动重新开始同一组审查。

停止边界针对已完成修订与复核后仍未解决的实质问题。任务内修复命令错误、回执格式错误或恢复中断，仍可沿原任务继续，不各算一次设计审查，也不能以修格式为名重开已耗尽的语义修订组。完成部分修改但未通过时保留产物及旧接受基线，受影响下游不消费未接受改稿；不回滚正确工作，也不更新基线伪装通过。

## Scene 问题归因与处理边界

| 已核对的事实 | 归因与处理 |
| --- | --- |
| 原任务包含项目根目录，生成器也使用了正确的项目路径 | 不能归为未提供工作目录。应区分项目根、任务临时目录与原生 Shell 临时目录，执行脚本的实际保存路径 |
| 脚本保存在任务目录，执行命令却使用更深一层的 `$TMPDIR` | 路径使用错误已确认；不要把原生临时目录默认当作任务脚本目录 |
| 两次执行返回 `CouldntReadCurrentDirectory` | 当前目录不可读的底层触发尚未确定，需要检查实际执行目录、目录存在性与沙箱可读性，不把它等同于普通文件不存在 |
| 正常 Scene 文件名被外围脚本拼成含编号和宽高的名称 | Shell 参数拆分错误，不是 Scene 命名规范缺失；批量入口直接消费文件与独立参数，避免 Agent 临时拼接循环 |
| 检查失败后，外围脚本仍输出 `done` 并成功结束 | 失败被外围执行包装掩盖；结果与退出状态必须反映实际失败 |
| 修改关卡后再次求解 | 必要验证，保留 |
| 未改变输入，末尾连续两次重新求解 | 可避免的重复执行；文档计数核对使用已有有效结果，不因此重新求解 |
| 求解器与 Scene 生成器各自维护关卡定义 | 两份输入可能分叉。求解证据必须对应实际 Scene，不能只证明另一份内置关卡正确 |

以上事实用于确定通用修复方向，不向系统写入本测试关卡的布局、路线、答案或专用文件名。

## Scene 检查与求解的流程

**实际 Scene 保存完成 → 批量结构与空间检查 → 必要的规则验证消费同一份实际数据 → 汇总结果 → 使用结果编写或核对文档。**

冻结前已发现的空间问题沿用 UI 的报告直达 Revision、修改后重算、Verify 核对关闭路径；冻结后按问题分流处理。关卡可解性、路线计数与空间可见性是不同检查，结果分别说明范围；不能用空间通过代替可解性，也不能用可解性通过代替实际数据一致性。

- 场景作者可以在冻结前设计迭代中修改关卡。关卡或规则改变后执行必要验证；冻结后不能自行修改关卡来适应错误实现，必要变更须明确授权。
- 正式检查输入从实际保存的 Scene 获取；必要的转换由验证脚本读取 Scene 生成，不由作者另行维护一份独立关卡表。
- 算法所需规则、坐标、对象身份或障碍信息无法可靠取得时，明确未验证，不能使用猜测默认值。
- 尚无适用验证器的游戏，不建立通用解谜求解平台。确有必要时允许最小的任务内验证脚本，但它必须读取实际产物，说明适用规则及限制。
- 读取同一 Scene 只解决数据分叉，不证明验证脚本正确实现了 GDD。对本次使用的关键规则保留能区分正确／错误行为的最小断言或轨迹核对；未核对规则实现的求解结果只能作为有限证据，不能据此宣称可解性已可靠证明。
- 有效求解结果包含对应输入、规则口径及所需计数。文档从这个结果引用，不让模型凭记忆重写数字；正文修改不自动使关卡求解失效。
- 原型与实际运行仍用于验证动态行为、手感和体验，不由静态求解代替。

## 实施原则

1. 批量检查与 CLI：沿用现有算法和入口，统一报告结构与必要修正指导，不新增一套空间计算器。
2. 任务交接与调度：冻结前程序报告直接作为 Revision 输入，不要求空间 Review 重述或制造语义 finding。原有专业审查保留；冻结后不默认自动回修设计。
3. Revision 与 Verify：删除要求模型重复调用未变检查的指令，保留宿主必要重算，明确修订范围、修改后验证和独立关闭核对；实质设计修订沿用既有文档升版本要求。
4. 结果复用：使用本次实际检查或依赖充分的已有记录；设计版本不足以证明资源相关检查有效，没有可靠依据时由宿主重算，不建立额外缓存协议或第二套布局权威。

确定性自动修正不作为本次落地前提。后续仅考虑规则明确、结果唯一且不会改变设计意图的修正，不制作通用自动排版器。

## 实施步骤

以下编号用于定位工作包，不要求所有工作串行等待。先交付已证实 P0 的报告／选项一致与定向读取范围修复，再接入冻结与修订调度；目录异常追因并行，资源工具和上下文优化随后按实际缺口推进。未复现的 `CouldntReadCurrentDirectory` 不阻塞其他已定位修复，报告建议值及基础音频也不是 P0 的前置条件。每项完成对应本地回归即可合并，不等全部工具建完才检验主流程。复用已有检查器、交付状态、权限与版本机制，不增加新角色、任务数据库或通用工作流框架。

### 第一步 定位执行目录异常并明确路径使用

涉及现有 `project-execution-access.ts`、`native-cli-process-runner.ts`、`src/utils/shell.ts`、`src/utils/shell/bashProvider.ts` 与作者任务交接。

1. 核对原生进程与 Bash 子进程的实际工作目录、任务临时目录及沙箱临时目录。日志只记录必要路径和错误，不输出完整环境变量或凭据。
2. 使用合成项目分别验证：项目根执行、任务目录中实际脚本执行、Shell 临时目录中不存在的脚本、目录消失或不可读。区分路径写错与运行环境异常。
3. 依据复现结果修正目录创建、传递、可读性或恢复路径。若无法复现原异常，保留待定位结论，不凭改了提示词宣称修复。
4. 作者交接只给清楚的项目根和已创建任务目录。脚本执行使用实际保存路径；不要复用或改写系统临时变量来标记业务目录。
5. 已有明确项目执行根不重复再提供一套目录规则，也不扩大沙箱权限来掩盖错误。

完成条件：合法目录与实际脚本可正常执行；缺失或不可读目录能准确报告原因，不诱发反复换路径碰运气。

### 第二步 复用批量入口并保留完整失败结果

涉及现有 `game-content-validation-cli.ts`、`design-layout-check.ts` 及其任务交接入口。

1. UI 在全部保存后使用一次批量检查；Scene 复用已有批量覆盖能力，缺少的具体能力只在现有入口补齐。
2. 在程序中处理文件列表和参数，不让 Agent 自造 Shell 拆分、输出文件命名与汇总循环。视口来自已确认要求和实际源数据，不从文件名猜宽高，也不把整个窗口默认当作 UI 内游戏区域。
3. 继续使用现有文件名，不新增强制编号模板。文件路径、宽、高作为独立值传递，正确处理空格及特殊字符。
4. 单个文件失败仍检查其他独立文件，但批次结果保留失败与缺口。CLI 退出状态按其既有约定准确反映失败；不能在最后一条 `echo done` 后掩盖检查失败。
5. 汇总结果直接返回 Agent，不要求它查找临时输出文件、重复解析或截取报错。
6. 使用与宿主相同的确认设置和适用检查选项；草稿模式、资源延期与正式 Content 的差异明确显示。预期输出与已保存文件的覆盖核对沿用既有索引和链接，不能仅扫描目录后宣称完整。

完成条件：多文件检查返回完整汇总；参数错误、缺文件、格式错误与检查失败均可定位，失败不会显示成成功。

### 第三步 统一报告并补充可靠修正指导

涉及现有 `ui-layout-audit.ts`、`design-layout-check.ts` 与 CLI 输出。

1. 沿用现有问题字段补足文件、节点、视口、原因、必要几何数据和关闭条件；字符串报错与结构化诊断来自同一结果，不维护两套判断。
2. 区分明确错误、重叠候选和未验证项；记录受影响范围，归并有依据的共同根因。
3. 首先交付准确定位与实际几何依据。推荐位置、尺寸或约束调整仅复用已有可可靠计算的能力，不作为首批完成条件；若还需搜索布局方案，保留明确诊断交给 Revision，不为建议值另造求解器。未验证建议不能标为已验证。
4. 建议验证也使用现有算法。遇到多解、未知字体或资源尺寸、互相冲突的约束时，明确需要取舍，不为了覆盖全部问题另造排版优化器。
5. 任务输入默认携带精简问题和定位信息，完整几何仅按需读取；不让模型重复转述报告。

完成条件：Revision 可从报告定位和修正；结果不依赖猜字段，建议不会伪装成唯一正确答案。

### 第四步 验证实际产物并复用已有计算结果

涉及现有 Scene 读取与检查能力、任务内规则验证脚本、报告交接及版本记录。

1. 空间检查直接读取保存的 Scene。必要规则验证也读取实际 Scene，或从它机械导出验证输入，保留源对象对应关系。
2. 调整系统任务交接及验证工具的数据来源要求，避免验证脚本与生成器人工分别维护关卡定义；不能只通过修改两份副本来维持表面一致。系统开发代理不直接删除或改写真实项目已有脚本。
3. 计算结果与其实际输入、规则口径、依赖和计算器版本关联。规则脚本本身改变也使旧结果失效。优先使用已有记录机制；若现有机制不能覆盖依赖，由宿主重算或标为未验证，不仅凭设计指纹复用，也不建立第二套完整缓存协议。
4. 关卡、规则或相关几何依赖变化时重新计算；只修改文档叙述或切换阶段时，读取仍有效的结果。
5. 移动步数、推动次数等指标使用明确口径，不混写。核对与修正文档引用，不能用重新求解代替读取结果。
6. 版本与来源无法可靠确认时重新验证或标为未验证；不能为降耗复用可能过期的证据。

完成条件：实际 Scene、规则脚本或相关依赖变化会使对应检查失效；全部实际依赖与选项未变且记录充分时可复用结果。内置另一份关卡通过不能使错误 Scene 被放行。

### 第五步 完成技术接线与冻结前设计收口

涉及现有 `project-delivery.ts`、`project-conversation.ts`、`project-author.ts`、`src/beegame/design-review.ts` 与相关结束检查。

先调整技术接线与状态维护，再接入本步已有的 Review Revision Verify：

- 在 `project-author.ts` 及相关作者交接中，将最终技术任务的默认“全文读取八文档”改为当前技术基线、已有索引、专业接线事项与原文定位；保留按需扩读能力。任务独立上下文不等于重新输出全部旧正文。
- 在作者编辑要求与联合审查交接中明确局部补全，并提供实际差异及受影响来源。联合 Review 核对接线与实现任务，不新增一个总结或审查角色；既有引用检查入口继续负责索引一致性。
- 核对模板、任务提示与相关 Skill，删除动态生产状态标签的生成要求，保留真实未知决定和生产验证要求；不能只改模板而保留任务中的相反指令。
- 核对现有状态保存与放行顺序，使正式接受的基线对应最终版本及证据。状态写入失败不得对外宣布放行；不在放行后自动补写正文标签。
- 给下游交接实际基线与当前阶段。旧冻结文档存在过期标签时按正式记录执行，不因标签新建修订任务，也不静默接受真实未授权变化。
- 将 `saved-draft-check.ts` 的读取结束核对与任务范围对齐：全局 Review 保留全稿覆盖；定向 Revision Verify 核对必要源条款、实际修改和关联要求，不在结束时突然要求整批文档全文读取。保留读取证据与未验证处理，不把可写文件范围当作必读全文范围。
- 将布局报告、回执和大输出定位的可用性合并入现有执行接口修复。只有当前版本的实际检查和证据可用于关闭；回执格式重提不触发重复检查。

1. 冻结前全部 UI 输出后的程序报告作为既有 Revision 的独立输入，不要求模型转写 finding。先让本轮专业 Inspect 在稳定来源上完成，再将其语义问题与程序诊断集中修订；不在另一条支线先改同一文件。仅有程序问题也保留变更的专业影响核对；全无问题则宿主完成放行，不调度空 Revision／Verify。
2. Revision 获得问题、实际来源、必要关联要求与明确写入权限；只修改授权文件和相关条款，集中完成后统一检查。
3. 删除要求模型在每个阶段重新调用未变检查的指令与重复交接。系统依据实际检查依赖确认有效性；必要的廉价宿主重算保留，不要求 Agent 重算来证明使用过工具。
4. 修改后重算受影响及关联布局。无法可靠确定影响范围时批量重算；不默认为只查一个修改节点。
5. Verify 消费最终有效报告及相关改动，核对关闭与设计影响。几何无错误不豁免内容、交互、标准和关联要求的核对。
6. 实质设计修订沿用既有文档升版本与基线规则。Verify 失败或存在未验证项时停止该组自动流程，记录原因，不换编号重新开启循环。
7. 如果现有专业审查正在执行，可合并同一次合法 Revision 的问题范围，避免为同一组改动开启两套修订；不能因此取消专业审查或扩大写入权限。
8. 收口首次 Review 的已知问题：必要设计矛盾在这次集中修订关闭；纯状态清理和不影响核心执行的可选事项不再设置强制 Content 截止，也不因此产生后续自动回审。不能凭“待编写”等关键词自动删除 finding 或 deadline，必须有当前实际决定已经存在的来源依据；既有必要依赖仍缺失时继续阻断。
9. 核对 `neededBefore` 的实际语义。真正核心依赖不允许改成 follow-up 后延期放行；未知资源验证与非阻断待办分别保留适用范围，不把所有未来事项一律提前变成设计阻断。
10. 设计审查、必要修订与 Verify 完成后保存基线并进入资源制作。资源输出未到不能假称导入验证通过，但不为此重新审查已定的设计方向。

完成条件：技术接线按实际来源局部补全；程序报告直接作为集中 Revision 输入；修改前不额外触发重复模型检查；修改后有有效结果及必要的独立 Verify，不能由作者声明替代；必要设计问题已收口；评审与放行状态使用现有记录，非阻断状态清理不制造下游关卡。

### 第六步 取消冻结后的默认自动回修

涉及现有 `affectedDesignRepair`、`prepareProjectDependentDesign`、`advanceProjectDeliveryAfterTurn`、`requestProjectDesignResolution`、`project-conversation.ts` 的调度与任务交接。

1. 逐条核对资源、Content、实现、验收进入或结束时的自动回审触发。冻结基线存在时，不能仅因旧 follow-up 到期、新的作者指控或设计指纹变化，自动授予设计修改权限并启动 Review 或 Revision。
2. 保留来源变化、权限与版本检查。已发现的未授权修改不能因关闭自动修订就获得追认；继续暂停受影响依赖，说明变化来源和缺少的决定，保留原基线及证据。
3. 当前阶段职责内的产物错误留在当前阶段修复，复用现有验证入口。修正资源、代码和合法绑定不等于获准修改规划文档、场景布局或核心规则。
4. 仅需记录的小问题不产生受影响设计任务。对实质矛盾或无法满足的要求，返回清楚的问题、影响、责任与可选处置，由用户决定；不通过自动换 phase 或自动继续消息暗中启动付费回审。
5. 显式用户变更仍走既有 `requestProjectDesignResolution` 或等效已授权入口。程序诊断或模型建议不充当用户指令，也不自动填写用户答案。
6. 明确变更后的 Revision、文档升版本、Verify、失效处理与恢复能力继续保留，只关闭“发现问题就自动回修”的默认入口，不删除必要正确性检查或重写整个交付状态机。
7. 用户变更只覆盖明确范围，更新有关来源和影响记录，不重新开放八文档自由策划；保留仍有效产物，按实际失效范围恢复。
8. 对已有未完成项目：保留原始问题和历史，不静默宣称已关闭；已有明确用户授权的修订仍按授权执行，没有授权的冻结后设计回修暂停等待方向。不能直接改旧项目回执或洗掉未复核变更来完成迁移。
9. 同步相关提示词和 Skill：生产阶段修产物、按基线执行，验收阶段检查交付是否满足原范围；不能一边关闭代码自动回修，一边继续要求 Agent 自行重开设计。

完成条件：冻结后的正常生产不自动穿插设计审查；新问题按职责处理；必要设计变更只有明确方向后才执行；未授权变化和核心失败不会被误放行。

### 第七步 调整资源工具交接与上下文边界

涉及现有 `project-delivery.ts`、`project-conversation.ts`、`direction-authors.ts`、`src/beegame/native-assignments.ts`、资源验证及原生工具结果读取入口。先检查现有能力，不预设每个文件都必须新增机制。

内部工具按前述三批推进。复用现有图像依赖、`sprite-sheet.ts`、`tilemap-contract.ts`、`programmatic-audio-resource.ts`、`asset-contracts.ts`、`asset-contract-audit.ts` 与资源验证入口；按职责提取必要公共能力，不通过导入整个预览器或复制现有检查代码实现生产。帮助和任务交接只有在入口实际可运行后才宣告可用。

1. 依据日志列出资源阶段反复编写、修补或查找的机械操作，标明已有工具和实际缺口。先收拢图像处理与图集生产；音频导出先核对已有渠道，确认缺口才建设。优先交接已有可用入口，验证参数错误、文件名空格、失败退出和实际输入读取，不同时建立 SDF 或万能素材引擎。
2. 在现有资源任务交接里提供适用源条款、实际路径、工具签名、结果位置和限制，删除要求探索检查器源码或重复自写验收的指令；同步对应帮助说明，避免代码与说明各用一套接口。
3. 现有 resources／content 已分别使用独立原生任务，不重复实现这层隔离。进一步核对 resources 内部是否可利用已有委派能力分离视觉与音频制作；固定共享 Manifest 的单一写入方，保留总任务的最终回执及恢复关联。先验证部分完成、取消和恢复；不要以清空会话替代交接，也不专门增派一个模型仅重抄最终清单。
4. 交接使用当前文件、既有索引与有效结果。保留共同专业要求和未关闭问题，去掉无关源码、制作试错和旧工具输出；原日志保持可追溯，必要时按需读取。
5. 批量执行已知独立操作，保留依赖顺序和异常证据。原生流式失败与回退单独核对，不额外添加重试层；恢复不能重复提交已成功产物。
6. 核对调度、帮助、工具结果和宿主放行的一致性。调度不因进入注册或收尾又默认要求全部历史，也不因换上下文丢失必需未决项。

完成条件：正常生产不重新建设已有检查能力；报告、回执和归档可直接消费；新上下文使用当前来源，既有成果和必要约束没有丢失；恢复不重复已完成副作用。质量、耗时与净 Token 改善仍需真实运行确认。

### 第八步 做本地回归并核对真实成本

1. 合成输入覆盖目录、参数、批量失败、输入一致性、结果失效、技术局部接线、状态维护、检查范围一致、报告与归档读取、资源交接、请求恢复、冻结前直接修订、Verify、冻结后问题分流及显式变更的正常与错误分支。
2. 核对模型调用轨迹：没有只为总结报告的空间 Review，没有读取未变报告后再次求解的无效调用，没有为了更新评审标签或重述八文档而新增的任务；保留真实修改后的验证。
3. 系统回归通过后，在有效用户授权范围内做真实付费测试；已有授权覆盖的运行无需重复询问，本次文档审计本身不新增付费授权。使用不同机制的新 idea，不人工预填本案例布局或解法。
4. 按文档作者、技术接线、Inspect、Revision、Verify、视觉资源、音频资源、注册及收尾分别记录模型请求次数、上下文大小、重复读取和检查次数、输入与缓存 Token、输出 Token、耗时及最终交付状态。注明真正检查范围和覆盖，缓存与普通输入分别统计，不把 Token 直接等同费用；请求异常额外耗时与用量单列。
5. 按相近工作量比较结果；减少消耗不能以漏检、取消修订后的必要 Verify 或交付仍失败为代价。不能把旧实现当作正确性标准，也不承诺固定降幅。分别报告是否消除了已知重复路径、总用量／耗时变化和实际交付质量；不同 idea 的复杂度不同，不能把两次总量之差全部归因于系统修复。

完成条件：确定性路径正确，必要验收没有被删除；真实降耗与质量改善分别以实际运行证据判断。

## 验收条件

- 批量检查核对预期与实际 UI 来源，并覆盖全部可检查文件；部分文件失败时仍返回其他文件结果及明确缺口。未登记的需求遗漏不被算法通过掩盖。
- Agent 无需猜报告字段或反复探索检查器，能从报告直接定位并集中修正。
- 冻结前空间报告直接进入 Revision，没有独立模型调用只为总结该报告。
- Revision、Verify 不额外发起重复模型检查；宿主可为正确性重算。复用结果核对实际依赖、选项与版本，合法绑定变化也按影响失效。
- 修订后的独立 Verify 保留，且不能通过删内容、降低标准或改变既定交互取得关闭；无修订且必要 Inspect 已完成时不新增空 Verify。
- 无问题、缺输入、允许重叠、关联影响和持续失败分支均正确处理；失败不会自动无限循环。
- 使用合成输入做系统回归，不人工修补真实测试项目。请求次数、重复读取、Token 与耗时的实际降幅另行验证，不预先承诺节省比例，也不以降低验收质量换降耗。

Scene 与执行接口另需满足：

- 项目根、任务目录、Shell 临时目录不混用；合法路径可执行，目录不可读与文件不存在有明确区别。
- 文件名无需改变，批量参数独立传递；检查失败不会被成功输出掩盖，后续也不因查找错误临时文件反复调用模型。
- 规则验证使用实际 Scene；生成、检查和文档不人工维护两份独立关卡事实。
- 同一有效输入的求解结果可复用，输入变更会使结果失效；文档计数核对不重复求解。
- 没有适用规则验证器、求解未完成或检查覆盖不足时明确未验证，不把算法限制当成游戏已通过。

设计冻结与交付顺序另需满足：

- 正常主线为设计收口后冻结，再生产与验收；资源后的设计回修不再是默认自动路径。
- 已知必要设计问题冻结前关闭；非阻断小问题不被设置为未来自动回审期限。
- 生产和验收按原要求修产物，不通过改文档迁就错误实现，也不以新的审美偏好重开设计。
- 只有明确用户变更方向才能修改冻结设计；旧基线、版本与失效检查继续有效。
- 显式变更后只验证和恢复受影响范围，仍有核心失败不宣称通过；没有以接受小缺陷为由隐藏必需功能缺失。

技术接线与状态维护另需满足：

- 前期基线和后期接线在同一技术文档完成，不默认重读或重写全部内容；实际专业接口和实现任务不因降耗被省略。
- 联合修订涉及专业接口时同步受影响技术条款，不在放行后另起全文技术集成任务。
- 正文不重复维护流程标签；宿主依据最终版本、有效结果和必要检查保存正式基线，不能由模型声明替代。
- 状态更新不触发正文改写或新审查，真实生产依赖与后续验证仍保留；旧项目历史不被直接修改。

通用效率调整另需满足：

- 初次全局审查与后续定向检查的范围明确，任务开始、执行和结束条件一致；必要关联没有被删除。
- 检查、报告、回执和归档读取接口一致，Agent 不必临时建设验收工具或寻找结果字段。
- 后续资源与收尾任务不默认携带无关生产历史，交接仍包含真实来源、共同要求和未关闭问题。
- 不新增硬次数限制、自动重复审查、通用工具平台或摘要框架；未证明净成本改善就不宣称降耗成功。
- 底层请求异常有独立证据及恢复结果，失败成本不重复统计，已完成副作用不重复执行。

内部资源工具另需满足：

- 首批图像处理和图集工具可直接调用，使用实际输入和消费者兼容格式；作者无需重复编写 PNG 编解码或常规打包器。
- 如实际补建音频导出，复用参数格式且临时描述不冒充最终文件；复用既有渠道时也保留真实解码、试听及必要循环检查，不把新音频工具建设当作流程通过条件。
- 生产输出与注册失败分开处理，不丢失已有产物、不默认为再次生成，也不另建平行资源协议。
- 不把统一工具变成统一风格或最低品质上限，不取消必要 BGM、美术层次、动画和独立资源。
- SDF 和通用素材引擎不作为前提；确有新需求允许最小扩展，复杂度必须对应已证实缺口。

## 范围与交付边界

本文件保留完整目标与验收标准，实际完成范围以顶部“本轮落地记录”为准，不将条件项或未完成的真实验收写成已完成。其设计冻结规则更新本文件此前对修订路径的范围解释：自动空间修订用于冻结前，冻结后不默认自动回修；其他方案中更宽的自动设计修复要求不再作为本轮主线，不改写旧项目历史记录。

实施只修改 BGS 系统与合成回归，不直接修改真实项目的文档、Scene、UI、脚本、资源或回执。原项目修改通过用户授权的正常生产流程完成；冻结后的设计变更还需明确变更方向。本次文档更新不授权付费运行。
