# BGS 游戏构建与交付方案

**版本：** v1.0（建议方案）  
**日期：** 2026-10-06  
**适用流程：** Idea → 八文档 → 联合 Review／Revision → 资源制作 → 内容数据 → 游戏实现 → 运行验收 → 交付。

> 核心调整：保留现有五组规划和集中审查，在已有流水线中补齐需求追踪、数据约定、运行证据和明确的停止条件。LLM 负责提出设计与实现；程序依据已定义的检查决定能否推进；无法可靠自动判断的质量要求保留人工判断。

本文基于你描述的流程设计，未审阅 BGS 仓库。已有空间布局计算器继续复用；运行时测试接口、权限隔离等能力是否已经实现，需要按本文逐项核对。文件名、字段和状态是建议，不代表当前系统已有这些接口。

## 1. 先明确方案的边界

**不能仅凭“八文档交给 CC”断定任务一定太粗。** 实际缺陷可能来自需求遗漏、文档冲突、任务缺项、实现偏离、数据没有接入，或者验收没有发现问题。任务拆细只处理其中一部分。

**Capability Map 不是正确性保证，也不需要成为第九份设计文档。** 将它作为统一交付清单中的能力分组即可，不再额外维护一份会与八文档竞争的规格说明。

**规划阶段已经生成实际 UI JSON，就应立即使用现有布局校验。** 不按“规划／实现”的名称决定是否检查，而按“数据是否已经具备可检查条件”决定。占位资源下通过，不能替代真实资源和真实运行下的检查。

**自动检查只能证明已定义条件在已测范围内满足。** 它不能证明没有漏需求、没有其他缺陷，或者游戏一定好玩、优雅。程序判定、模型审查和人工判断各有边界；模型评分需要校准，不宜单独承担最终质量判定。[^1]

方案追求的是：让常见缺陷更早暴露、失败可以定位和回滚、无法验证的内容不会被伪装成完成。交付目标仍是**约定首发范围内的完整游戏**，不是把首个可玩闭环当成最终 MVP。

## 2. 总体流程：保留主链路，只设置三个正式放行点

```text
用户确认 Idea
  ↓
八文档按现有五组依赖生成
  ├─ 作者同时登记需求 ID、跨文档引用与未决事项
  └─ 已产生的 UI／Scene 数据立即做可执行的程序校验
  ↓
汇总统一交付清单：需求索引＋Capability 分组＋任务草案
  ↓
联合 Review → 一轮集中 Revision → 定向复核
  ↓
G1：规划基线通过
  ↓
资源制作与校验
  ↓
补全内容数据、绑定真实资源、复核布局与引用
  ↓
G2：内容可交给实现消费
  ↓
补齐任务输入 → 按依赖增量实现 → 每个任务执行相关检查
  ↓
运行最终候选构建：功能／数据消费／视觉／性能／目标环境
  ↓
G3：交付验收通过
  ↓
交付该次被验收的构建及报告
```

| 放行点 | 要回答的问题 | 不能由此推断 |
|---|---|---|
| G1 规划基线 | 必须处理的设计决策是否明确，已登记要求是否有实现与验收安排？ | 设计没有任何遗漏、实际游戏已经好玩。 |
| G2 内容准备 | 必需资源和数据是否备齐、通过可执行的静态检查，并有明确的消费接口？ | 游戏逻辑已经真正使用这些数据；尚未具备条件的运行检查已经通过。 |
| G3 交付验收 | 当前构建是否满足已批准范围内的必需检查与质量判断？ | 所有未知情况都不会出错、未测平台也受支持。 |

写入时的 Schema 校验、布局计算和逐任务测试是流水线检查，不再各自扩成一套多 Agent 审计。**联合设计审查仍然只有一次集中入口；实际运行验收不能被它替代。**

## 3. 八文档：保留五组依赖，补齐交接约定

技术基线与技术设计补全属于同一份技术设计文档的两个阶段，不新增文档。

| 分组 | 文档 | 本轮需要明确的交接内容 |
|---|---|---|
| 1 | GDD | 首发范围、完整核心循环、输赢／结束条件、主要状态与输入方式。把用户明确要求、平台默认策略和待确认假设分开记录。 |
| 2，并行 | 技术设计基线、美术方向、音频设计 | 技术基线选择平台已有且受支持的数据协议、渲染／输入方式和约束；美术明确参考、组件与风格规则；音频明确事件、资源与播放／静音规则。 |
| 3，串行 | 关卡／场景设计 → 数值设计 | 场景写明空间关系、尺度、通行和相机约束；数值消费保存的场景方案，并检查相关假设。发现不可满足的情况，登记冲突，不能私自改另一份文档。 |
| 4 | UI／UX | 定义界面状态、状态转换、信息优先级和交互区域；生成规划版 UI JSON，运行现有布局校验，能够预览时生成预览。 |
| 5，串行 | 资源计划 → 技术设计补全 | 资源计划汇总前面声明的需求；技术补全明确数据加载、事件绑定和资源消费接口，并核对现有运行时是否支持。 |

### 3.1 技术基线优先选择已有能力，不让每个游戏重新发明协议

优先由 BGS 维护版本化的 Schema、组件注册表、内容加载器和基本测试接口。技术作者在其范围内选择和配置，而不是自由生成一套下游不支持的 UI／Scene 格式。

确需增加组件或修改协议时，作为显式平台扩展任务处理，先补运行时与验证支持，再允许项目使用。不能只因为 JSON 结构合法，就认为其中的组件已经能执行。

### 3.2 一项事实只保留一个权威值

| 事实类型 | 建议的权威来源 | 其他文档的用法 |
|---|---|---|
| 玩法规则与首发范围 | GDD | 引用规则 ID，不自行增删承诺。 |
| 最终可编辑数值 | 规划期由数值设计确定；内容基线建立后，由版本化数值数据保存运行值 | 引用参数 ID、单位和范围，不维护第二份默认值。 |
| 场景结构与空间约束 | 场景文档维护设计约束；Scene 数据生成后保存具体几何值 | 声明需求与约束，不复制一套独立坐标。 |
| 界面状态与交互流程 | UI／UX 维护行为要求；UI 数据保存可执行结构与绑定 | 引用 screen、state、action ID，不在多个文件重复定义实际绑定。 |
| 数据格式和运行时接口 | 平台协议版本＋技术设计 | 使用批准版本，不在后续步骤悄悄改字段。 |
| 资源交付元数据 | 资源清单 | 通过稳定资源 ID 引用真实文件。 |

例如，场景可以提出“某跳跃段需要跨越 3 个单位”，数值给出“角色跳跃能力”。系统检查约束是否满足，但不能因为数值文档是权威来源，就无条件覆盖场景设计。**权威来源用于避免重复维护，不是自动裁决所有设计冲突。**

规划基线通过后，运行参数由内容数据消费，文档描述含义和约束。数值或布局有实质变更时，同步更新受影响的设计说明与基线；不能让文档和 JSON 永久各说各话。

### 3.3 未决事项必须有去向

影响核心玩法、目标平台、资源可实现性或数据协议的未决事项，在 G1 前解决。只有不改变已批准范围、且已有明确默认策略的小问题，才可按平台策略继续，并记录采用了什么默认值。

若用户只确认了 Idea，而未确认详细范围，GDD 应显式展示采用的默认范围。涉及实质范围变更、重要风格选择或无法满足的承诺时，由用户或有权限的产品负责人处理；不能让 Agent 用“合理假设”隐式降级。

## 4. 统一交付清单：CM、需求追踪和任务放在一处

建议使用一个结构化交付清单，例如 `delivery-plan.json`。已有统一规格或任务存储时，直接扩展现有存储，不另建一套事实来源。

| 内容 | 必需信息 | 作用 |
|---|---|---|
| 需求索引 | 稳定 ID、来源位置、来源版本、类型、适用条件、验收 ID | 记录要交付什么，包括行为和跨能力质量约束。 |
| Capability 分组 | 能力 ID、关联需求 ID | 将跨八文档的同一能力聚合，供导航和拆任务。 |
| 任务草案 | 目标、依赖、输入引用、关联需求、预期输出、检查 ID | 将需求变成可执行工作。 |
| 验收定义 | 前置条件、操作、预期结果、验证方式、所需环境 | 避免到实现完成后再随意发明“通过标准”。 |

**不要把所有要求都硬塞成玩法能力。** 字体与风格、输入平台、性能预算、数据可编辑性等，应作为全局约束关联相关任务或最终检查。

### 4.1 需求尽量在写文档时登记，不完全依赖事后 LLM 抽取

新生成文档采用固定的需求条目格式，作者写正文时同步给出需求 ID、验收意图和引用。程序负责收集、去重和检查引用。

已有文档可以让 Agent 提取一次候选需求，但联合 Review 必须回看原文。作者也可能漏登记，因此登记格式不能替代语义核对。对首发承诺和关键状态应重点逐项核对，其他章节按风险检查。

### 4.2 程序检查关系，Reviewer 检查含义

程序可检查：来源锚点是否存在、ID 是否唯一、必需字段是否齐全、依赖是否成环、每个已登记必需需求是否有任务和验收方式。

Reviewer 检查：原文是否有遗漏、同名概念是否实际不同、某项验收是否真的对应需求、规划是否引入未批准的功能。独立 subagent 保留，但它仍可能与作者犯相同错误，不能因“独立审查通过”就当成语义正确性证明。

对外分别记录：

```text
需求映射情况：已登记的必需需求中，有多少已关联任务和验收定义。
运行验证情况：已登记的必需需求中，有多少已有当前版本的有效通过证据。
原文审查范围：哪些章节／首发承诺经过核对，哪些仍待确认。
```

不要用单个“覆盖率 100%”代表“游戏完整性 100%”。如果漏掉了登记，映射统计也发现不了。

### 4.3 一个任务的建议格式

以下是交付清单中单个任务的示例，不是完整 Schema。`checks` 引用 BGS 注册的检查定义，不是任意可执行命令。

```json
{
  "id": "TASK-RESTART",
  "goal": "玩家结束一局后，可以从结算界面重新开始",
  "requirement_refs": ["REQ-GDD-RESTART", "REQ-UI-RESTART"],
  "capability_refs": ["CAP-ROUND-LIFECYCLE"],
  "depends_on": ["TASK-GAME-OVER"],
  "input_refs": [
    "docs/gdd.md#REQ-GDD-RESTART",
    "docs/ui-ux.md#REQ-UI-RESTART",
    "content/ui.json",
    "content/balance.json"
  ],
  "outputs": [
    "结算界面的重开操作绑定",
    "单局状态重置实现",
    "相关测试"
  ],
  "acceptance": [
    {
      "id": "AC-RESTART-01",
      "given": "玩家已结束当前局，结算界面可见",
      "when": "通过实际界面触发重新开始",
      "then": "蛇、食物、分数和计时状态按批准的初始配置重置，游戏恢复运行",
      "checks": ["snake.restart.runtime", "ui.restart.interaction"]
    }
  ],
  "out_of_scope": ["修改初始数值", "增加新模式"]
}
```

`then` 的行为意图还需要落成具体断言，例如分数、长度、状态和计时器的预期结果。**字段填齐，不代表验收已经可执行。** JSON Schema 可以约束类型、必填项和允许的字段；跨文档语义与运行效果仍需额外校验。[^2]

任务生成采用“行为完整、依赖明确、结果可检验”的尺度，不按文件数机械拆分。完整功能清单与增量执行是可借鉴的长任务做法，但不能直接推导出 BGS 的完成率或成本改善幅度。[^3]

## 5. 联合 Review／Revision：一次集中处理，不无限循环

### 5.1 先跑程序，再交给独立 Reviewer

程序先提供结构、引用、依赖、资源声明和已有布局检查结果。Reviewer 读取八文档、交付清单、未决事项和程序报告，集中找语义冲突与缺项。

每个问题至少记录：`issue_id`、来源位置、问题描述、可核查依据、影响对象、建议处理方和阻断级别。禁止只输出“布局不合理”“需要优化”等无法定位的结论。

| 问题类别 | 处理原则 |
|---|---|
| 可复现的硬错误 | 如引用不存在、关键区域越界、必需组件未支持；未修复不得通过相关 Gate。 |
| 明确的设计矛盾或关键未决事项 | 提交冲突双方及影响，由批准的决策规则或有权限的人处理。 |
| 模型发现的疑似问题 | 要求具体来源、截图或复现条件；不能无依据地自动修改规格。 |
| 非必要审美建议 | 进入建议清单，不因模型每轮产生新偏好而无限重做。 |

### 5.2 一轮集中修订，再定向复核

集中修订必须同时更新受影响的文档、规划 JSON 和交付清单。随后重跑便宜的全局程序检查，语义复核聚焦已修问题及其明确依赖。

仍有阻断项就进入 `BLOCKED` 或 `NEEDS_REVIEW`。不能通过自动删除需求、降低验收标准或反复开启“新一轮 Review”绕过停止条件。

这里的“一轮”是初始运行策略，不是证明一轮足够。处理完阻断原因后，可以由有权限的操作重新启动受影响阶段，并产生新版本。

### 5.3 G1 保存一个可追踪的规划基线

保存八文档版本、交付清单、Schema 版本、规划数据、已处理问题和仍允许存在的非阻断说明。实现端读取这个基线，不根据聊天摘要自行重建范围。

“基线通过”代表关键决策已处理、相关检查已完成，不代表设计永远不能改。后续变更必须有差异和影响范围，不能默默覆盖旧结果。

## 6. 资源与内容数据：区分“准备好了”和“已经被游戏使用”

### 6.1 资源制作遵守已经声明的交付约定

资源清单沿用已有机制，但需要稳定 ID、预期用途、必要规格、实际文件、校验状态和版本。资源的尺寸、比例、模型单位、动画名称等会影响布局和运行时的属性，必须在交付约定中明确。

真实资源不符合约定时，应修资源或正式修改约定并复核受影响内容，不能在消费端偷偷拉伸、缩放或替换，以掩盖不一致。

缺资源时可以使用占位资源继续开发和测试，但这只是开发状态。占位项必须可识别、可追踪，最终交付中不得残留未批准的占位资源。风格本身采用程序化图形不等于占位，区别在于它是否是批准的最终表现。

### 6.2 UI／Scene 保留同一套数据身份，逐步提高成熟度

```text
规划数据：结构、稳定 ID、空间意图、必要几何信息、逻辑资源引用
    ↓
补全数据：绑定真实资源、最终内容、事件和参数
    ↓
验证数据：通过该阶段的结构、引用与布局检查
```

这些是同一份逻辑数据的版本演进，不是让两个 Agent 各自重写一套 UI／Scene。补全时尽量保持节点 ID、事件 ID 和资源 ID，避免任务与代码引用失效。

涉及玩法相关的空间约束，不能全留到最后。例如出生点、通道宽度或关键区域尺寸，规划阶段具备计算条件时就应验证；真实碰撞体、动态遮挡等则要在后续验证。

### 6.3 G2 的放行要求

必需资源已到位，数据通过批准 Schema，必需引用可解析，事件和组件名称属于支持范围，真实资源替换后的布局已复核。若已有运行时加载器，还应进行数据加载／预览检查；没有加载器的项目不得把这项标记为通过，应明确留作实现依赖和 G3 必需项。

G2 之后只补齐任务中的真实资源与内容引用，不让 Agent 重新决定游戏范围。若资源或内容暴露了设计不可实现的问题，返回受影响的规划项，产生变更，而不是在实现阶段临时简化。

## 7. UI 与 Scene：三次检查，分别解决不同问题

不是增加三次 LLM 审计，而是复用同一组规则，在条件变化时重新检查。

| 时点 | 检查对象 | 主要目的 |
|---|---|---|
| 规划 JSON 生成后 | 当前已具备的结构、约束、尺寸和状态 | 尽早发现现有规则可以识别的错误。 |
| 真实资源绑定后 | 实际字体、图片、模型与内容长度 | 发现资源替换引起的尺寸、裁切、包围体变化。 |
| 游戏实际运行时 | 最终屏幕、相机、动态状态和真实输入 | 验证引擎最终排版、遮挡、事件与玩法是否一致。 |

### 7.1 空间检查不能简单等同于“所有矩形都不许重叠”

UI 重叠检查应考虑当前状态中哪些节点同时可见，以及父子关系、装饰、模态层、允许覆盖区域和实际点击对象。隐藏页面、按钮内文字、合法背景叠加不能误报。

建议已有计算器逐步覆盖：必需可见元素的有效边界、禁止重叠关系、触控／点击区域、裁切和安全区。文字溢出应结合真实字体和实际排版结果，不能只看 JSON 中的容器尺寸。

目标尺寸、输入设备和语言范围来自已批准的平台配置。检查代表性尺寸及支持范围的边界，不能用三个截图宣称适配所有分辨率。字数变化、大分数、长按钮文案等作为风险场景按游戏需求加入。

### 7.2 Scene 的几何检查必须说明采用了什么近似

包围盒、碰撞体、可行走区域和相机视锥可以作为不同检查输入，但不能混为一谈。包围盒相交不一定是实际穿插；位于视锥内不等于没被遮挡；静态区域可达也不等于当前角色能力和动态机关下可达。

因此建议报告标明检查模型，例如“按静态碰撞体检查出生点净空”或“按当前相机检查关键点投影”，不要只给一个没有范围说明的 `scene_valid: true`。

优先对当前已支持的游戏类型写具体规则，不在第一版追求通用 3D 场景审美与可达性求解器。超出已实现规则的项目进入待验证范围，而不是让 LLM 宣布“应该没问题”。

### 7.3 UI 和 Scene 要在同一个最终画面中检查

HUD 是否遮挡蛇头、操作区是否覆盖关键对象、结算弹窗是否阻止底层操作，需要在合成画面和真实状态里验证。单独通过 UI 编辑器和 Scene 编辑器的检查不够。

对于 Web 项目，DOM 界面可以使用实际边界和交互测试；Canvas／WebGL 内部对象需要引擎侧的场景或状态观测，不能只定位到整个 Canvas 就认为测到了其中的对象。Playwright 的交互检查会核对元素可见、稳定、可接收事件等条件，但这不是游戏语义验收。[^4]

### 7.4 审美控制优先依赖已有设计资产，而不是临时评分

BGS 应积累经过人工认可的组件、布局模式、字号与间距规则、风格配方及参考画面。让模型在明确的选择范围中组合，比把“高级、优雅”留到最后作为一句评语更可操作。

这不要求所有游戏共用一种风格，也不限制用户已经批准的创意。自定义构图或新风格仍可生成，但应明确它尚未获得既有设计资产的质量背书。

| 视觉判断 | 建议的最终依据 |
|---|---|
| 明确的越界、非预期遮挡、按钮无法交互 | 可复现的几何／交互检查。 |
| 与批准参考是否发生不允许的改变 | 人工批准的基准画面＋受控环境下的差异检查。 |
| 新设计是否优雅、层级是否舒服、场景是否有表现力 | 人工看实际画面；LLM 给出候选问题和定位，不能独自签字放行。 |

截图差异只能帮助发现“变了”，不能判断初始画面是否好看。浏览器截图受运行环境影响，基准图与比较图应尽量使用相同环境；首次输出也不能直接自动成为合格基准。[^5]

现阶段，对首次出现的自定义视觉方案，建议保留人工预览确认。只有在已验证模板及其适配范围内、变更没有超出批准规则时，才考虑减少重复人工检查。无法安排必要人工判断的项目应标记“待确认”，不能改成“AI 审美评分通过”。

## 8. 游戏实现：按工作包增量推进，不追求无限原子化

### 8.1 任务分成三类即可

| 类型 | 示例 | 通过条件 |
|---|---|---|
| 基础设施任务 | 加载内容数据、建立输入适配、建立可观测状态 | 接口契约与相关程序测试通过。允许它暂时不能独立呈现完整游戏。 |
| 行为任务 | 吃食物后增长并更新分数 | 所需依赖已就绪，行为断言与相关界面／数据集成检查通过。 |
| 集成任务 | 开始 → 游玩 → 失败 → 重开 | 从真实入口执行完整流程，跨系统结果正确。 |

不要要求每个任务都能独立启动一个完整游戏，也不要把“添加函数”“创建文件”作为主要交付单位。基础设施任务通过，不等于它服务的游戏能力已经完成。

一个合适的任务应能说明一个局部目标、明确输入依赖、给出检查结果，并在失败时定位和回滚。任务文件数与执行时长可用于发现异常，但不设脱离实际项目的统一“原子任务大小”。

### 8.2 任务执行流程

```text
调度器选择依赖已满足的任务
  → 提供基线、相关原文、实际内容引用、接口、已有进度和检查要求
  → CC 实现并提交候选变更
  → 独立检查进程在候选版本上运行相关测试
  → 通过：记录正式结果，继续下一任务
  → 失败：有限修复后重跑；超预算则停止并保留诊断
```

实现上下文不需要每次重读全部八文档，但必须包含项目全局约束和当前任务直接依赖，且原文可追溯。不能把有损摘要当成唯一设计依据。

起步时建议同一项目只保留一个代码写入执行者，先避免并发修改带来的干扰。它可以在同一会话连续做多个就绪任务，不必每个小任务都启动新 Agent。后续是否并行由实际独立性和回归结果决定。

CC 保留任务内部的实现选择权；新增范围、改数据协议、改权威数值和降低验收要求都应提交变更，不能自行决定。

### 8.3 贪吃蛇的任务示例

```text
T01：项目启动、内容加载、输入与可观测状态
T02：移动和方向约束
T03：食物生成、进食、增长与计分闭环
T04：碰撞、单局结束与结算状态
T05：从真实界面开始／重开，并完整重置单局
T06：按批准设计接入 HUD、资源、音频及其他首发要求
T07：完整流程、边界情况、目标屏幕与数据消费验收
```

这只是拆分形态，实际任务从批准的八文档产生。不能因为示例没有暂停、存档或某种演出，就遗漏项目中已经要求的功能；也不能因为常见贪吃蛇有这些功能，就擅自增加。

先形成最小可测试闭环，是为了更早接通系统；之后仍必须完成所有首发必需项。任务完成和整个 Capability 通过分开记录：只有关联的集成验收通过，能力才算通过。

## 9. 运行验收：用真实结果，不用作者声明

### 9.1 先建设可以复用的运行观测能力

为当前引擎／运行时提供最小测试适配器：读取游戏状态、观察 UI／Scene 标识、获取错误日志，以及按需要设置可复现的初始局面、随机种子和测试时钟。

适配器必须连接真实游戏状态，不能只是另一份维护给测试看的镜像。它帮助观察结果，不代替真实输入。关键 E2E 应通过实际按钮或输入路径进入游戏，不能直接调用内部函数跳过待测试行为。

测试模式和发布模式共用游戏逻辑；最终还要在关闭测试捷径的发布候选构建上跑核心冒烟测试。没有这些观测能力时，先补基础设施任务，不把“让 Agent 自己玩一下”视为可靠自动验收。

### 9.2 按不同问题选择验证方法

| 验收层 | 核心内容 | 不能替代什么 |
|---|---|---|
| 构建与加载 | 编译／构建、必需资源加载、启动错误 | 不能替代玩法正确性。 |
| 规则测试 | 状态变化、数值计算、碰撞或生成规则的已定义断言 | 不能替代真实 UI／Scene 集成。 |
| 运行集成 | 真实输入 → 游戏行为 → 界面反馈 → 结束／重开 | 不能证明未测路径没有缺陷。 |
| 数据消费 | 内容修改对实际行为或画面产生预期影响 | 不能只检查文件已经被读取。 |
| 视觉与交互 | 合成画面、实际排版、点击遮挡、关键状态 | 不能仅用代码审查代替。 |
| 性能与稳定性 | 批准设备／环境、内容规模和测试时段下的指标 | 不能把 CI 机器表现当成所有用户设备表现。 |
| 体验判断 | 规则可理解性、节奏、反馈、视觉观感 | 自动规则和模型审查都不能独自证明“好玩”。 |

Claude Code 官方实践建议提供可运行的测试、截图或其他检查，并要求实际证据。这里将它落成 BGS 的外部放行机制，而不是只在 Prompt 中要求模型自觉验收。[^6]

### 9.3 数据消费必须观察效果

建议对关键可编辑数据做受控变化测试。例如在隔离测试副本中，修改移动速度后，观察固定时间内的实际移动距离或步数是否按设计变化；修改出生点后，观察实际生成对象的位置；替换 UI 资源后，观察真实渲染结果。

只读回配置、打印加载日志，或在调试面板显示新值，都不能单独证明游戏使用了它。至少选择对产品承诺重要的配置、场景和 UI 项进行这种检查。

变更测试不得污染最终交付内容。结束后恢复批准版本，并对最终候选构建重新做必要检查；测试副本的通过证据不能冒充最终构建证据。

### 9.4 游戏专用测试本身也需要可信来源

通用 Schema、引用、加载和基础输入等检查，优先由 BGS 维护固定测试。游戏专用断言可以由 LLM 起草，但在纳入正式验收前应核对它是否对应批准需求。

对首批游戏、全新玩法和关键胜负规则，建议人工核对核心断言；对于已支持类型，逐步复用经过验证的规则测试。不能让同一个执行者任意修改玩法和期望值，然后用“两者一致”证明正确。

对重要检查可做针对性故障注入，例如让重开不清分数，确认检查确实会失败；或禁用某个 UI 绑定，确认交互测试能够发现。这样只能验证这类故障是否被覆盖，不能证明测试已经完备。

### 9.5 不允许用模糊状态掩盖未测

正式检查至少区分：`PASS`、`FAIL`、`NOT_RUN`、`BLOCKED`、`INFRA_ERROR`。不适用项根据明确条件登记为 `NOT_APPLICABLE`，不能把必需但无法执行的检查改成不适用。

必需检查没有运行、执行环境失败、结果过期或没有找到测试，都不能通过 G3。测试进程退出码为 0 也不够，还应核对预期检查是否实际执行、是否被跳过。

例如：

```text
已登记必需需求：18
已建立任务和验收映射：18
当前版本验证通过：14
失败：2
未验证：2
交付状态：不通过
```

统计中的 18/18 只说明映射齐全，不说明已经交付完整游戏。

### 9.6 G3 放行规则

当前批准范围内的必需需求都有相应的有效验收结果；不存在未处理的阻断项；所需的视觉／体验确认已经完成；最终资源不是临时占位；最终候选构建与被验收的产物一致。

非阻断问题可以记录在已知问题中，但不得靠标记“已知问题”放行核心功能缺失。降低范围或豁免原本必需的要求，需要有权限的人明确批准，并更新基线和对外承诺。

没有必要对每个游戏每个细节都人工复审，但也不能省掉当前尚无可靠替代方法的质量判断。是否减少人工步骤，应以对应类型的历史结果为依据，而不是以 LLM 自评分为依据。

## 10. 放行权、证据与变更：由 BGS 程序控制

### 10.1 Worker 只提交候选结果，不直接宣布正式通过

CC 可以写代码、补测试草案、运行自检和提出修复。正式 Gate 由独立的程序检查进程执行，记录结果，并由 BGS 状态机决定是否推进。

这里的“独立”首先指执行和权限边界，不是再增加一个 LLM。

| 对象 | 写入权限建议 |
|---|---|
| 项目代码与当前任务允许修改的内容 | CC 在隔离工作区修改，提交可检查差异。 |
| 批准的范围、Schema、检查规则、视觉基准 | 通过专门变更入口更新，不能由普通实现任务直接改。 |
| 新增测试或检查规则草案 | CC 可以提出；批准前不作为唯一正式验收依据。 |
| 正式运行报告、通过状态和交付版本 | 由受控检查进程与 BGS 状态机写入。 |

只在 Prompt 中写“不要修改测试”不构成权限隔离。建议把正式检查定义、基准和报告保存在 Worker 不能直接写入的位置，检查时从可信版本加载；阻止修改检查配置、跳过必需测试、自动更新基准图等绕过方式。生成代码和测试在隔离环境执行，不授予不必要的凭据。

这仍不能防止所有缺陷，但能避免将“执行者自己给自己写通过状态”当成交付依据。

### 10.2 证据绑定实际版本

每次正式报告至少记录：

```text
run_id
planning_baseline_id
code_revision
content_and_asset_digest
candidate_build_digest
check_suite_version
execution_environment
executed_check_ids / skipped_check_ids
results_and_evidence_locations
```

记录所用随机种子、视口等关键测试条件。报告来自实际执行，截图与日志关联具体检查。不同版本的代码、内容或测试结果不能拼成一次“全部通过”。

文件 Hash 只能帮助确认产物身份，不能证明内容正确。验收记录应绑定实际构建产物，而不只记录 Git 提交；否则未纳入提交的文件或构建差异可能没有被覆盖。

### 10.3 修改上游后使相关结果失效

数值、Scene、UI、资源或接口改变后，标记相关结果为待重新验证，重跑廉价全局检查和核心冒烟，再按影响范围补专项检查。

依赖关系不能确定时采用保守复核，不能因为没有登记依赖就默认不受影响。第一版无需开发精确到每个字段的影响图，可先用文档／数据文件／能力级依赖，可靠运行后再细化。

回滚代码不一定回滚全部资源与数据；回滚应恢复对应基线的完整候选产物组合，并确认它仍匹配所使用的报告。

## 11. 失败处理与预算：允许停下，不允许无限自修复

建议设置项目级总预算，以及规划修订、资源修复和任务修复的阶段预算。以下仅是可调整的初始策略，不是经验保证值。

| 失败 | 建议初始处理 |
|---|---|
| 联合 Review 发现问题 | 一轮集中修订＋定向复核；仍有阻断项则停止。 |
| Schema、引用或布局规则失败 | 返回具体错误；允许有限修复，不能删除规则或自动扩大例外范围。 |
| 单个实现任务失败 | 可先设最多两次自动修复；仍失败则保留候选差异和报告，阻断依赖任务。 |
| 工具／执行环境故障 | 与产品缺陷分开记录；按单独的有限策略重试，不能算作验证通过。 |
| 设计矛盾或未知需求 | 交给已有批准策略或有权限的人；没有明确决策就保持待处理。 |
| 预算耗尽 | 停止自动运行，报告完成项、阻断项、证据和恢复点。不得改成“已完成”。 |

同一根因不因换 Agent、重开会话或重命名任务而清零重试次数。每次修复应对应具体失败，禁止无关重构扩大影响面。

继续执行应来自明确的恢复操作或新批准的变更，而不是自动重新开启一个无限循环。失败报告也应是正常产品状态，不只是聊天里的一句报错。

## 12. 落地顺序：先做小而可靠的控制层

下面是 BGS 平台改造优先级，不是降低生成游戏的交付范围。

### 第一批：直接补现有流水线，不重构成新框架

**统一需求与任务记录。** 新文档登记稳定需求 ID；在现有任务存储中加入来源、依赖、验收与实际检查状态。CM 先作为分组视图，不单独维护大图或新的自然语言规格。

**复用现有数据校验。** 在 UI JSON 生成和真实资源替换后调用现有布局计算；盘点它实际能检查什么，未覆盖的内容明确标记，不能假设已经支持文字溢出、动态遮挡或复杂 Scene 可达性。

**分离正式放行状态。** 建立统一检查报告和版本关联；把“未运行、失败、阻断”从“通过”里分开。G1、G2、G3 的推进交给程序，不读作者一句“完成”就推进。

**补最小真实运行验收。** 先覆盖已支持游戏类型的启动、主要行为、结束／重开与关键数据消费。尚不能自动验证的必需项，使用明确人工验收，而不是暂时忽略。

### 第二批：积累可以复用的验收与设计资产

在前一批稳定后，增加真实字体／文字范围测试、UI 与 Scene 合成检查、关键配置变化测试、已批准视觉基准和常见游戏类型的规则测试。

对首次设计和关键玩法保留人工核对；把已经被验证有用的判断逐步转成规则、模板或回归用例。优先补实际漏检过的问题，不一次性构建通用审美系统。

### 暂不作为前置条件的工作

不要求完整知识图谱、自动通用空间求解器、所有文档逐组多 Agent 审计、每个小任务独立 Agent、多模型投票放行，也不要求维护多份相互复制的需求／CM／最终 PRD。

它们是否值得引入，应由现有系统的具体失败和测量结果决定，而不是因为流程看起来更专业。

## 13. 如何验证这套流程值得保留

先回收已有失败项目，将问题归到需求遗漏、设计冲突、内容错误、实现偏离、数据未消费和验收漏检。否则可能花很多成本优化任务拆分，却没有处理真正的主要缺陷。

选一组固定、代表当前支持范围的项目，同时保留若干真实失败案例。对比原流程与改进流程，保持需求、模型版本、运行环境和可比较的预算条件，做少量重复运行并保留全部结果，不只展示最好的一次。

重点记录以下四类结果：

| 指标 | 具体记录 |
|---|---|
| 放行后的缺陷 | 被标记可交付后，人工或后续运行又发现了哪些必需功能缺失、交互或视觉问题。 |
| 自动检查有效性 | 哪些已知故障能稳定检出；有哪些误报，以及是否导致不必要阻断。 |
| 人工负担 | 每个项目需要多少次确认／干预，主要发生在哪个阶段。 |
| 总成本与产出 | Token、工具和构建成本、重试次数、总耗时，以及最终是否真的交付，而不只是测试数增加。 |

对首批核心行为、视觉与体验进行人工核对，以便识别“测试绿了但产品仍有问题”的情况。不要把新增流程本身等同于质量提升；若某环节成本高而没有检出有效问题，就应收缩或调整。

## 最终建议

**保留你的主流程与八文档依赖。把 CM 做成交付清单中的统一索引，把空间校验放在数据具备条件时执行，把实现切成有依赖和验收的工作包。**

**真正需要加强的不是“让 Agent 再仔细一些”，而是让 BGS 明确记录：承诺了什么、实现了什么、验证了什么、还不能证明什么，以及谁有权决定继续。**

自动化先覆盖能够稳定检查的范围；对新玩法、设计判断和未覆盖环境保留明确的人工入口与停止状态。随着实际证据积累扩大自动放行范围，不先承诺模型已经能替代这些判断。
