# Review 实质复核修正

## 已证问题

前一轮在同一项目原生会话评审八稿，最终返回PASS，但L格撤离推导、即时连锁时间、竖屏居中留白、弹窗缺项算式等错误保留。工具记录为25次Edit、5次TodoWrite、1次Grep；Grep只搜索草案／未决／挂起／旧版本。它解决了显式挂起的接触规则和音量控件交接，却把“未决标签清除”扩展为整套设计通过。

已有指令包含数值与矩形检查，不能把缺少一句提醒认定为唯一根因。当前有直接证据的是：未对设计结论形成可靠的核查依据，修订后未复核依赖该改动的其他结论。长上下文、自我确认、模型能力可能影响结果，尚未以对照试验分离。

## 系统改动

替换project-delivery.ts中现有review指令，仍为同一阶段内的评审与修订：

- 以当前八份文件为评审对象；既有摘要、完成标签和自身旧结论也需要验证。
- 覆盖玩法／内容、数值推导、空间适配，以及美术／音频／资源／技术交接，避免只搜索标注的未决项。
- 从源文件形成具体发现，再修订并对照原要求复核受影响内容；错误计算不能仅改名为playtest假设。
- 结论简短且能定位文档章节；先实质复核，后更新版本和评审状态。

仅替换任务描述。没有新增阶段、平台设计裁判、自动修复回合、强制子代理或第二个项目session；方法、工具、Skill和分工由Agent选择。现有完成交接仍用于记录Agent结论，不能认证结论真实性。

### 新发现：权限等待阻塞整个原生消息读取

`native-cli-process-runner.ts`的consumeStdout逐行await onMessage；control_request分支又await resolvePermissionRequest，而后者等待用户决定。这使某个子任务的待审批请求阻塞后续stdout读取，包括其他任务的输出、完成通知和主代理进度。

证据不是仅凭界面猜测：平台transcript最后可见的正常事件是审批请求；实验代理保存了此后主代理的TodoWrite、Grep及TaskOutput请求，而这些没有进入平台事件流。说明原生CLI仍在执行，BGS输出消费被等待占住。隔离夹具缺少审批入口导致此次等待无法结束，但串行读取耦合是独立的系统问题，真实界面存在审批时也会影响其他任务进度显示。

后续应先解除消息读取与审批决定的串行耦合：继续有序处理普通事件，权限决定按原请求ID独立返回；停止／换回合后不允许迟到决定写回新任务。保持现有权限边界，不默认放行项目外访问，也不调整Agent的设计职责。免费回归应覆盖“审批未解决时其他消息照常到达”“多个审批独立关联”“停止后迟到决定不串回新回合”。这是消息通道修复，不是BGS设计裁判或新的评审编排。本轮只定位和记录，未修改该代码。
