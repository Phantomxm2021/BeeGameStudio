# Foundation 停止链路修复

## 事实与定位

验收任务 `9fe25f58-b04d-4425-a6c4-5b07aa07a168` 在 02:22:36 UTC 已持久化工作流停止意图，但 Revision 日志直到 02:29:10 仍追加进度；1,762 条事件中没有 `stop_requested` 或终止回执。只读重放实测约 978 ms。日志缺少当时的 CAS 冲突次数，因此不能仅凭旧日志断言每一次重试原因。

代码和确定性复现证实：停止命令与进度争用同一序号，失败后全量重放会导致控制操作持续落后。前端适配器另有独立错误：任何成功 HTTP 响应均被改成 `stopped`；普通会话的停止状态也可能覆盖仍在清理的工作流状态。

## 修复

- 仅在同一次控制提交的 CAS 重试中保留已验证的不可变前缀，冲突后读取新增事件；提交提案使用副本，失败不污染前缀。没有跨请求缓存、额外锁或新持久化协议。正常读取仍完整验证历史。
- 控制日志记录接收、提交、重放和失败，以及时间、句柄、请求 ID、耗时、冲突次数；不记录文档或密钥。
- HTTP 保留工作流真实状态；前端区分已停止与请求已提交，清理未确认时不展示完成消息，并刷新状态。

## 验证与边界

先在旧代码强制四次 CAS 冲突，历史首条被重读五次，回归测试失败；修复后扩展至 1,800 条历史记录，首条只读一次且成功停止。真实本地子进程停止、退出、用量封存、停止期间不派发后继均通过。后端 52 项、前端 104 项针对性测试，以及前后端类型检查和 `git diff --check` 通过。

没有重启服务、开启真实模型验收或修改旧项目记录。旧任务已有进程退出但无终止回执，本修复不伪造其停止确认或计费结算。
