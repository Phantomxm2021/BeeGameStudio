## 1. 目标与范围

目标：阶段拥有业务决策和执行状态；平台提供受限能力；编排只负责阶段交接。

不是让阶段只剩提示词，也不是把业务逻辑全部交给 Hook。否则会重新形成一个懂所有阶段的大型共享执行器。

本提案在当前“阶段之间执行职责隔离”的基础上，进一步定义平台依赖、执行引擎和存储的可替换边界。不要求拆仓库、微服务、独立进程或建立第二套编排入口。

### 1.1 当前状态与目标的区别

当前 Author、Reviewer、Revision 已分别通过既定范围的独立模块离线验收，但仍存在以下绑定：

| 类别 | 当前状态 | 目标 |
| --- | --- | --- |
| 鉴权及配置 | public 工厂要求 owner-bound runtimeConfiguration，默认适配器连接平台鉴权及配置仓库 | 显式执行授权与运行能力；阶段不认识账户供应商或平台配置库 |
| 计费 | 要求 billing 客户端，阶段提交用量并暴露 billingStatus | 阶段可靠交付用量事实，外部消费者负责财务处理 |
| 身份 | ownerId/projectId 进入输入、结果和持久化；部分模块由 billing 客户端取得 ownerId | 从可信执行上下文绑定身份，不从计费推导身份 |
| 执行 | 内部处理 Native CLI、流消息、session 和工具协议 | 技术传输由适配器实现，业务调度仍由阶段拥有 |
| 存储 | 固定本地目录、文件日志及进程相关所有权机制 | 定义明确一致性要求的受限存储能力，先承接现有本地实现 |
| 阶段协议 | 文档、问题、候选等有明确格式及版本 | 保留必要的数据契约，不共享阶段执行实现 |
| 领域规则 | 八文档、审计、修复规则在阶段内 | 继续由所属阶段拥有，不为了通用化外移 |

现有验收不等于已经满足本提案。将本提案转为实施任务、重排 P4 或扩大验收范围，需要另行明确，不由文档落盘自动触发。

## 2. 总体架构

~~~mermaid
flowchart TB
    UI["产品入口 / API / UI"] --> HOST["应用装配层"]
    HOST --> WF["流程编排"]
    HOST -. "注入受限能力" .-> STAGE
    WF <-->|"公开命令、句柄、结果"| STAGE["独立阶段模块"]
    STAGE --> CORE["本阶段业务规则、调度、状态与结果发布"]
    STAGE --> PORT["能力接口"]
    PORT --> EXEC["模型 / 工具执行适配器"]
    PORT --> STORE["私有状态 / 产物存储适配器"]
    PORT --> POLICY["执行授权适配器"]
    PORT --> EVENT["可靠事件投递"]
    POLICY --> PLATFORM["平台鉴权、额度与业务策略"]
    EVENT --> BILL["计费消费者"]
    EVENT --> OBS["日志 / 监控 / UI 投影"]
~~~

图中的“独立阶段模块”表示多个独立模块，不是统一的阶段运行内核。图中阶段到能力接口的箭头表示调用方向；适配器实现受限能力契约，不要求阶段导入具体平台实现。

| 层 | 拥有的责任 | 不应拥有 |
| --- | --- | --- |
| 应用装配层 | 连接平台服务，绑定可信身份和权限，选择和注入适配器 | 阶段业务决策 |
| 流程编排 | 阶段顺序、公开结果交接、整链停止和续接 | 阶段内部任务、重试、checkpoint |
| 阶段模块 | 自身业务规则、内部调度、业务重试、状态、完成判断 | 登录、价格、账本、平台配置仓库 |
| 能力适配器 | 执行、存储、授权、可靠投递的技术实现 | 判断文档通过、决定修复范围、修改业务状态机 |

## 3. 各阶段职责

| 阶段 | 自身业务职责 | 对外输出 |
| --- | --- | --- |
| 八文档 Author | 文档依赖、提示、生成、结构校验、文档重试、完成判断 | 完整文档集合及版本依据 |
| Reviewer | 事实抽取、审计规则、问题登记、候选复核 | 审计结论及问题证据 |
| Revision | 问题消费、修复规划、局部保留、修改完整性、候选生成 | 候选版本、变更、修复声明 |
| Game IR | 从已通过并发布的文档编译、验证结构化执行投影 | 绑定 Foundation 版本的不可变 IR、来源追踪或待核验缺陷报告 |
| Checklist | 将需求转换为可验证的检查项 | 版本绑定的检查清单 |
| 资源准备 | 资源需求解析、准备、校验及就绪判断 | 资源清单和产物引用 |
| 任务规划 | 需求覆盖、任务拆分、依赖和可执行性判断 | 实施计划 |
| 实现 | 代码和配置修改、自测、修复 | 实现候选及执行证据 |
| 实现审计 | 对实现候选独立审计 | 通过结论或返修问题 |
| 验收 | 按 Checklist 验证交付条件 | 验收结论和证据 |
| 交付 | 核对已验收版本、组装交付物 | 不可变交付清单 |

阶段只能消费其他阶段的公开数据，不能调用其执行实现或读取私有状态。例如 Revision 理解 Reviewer 的问题协议是必要依赖；读取 Reviewer 的事实库或调用其审计函数则不允许。

简报确认保持既有入口边界。Game IR、资源工具等现有能力需要按实际生产者、消费者及写入权清点，不因采用新分层而删除、旁路或另行设计。

## 4. 阶段内部结构

建议的逻辑分层，不要求立即按以下目录重排现有文件：

~~~text
阶段模块
├── public          公开命令、输入输出契约
├── application     本阶段生命周期、调度、重试、提交
├── domain          本阶段规则、策略、校验、业务模型
├── ports           本阶段需要的能力接口
└── private-state   本阶段状态结构和演进规则
~~~

- domain 不访问文件系统、数据库、网络、账户或计费。
- application 决定接下来做什么，通过能力接口执行。
- 状态结构、迁移、业务有效性及终态接纳由阶段拥有；存储适配器只保存数据并提供声明的一致性保证。
- 阶段内部任务不成为上层编排的操作对象。
- 提取执行或存储适配器，不意味着提取阶段调度。
- 各阶段不强制继承共同基类，不引入统一的业务状态机。
- 阶段专属需求由本阶段定义；确实通用的基础能力可使用小型版本化契约，不建立包含所有阶段业务的公共 SDK。

## 5. 能力接口

以下名称为设计语义，不是已经发布的 API。

### 5.1 可信执行上下文

宿主绑定主体、租户或隔离域、运行标识和追踪信息。阶段使用不透明身份验证归属，不处理登录或令牌刷新。

- 身份不能来自计费客户端。
- 调用方提交的身份不能直接当成授权证明，必须与宿主绑定上下文核对。
- projectId 若表示游戏项目业务归属，可以保留。需要移除的是对平台项目表及特定账户系统的直接依赖，不是机械删除字段。
- 权限不通过可任意修改的上下文对象传递；注入的能力应绑定明确主体、资源和作用域。

### 5.2 执行授权

阶段在产生受控外部操作前申请许可。适配器判断权限、资源限制，以及平台既定的额度等执行条件。

阶段只处理允许、拒绝、暂不可用及必要的许可约束，不拥有账户、余额或计价算法。

- 授权是必须等待的请求响应接口，不是可忽略的通知 Hook。
- 授权失败阻止新的受控执行。
- 许可的使用范围、有效期及必要的执行时校验必须明确，不能用一次启动鉴权替代长期执行授权。
- 已有执行是否停止、何时停止遵守明确策略；不能伪造关闭成功。

本提案不新增额度算法，也不决定变更现有计费故障时的执行政策。

### 5.3 模型和工具执行

阶段提供提示、输出要求、允许的工具能力和稳定执行请求标识。适配器负责：

- Native CLI、HTTP 模型接口等具体技术传输；
- 供应商认证和环境配置；
- 流协议及进程、远端请求的技术生命周期；
- 标准化输出、实际用量、取消和关闭证据。

阶段继续拥有提示、模型能力需求、业务输出校验、重试决定及修复范围。供应商和部署选择由外部配置解析，不能擅自改变阶段要求的模型策略。

技术重连与业务重新生成必须区分。共享适配器不能隐藏产生额外执行和用量的业务重试；远端结果不确定时也不能盲目重发。

实现、资源准备等阶段按需获得沙箱执行、资源生成等能力，不向所有阶段注入万能 Shell 或无限制文件访问。适配器执行阶段声明并获授权的操作，不自行扩大工具权限。

### 5.4 私有状态存储

提供版本读取、条件提交等明确语义。阶段拥有状态 schema、业务迁移和命名空间；适配器不理解文档任务或审计事实。

只定义 get/set 不足以替换现有文件日志与执行租约。实施前必须定义：

- 并发写入及条件提交的线性化点；
- 所有权、失效及旧执行写入拒绝规则；
- 持久化确认与错误／未知结果的语义；
- 阶段状态与可靠事件待投递记录的一致性；
- 只读查询及跨命名空间访问限制。

先用适配器承接当前本地实现，不立即引入数据库或分布式系统。缺少等价安全保证的后端不能被宣布为可替换实现。

### 5.5 不可变产物存储

提供内容写入、摘要、版本和受限读取。跨阶段交接不可变产物，不交接可任意修改的工作目录。

阶段决定产物何时业务完成；存储适配器提供完整提交后可见的技术保证。引用应包含足够的版本、摘要及访问约束，消费者必须校验。

如需要将已接纳版本映射到产品当前文档视图，应由明确的应用产物管理边界执行，不能让编排读取阶段私有文件自行拼装或补签结果。

### 5.6 可靠用量事件

阶段或执行适配器采集实际用量，阶段可靠记录并交付。事件表示某次执行消耗了哪些资源，不表示应扣多少金额或余额还剩多少。

- 外部计费消费者拥有计价、记账、扣费和幂等去重。
- 阶段保存用量事实及投递状态，不保存财务权威。
- 业务状态、用量交付状态、财务处理状态分别表达，由应用组合展示。
- 迁移期间的旧 billingStatus 需要显式兼容映射，不能直接改名后改变含义。
- 执行失败、停止、部分输出及未知用量均按真实事实表达，不伪造零用量。
- 采用至少一次交付及幂等消费，不承诺跨系统恰好一次。
- 用量与执行终态的持久化关系必须明确，不能出现业务完成已确认但用量事实无可重放记录的静默缺口。

解耦不自动意味着计费故障时允许继续执行。是否阻止新执行属于既定平台政策，通过授权接口落实；未经明确决定不得改变。

## 6. Hook 与事件机制

不建议只有一个泛化 hooks 对象。应区分三类机制：

| 机制 | 用途 | 失败语义 |
| --- | --- | --- |
| 必需能力接口 | 授权、执行、状态提交、产物读取 | 必须处理，不能忽略 |
| 可靠事件接口 | 用量、已提交结果的通知 | 持久化、可重放、消费者幂等 |
| 观察 Hook | UI 进度、普通日志、调试观测 | 不改变业务结果，故障隔离 |

事件至少应具备版本、稳定事件 ID、来源运行、类型及必要数据绑定。订阅者只获得允许的信息，不接收凭证、完整私有状态或不必要的模型正文。

禁止：

- Hook 修改阶段私有状态；
- Hook 返回“把任务标成通过”；
- Hook 接收原始凭证或无限制项目上下文；
- 用完成通知代替公开结果的版本校验；
- 普通观察者故障阻塞业务提交；
- 可靠用量交付退化为可能丢失的 onComplete 回调。

通知可以订阅，业务权威不能分散到订阅者。编排可以通过可靠通知获知结果可用，但必须读取并校验正式公开结果后交接。

## 7. 公开生命周期与编排边界

阶段保留以下操作语义，各自维护公开类型，不强制共享大型状态机：

~~~text
start(业务输入、调用身份) → 不透明句柄
getResult(句柄)          → 运行状态或已提交结果
stop(句柄、请求身份)     → 停止确认或需要处理
resume(句柄、请求身份)   → 显式续行结果
~~~

阶段运行状态与业务结果分开。例如 Reviewer completed 表示已发布审计结果，不等于审计 passed；Revision candidate_ready 不等于修复已获审计通过。

保留当前已确认的 needs_action 行为。failed 仅适用于实际定义的不可恢复终态，不为了统一标签制造从不返回的分支。

编排只持久化阶段身份、公开句柄、输入摘要、已接纳结果版本、下游调用身份和整链停止意图，不持有内部任务或 checkpoint。

文档修复闭环：

~~~text
Author 完成 → Reviewer 审计
Reviewer issues_found → Revision 修复 → Reviewer 复核
Reviewer passed → 通过文档发布/接纳 → Game IR ready → Checklist
需要处理 → 停止等待明确操作
~~~

编排决定下一阶段是谁；Reviewer 决定是否通过；Revision 决定如何修复。不新增轮数上限、降级放行或自动放弃策略。

2026-09-07 审计后修订：Game IR 旧分支是待整改/重验的复用候选；已复现跨域引用、来源完整性、preflight 无进展等偏差。按 [Game IR 整改与接入计划](game-ir-module-implementation-plan-2026-09-07.md) 先通过 IR-R0—R6，再迁入 stateless/obligation 链，适配公开输入、私有状态与平台端口；reader、缺陷回流、Checklist bridge 在新边界一次完成。不从零重建、不整体移入旧 DeliveryRun 控制逻辑。本次未改变生产停点。

崩溃、停止及重放边界：

- 阶段完成但尚未交接：重新读取相同公开结果。
- 下游启动确认丢失：使用相同调用身份重试，不重复开启业务运行。
- 停止与完成并发：可以保存结果，但停止状态下不自动启动下游。
- 模块停止超时或关闭未知：保持需要处理，不伪造停止成功。
- 旧候选结果迟到：不能覆盖当前指定候选。
- 不兼容、过期或不完整结果：拒绝交接，不改上游私有状态“修复”。
- 编排不得通过读取 worker 日志猜测完成或自行接管内部任务。

上述设计不新增自动接管、后继租约、孤儿进程清理或监督机制，也不代表这些能力已实现。

## 8. 共享与依赖规则

允许共享：

- 小型、版本化的基础能力契约；
- 不理解阶段业务的技术适配器；
- 传输、存储、可靠投递等通用设施。

禁止共享：

- 全阶段业务 dispatcher；
- 全局可变运行对象；
- 文档／审计／修复共同 controller；
- 能替任意阶段改 checkpoint 的 SDK；
- 通过阶段名称分支决定业务行为的通用执行器。

各阶段自行校验业务输入，不建立公共业务 parser。可以共享协议样例及负例，不因此共享生产校验内核。

依赖审查要覆盖运行时、类型导入、动态加载、路径别名及符号链接，不仅检查显式 import 文本。

判断适配器是否越界的简单标准：新增一个阶段，若必须修改模型或存储适配器中的业务分支，说明阶段责任已泄漏到公共层。

同进程崩溃、错误输出或不兼容契约仍可能影响调用方。本设计不承诺零故障传播，不因此扩大为进程隔离工程。

## 9. 建议迁移顺序

以下为建议顺序，未自动加入现有任务清单：

1. 明确责任与接口：逐阶段列出业务责任、能力需求和既有失败政策，冻结可观察行为。
2. 拆平台语义：身份移出计费客户端；直接计费调用替换为可靠用量交付，外部适配器承接现有计费实现。
3. 拆执行绑定：CLI、供应商和环境配置进入受限适配器；提示、模型需求、调度及业务重试留在阶段。
4. 按需要拆存储绑定：先适配当前文件实现，证明一致性等价，不立即引入数据库或分布式系统。
5. 逐阶段重新验收：Author、Reviewer、Revision 分别验证；后续阶段按同样边界建设。
6. 接入编排闭环：公开契约稳定后实施 P4 交接和离线闭环。

不推倒已验收的阶段实现，不变更八文档业务、审计或修复规则。授权、计费失败政策、公开状态或恢复语义若需改变，须单列裁决后实施。

文档落盘不授权运行真实模型、服务、计费、数据库或既有项目，不授权删除旧路径、部署或提交 Git。

## 10. 验收标准

新增目标应至少证明：

- 不连接真实平台账户、配置库或计费服务，也能用显式测试适配器完整运行。
- 更换平台适配器不修改阶段业务代码。
- 阶段不调用其他阶段、不访问其私有状态。
- 授权失败不执行；观察 Hook 失败不改变业务结论。
- 重复及乱序事件按契约处理；用量重放不重复记账。
- 已提交结果重放不重复执行，下游调用确认丢失不产生重复运行。
- 模块仅访问获授权的状态命名空间、产物和工具。
- 模型执行取消与关闭证据保持真实，不以父进程退出推断全部执行已关闭。
- 产物提交不暴露部分结果；摘要、版本及前驱绑定不能被绕过。
- 冻结的文档、审计、修复规则及现有安全保证不变。

测试证据应分开记录：

- 纯业务单元及冻结规则对照；
- 固定输入、假能力适配器的独立阶段运行；
- 能力适配器的契约与故障语义；
- public 编排交接及离线闭环；
- 另行授权的真实环境验证。

测试替身证明能力边界可替换，不证明所有生产后端都已完成适配。既有阶段间隔离验收和本提案的新增验收必须区分。

## 11. 实施前需要定稿的事项

- 每类执行授权的粒度、许可约束及执行时校验。
- 现有计费故障政策与新授权／用量投递接口之间的等价映射。
- billingStatus 的兼容迁移与应用侧组合展示。
- Native 执行能力的输出、用量、取消、未知结果和关闭证据契约。
- 私有状态与 outbox 的一致性及现有存储适配方案。
- 各阶段产物提交与产品当前版本展示之间的写入权。
- 接口版本、输入反例和迁移回归清单。

最终原则：阶段是完整的业务模块，适配器是可替换的技术能力，编排是公开结果之间的连接者。Hook 只是通知机制，不是整个架构的中心。
