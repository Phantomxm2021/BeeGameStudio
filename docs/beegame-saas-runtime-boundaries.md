# BeeGame SaaS Runtime Boundaries

This document defines the production boundary between Supabase and the local BeeGame runtime host.

## Production Responsibilities

Supabase owns durable user and business data:

- Auth sessions and OAuth providers.
- User profile, workspace membership, role, and permission state.
- Project/session metadata, model config metadata, runtime settings, MCP metadata, asset manifests, preview metadata, credits, and audit events.
- Row Level Security for owner-scoped and member-scoped data access.
- Credit reserve, settle, and refund mutations through authenticated RPC.

The BeeGame runtime host owns local execution only:

- Claude/BeeGame session hosting.
- Workspace filesystem access inside the configured project root.
- Preview process start/stop.
- Tool permission policy and transcript/event streaming.
- API request authorization by validating the user's Supabase JWT and mirroring the permissions returned by Supabase.

## Forbidden In Runtime Host

The runtime host must not depend on:

- Supabase service role keys.
- Supabase Auth admin APIs for account deletion, user creation, or role elevation.
- Local JSON/SQLite stores as a production fallback when Supabase is configured.
- User self-assigned admin roles from frontend state or query parameters.

Admin status must come from Supabase-controlled state only:

- `auth.users.raw_app_meta_data.beegame_role = "owner"`, or
- a workspace membership row where the current user is `owner`.

Account deletion also belongs to Supabase. The runtime host may call
`beegame_delete_current_user()` with the current user's JWT, but it must not use
Supabase Auth admin APIs or service role keys to delete users.

## Dev And Offline Mode

Local JSON/SQLite stores and static bearer tokens exist only for development, tests, and offline packaging experiments.

- `BEEGAME_AUTH_TOKENS` is disabled in production unless `BEEGAME_ALLOW_DEV_AUTH_TOKENS=1` is explicitly set.
- `VITE_API_AUTH_TOKEN` is ignored in frontend production builds unless `VITE_BEEGAME_ALLOW_DEV_AUTH_TOKEN=1` is explicitly set.
- `dashboard-local` is a migration/dev identifier, not a signed-in production user.

## Settings Ownership

Normal user settings should stay personal and low risk:

- Language.
- UI preferences.
- Profile actions.

Deployment and platform settings belong in the admin console and must remain owner-only:

- Model provider configuration.
- Web search provider keys.
- Runtime settings.
- MCP discovery/import settings.
- Workspace root policy.
- Audit log access.

In hosted SaaS mode, users should not set arbitrary workspace roots. Project paths are generated by the platform.

## Credit Flow

Credit mutations must follow this order:

1. Quote the task type.
2. Reserve credits before the turn starts.
3. Settle by weighted token usage after the turn ends.
4. Refund unused reserved credits.
5. Record each mutation in the ledger.

The runtime host may request these mutations, but Supabase RPC performs the actual balance update under the authenticated user's RLS context.

## Supabase Smoke Verification

For the full production checklist, see [BeeGame SaaS Preflight Checklist](./beegame-saas-preflight.md).

After applying the schema, run the smoke check before treating a deployment as ready:

```bash
bun run supabase:smoke
```

The script reads `.env.local` automatically. It requires:

- `BEEGAME_SUPABASE_URL`, `SUPABASE_URL`, or `VITE_SUPABASE_URL`.
- `BEEGAME_SUPABASE_ANON_KEY`, `SUPABASE_ANON_KEY`, or `VITE_SUPABASE_ANON_KEY`.
- Either `BEEGAME_SUPABASE_ACCESS_TOKEN` + `BEEGAME_SUPABASE_USER_ID`, or `BEEGAME_SMOKE_EMAIL` + `BEEGAME_SMOKE_PASSWORD`.

The smoke check uses the user's access token only. It does not use service role keys.

It verifies:

- `beegame_current_user_context` returns the expected user, workspace, role, and permissions.
- Project metadata can be inserted and deleted under RLS.
- `beegame_assets` can store an asset manifest for that project.
- Supabase Storage can upload and delete an avatar object under `avatars`.
- Supabase Storage can upload and delete a private project asset under `beegame-assets`.
- Credit reserve and refund RPCs work without consuming final credits.
- `beegame_runtime_env` returns runtime env values with secrets redacted in output.
