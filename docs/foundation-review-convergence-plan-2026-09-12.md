# 基础文档审计与修订收敛方案

日期：2026-09-12  
状态：源码实施、离线验收、本地新版加载及 Chrome 政策切换验收已完成。现有真实验收项目保持暂停，尚未恢复付费审查。  
适用范围：Foundation Reviewer、Foundation Revision 之间的工作流验收、路由及展示；不涉及修改原生 Claude Agent 运行机制。

实施与主 Agent 独立审计见 [实施记录](foundation-review-convergence-implementation-2026-09-12.md)。后端综合 555 项、前端 723 项测试通过；本轮未恢复付费任务。

后续本地加载与真实暂停任务切换记录见 [Chrome 验收记录](foundation-convergence-chrome-deployment-2026-09-12.md)。

## 1. 结论与目标

把“审计发现的问题”与“阻止交付的问题”分开。完整记录所有发现，但不再为低价值问题无限启动新一轮模型调用。

默认方案：

1. LOW 作为建议保留，不单独触发自动修订。
2. MEDIUM/HIGH 暂按阻断项处理；有争议时允许用户明确接受风险，不由宿主猜测或改写严重程度。
3. 每个验收周期最多自动执行两轮 Revision，每轮完成后仍交给 Reviewer；预算耗尽仍有阻断项则暂停，不伪造通过。
4. 验收采用独立的工作流决定：“接受”“接受并附建议”“需要修订”“需要用户处理”。原始审计报告不变。
5. 不限制 Agent 的工具、思考、委派、检查范围、修改范围或单次运行时长。预算仅决定是否启动下一次调用，不中断正在执行的 Agent。

这是一项明确的产品验收政策调整，不宣称工作流对结果完全没有影响；保证的是不干预原生 Agent 的内部执行与自主判断。

## 2. 依据与问题定位

Chrome 真实验收中，本次恢复后运行约 40 分钟；项目全部审计/修订原生进程累计约 92 分钟，包含历史版本和中断尝试，不含人工暂停。

| 本次阶段 | 原生进程耗时 | 结果 |
| --- | ---: | --- |
| 第 4 轮候选修订 | 17分40秒 | 成功 |
| 第 4 轮候选复审 | 6分43秒 | 剩余 2 项 LOW |
| 第 5 轮候选修订 | 11分58秒 | 成功 |
| 第 5 轮候选复审 | 3分05秒 | 用户暂停，未形成结论 |

本次约 89% 的执行时间处于非工具执行区间，包含模型生成、推理、请求等待及其他开销；不能全部解释为推理。阶段间隙仅约 22 秒。关键浪费在于：仅为 2 项 LOW，又支付约 15 分钟修订和未完成复审。

现状代码 `foundation-review-link.ts` 对任意 `issues_found` 都派发 Revision，没有严重程度分流；Revision 结束必然再调用 Reviewer。已有六轮上限只能防止无限运行，不能防止低价值返工。问题数曾出现 19 → 7 → 5 → 7 → 2，不能依赖发现数量单调下降。

本次两个 LOW 是重开按钮适用状态的说明方式，以及雨滴密度单调措辞未限定恢复窗口。它们应保留为建议，不默认享有与核心玩法错误相同的自动返工优先级。

## 3. 原生 Agent 的不变边界

实施本方案时保持以下内容不变：

- Reviewer 自由审查整套文档并报告全部问题；不要求只看差异、不隐藏历史上下文、不禁止发现新问题。
- Revision 自由判断问题是否成立、修改哪些文档、是否顺带修复建议项，以及如何验证。
- Bash、Agent、TaskOutput、读写工具和原生上下文机制保持可用；不加工具白名单、思考长度或子 Agent 数量限制。
- 不加入额外“仲裁 Agent”“验收 Agent”对每份报告二次分类，避免新增付费循环。
- 本期不修改 Reviewer/Revision 提示词、输出格式或原生运行时。尤其不把“LOW 不触发下一轮”改成“Agent 禁止修复 LOW”。
- 保留目录隔离、只读证据、用户停止、用量结算、身份/版本绑定及幂等发布。

工作流只在一次阶段完整结束并结算后，决定接受、派发下一阶段还是暂停。

## 4. 验收规则

### 4.1 前置条件

仅当 Reviewer 已完成、结果契约有效、输入与文档摘要匹配、计费结算完成时，才评估质量政策。

`blocked`、失败、未完成、无效/缺失严重程度、计费未结算、文件损坏、越界或用户停止，不得因为“没有 HIGH”而接受。发布前的文件绑定与冲突校验继续执行。

### 4.2 确定性路由

| 有效审计结果 | 工作流决定 | 后续动作 |
| --- | --- | --- |
| 没有 findings | 接受 | 发布已审查字节，进入既有交接边界 |
| 只有 LOW 或已被用户明确接受风险的 findings | 接受并附建议 | 保留完整报告，不启动 Revision |
| 有未豁免的 MEDIUM/HIGH，且剩余自动修订预算充足 | 需要修订 | 派发一次 Revision，再复审 |
| 有未豁免阻断项，但预算耗尽或发生无进展 | 需要用户处理 | 保留候选与报告，不继续付费循环 |

首版不对自然语言标题做关键词降级，也不使用“只有 HIGH 才修”的粗暴规则。历史记录里文案差异也曾被标为 MEDIUM，说明严重程度并非绝对真值；处理办法是可审计的用户裁决，而不是隐蔽语义判定。

### 4.3 用户裁决

用户可明确选择“接受该风险”或“继续修复”。裁决记录包含操作者、理由、时间、原始 finding 标识、审计结果摘要与文档集合摘要。

接受风险不修改原始 finding 的 severity、actual、expected 或 Reviewer 结论。裁决只对明确绑定的报告和文档版本生效；文档变化后不自动继承，不能凭相似标题把新问题一并豁免。首版不提供无条件“接受所有未来问题”。

需要用户理解的阻断标准：是否违背明确需求、导致核心玩法无法实现/验收、造成实质运行错误，或存在安全/数据风险。措辞、排版、重复说明、表达润色通常是建议；遇到语义争议由用户裁决，不在宿主中实现自然语言推断器。

## 5. 收敛与停止规则

- 默认每个验收周期最多两次自动 Revision；初审和每次修订后的复审不占 Revision 次数。正常上限为“初审 → 修订 → 复审 → 修订 → 复审”。这是次数上限，不承诺总耗时上限。
- 已结算并产出候选的修订计入预算。用户中断/失败不伪造完成次数，但实际耗时和费用仍保留；失败与停止不得自动重试。
- 若修订后文档集合摘要与输入完全相同，仍允许一次 Reviewer 复审，因为修订可能合理反驳原有发现；若复审仍存在阻断项，暂停为“无文档变更且仍有阻断”，不再自动重复修订。
- 不以问题 ID、标题或总数量的变化判断语义进展；文档发生变化但问题仍存在时，由两轮预算兜底。
- 无阻断项立即接受并附建议，不为新增 LOW 继续一轮“顺手清理”。
- 预算耗尽时，由用户明确选择接受已列明风险，或授权一个额外修订周期。普通刷新、重启和“继续”不能悄悄清零预算。
- 用户停止优先。停止后可以完成清理和待结算记录，但不得发起新模型调用或提交新的接受决定。

## 6. 状态与发布契约

新增工作流拥有的、版本化的 `acceptanceDecision`，独立于 Reviewer 结果。建议最小字段：

| 字段 | 含义 |
| --- | --- |
| policyVersion | 本次适用的验收政策版本 |
| reviewResultId / reviewResultDigest | 原始审计结果绑定 |
| documentSetDigest | 实际被审查的完整文档集合 |
| disposition | accepted / accepted_with_advisories / repair_required / needs_action |
| advisoryFindingIds / blockingFindingIds / waivedFindingIds | 完整分类与用户裁决引用 |
| automaticRepairLimit / completedRepairCount | 持久化预算快照 |
| reason / overrideReferences | 决定原因与裁决记录 |

确定性检查要求所有 findings 被完整、唯一地归类，引用均来自绑定报告；不能丢失 HIGH/MEDIUM、注入不存在的 finding 或跨版本使用裁决。

当前 `acceptedReview` 及发布逻辑仅接受 `passed`，不能直接塞入伪造的通过报告。实施时必须同步修改持久化 schema、发布入口和下游交接：以有效的 `acceptanceDecision` 加原始审计报告作为授权；发布内容仍只能是被审查的确切字节。

发布与工作流确认维持可重放、幂等的先后关系。策略版本在验收周期开始时冻结，重启不重新解释历史结果，策略切换不追溯重写旧记录。

“接受并附建议”只是文档验收决定，不自动扩大到游戏制作、素材生成或对外发布权限；本次测试仍止于原有文档交接边界。

## 7. 实施步骤与范围

### 第一阶段：规则与契约

在 delivery-workflow 内新增纯函数验收政策，不引入模型调用；实现分级、裁决绑定、两轮预算与无进展停止。扩展状态 schema 和接受决定，先完成离线测试。

主要影响点：

- `packages/agent-workflow-server/src/beegame/delivery-workflow/foundation-review-link.ts`
- `packages/agent-workflow-server/src/beegame/delivery-workflow/foundation-review-link-schema.ts`
- `packages/agent-workflow-server/src/beegame/delivery-workflow/foundation-accepted-artifacts.ts`
- 上述状态的交接消费者与相关测试；实施时检索全部 `acceptedReview` 使用点，不局部绕过验证。

Reviewer/Revision 的 public result、私有执行器、原生 CLI 及提示词不因本方案而改写。

### 第二阶段：界面与观测

展示“通过”“通过，附 N 项建议”“需修复 N 项阻断问题”“自动修订预算已用完”等明确状态，建议默认折叠但可展开查看原文。

修复“执行中同时显示等待中”和子任务等待时误显示“正在准备”的问题。展示本次调用耗时与历史累计耗时，区分模型响应、工具执行、子任务等待、结算和交接。无法区分的模型/网络等待明确标为合并统计，不虚构精确推理时间。

### 第三阶段：兼容与验收

- 新验收周期采用新政策；旧任务保持原始政策与暂停状态。用户显式选择采用新政策时，新增政策切换事件，不修改历史报告/账单/次数。
- 当前《蜂蜜快递》可利用已完成的“仅 2 LOW”报告做离线回放；该报告只对其对应候选有效，不能用于直接批准后来发生变化的候选。
- 离线回放通过后，再经授权恢复或启动一轮 Chrome 真实验收；不得借验证方案自行恢复付费任务。
- 回滚只影响未来周期的政策选择，不撤销已发布的接受决定、不重复扣费。

## 8. 验收标准

1. 仅 LOW 的有效已结算报告产生“接受并附建议”；Revision 调用次数为零，原始 issues_found 不被修改。
2. 未豁免 MEDIUM/HIGH 仍触发修订；混合报告保留全部建议，不限制 Agent 顺带处理它们。
3. 两轮后仍有阻断项则暂停；刷新、重启、普通恢复不会产生第三次自动 Revision。
4. 无变化候选经复审仍被阻断时停止循环；若复审接受，则正常接受。
5. 无效报告、未结算、用户停止、版本不匹配、发布冲突不能绕过；并发观察、重放和崩溃恢复不产生重复调用、重复发布或重复扣费。
6. 用户裁决准确绑定原报告与文档版本，不能继承到新版本。
7. 用本次“剩 2 LOW”报告回放证明后续调用被省去；其已发生的约 15 分钟为该案例可避免的后续执行量，不作为普遍性能承诺。
8. 原生 Bash、Agent、TaskOutput、工作文件、完整父子用量统计和停止清理回归保持通过；提示词与工具可用性没有新增约束。

本方案优先消除不必要的整轮调用，不保证一轮 Agent 更快，也不把“零 finding”继续当作完成标准。
