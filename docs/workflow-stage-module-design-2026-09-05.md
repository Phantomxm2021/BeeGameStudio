# 工作流独立阶段模块设计

状态：设计已确认；Reviewer 入口、调度、事实归并、确定性准备、语义汇总及终态接纳四批迁移已实施，其余业务迁移及真实审计修订验收未完成。

## 目标与约束

每个阶段独立拥有自己的业务规则、输入投影、状态、提示、调度、输出校验、提交及恢复决策。阶段间仅通过明确的交付物和结果交接，不调用其他阶段的内部实现，不读写其他阶段的私有状态。

全局层只拥有阶段路由和整体生命周期；锁、存储、传输、日志与计量继续复用。这是业务模块隔离，不是每阶段独立服务、进程或数据库，也不是所有代码零共享。

用户已允许为隔离调整共享层路由调用，不允许借迁移改共享业务规则。已有未提交修改原样保留。本方案不重写初稿、不重新生成八文档、不自动启动现有暂停项目。

## 现状与不能混淆的边界

- 八文档作者已有独立 context、boundary、scheduler、state、recovery 模块；仍须纳入统一边界验收，不能只凭文件名宣布全部隔离。
- Reviewer 的事实抽取和语义任务已有专用模块，但调度、终态归并与状态推进仍在 controller 中。
- 修订的任务包、暂存与发布已有专用模块；规划、复核调度、发布协调及轮次结束仍在 controller 中，并共用 foundationAuditState。
- DOCUMENT_REVIEW 同时承载 FOUNDATION_REVIEW 与 CHECKLIST_DRAFTING，持久化 phase 不是业务模块边界。
- validation-stage 同时拥有实现审计与验收，应分为不同阶段模块。
- 当前修订策略为问题未清零则继续下一轮，没有业务轮数上限。本次仅保持行为，不新增一轮限制、降级放行或默认放弃策略。

## 目标阶段划分

以下为业务模块名，不直接更改现有磁盘 phase、workerType 或 UI 编号。

| 模块 | 唯一业务职责 | 输入与输出 | 不得承担 |
| --- | --- | --- | --- |
| brief-confirmation | 简报澄清与用户确认边界 | 用户需求 → 已确认简报及摘要 | 代替用户批准需求变化 |
| foundation-authoring | 八文档依赖调度、撰写、自检及交付 | 已确认简报、已交付上游文档 → 初稿文档包 | 全局审计、跨文档自动修订 |
| foundation-review | 事实抽取、确定性检查、语义审计、问题登记与修订后复核 | 固定版本文档包、可选变更范围 → 审计证据、问题集、通过或需修订结果 | 写入八文档正文、代替修订阶段实施修改 |
| foundation-revision | 按授权问题规划修改、生成暂存候选、校验修改范围及发布 | 文档包、授权问题集 → 修订候选、变更说明、已验证发布回执 | 自行消除问题登记、降低审计标准、修改无关章节 |
| checklist-authoring | 将通过审计的文档转换为验收清单 | 审计通过的文档版本 → Checklist 及回执 | 重审或重写八文档 |
| resource-preparation | 资源计划、清点、内容生产、资源就绪门禁 | 已批准文档、清单 → 资源与内容包、就绪证据 | 替上游修改需求来适配工具能力 |
| atomic-task-planning | 拆分实现任务、依赖与可执行性检查 | 已批准文档、清单、资源就绪证据 → 原子任务图 | 实现代码、擅自跳过资源门禁 |
| implementation | 执行任务、代码提交与任务级验证 | 任务图及批准的输入版本 → 实现产物、任务回执 | 自己出具实现审计或最终验收通过结论 |
| implementation-audit | 独立检查实现及问题定位 | 实现产物及批准依据 → 实现审计证据、返修要求 | 直接修改实现代码 |
| acceptance | 按 Checklist 执行验收及收集证据 | 实现、清单、审计证据 → 验收结果 | 放宽清单、代替实现阶段修复 |
| delivery | 验证交付依据、汇总交付结果 | 通过验收的版本及证据 → 最终交付记录 | 重新实现、重新审计或跳过门禁 |

brief-confirmation 是 delivery run 的上游入口，先定义公开交接，是否迁移其现有实现须先检查其所在系统，不能凭此设计扩大修改范围。资源阶段的四个现有子步骤由资源模块内部拥有，不因此建立新的全局阶段。Game IR 保持现有能力归属；迁移对应消费阶段前必须清点，不因为本表未新增 phase 而删除、旁路或重新设计它。

## 交接与审计修订闭环

主路径：简报确认 → 八文档初稿 → Reviewer → Checklist → 资源准备 → 任务规划 → 实现 → 实现审计 → 验收 → 交付。

Reviewer 发现问题时，交接修订；修订生成候选后交回 Reviewer 复核。实现审计及验收的返修沿既有路由返回实现阶段，不能另建一套隐式补写链路。

修订闭环的职责细分：

1. Reviewer 对固定文档版本产生带证据的问题集及可修改范围。用户目标或权威来源无法确定时返回 needs_action，不自行裁决需求变更。
2. 修订模块只消费该版本的问题集，按文档/章节生成候选；检查基础摘要、允许路径、操作有效性及回执。这类修改完整性检查不是 Reviewer 的内容审计。
3. 修订阶段输出候选包与变更范围，由全局路由交给 Reviewer 的复核入口。Reviewer 重建受影响事实、执行必要的确定性与语义复核；不得因暂存文档未发布而读取旧正文冒充复核。
4. Reviewer 输出绑定候选摘要的复核结果，不直接发布正文。修订模块仅在所需复核通过、基础版本仍匹配时调用既有发布能力，提交正文和绑定的结果回执；跨文件一致性与恢复语义保持现状。
5. 全局路由仅根据已提交结果选择下一阶段。剩余问题及下一轮修订资格由 Reviewer 的闭环策略决定，沿用当前问题清零策略；修订阶段不能自行宣布问题已解决。
6. 任一基础文档或候选摘要不匹配，拒绝继续消费过期结果，交回其所有者重新计算或要求人工处理。不得静默把旧证据绑定到新版本。

审计中的初次检查和复核共用同一模块的规则，不在修订模块复制第二套规则。迁移时先提取现有行为、再通过适配接线，不重写规则实现。

## 模块接口与依赖方向

目录目标为 stages/<stage-name>/，每阶段按需要组织 public、context、state、scheduler、terminal、recovery、prompts、validation 与 tests；小阶段不强制创建空文件。公开入口采用显式函数，不引入插件注册中心或通用策略引擎。

公开操作包含进入、处理本阶段终态、恢复、响应停止/继续；具体参数采用阶段专有类型。输出只能是本阶段状态更新、任务意图或交接结果，禁止返回任意 Partial<DeliveryRun>。

公共交接协议至少绑定 run/project 身份、生产者阶段、交付物版本与摘要、证据/回执引用，以及明确的结果种类。文档修订另绑定基础版本、候选版本及问题集摘要。已有协议能表达的字段直接复用，不为统一形式立即添加另一套持久化结构。

依赖方向：全局路由 → 阶段公开入口 → 阶段内部实现；阶段可使用协议及注入的基础能力。阶段 A 不 import 阶段 B 的私有模块。复核使用 Reviewer 公开协议，经路由交接，不从修订阶段反向调用 controller。

context 是可读状态投影，boundary 是受限回写适配器；两者必须复制嵌套可变对象并使用字段白名单。旧 foundationAuditState 即使暂时保留磁盘形状，也不能作为可变整体暴露给两个模块。问题权威属于 Reviewer，修订执行状态属于 Revision，由适配器分别读取与写回。

阶段业务决定：哪些任务可启动、业务并发与重试条件、何时合格、哪些失败需人工介入。公共设施执行：会话传输、持久化、锁、事件追加、日志及计量。既有基础设施的协议拒绝机制保留，不能把所有校验误归为阶段业务。

## 全局层最小职责

- 根据公开交接结果选择下一阶段，拒绝不合法或过期交接。
- 执行用户停止、继续和运行生命周期；将业务恢复交给当前阶段。
- 路由终态到真正拥有 dispatch 的阶段，包括嵌套任务、重复终态及重放。
- 维护公共 run envelope、锁与事件持久化；不内嵌事实检查、修订批次规划、Issue 严重性决策或合格判定。
- 展示阶段公开进度；前端不得靠读取其他阶段私有状态推断当前阶段是否完成。

审计修订真实验收前必须有可靠的边界停点，确保通过后停在 Checklist 之前；不能靠人工轮询及时点停止。若现有公开协议不能表达，单独列出必要的交接控制变更并确认后实施，不在 Reviewer 业务内塞测试专用停点。

## 分步迁移

1. 建立行为基线：保存当前未提交修改清单；清点 controller、transition、dispatch、recovery、projector、worker 提示与前端投影的所有者。冻结输入文档、审计契约、模型及策略，区分已有变更与本次变更。
2. Reviewer 模块：先迁事实抽取、审计调度、终态归并、状态与恢复；共享处仅换为委托。通过冻结输入等价测试后再推进。
3. Revision 模块：迁问题消费、批次、候选、提交与恢复；将复核所有权交给 Reviewer 的公开入口，闭环策略行为保持不变。不得由两个模块共享可变状态或重复拥有 Issue 权威。
4. 验证作者 → Reviewer → Revision → Reviewer 的接口、恢复及隔离；在具备可靠停点后，使用本轮八文档的冻结副本进行真实验收，保留原始初稿证据。没有新生成授权不重跑作者。
5. 拆出 Checklist、资源、任务规划；再拆实现、实现审计、验收、交付。每阶段完成一批迁移与回归后再动下一阶段，不能同时大改整条工作流。
6. 最后统一目录和移除旧业务入口；不保留新旧双实现、兼容开关或运行时任选路径。磁盘 schema 暂时保持原样；若必须变更，单列迁移及恢复验证，不随目录整理暗改。

## 验收要求

- 静态依赖检查：阶段不得引用其他阶段私有实现；共享文件不得重新积累已迁出的业务逻辑。
- 状态隔离：拒绝越阶段输入、越字段回写及嵌套引用泄漏；Reviewer 无正文写权限，Revision 不能修改未授权路径或自行签发审计通过。
- 交接正确性：基础/候选/问题集摘要匹配，公开结果可重放，重复终态不得重复发布；拒绝过期回执。
- 行为等价：同一冻结文档包、模拟 worker 输出下，迁移前后问题集、修订范围、状态轨迹、发布结果一致；不能只对比函数名。
- 恢复：覆盖事实抽取中、审计中、候选生成后、复核中、发布中及发布后交接前的停止、继续、重启和并行兄弟任务异常。
- 非目标回归：作者及下游阶段行为保持；模型、Token 计量、业务并发与重试策略不随迁移改变。
- 真实验收：分别记录审计发现率、误报、修订正确性、新增问题、复核闭合、耗时及 Token。初稿问题是测试样本，不要求作者代替审计消除。
- 报告分开标注“设计完成”“业务迁移完成”“离线验证完成”“真实闭环验收完成”，不得用已建目录代替已实现隔离。
