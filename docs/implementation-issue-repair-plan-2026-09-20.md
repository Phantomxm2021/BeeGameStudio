# 实现期间的问题记录与定向修复

## 目标

先完成游戏逻辑，再集中处理不阻塞实现的问题；资源修复与代码修复各负其责，最终校验当前产物。适用于所有项目。

## Agent 执行方案

1. 发现问题时先判断是否阻碍继续实现。外观瑕疵等非阻塞问题记到 `.beegame/implementation-issues.md`，继续完成逻辑；关键文件不可加载、接口/动画定义不明等真阻塞问题提前处理。
2. 记录保持简短：现象、证据、影响、应交给谁、处理结果。没有问题不建空报告。已有记录继续更新，不从头审计或扩展需求。
3. 游戏逻辑完成后集中处理：源素材问题交资源修复任务；加载、渲染、交互问题由实现任务处理。可使用原生委派能力，不指定工具、人数或固定轮数。无法完成交接则如实报告，不默默越界修改或假称完成。
4. 资源修复只处理相关素材，同时维护其 Manifest 哈希、元数据和加工来源；不得只刷新哈希来掩盖错误，也不重跑整个资源生产。
5. 消费修复后的资源，运行现有资源校验及受影响的构建/交互检查。最终验收针对修复后的产物；此前 PASS 不自动沿用。未解决的交付要求应在现有验收记录中报 failed/blocked。

## BGS 调整范围

- 删除“IMP 可以直接修任何素材/Manifest”的笼统授权；正常实现、续跑和变更请求共用上述分工。
- 实现任务提供既有资源库/生图入口，供定向资源修复使用；不因此增加生成调用。
- 传入现有资源契约和只读校验命令。续跑时交付当前实际校验问题，不让 Agent 从一句 failed 猜原因。
- 保留最终哈希、引用和版本校验。合法资源修复后更新 Content 版本绑定；不盲目重算哈希、不新增审核 Agent、阶段、采购状态机、自动重试或问题文本解析器。
- 一个 CLI 任务可协调实现和资源修复，所以不新增工具拦截或固定目录写入顺序；广泛的技术访问能力不等于取消职责分工。

## 验收

- 普通素材瑕疵不会要求重启文档/资源阶段；真阻塞项不会被拖到错误实现之后。
- 实现及续跑都收到相同职责说明、真实资源问题和可用访问入口。
- 修改文件但漏同步哈希仍被拒绝；经确认的资源修复同步 Manifest 后可以继续接入当前实现。
- 资源修复后复验相关结果，无新增自动循环。本批代码测试不代表测试项目已重新交付。
