# 从 boss-bomb-arena 全链路复盘得到的 BGS 系统修复计划

日期：2026-09-27。状态：**P0 与部分 P1 已实现并通过定向回归；未做真实新项目验收，也未重启运行中的服务**。测试项目仅只读取证；其 Agent 在本次审计时仍执行 acceptance，以下结论以 2026-09-26 22:00 UTC 前的日志及文件为准，不把进行中的修复算作已交付。

## 1. 先说结论

不是「Agent 太自由」或「八文档/资源/Scene/UI 没做」。它们已经产出，且资源和内容格式检查通过。系统性故障集中在三处：

1. **交付阶段只看回合结束，不看前一责任是否真正闭合。** Review 报出 17 个问题，revision 回合 9 秒、零工具调用就进入 resources；Agent 随后在 resources 才补修文档。
2. **正确的数据语义没有贯穿到最终运行与检查。** 内容阶段的离屏预览正确读取图集 `.frame`、递归 UI 层级；实现阶段重写了解析器，按扁平图集帧和平铺 UI 消费。BGS 的静态校验不验证游戏运行时，已有可选 consumer 辅助模块也未进入生产交接。
3. **实现阶段的自报“通过”不是画面验收。** 项目脚本 16/16 检查了 DOM/玩法路径，却保存了缺少地面与精灵、标题文字叠层的截图。`acceptance.json` 被写成 `passed`；后续真正看图的 acceptance 回合才发现问题。当前 BGS 对报告做结构、文件、版本校验，不检查图片内容；代码还允许满足门禁的 implementation 报告直接跳到 complete。

因此：修正 BGS 的交接、契约、验收口径；**不**替该游戏修代码，不规定 Agent 用哪个引擎/工具或如何调试，也不造 BGS 游戏引擎。

## 3. 分类：项目现象、平台根因及证据边界

### A. 交付流转：BGS 确认存在缺口

- `project-delivery.ts` 的 `advanceProjectDeliveryAfterTurn` 对 review/revision 没有产物闭合检查；成功回合即可按 `NEXT_PHASE` 前进。本案 revision 没改文档，resources 才修。这是**阶段状态与实际工作脱节**，不是模型没理解需求。
- 同文件允许 implementation 的当前 `passed` 报告直接跳过 acceptance。这里因为报告列了 `knownIssues`/`unverified`，`runtime-acceptance.ts` 会将其降为 blocked，才进入实际 acceptance；**不能因此认定跳过分支安全**。
- 当前报告把跨浏览器、手柄、机器人通关及关键最终一击放在同一类未验证数组中，门禁不区分「确认范围内必验」与「范围外说明」。本案选择了手柄，属于确认范围；Firefox/Safari 未必属于确认范围。两者都不应靠一句 PASS 或一概全拦来处理。

### B. 资源/内容契约：平台描述不全，但原始数据已提供

- `assets/manifest/CONTRACT.md` 有图集嵌套 `frame` 的准确实例，却只给 `agent-authored` 来源对象实例；Web/资源库来源必填字段在 `asset-contracts.ts` 的校验器中。Agent 读压缩 `check.mjs` 寻找字段，属于**项目内作者接口与校验规则不等价**。应补同源实例，不把校验器源码当作者文档。
- 图集错误不是「BGS 没提供格式」：实现前 Agent 的查询脚本打印了 `v.frame`，把真实嵌套结构显示成扁平矩形；之后 `src/render/assets.ts` 返回原始 `sidecar.frames`，渲染器却取 `frames[name].x`。这是具体消费错误；BGS 缺的是能在真正运行画面前暴露它的反馈。
- `game-content-validation-cli.ts` 明确返回 `runtimeVerified:false`。它的 `valid:true` 只说明文件/引用/结构，不证明纹理显示、父子显隐、布局或玩法。
- `game-content-consumer.ts` 已复用 Editor 的解析/坐标函数，但 `CONTENT_CONSUMER_INSTRUCTION` 当前只在自身文件与测试出现，没有接入生产交接。要审计是暴露为**可选**能力还是删掉闲置入口；不强制项目依赖 BGS 包。

### C. 游戏运行时与 Editor：本案缺陷，揭示跨项目验收盲区

- 内容阶段的 `tools/render-content.mjs` 正确取 `meta.frames[name].frame`，递归 UI 子节点；最终 `src/render/assets.ts` 与 `src/react/UILayer.tsx` 最初走另一套解析。Editor/数据预览正常，游戏仍可错。**预览正确不能代表最终运行时正确。**
- 运行时 UI 起初只判断节点自身 `enabled`，禁用父节点的说明/错误覆盖层子节点露出；图集 UI 裁剪同样按扁平帧取值。保存的标题与战斗截图已经能看出问题。
- `src/render/renderer.ts` 固定图片路径和多处 48px 绘制，`src/game/world.ts` 固定 15×11 边界；VFX JSON 被加载但无使用点，TileSet 的部分绘制信息/排序没有成为通用驱动。它消费了若干 Scene 值，但并非「Scene/UI/VFX 是完整可编辑来源」。改变个别文案、网格原点的测试不能证明其他节点和资源跟随数据变化。
- `content/index.json` 将暂停、结算、VFX 标为 `on-demand`；`src/content/loader.ts` 启动时仍一次取完六份文档，`loadSceneAssets` 同时加载所有主要图片。这是已确认的加载语义偏差；**未实测速率，不能直接断言它是用户感知慢的唯一原因**。
- 自动化脚本会直接修改玩家坐标、触发私有方法、覆盖 gamepad，并主要断言 DOM/世界状态。它能证明选定机制的一部分，不证明正常玩家路径、手柄或画面。截图虽已保存，首次报告没有发现明显视觉错误。

### D. 工具与执行环境：有成本/安全信号，但不能夸大

- Implementation 自装/尝试多种 Playwright 浏览器，项目 `.beegame/tmp` 约 1.9 GB（两套浏览器缓存占主要部分）；不少脚本用 `--no-sandbox`，`tools/verify.mjs` 未带 `--mute-audio`。BGS 已有带静音与关闭生命周期的 Preview 测试浏览器，但本轮能力详情主要落在临时 `context.md`，当前回合只直接提示该路径。Agent 未使用它。**磁盘缓存与脚本参数可证；当前是否仍有存活进程/内存泄漏因本环境无法列进程，尚不能下结论。**
- `tools/acceptance-shots.mjs` 保存了当轮 Preview/CDP 能力 URL，而平台说明要求不要将能力写入持久项目文件。该 URL 是短期本地能力；未发现外传证据，但项目源码里留令牌仍是不必要的泄露面。
- 资源阶段网络 502、缺 PIL/fontTools、临时 cwd 错误等确实耗时，但并非全部归咎 BGS。优先修已证实的平台契约/能力入口，不把每个外部工具失败转换成新规则或强制资源路线。

## 4. 通用修复路径（按依赖，不改测试项目）

### P0 — 先修会造成错误流转或错误 PASS 的两处

1. **闭合 review→revision→resources 责任**：不再把「只写问题报告」和「修订文档」无条件拆成两个自动回合。以「评审并处理必要修订，交付当前八文档」为一个结果；Agent 在同一主 session 自选自查/子代理，BGS 只核对产物存在及版本变动，不解析自然语言关键词、不规定工具调用。迟到的子代理回执不是一次独立修订完成。仍可展示 review/revision 过程标记，但不让空白 revision 回合单独触发资源阶段。BGS **不能仅凭版本变动证明每条意见已闭合**；这一语义由 Agent 在同一任务负责，最终验收再看文档与实际成品是否一致。
2. **取消 implementation 自报报告直接完成交付的捷径**，直至它具备与 acceptance 等价的覆盖证明。保留一个最终验收责任：读取当前文档/内容，实际打开目标运行时并查看代表性画面与关键交互；有效证据与构建绑定。`runtime-acceptance.ts` 继续验文件/哈希，但不把这些自动称作视觉通过。明确范围内未验证与范围外限制，避免不相关浏览器说明阻断发布，也不能让已确认的手柄需求悄悄消失。无需另建独立审核模型或重跑资源/内容。

### P1 — 修补接口，不指挥 Agent 写代码

3. **从校验源生成完整作者契约**：`asset-manifest-authoring-contract.ts` 为每种允许的 `source.type` 给出最小合法实例/必填字段，并用现有校验器测试实例，避免再次反查压缩脚本。Scene/UI 图集、父子显隐、变换、排序沿用现有 schema/Editor 函数，不另写解释。
4. **交接现成可选能力的最短入口**：在当前回合直接给出 Preview 测试浏览器、项目内容辅助模块的简短能力索引和获取方式；详细文档仍在项目内，是否使用由 Agent 决定。端点/令牌只存在当轮临时能力，不在长期提示、持久脚本中充当默认值。若 consumer 模块不打算提供，就移除闲置说明和测试，不维持一条幽灵接口。
5. **复用少量同源契约夹具**：嵌套图集、禁用父节点、父子 Transform/排序、`loadPhase`。用它们验证契约、Editor、可选 consumer 的一致性；针对任意 Web 新项目可观察目标运行时的请求和代表性画面，区分「JSON 结构有效」与「项目代码消费正确」。不通过扫描项目源码或要求导入 BGS 函数判断正确性。3D/XR 仅验其适用的数据规则；XR 真机能力未有则如实未验。

### P2 — 缩短无效调试，保障能力生命周期

6. **测试证据先分型再结论**：BGS 已有 Preview 录制/静音浏览器，提供易见的入口、可复读的控制台/网络/截图证据。浏览器启动失败、测试机器人走位失败、产品实际缺图要分别显示；不要自动重复付费回合。Agent 仍自主选测试方法；实现/验收只需一次有代表性的实际画面检查，不把 16 项逻辑断言说成全量交付。
7. **能力与临时产物卫生**：测试浏览器继续由已有 `close()` 管理。对 BGS 自有缓存做边界明确的回收；Agent 创建的项目文件/缓存只报告位置、大小与原因，不擅自清理。发布/交付检查提示项目非临时文件内残留的 BGS 临时能力令牌，由 Agent 自行修正；不自动编辑项目文件。项目脚本若自行起浏览器，报告未静音/未关闭风险，不据此断言全部测试都静音。

## 5. 验收标准与边界

- **流转夹具**：迟到子代理通知不触发独立的空白 revision→resources；有发现的评审夹具在同一任务交付更新后的文档，无发现不额外消耗一个空回合。主 session 保持一个，Stop/Queue/Steer 与子代理继续正常。对自然语言评审意见不宣称平台能自动证明全部闭合。
- **接口夹具**：四类资源来源的示例全部过同一个正式校验器；图集/层级/Transform/排序的契约和 Editor/可选 consumer 结果一致。Agent 不必采用该 consumer。
- **错误 PASS 夹具**：仅 16/16 逻辑检查、自报 `passed`、证据文件及哈希齐全，但截图明显缺图/禁用层级泄漏时，不能直接成为完整视觉交付；正确截图与范围内验证可完成。无法判断须标未验证。无需第二个游戏引擎或像素完全一致比较器。
- **加载与效率**：Web 夹具的 `startup` 不请求 `on-demand` 内容；实现阶段至少记录墙钟、工具失败、模型新输入/缓存输入/输出、浏览器试错与验收调用。只报告真实前后差，不承诺固定节省比例。
- **隔离验证**：先在 BGS 的临时夹具免费验证，再用全新小项目做受控真实复测；付费复测另取当轮额度。不修改 boss-bomb-arena 或其他私有示例，不自动续跑/发布它们。
- **不会自动证明的事**：一种截图不能证明所有画面、玩法、设备、审美或 XR 真机体验；BGS 的职责是如实标注覆盖，Agent 的职责是自主实现与修复。

## 6. 方案自审

- 没把每个游戏缺陷做成 BGS 特判；同一修复覆盖使用图集、层级 UI、Scene 数据和按需加载的其他项目。
- 没有以旧版流程为正确性标准；只从本次真实日志、当前代码和可核验产物推导。
- 没有扩大 BGS 对 Agent 的控制：不强制子代理、浏览器、资源来源、框架、迭代次数或具体代码结构；平台只持有契约、交付状态、可信证据与工具生命周期。
- 不新增通用游戏引擎、第二份 Scene/UI 解析规范、复杂调度器或视觉像素评分器。若最终画面验收仍连续漏报，再用新证据评估是否需要独立看图能力；本轮先修已有 acceptance 跳过与证据口径。

## 7. 本轮落地与未完成项

- 已改：review 和必要文档修订在同一主会话回合处理；新项目不再自动派发独立空白 revision 回合。已有停在 revision 的状态仍能继续到 resources。平台不解析评审意见，也不指定子代理。
- 已改：implementation 自报 PASS 不再直接完成交付；验收回合或已完成后的重新验收才能捕获新报告。发布门禁仍绑定当前文件和证据。实现回合不再收到提前填写发布报告的接口提示。
- 已改：资源作者契约补齐四类来源的字段实例，测试用主机解析器逐一读取；现有的项目本地校验器仍是唯一格式检查器。
- 已改：实现／验收回合可选获得同源 Scene/UI 内容辅助 ES 模块，回合结束删除；直接提示可选的静音 Preview 测试入口。既不强制导入，也不提供游戏引擎。删除了未接入生产的长篇辅助模块说明。
- 已验：相关定向测试 35 通过、服务端 TypeScript 检查通过。更广的 beegame 测试目录有 201 通过、10 失败、4 跳过；失败集中在本执行沙箱不允许监听临时端口／运行内层 sandbox-exec，并非上述定向测试失败，不能宣称全量通过。
- 未验：服务重启后的线上回归、全新项目的实际画面／加载／耗时与 token 对照、XR 真机。原测试项目不修改、不作为修复产物。P2 的浏览器缓存和项目脚本中的临时能力卫生尚未自动处理；BGS 不应替 Agent 清理项目文件。
