# 八文档到实现清单的衔接方案

> 2026-10-08 更新：当前执行进度见 [八文档交付重整清单](eight-document-delivery-rework-checklist-2026-10-08.md)。本方案保留单一清单与来源映射；本次补充明确任务依赖、原始需求覆盖核对及按实际来源读取。下列历史测试／部署状态不是本次验收结论。

- 日期：2026-10-06
- 版本：1.2
- 状态：系统源码已实施并通过本地免费回归；尚未构建部署到运行服务，未启动付费真实生产验收。

## 1. 本次修订与目标

上一版只描述“作者登记 → Review → 实现”，没有说明八文档各自产出什么，以及如何把跨文档要求组织成可执行任务，不足以指导实施。另一个错误假设是“程序汇总索引就能生成合适的功能任务”：程序能收集条目，不能自己理解并合并游戏功能。

修订目标：**八文档决定完整游戏要求；现有技术设计补全环节把这些要求组织成任务草案；联合 Review 核对后交给实现 Agent。** 实现 Agent 在明确依赖约束内决定开发方法和顺序，但不能重新概括、删减这份必做清单。

当前代码已有 `outputs`、临时 `TodoWrite` 和验收 `requirementChecks`。缺少的是八文档要求到实现任务的明确关联，不是完全没有清单。

## 2. 八文档各自贡献什么

以下是各作者需登记的要求类型，按实际项目取舍，不要求所有游戏强行包含示例功能。不把整篇文档、每句话或每个资源文件机械变成任务。

| 文档 | 本文档必须明确并登记什么 | 对应的执行结果／典型颗粒度 |
| --- | --- | --- |
| **GDD** | 首发功能、玩家动作及后果、核心循环、必要状态和转换、输赢／重试及必要进度规则 | 一项动作闭环、一组明确状态转换、完整单局流程；不是“实现全部玩法” |
| **技术设计** | 内容加载与消费、输入／状态／事件接入、模块接口、初始化／重置／清理、存储与故障恢复 | 一项可核对的技术接入或生命周期；最终补全时还要组织跨文档实现任务 |
| **美术方向** | 场景和界面的视觉语言、构图重点、字体／层级标准、对象辨识、实际事件的动画和视觉反馈 | 某类事件的视觉反馈或某类画面的表现要求；共同风格作为全局约束，不列成像素任务 |
| **音频设计** | 必要 BGM／音效、事件触发、播放／停止、循环／并发、跨状态行为、静音／音量及保存范围 | 一组明确事件的声音映射、一个音乐生命周期、设置行为；不是“补上声音” |
| **关卡／场景设计** | 各关或复用类型的目标、路径、障碍、出生／结束条件、Camera、可见性，以及实际 Scene JSON | 一个关卡或生成器的必要行为及空间消费；不是“载入场景文件就完成” |
| **数值设计** | 可运行初值、单位／公式、合法边界、难度变化与调优假设 | 一组相关参数及计算／变化结果；不把每个常数拆成任务，最终平衡仍需实测 |
| **UI／UX** | 每个必要页面／HUD／覆盖状态的入口、显示、数据来源、输入、导航、反馈、适配，以及实际 UI JSON | 一个页面交互或状态闭环；默认、禁用、异常／恢复按规划明确；不是“完成 UI” |
| **资源计划** | 前七文档所需资源的用途、规格、变体、来源和允许回退 | 必要资源角色到实际资源、内容绑定和运行使用的对应；不是检查文件存在就完成 |

一项要求只由其专业文档定义。比如 GDD 定义是否暂停及玩法后果；UI 定义操作和界面；Audio 定义声音变化；Tech 定义执行和清理。**组织成一个任务，不代表这些决策改由技术作者决定。**

## 3. 在哪个环节出最终清单

保留当前五组撰写和后续阶段，不新增规划 Agent 或额外 Review。

| 现有环节 | 本轮增加的明确产物 |
| --- | --- |
| GDD | 登记首发核心功能／行为要求，供专业作者引用 |
| 技术基线／美术／音频 | 登记专业要求，与已有玩法来源关联；尚未形成的 UI／Scene 输入保留待补，不伪造 |
| 场景 → 数值 | 登记空间及数值要求，Scene 作者保存实际布局 JSON |
| UI／UX | 登记逐页面／状态的交互和表现要求，保存实际 UI JSON，与 Scene／Art／Audio 的相关要求对应 |
| 资源计划 → 技术设计补全 | 资源计划补齐资源角色；**技术作者从八文档索引定位必要接口、生命周期、共享约束和成果的原文，局部补全技术设计并整理实现任务；不自动全文重读／重写八份文档** |
| 联合 Review／Revision | 同时检查原文、专业要求及任务草案；核对缺项、粒度、关联和冲突，修订后形成已有规划基线 |
| 资源／内容 | 完成真实资源和原 Scene／UI 数据绑定；只补实际输入，不重写任务范围 |
| 实现 | 直接收到已审任务清单、相关原文、全局约束和实际数据入口；不重新生成另一份交付范围 |

各作者仍使用现有 `.beegame/design-handoffs/<文档名>.json` 的 `outputs` 登记必要要求，关联具体正文及验收章节。解释、参数、坐标和资源表留在原权威文件，不复制进索引。

### 任务怎么组织，颗粒度是什么

技术设计新增一个简短的“实现交付清单”章节，每个任务有：**稳定编号、明确目标、引用哪些专业要求、需要哪些实际输入、怎样核对结果**。业务规则只引用原文，不重定义。开发命令、代码结构和详细顺序留给实现 Agent。

- 主要粒度：一个可落实、可独立核对的功能／行为闭环。例如结束与结算、暂停与恢复、某类动作及其反馈。
- 基础设施：内容加载及实际消费、输入接入等可以独立成项，但其完成不等于玩家功能完成。
- 一个任务涉及多个专业时，列出各专业的必要关联结果，不能用“完成该功能”隐藏它们。
- 可分别失败、分别修复的功能拆开；共同构成一次交互的结果可以作为一个任务内明确子项。不设固定任务数或每任务文件数。
- 每个必要页面、关卡／复用类型、动作和重要状态转换都必须能找到具体任务；共同视觉、平台和数据约束统一保留，不能遗漏或每项全文复制。

### 跨八文档的具体例子

假设规划要求支持“单局结束后重新开始”，清单项不是“做重开按钮”，而是：

| 输入文档 | 该任务必须落实的内容，具体规则引用原文 |
| --- | --- |
| GDD | 结束条件、结算后允许的操作、重新开始进入什么状态 |
| 场景 | 新局出生位置／空间规则、必要镜头和可见对象 |
| 数值 | 单局初始值，哪些计分／计时状态需要重置 |
| UI | 结算界面的展示、数据来源、重开操作和返回后的 HUD |
| 美术 | 结算画面和重开反馈的规定表现 |
| 音频 | 结束声音、音乐转换、重开后的播放行为 |
| 技术 | 状态切换，旧局计时器／监听／对象清理，新局初始化 |
| 资源计划 | 上述画面和声音实际使用哪些已交付资源 |

完成条件：从真实游戏触发结束并操作重开，分别核对上述适用结果，而不是只证明内部重置函数能运行。未规划的效果不额外添加。这个例子是拆分方法，不是针对某个游戏预填答案。

## 4. 如何存储并直接交给实现 Agent

**区分两类记录：八文档的专业要求，和关联这些要求的实现任务。** 它们不是两套业务规格：前者定义事实，后者只安排落实。

- 专业要求：沿用各文档 `outputs` 的 `id`、`section`、`acceptance`。必要要求必须有可核对的完成条件；无法运行验证时保留未验证，不删除要求。
- 实现任务：沿用现有 `TECHNICAL_DESIGN` 索引的 `implementationItems`，每项为 `{id, section, requirementRefs:[{document,id}], dependsOn:[任务id]}`。`section` 指向技术文档中的任务段落，`requirementRefs` 精确引用各专业输出。新任务显式登记依赖；兼容旧索引缺字段，但不据此认定任务彼此独立。不增新清单文件或任务数据库。
- 全局约束：在技术清单正文引用其权威章节，入口一并提供；必要专业要求仍须有最终结果，不能因为称为全局约束就跳过验证。
- 程序按上述明确记录生成只读任务视图，检查已声明依赖的未知引用、自引用、重复与循环；不按标题相似度合并，不自行推导未声明的依赖。实现者在依赖约束内安排方法和顺序。

新增任务关联字段解决的是“同一功能横跨八文档，普通索引并集不足以指导执行”。它不保存第二套状态规则，也不承载调度器。若仅靠提示 Agent 自行合并，仍会回到当前的重新概括与遗漏问题。

进入实现时直接提供：完整任务概览和来源引用、已有有效结果、未完成项、全局约束、正式 `content/index.json` 和资源 manifest 入口。当前任务需读取相关原文及实际数据，标题不能替代规格。

Agent 可以排序、分组、增加技术子任务和选择工具。临时 Todo 必须标注所服务的原任务编号，不得替代或删减必做任务；不把通用 `TodoWrite` 改成交付数据库，也不逐项启新会话。

实现交接按原任务编号说明已落实的要求、实际检查及未解决项。结果继续使用专业要求的 `requirementChecks`，不另造任务验收系统。所有专业要求有结果，并且已有整体运行验收完成，才能讨论交付；Todo 打勾和 milestone `complete` 不能单独证明合格。

## 5. Review 与程序分别检查什么

| 对象 | 程序应检查（本次接入或复用） | 联合 Review／实际验收检查 |
| --- | --- | --- |
| 八文档 → 专业要求 | 编号、原文章节、必要验收声明、版本 | 原文有无漏登记；所有权、规则和专业决策是否清楚 |
| 专业要求 → 实现任务 | 引用存在；已登记必要要求是否关联任务；任务目标章节存在 | 关联是否实质正确；有无过粗任务、遗漏关联结果、擅自新增需求 |
| 任务 → 实际游戏 | 沿用结构／引用／空间算法及已有运行检查；结果覆盖与版本匹配 | 是否真实落实玩家行为、视听表现及完整流程 |

阶段权限、版本和现有基线保护继续使用；设计矛盾走受影响修订，不能由实现 Agent 静默删功能、改坐标或降低视觉／声音要求。专业要求变化影响任务时，将技术清单的受影响部分纳入同一次修订授权，不让任务关联与原文脱节。职责和必做产物由任务 prompt 定义，Skills 只提供专业工作方法。

已登记覆盖率不等于全部需求完整，填写通过不等于真实观察。现有验收器不能证明观察真实性，此次清单接入不能声称顺带解决它。模型也可能漏登记、错误关联或误判粒度；无可靠证据时保留未验证并说明影响，不能用更多模型 PASS 包装保证。趣味、手感和审美仍需实际体验判断。

## 6. 实施与验收顺序

1. **作者与技术补全入口：**修改 `project-author.ts`、`design-handoff.ts`，落实上述八文档登记分工与任务关联格式，不增加撰写批次。
2. **联合 Review 与基线：**在现有 Review 检查原文／要求／任务三者对应；Revision 同步受影响原文和索引。版本提升、写入权限和基线摘要沿用现有机制。
3. **实现输入与交接：**修改 `project-conversation.ts`、`project-delivery.ts`，提供已审任务视图和原文入口，明确执行及提交按原编号追踪；不增加自动调度、硬性轮次限制或每任务审批。
4. **程序检查与免费回归：**验证八文档来源引用、漏映射、无效引用、版本变化、上下文交付以及现有运行结果检查不被粗略 Todo／完成回执替代。映射只能证明关系存在，不证明含义正确。
5. **另行授权真实验收：**使用不同玩法的新 Idea，核对原文漏登记、任务漏项、执行偏差、证据不足和实际游戏效果，记录总 Token／耗时，不人工修补测试项目或预填案例答案。

保留 frontend 和无关修改。旧项目只诊断差距，不能自动把旧索引视为已满足新粒度；需要修订时经授权走正常流程。不回滚八文档，不新造第九份设计文档。

成本控制：任务整理并入已有技术补全，核对并入已有联合 Review；程序汇总替代额外模型抽取；允许批量实现和检查，不为清单更新单独制造模型调用。新增写作、映射和核对也有成本，必须实测，不能预先承诺降耗。

**验收目标：八文档里的必要承诺，能定位到实现任务和实际结果；遗漏更少，效果可核对，总成本可接受。不是清单齐全就宣称游戏合格。**

| 交接与验收 | 按原任务编号说明实现、检查及未验证项；仍用现有专业要求结果和整体验收，不另造任务结果协议 |
