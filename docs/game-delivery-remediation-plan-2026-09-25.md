## 1. 目标与边界

目标：八文档可实施，资源适用，Scene/UI 数据完整，游戏真正消费这些数据；减少平台制造的重复工作、等待与返工。

- BGS 负责项目会话、交付进度、当前输入交接、工具能力、格式检查与执行隔离；Agent 负责设计、规划、工具选择、委派、自查和修复。
- 每项目一个主原生 session；原生 subagent 不算拆分主会话。保留停止、恢复、queue、steer，不按“继续”等关键词推测意图。
- 保留八文档、评审及必要修订、资源、内容、实现、验收这些交付责任；不恢复旧控制器、强制 JSON 总结、审计清单或多 session。
- 不改私有测试项目，不改 Dashboard UI，不实现 BGS 游戏运行时引擎。代码修改限平台及隔离测试夹具。
- 历史实现用于解释差异，不作为正确性标准。本文所有数字是观察或验收标准，不是节省承诺。

## 3. 目标交付链与单一数据来源

**文档初稿（自主自查） → 评审并完成必要修订 → 资源 → Scene/UI/VFX 内容 → 运行时加载与行为实现 → 当前版本验收。**

这是交付责任顺序，不是 Agent 内部操作脚本。BGS 不指定如何思考、先用哪个工具、必须几个子任务或几轮自查。

| 内容 | 唯一权威位置 | 代码职责 |
| --- | --- | --- |
| 设计目标、关卡差异、交互/适配规则 | 八文档 | 指导实现和验收，不维护第二份精确数值表 |
| 资源文件、图集/TileSet 元数据、来源 | assets 与 Manifest | 加载、缓存、按引用获取资源 |
| 节点 ID/层级、布局、Transform、文字、图片、地图单元、放置点、交互绑定 | Scene/UI/相关内容 JSON | 按目标引擎解析并渲染，不抄写布局常量 |
| 移动、碰撞、计分、AI、动画驱动等行为 | 项目源码 | 消费内容配置、更新运行状态 |

继续使用现有 JSON，避免引入 YAML 双轨。运行时允许打包、缓存、编译内容，但编译产物不能成为另一份手工维护的布局来源。程序化关卡允许生成算法，但参数、种子和可编辑配置属于数据；不能把已有手工设计的关卡改称程序化来绕过内容交付。

## 4. 按依赖实施的六项改动

### P0-A：去掉强制重复核验，保留 Agent 自查能力

- 修改原生提示中按“3 个文件”等条件强制 verifier、循环到 PASS、PASS 后固定复跑的产品默认规则；保留 verifier 工具和自主委派。
- 将评审和必要修订作为同一工作单元，不再无条件另开空转 revision 回合。完成指的是问题已处理或明确未解决，不是只输出一份意见。
- 作者自主检查不被删除，也不由 BGS 强制加一次子代理审核。文档有实质修改时更新版本，无修改不虚增版本。
- 落点：`src/constants/prompts.ts`、本地 feature 默认配置、`project-delivery.ts`、`project-conversation.ts`。
- 验收：实际 runner 输入不含强制核验循环；author 可使用 Agent；无问题评审不再触发修订模型回合；有问题夹具能完成改文档后再进入资源。同一主 session 不变。

### P0-B：修复权限误报，不放开宿主边界

- 定向修复已隔离执行中的项目 scratch 清理：只接受执行上下文中可信且能安全确定的临时目录，校验规范化目标后沿用自动授权。
- 不执行 shell 来“试算”路径，不用通用变量解释器解决一个临时目录问题。无法证明目标、符号链接逃逸、项目根目录/宿主删除等仍保留保护。
- 落点：`packages/builtin-tools/src/tools/BashTool/bashPermissions.ts`、同目录 `pathValidation.ts`、`project-execution-access.ts`。
- 验收：日志复现的合法临时文件清理无需人工批准；根目录、宿主文件、逃逸链接及动态命令替换不能被误放行。Git、依赖安装、资源读取、浏览器及 subagent 正常工作。
- 不以 macOS 通过冒充 Windows/Linux/XR 设备执行器已验收；未验证环境列出边界。

### P1-A：补齐初稿的可实施性，不追加长篇过程指令

- 在现有文档说明中明确交付内容，而非命令 Agent 的写作方法；基础内容契约从初稿可见，实际资源引用在后续阶段填入。
- UI：覆盖所有界面及关键状态，明确节点/控件身份、布局与尺寸规则、文字/图片、交互绑定、输入和屏幕适配。允许锚点/约束/可计算规则，不要求在 Markdown 重抄全部 JSON。
- Scene：覆盖每个计划关卡的目标、空间结构、出生/目标/障碍/交互对象及规则；具体布局在内容阶段落成数据，不推迟到运行时代码里设计。
- 2D 明确坐标/网格和可达性依据；3D 明确单位、尺度、朝向、可行走空间；XR 明确参考空间、玩家尺度、交互距离和目标设备约束。只展开项目实际需要的维度。
- 同一个可调值有一个配置来源，其他文档引用，不要求跨八文档复制维护。
- Author 的可实施性自查和后续评审都应能发现缺项；BGS 不因“八个文件非空”宣称质量通过，也不通过扫描自然语言关键词代替判断。
- 落点：现有阶段说明与文档写作指导，不新增评分器、字数指标、关键词审查或强制 Skill 调用。
- 验收：新项目全部计划界面/关卡可从设计找到对应内容；不再出现“权威地图由 implementation 的 levelN.ts 定义”。合理的程序化项目单独按生成配置验收。

### P1-B：资源与内容交接完整，并由同源检查器解释错误

- 资源选择交给 Agent：优先考虑已有适配资产，但库、Web、AI、程序绘制没有强制搜索梯队。按表现需求、授权、目标设备、成本和复用性决定。
- 平铺环境适合时提供 TileSet 和图集；3D 提供合适模型/材质；XR 结合设备预算。AI 原图尺寸不直接决定世界/界面尺寸；不要求每个项目使用 AI 或 Tilemap。
- 复用已修复的当前回合能力交接及 `check-content.mjs`，核对资源能力端点更新、真实契约、格式与服务端检查一致；不再另造检查器。
- JSON 内容应包含计划布局及引用，不只放空 Grid 或行为名称。共享 Scene + 关卡数据与多 Scene 都可，须被现有格式登记并被编辑器及 runtime 读取。
- 先验证现有 Tilemap、图集、内容文件类型能承载需求；只有确实表达不了时才最小扩展格式与编辑器，不为此新写引擎。
- 平台错误区分缺失、格式、引用、过期输入和能力故障；反馈精确文件/字段和可用的项目内检查入口，不让 Agent 猜平台摘要算法。
- 文档/资源摘要由平台提供；Agent 不负责实现摘要计算，也不能静默重签变化后的内容。
- 落点：`asset-manifest-authoring-contract.ts`、`scene-ui-content-authoring.ts`、`game-content-package.ts`、`project-content-authority.ts` 与资源能力交接。
- 验收：重复错误可本地一次复现；检查器和服务端结果一致。2D TileSet/图集和 3D 内容夹具能解析，所声明文件及资源引用 100% 可解析。结构通过不宣称设计或视觉通过。

### P1-C：用运行验证证明“加载数据”，不只改提示

- 沿用 Agent 选择的引擎/框架；Agent 写项目侧解析和行为代码，BGS 只提供清楚的数据格式及编辑器。
- 用临时夹具覆盖 UI 标签/图片/锚点/显隐和 Scene Transform/Tilemap 单元/对象放置：仅改变源 JSON，编辑器与 runtime 都出现预期变化，不改项目源码中的副本。
- 文档规定的全部关卡/界面，必须有可追溯的数据入口并可加载；单个 Scene 可以复用，不用文件数量代替覆盖率。
- Agent 选择游戏专属的可达性、物理和胜负检查；BGS 不构建通用玩法证明器。
- 落点：现有内容契约、编辑器解析器及隔离端到端夹具；真实项目由其 Agent 生成解析代码，不由本次修复手工改样例。
- 验收：上述数据变更用例全通过；最终目标视口无裁切、关键按钮文字可见、全部计划关卡入口可达。不同引擎不要求像素级完全一致，但内容与布局语义一致。

### P2：消除重复验收与无信息续跑

- implementation 已完成当前版本测试并留下有效证据时，BGS 直接校验并记录；缺什么才交给 Agent 验什么。不把每个实现结束都变成另一次全量验收模型任务。
- 改动后只使受影响证据失效；先沿用现有版本判定，不能为此新建复杂依赖推导系统。不能安全确定影响时明确需要重验。
- 检查失败不是 BGS“自动修复”：BGS 反馈真实原因，Agent 决定处理。服务或输入故障先交还平台，不反复派发同一泛化任务。
- 现有“任何文件变化就算进展”需要移除其不成立的含义；不以任意重试次数替代根因修复。同一输入/同一检查失败，不产生无新增信息的重复自动提示；用户主动要求重试不被吞掉。
- stop 保留进度；恢复向同一 session 交接当前状态和欠缺产物。普通消息保留原文，由 Agent 理解；queue 等当前任务结束，steer 才即时引导，不抢跑或暗改消息。
- 落点：`project-delivery.ts`、`project-conversation.ts`、`runtime-acceptance.ts` 和已有队列/发布校验接口。
- 验收：当前版本证据有效时零额外验收模型调用；旧证据不能发布新版本；中断恢复不跳过资源/内容；重复回调不重复派发；Chat 的口头 PASS 不能替代证据。

## 5. 验收与量化：先免费，再受控真实复测

1. **离线回放**：固定日志快照，脱敏记录证据；重放权限、重复评审、阶段交接、单 session、stop/queue/steer、验收版本等已证实失败点。先确认复现，再修改，再确认通过。
2. **无费用集成**：现有检查器同源测试；2D 图集/Tilemap、多关卡/UI 夹具；3D/XR 空间配置夹具。不能把格式测试当真实设备体验验收。
3. **部署核对**：需要时从产品根目录环境配置启动，核验运行 worktree/构建版本和健康状态。不因重启自动恢复付费任务。
4. **新项目真实测试**：先做一个无新框架的 2D 多关卡案例，用户输入采用初学者表达。固定模型、目标平台、预算和测试条件；不手改它的产物、不用旧项目修补结果充当成功。
5. **扩面**：核心链路通过后再验一个 3D 案例；XR 先验证数据与交互模拟，真机不足则明确“未验收”，不扩大宣称。

| 指标 | 可执行判定 |
| --- | --- |
| 会话连续性 | 每项目主 native session ID 数量 = 1；子任务另列 |
| 平台额外开销 | 强制 verifier 次数 = 0；无修改的强制 revision 回合 = 0；有效证据后的重复验收调用 = 0 |
| 无效等待 | 已复现的安全 scratch 清理人工授权次数 = 0；未识别的权限请求逐项解释，不全部默认允许 |
| 内容完整性 | 计划关卡/界面到实际数据入口覆盖率 = 100%；声明资源/内容引用解析成功率 = 100% |
| 数据驱动 | UI/Scene 源数据变更用例全部生效，不改布局源码副本 |
| 安全性 | 宿主源码/凭据边界及逃逸用例不因权限优化退化 |
| 耗时/费用 | 每阶段列墙钟、权限/用户等待、工具耗时、模型输入/缓存读取/写入/输出、真实费用或明确估算；主/子任务去重 |

token 按原生消息 ID/用量结算去重，不能把 stream 快照相加；并行子任务时长不能直接加成主任务墙钟。用已有日志和脚本导出，不新建性能监控平台。
