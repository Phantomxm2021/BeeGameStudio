# 游戏 UI 视觉设计修订方案

日期：2026-09-29  
状态：已更新 Author、Review 与内置 UI／美术 Skill，免费回归通过；尚未用付费新项目验证实际设计与画面。

## 1. 目标与事实

目标：让游戏界面同时具备游戏身份、清晰构图、可用布局与合适反馈，而不只是通用应用控件换色。

本轮依据为 zone-survival-snake 的 ART_DIRECTION、UI_UX_SPEC 和 menu.json；未核对运行截图，不能断言实际运行画面全部表现。

已确认：
- 美术提出霓虹街机，但 UI 主要落为胶囊、细描边、圆角按钮与中央卡片。
- Menu 采用标题、介绍、开始按钮、最高分、操作说明的居中纵列，未明确玩法主题的视觉焦点。
- 已生成的游戏主体素材没有被 Menu 数据直接引用；菜单资源引用只有字体和图标，不能因此断言其背后的场景也未渲染主体。
- 动效主要是呼吸、缩放、淡入；界面与游戏主题的演出关系没有具体落实。

判断：本例在规划阶段就缺少画面设计，不宜把问题全部归因于实现。尚不足以证明所有项目有相同根因。图集改善资源组织，不等于改善审美。

## 2. 改什么、放在哪里

| 职责 | 系统修订 | 应交付的结果 |
| --- | --- | --- |
| ART_DIRECTION | 在现有 Author 美术职责中补充主题如何进入界面：视觉主角、焦点、层次、标题性格、材质/轮廓和动效性格 | 对项目主要界面给出可执行的视觉方向；不能只列风格词和色值 |
| UI_UX_SPEC | 在现有 UI 职责中要求先定义视觉主次，再描述布局与操作；区分菜单、HUD、暂停、结算的目的 | 每屏明确主要关注点、主操作、次要信息和相应空间关系；继续遵守自适应规则 |
| ASSET_PLAN / 资源 | 从界面设计提取实际需要的主体、背景层、标题装饰、按钮装饰等，不规定每个游戏必须都有 | 说明素材在哪个界面、承担什么视觉作用；AI/检索/程序制作均可，不能把要求的美术静默替换成通用几何 |
| Review / Revision | 在现有评审中核对上述视觉决策是否具体、跨文档是否一致，资源计划是否承接 | 发现空泛设计就在文档环节修订；不把文档通过当作画面审美已经验证 |
| Content / 实现 / 验收 | 延续文档和资源约定，不重新设计；在现有目标运行时检查实际呈现 | 核对构图、层次、素材使用、文字与操作、状态反馈；指出是规划、数据还是代码偏差 |

预期代码入口：project-author.ts、project-delivery.ts。先调整对应职责，避免同一句要求复制进每个阶段。仅在现有 Skill 指导有矛盾时同步修订，不以增加 Skill 数量替代实际质量。

## 3. 最小设计要求

- 菜单：明确希望玩家第一眼看到什么，以及为何想开始；玩法主题可以通过字体、构图、场景、图案或主体表达，不强制封面插画。
- HUD：重要信息按游玩优先级组织，不用装饰妨碍读数和操作。
- 暂停：保留局面辨识，明确恢复入口；不必重复主菜单的复杂演出。
- 结算：让胜败、成绩、奖励或进步形成视觉主次，不只是通用表格和两个按钮。
- 动效：围绕操作确认、状态转换与情绪反馈定义触发和节奏，保持可打断、输入响应与减弱动效方案。不是所有界面都要强烈演出。

共享组件负责一致性，不决定所有页面必须长成同一种卡片。极简、居中、圆角或矢量风格本身不是错误；缺少与游戏体验相关的设计决定才是问题。

## 4. 验证与通过标准

### 文档阶段

逐个检查已规划的主要界面，而不是新增一份强制报告：
1. 有明确焦点、主操作和次要信息关系，描述与布局一致。
2. 美术要求能映射到具体素材或运行时表现，没有只有风格词的关键区域。
3. 参考和最小支持容器下必要内容可容纳；装饰有退让方式。
4. 已确认需求覆盖完整，无需实现者补做核心视觉设计。

“去掉游戏名后是否仍能感到主题”仅作评审启发，不能成为硬门禁，也不强迫极简游戏增加装饰。

### 资源与运行阶段

- 资源逐项对应设计用途；相同用途不因来源改变而降低视觉要求。
- 在约定容器下检查正常界面和关键状态，验证主操作可识别、文字可读、素材不失真、关键反馈可感知。
- 实际画面与文档比较，不能以节点存在、资源加载或 Schema 通过代替视觉核验。
- 截图只能检查静态表现；过渡与反馈需观察实际交互。
- 记录真实缺陷及是否修复，不用虚构审美分数或测试数量证明美观。

## 5. 实施顺序与边界

1. 修改 Author 中美术/UI/资源职责，替换重复或空泛表述，不无限追加规则。
2. 衔接 Review 和现有运行验收，保持原阶段与项目会话结构。
3. 免费回归：核对指令一致性、范围与资源交接；不宣称文字回归可以证明画面美观。
4. 新项目验证规划与实际画面；开始收费实验前另行确认额度。旧测试项目只读，不改其文档、素材或代码。

不新增视觉确认阶段、强制概念图、人工审批、运行引擎、自动续跑或审美门禁。不规定 Agent 的工具顺序和子代理分工。不把游戏开发 UI 套用 BGS 产品后台的组件风格。

## 6. 自审结论

方案直接针对已证实的规划缺口，复用现有文档与阶段，不增加调度机制。主视觉并不等于必须生图，游戏感也不等于复杂装饰。布局正确与视觉品质分别验证。指令与 Skill 修改不能证明新项目会更美观或更省时。

## 7. 本次落地与实测范围

chain-bomb-puzzle 的只读审计进一步确认：美术只给世界对象详细造型，UI 主要列通用组件；UI 变体条件重叠且未覆盖完整容器范围，只核算 HUD，选关中间尺寸与低高度仍溢出。因此本轮只补设计职责、交接和对应 Skill，不修改该游戏，也不把其断点、尺寸或主题推广为全局规则。

- Author：美术明确画面身份；UI 将其落实到每屏构图、主次、资源用途及适配条件；Asset Plan 保留这些用途而非以来源替换设计。
- Review：核对视觉交接，并检查适配条件交界和高度不足的相关情形，不新增阶段或审美自动门禁。
- 免费回归：project-delivery、content-handoff 共 17 项通过；两个修改的 Skill 格式校验通过。此类回归只证明交接机制未被破坏，不证明 Agent 遵从或画面质量。
- 收费验证：使用全新隔离项目，输入普通游戏需求，不提示要设计 UI 或调用特定 Skill。先核对文档是否给每个计划页面明确视觉焦点、主操作、布局规则与美术用途；有实质缺口时停止，不继续付费实现掩盖上游问题。
- 文档合格且预算允许时继续资源／内容／实现，核对实际画面、布局变化及交互反馈。选择文档声明的边界与中间尺寸，记录遮挡、越界、可读性、资源和设计一致性；不以截图数量或主观美观分数代替问题说明。
- 本轮额度需单独确认，达到上限停止，不沿用历史额度。未完成运行观察时明确标注未验收，不承诺全部 UI 问题已解决。
