# 设计审计与下游修订衔接方案

> 2026-10-09 更新：下述“一次集中修订后终止”已由[当前实施清单](eight-document-delivery-rework-checklist-2026-10-08.md)的 E4 替代。独立 Verify 确认必需问题关闭后，剩余可修问题可继续定向修订；确定性检查的错误集合严格缩小也可续修。没有可确认进展、缺事实依据或超出已发布基线的原授权范围则停止，不放行、不重跑八文档。以下旧验收数字不代表此轮结果。

> 后续修订：当前执行进度见 [八文档交付重整清单](eight-document-delivery-rework-checklist-2026-10-08.md)。受影响阅读范围现由具体问题、真实改动及匹配消费者决定，不因涉及一个文档就强制读取其全部产出；补读留在原步骤，按覆盖缺口是否实际缩小判断进展。以下验收数字与构建状态为原轮次记录，不代表本次部署或付费结果。

- 日期：2026-10-08
- 版本：1.1
- 状态：系统修改及本地回归完成；真实付费验收尚未进行，运行服务尚未重启。

目标是让确定性错误在设计交付前被发现，让下游新发现的设计缺陷有正常的修订入口。程序提供真实检查结果；专业修订负责设计取舍；依赖工作只消费已复核的版本。保留八文档业务流程及 Agent 的工具、实现方法和委派自由。

本方案覆盖 Review 检查输入、内容字段归属、跨阶段问题交接、版本与恢复、停止规则。它不承诺模型能发现全部语义问题，也不以更多拦截或无限重跑作为补偿。

## 实施顺序

| 次序 | 交付内容 | 开始下一项前的条件 |
| --- | --- | --- |
| 1 | 所有审计步骤得到真实程序诊断及覆盖说明 | 原非交互溢出可在设计阶段发现，缺输入不显示通过 |
| 2 | 核对并统一字段归属，完成指纹兼容设计 | 合法绑定不失效，设计变化不被漏掉；旧基线不被静默替换 |
| 3 | 接入跨阶段问题转交及定向修订 | 来源、版本、责任和恢复阶段明确；不把报告当事实 |
| 4 | 接入中断恢复、失效清理、问题展示和停止规则 | 模拟失败、重复报告和恢复均不导致误放行或重复调度 |
| 5 | 构建与有限真实验收 | 本地正常、错误、兼容路径全部通过后再运行新 idea |

每项单独可核对。前两项的单纯修复不依赖先造完整问题调度框架。

## 一 程序结果进入 Review

继续使用 Editor 的空间算法及现有 handoff、引用、Scene、UI 检查，不另写一套计算。

删除 Inspect 阶段隐藏错误详情的分支。Inspect、Revision、Verify 均获得当前输入版本的同一检查结果；Inspect 用它理解上下文和关联影响，Revision 修正已知错误，Verify 核对结果。已知程序错误不要求模型重新发现、重新归因或伪造语义 finding。

在现有检查返回值最小补充可定位诊断和覆盖说明：

- 诊断包含实际 source、责任文档、问题种类，以及适用的 node、viewport。issues 字符串从同一结果生成，保留 CLI 和旧调用方的兼容接口。
- 覆盖说明列出已检查文件、目标视口、检查种类及明确未检查项目。检查失败或输入缺失时，保留错误；不能以 issues 空数组掩盖未运行。
- 不把全部节点矩形、完整 JSON 或每次算法原始输出塞进主上下文。几何细节通过现有 --layout 和节点定位按需读取。

对字段错误、缺文件等直接复用现有校验结果；只给需要转交的错误补充来源。不要先建立统一错误分类平台。

流布局的非交互子项也应检查容纳关系。故意绝对定位、隐藏节点和显式覆盖关系按现有语义处理；重叠候选不自动判错。真实字体测量、视觉品味和实际运行反馈仍需各自验证。

## 二 设计字段与绑定字段

先完成一张从实际 schema、校验器、消费约定和作者职责推导的字段对照表。只对当前明确支持的字段得出结论，开放 data/style 不算天然已经定义完毕。

| 内容 | 下游可直接完成 | 保留设计责任 |
| --- | --- | --- |
| Scene 资源组件 | 现有组件资源 assetRef，已支持的 member、atlasMember、frame | 节点与组件身份、层级、位置、尺寸、Camera、碰撞、网格、行为、视觉参数 |
| UI 资源节点 | 实际资源及成员定位、已规定的动作和状态绑定 | 文字、层级、布局、可见性、适配、字体设计与已选视觉参数 |
| UI data/style | 明确验证过的资源定位路径 | 其他已定义设计参数；无法区分职责的字段先补接口定义 |
| 其他证据与文档 | 无一般性绑定豁免 | 原文、索引、数值证据及静态参考资料保持原有版本和证据语义 |

UI 的颜色、透明度不应一概忽略，也不能把任何 style 增补一概视为越权。应先判断它是专业作者已选的设计参数，还是按已定要求完成的资源定位。缺少必要设计参数由对应所有者补齐；新增运行时专用数据也不能仅凭名称被当成新的设计决策。

把确认后的绑定路径定义放在现有内容模块的一处小型函数或常量中，由设计指纹和格式说明共同使用。格式校验调用同一定位定义，再执行其自己的合法资源检查；职责判断不代替资源解码和专业一致性验证。

默认不豁免未知 Scene/UI 设计数据；也不递归删除任意深度同名的 assetRef/member。嵌套纹理、字体和图像引用只在当前接口确实支持的路径上处理。不能为通过指纹检查发明字段。

保留目前正确的几何和未知 Scene 字段保护，替换 UI 忽略整个 data/style 的粗筛选。此处需要一次字段对照及参数化回归，而非按每个新案例补键名。

### 指纹兼容

在现有 designDrafts/designBaseline 记录指纹算法版本；旧状态无版本时按旧算法解释，不能把规则升级误报成文件被改。

新项目使用新规则。旧项目先按旧规则验证原有受保护内容，同时按新规则检查当前缺陷；由于旧规则未保护某些字段，无法证明这些字段从未改变。对原来未保护的相关来源做一次有限的专业检查后，才能生成新基线。

该兼容检查不重写游戏产物、不替换原始证据、不自动把当前内容宣布正确，也不重跑八份文档写作。相关来源无法确认时显示未验证。

## 三 下游发现问题后的正常交接

沿用 DesignFinding 的原文依据、下游影响、负责文档和关闭条件。只在现有阶段回执增补可选 designIssues；资源、Content 和实现使用同一个已有回执读取入口，验收复用自己的现有报告。不另建工单文件或数据库。

旧的正常回执继续兼容。带 designIssues 的回执表示有问题需要处理，不能同时据此完成受影响交付；不从自由文本的“建议修改”推断授权，也不让普通聊天直接重新开启付费任务。

同一阶段当前已知问题合并转交，不按每条问题开启一个 Agent。问题来源有三种：

先区分是否真的需要设计所有者处理：资源路径、成员定位、绑定缺失等当前作者职责内的错误，仍由当前阶段修正，不转入设计 Review。只有涉及设计来源、设计决定或其证据的问题才进入下面的交接；不能把 check-content 的全部错误统一升级为设计问题。

| 来源 | 处理路径 | 不能直接推断的结论 |
| --- | --- | --- |
| 程序可确定且来源明确的错误 | 进入已有范围内的 Revision，再定向 Verify | 程序知道修正后的设计答案 |
| 作者提出的语义冲突或缺少决定 | 先做受影响来源的只读 Inspect；问题成立后才 Revision、Verify | 作者说有错就一定有错 |
| 未审计的数据变化 | 列出实际变化与写入证据，判断能否归属于当前任务；可归属者先专业检查 | 当前文件就是应当追认的新设计 |

专业修订在原需求内可以完成，不需要每次用户批准。改变玩法、首发范围、用户要求或有不可替代的用户选择时，复用既有 AskUserQuestion 和真实答案记录；专业补全与用户裁决分开。

复用现有 returnPhase、writableDocuments、writableFiles、userDecisions、版本维护和 review history。将已有 owner-resolution 逻辑中的来源检查、范围计算抽为小型内部入口；用户 API 仍用于显式用户决定，自动交接不伪造用户 instruction 或 answer。

原实现不支持对已发布基线直接启动 affected Inspect，且 Inspect 固定检查八文档；现已改为初次审计保持八文档范围，下游问题只检验指定来源和必要关联要求。

## 四 真实变更与已审计基线

保留一次统一的前后版本核对；不新增逐文档、逐工具的写入拒绝规则。它的职责是识别变化并安排处理，不是独自判断语义正确或宣布工作永久失败。

程序保存本轮准备时的来源版本，并利用已有 tool.completed 记录核对实际写入路径与结束时字节。可归属到当前交付的改动进入受影响专业检查；无法归属的命令写入、外部进程改动、并发修改或缺失记录不自动获得授权。

归属不明时，保存可见的待处理状态和变化来源，允许受影响只读检查，但不自动授予修改权限或继续依赖交付。检查能确认是当前任务产物后才进入原范围修订；仍存在外部或并发改动时，说明缺失的归属证据并请求确认，不重新退回一条没有处理入口的通用错误。

也不能只凭“本轮开始时基线干净，结束时变了”就认定作者改动合法。写入证据只能证明发生过修改，不能证明修改正确。

专业修订之前，已审计基线保持不动；当前已改文件是待核对稿。若所有者接受作者提前作出的改动，仍按原已审计版本识别实质变化、提升文档版本，并重新复核。不能因为进入 Revision 后没有再改一次而漏掉升版本。

只保存差异归属和必要版本信息，复用现有快照和事件记录，不复制一套布局权威或八文档正文。没有原始字节时不虚构逐字段差异，只能展示文件变化及实际写入记录。

## 五 恢复工作和失效范围

修订前记住受影响工作原本停在哪个阶段。复核通过后重新生成有关的合同与引用版本，恢复实际需要补做的阶段，保留不受影响的正确工作。

原实现按“改了哪份文档”粗略决定返回资源或 Content；现由受影响复核在回执提供 resumeFrom，并在关闭证据或 resumeReason 说明实际影响。资源规格变化先处理资源；绑定或布局变化先处理内容；仅运行行为约定变化处理实现。程序不允许跳过原待交付阶段；影响无法判断时，复核保留问题，不采用作者建议作为事实。

文档整体 revision 改变时，content/index 的整体引用版本需要刷新；这不代表所有资源、场景和实现都要重新制作。实际文件未变且验证条件仍成立的结果可以保留，重新绑定/复核受影响来源。

发现来源变化时，立即将受影响接受声明标为不适用于当前内容，并暂停相关交付；不等新基线提交后才失效。保留旧声明、证据和已完成记录用于审计，不提前删除它们再尝试提交新状态。将 pending 状态及受影响范围原子保存；复核通过后才提交新基线和新的可用声明。中断或失败恢复 pending 状态，不能重新声称旧声明覆盖新内容。

同一问题组只自动执行一次集中 Revision 和一次 Verify；语义问题前面可有一次只读 Inspect。持续失败就保留问题、证据和责任，停止该组自动循环。

在现有交付状态最小记录该问题组的起始 turn 与原返回阶段，复用 review history 记录处理。次数不因文档升版本、重命名 finding、重启进程或回到生产阶段而重置；这是跨阶段修订的停止规则，不是 Agent 的全局轮数或 Token 限制。

恢复后若原待交付再次报告设计缺陷，不自动新建问题组掩盖上轮失败。展示残留或新增问题，由明确的后续指示重启处理；不会永久禁止其他独立任务。

## 六 Agent 输入与成本

移除隐藏诊断详情及“发现问题只报错后另发手工请求”的死路，替换为短交接说明。不追加大量自检 prompt，不建立新角色名册。

定向检查继续使用现有新建的 Review/Revision Agent；输入只包括原需求、负责来源、变化记录、已知诊断、依赖要求和必要已答决定。Scope 之外的引用可以读取，不能因此自动获得修改权。

进入修订和恢复生产时提供当前实际版本与未关闭问题，过期历史声明不构成新版本通过证据。复用已有 Skills 专业检查方法，不把职责边界再复制成第二套 Skill 规则。

不向主上下文重复传入全部算法矩形、八文档或长工具日志。免费程序检查先解决确定项；多条独立修正合并为一次任务；未变化结果不因切换阶段自动重跑。

成本验收比较请求次数、输入与缓存 Token、修订文件数和重复读取量。新旧对照保持 idea 复杂度与运行条件可比，不保证预先指定的降幅，也不拿更便宜但漏检的结果证明优化。

## 验收与停止标准

本地合成测试先覆盖下列边界，不改真实测试项目来制造通过。

1. 非交互文字流、带图片的信息区、响应式布局均能产生真实溢出诊断；隐藏、绝对定位、合法覆盖不被机械判错。
2. 三个审计步骤收到同一版本的失败详情和检查范围；缺输入显示未验证，不显示无问题。
3. 当前定义的资源绑定字段可正常完成；设计颜色、透明度、空间、层级、行为改变可被识别；开放字段不会仅因同名被豁免。
4. 当前作者职责内的绑定错误原阶段修复；明确设计程序缺陷转交修订；假的语义指控在 Inspect 后不触发无谓返工；未知来源改动不自动获得授权，但有可见的检查与确认入口。
5. 作者漏报问题时，程序可确定的问题仍会触发处理；语义漏报仍可能漏检，不能算已经保证质量。
6. 必要用户决定确实产生 Question，并在真实答案后继续；不需要用户决定的专业补全正常修订。
7. 作者提前改稿被接受时仍升版本；未接受时维持未复核状态；后续只消费复核后的版本。
8. 同一问题组在中断、重启、变更编号或返回生产后不会重复进入无限修订。
9. 原设计字段不变的旧项目保持正常；旧规则未保护的字段不能无检查获得新基线。
10. 来源变动后立即暂停使用受影响旧接受声明；修订中断、保存失败和复核失败均不能恢复其有效性。通过后恢复正确阶段、保留无关成果；专业修订失败不能继续受影响交付。

本地通过后，用不同机制的新 idea 验证至少两条路径：直接通过，以及下游发现问题并正常修订恢复。不能人为预填固定错误和答案来证明真实 Agent 会正确反馈；合成注入只用于确定性路径回归。

模型漏报语义错误、错误否定合理要求、错误批准方案仍是残留风险。真实验收需独立检查实际游戏和输入覆盖；现有可观测性及有限修订只能降低风险，不能把多轮模型判断包装成绝对可靠。

## 方案审计结论

| 审计风险 | 未修订方案的后果 | 本方案的约束与判定 |
| --- | --- | --- |
| 给 Review 所有原始算法数据 | 上下文膨胀，重点反而被淹没 | 只传同源问题、覆盖和定位入口；接受 |
| 将作者报告自动当成设计问题 | 错误指控驱动返工 | 语义问题先受影响 Inspect；接受，仍依赖专业判断 |
| 所有内容错误都转入设计修订 | 普通绑定修复也付费重审，阶段往返增多 | 当前作者职责内修正留在原阶段；接受 |
| 自动追认越权改动 | 新内容没有审计就获得权威 | 保持旧基线，先检查变化，再修订升版本；接受 |
| 保留旧记录被误解为旧验收仍有效 | 修订期间继续消费未复核内容 | 记录保留、有效性立即暂停；中断不恢复有效性；接受 |
| 新指纹直接替换旧指纹 | 误停旧项目或洗白原来未保护的变化 | 规则版本及受影响兼容检查；接受 |
| 以文档名决定重做阶段 | 无谓重做资源，或漏掉真实影响 | 检查证实影响后返回；接受，影响无法确定时不猜 |
| 修订后换编号继续循环 | Token 持续上涨 | 问题组跨阶段保留身份和已用修订，失败显式停止；接受 |
| 全部未知字段锁死 | 正常资源接入被不断退回 | 先明确当前接口职责；新增运行数据不伪装为设计绑定；实施时重点复核 |
| 用更多 prompt 保证作者不越权 | 模型一旦漏读方案就失效 | 短交接入口加保存结果核对；不承诺模型遵从 |
| 每个小问题都问用户 | 工作流被频繁打断 | 专业补全在原范围修订，只有用户决定走 Question；接受 |

审计后的可实施结论：先完成诊断和字段职责，再接有限的正常修订交接。不要同时改 Agent 核心执行机制、建立通用工作流引擎或增加逐文档拦截。实施以这些具体路径正确为准，不能只凭回归数量、Reviewer 的 PASS 或低 Token 消耗宣称系统已经可用。
