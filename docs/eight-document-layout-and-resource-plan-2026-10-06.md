# 八文档布局数据与资源绑定实施方案

- 日期：2026-10-06
- 版本：1.0
- 状态：系统调整已落盘，免费回归已通过；未进行真实付费生产验收。

保留八文档及现有阶段顺序。规划阶段由场景、UI 作者保存正式路径中的布局 JSON；资源阶段提供真实资源；内容阶段在同一份 JSON 上补齐绑定。目标是减少实现时重新解释文档和重写坐标，同时保留美术、字体、音频等专业工作。布局数据齐全不等于游戏完成或质量合格。

## 阶段职责与交付

| 阶段 | 必须交付 | 此时不能宣称完成 |
| --- | --- | --- |
| GDD 与专业规划 | 玩法与专业决策，资源需求、规格、可用回退和必要验收条件 | 资源已可用、实现已验证 |
| 场景规划 | `LEVEL_SCENE_DESIGN.md` 与其明确链接的 `content/scenes/*.json`：层级、空间、对象身份与摆放、障碍与路线、必要参数及取景需求 | 完整资源绑定、脚本执行、关卡趣味与最终镜头效果 |
| UI 规划 | `UI_UX_SPEC.md` 与其明确链接的 `content/ui/*.json`：必要界面、文字、状态、布局关系、游戏区域与控件分配、适配尺寸 | 使用实际字体的文字适配、完整交互与美观验收 |
| 联合 Review 与修订 | 原文与布局稿一致，已有程序重新计算可确定的空间问题；修订只改被授权的源文件 | 模型没有发现问题就是零缺陷，空间合法就是好玩或美观 |
| 资源制作 | 可解码、可使用的实际字体、图片、图集、声音等，以及资源清单和规格 | 文件存在就是符合设计，背景音乐与音效留空也算完成 |
| 内容补全 | 在原 Scene／UI 文件中补齐真实资源、字体、图集和必要状态／动作绑定，登记 `content/index.json` | 仅改引用即可证明显示和交互正确 |
| 实现与运行验收 | 实际消费数据，检查最终字体排版、场景取景、输入、反馈与声音；按影响修复并重测 | 构建或回执通过就是高质量游戏 |

## 同一份布局源

1. 场景与 UI 各自的文档链接其实际 JSON，不建立第二份坐标表、临时布局包或额外交接协议。每个必要场景和界面的覆盖仍由原文明确；共享或生成式内容可以复用，不强制每关一个文件。
2. Scene 作者先明确空间和可见性要求。UI 作者确定游戏区域后，使用同一 Scene／Camera 输入核对取景；需要调整场景决策时交给场景所有者，不私自维护另一套镜头偏移。
3. 沿用现有格式、链接、版本、Review 和 Content 基线保护。扩展它们识别 Scene 布局稿，不另造审计框架。后续补绑定不必重新审批整套规划；改变层级、空间、碰撞、取景或 UI 布局等已定设计，则走现有的受影响修订。
4. 规划阶段不要求完整资源清单或内容索引。尚无实际资源时，使用格式允许的布局表达；需要逻辑引用时只能表示计划需求，不能伪造已交付资源、哈希或验证结果。未完成项及其消费阶段写在已有专业文档中。

## 字体与素材对布局的影响

资源需求必须包括会影响布局的规格，例如字体与必要字重、文字范围、图片比例、逻辑尺寸、透明区域、图集帧与声音循环方式。

已有合适资源可以在规划阶段直接引用。若特定字体或素材是确定布局的必要条件，规划可以使用现有资源能力获取最少的关键样本，保留来源并说明验证范围；不因此提前制作全部资源。无法取得时记录不确定项和已有授权回退，不把占位显示当最终效果。

实际资源到位后，内容阶段必须核对文字尺寸、图像比例、裁切与取景。绑定造成设计不适用时，通过现有受影响修订修改相关布局与文档版本；不静默缩字、删除内容或降低控件最小尺寸以获得通过。算法能发现的几何问题由算法查；字体显示、视觉一致性、声音和交互由真实运行查。

## 实施顺序

1. 同步作者、Review、资源、内容与实现的任务说明，保留原阶段和专业职责。
2. 扩展现有链接收集、版本摘要、作者与修订权限，支持场景作者的明确 Scene JSON 链接；不授予整个项目目录的写权限。
3. 将 Scene JSON 的格式、身份与现有空间检查接入现有 Review；缺少必要输入不能靠空 Review 回执放行。相机检查只覆盖现有算法支持的表示，不伪装成任意场景或动态关卡验证。
4. 基线记录布局决定，而不是完整资源绑定。内容补全允许可识别的绑定变化；布局变化仍需受影响修订。无法区分的字段保持保守，不假装已证明只是绑定。
5. 同步相关 Skills 的工作方法。职责与产物要求继续由任务 prompt 定义；Skills 不维护第二套阶段边界。
6. 用临时系统测试夹具验证：缺失、无效与越界 Scene；场景稿的版本变化；资源绑定补全；未授权布局变更；跨文件 UI／Camera 连接；现有八文档完整流程。核对 frontend 未变，并做类型检查和构建。

## 范围与效果边界

frontend、已生成测试项目和原始证据不改动，不自动迁移项目，不启动付费测试。保留现有正确公共能力及无关修改。

已有项目不能直接被视为满足新交付要求。缺少 Scene 链接或布局输入时，需要补齐受影响的规划；旧基线未包含此次保护的相机链接或排版尺寸时，需要明确的定向 Review 更新基线。系统不自动修改项目、重算哈希来掩盖差异，也不因此重跑全部八文档。

预期减少重复翻译设计与布局漏项，但不能预先承诺 Token、耗时或成品质量改善。规划 JSON 仍由模型生成，必要内容的语义覆盖、趣味、美术品味和手感不能仅靠格式或布局计算保证。免费回归证明的是系统行为；实际生产效果需另行授权验收。

## 实施记录

- 保持八文档、原有依赖批次及联合 Review／Revision 顺序，不新增阶段或交接协议。Scene 作者与 UI 作者保存正式路径的布局稿，后续内容阶段沿用原文件补绑定。
- 作者收到所需 Scene／UI 格式节选；资源、内容与实现说明明确真实字体、图像规格、图集和声音仍需制作、绑定及验证。必要关键样本允许先使用，完整资源批次不提前强制。
- Scene 链接进入现有修订授权、版本及基线摘要。场景稿不再作为不可变证据冻结；已知资源引用、member／frame 可后补，位置、层级、碰撞、Camera 和无法判断为绑定的字段仍受保护。UI 的相机链接和排版尺寸也进入基线；资源选型不是静默缩字或换镜头的授权。
- `--review-layouts` 与宿主释放检查使用相同 Scene／UI 检查入口。Scene 复用 Content 的层级、组件、坐标系和 Camera 格式检查，仅推迟尚未交付的资源绑定。二维必要可见性使用同一 Scene 在 UI 实际分配的游戏区域内计算；缺少连接不能用独立相机数据替代。
- 更新关卡设计、UI 设计和文档 Review 三个专业 Skills 及相关参考方法；职责与产物要求仍由任务 prompt 定义。
- 免费回归：13 个测试文件共 309 项通过，覆盖既有流程、Scene 缺失／无效／符号链接、空 Review 不能放行、确切修订权限、绑定与布局变化、版本提升及跨文件取景。夹具只在临时目录创建，不修改已生成游戏。
- 服务端和 frontend 类型检查通过，CLI 构建通过，三个修改的 Skill 格式校验通过，`git diff --check` 通过。Frontend 的 9 个既有修改文件与恢复前记录的 SHA-256 全部一致。

这些结果不证明实际游戏更好玩、更美观或更省 Token；三维／XR、动态玩法、实际资源显示和输入声音仍按既有后续阶段验收。未重启服务或触发项目续跑。
