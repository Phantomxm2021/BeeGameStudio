## 1. 目标与不承诺的事情

目标：用户提出 Idea 后，系统能在明确支持的范围内，制作、验证并交付一个可运行、可继续修改的游戏。

交付应满足：

1. 核心玩法和首发内容符合已确定的要求，不在实现中偷偷改变规则或缩减范围。
2. 数值、场景、UI、资源和代码共同组成真实游戏，不是文档完整但实现缺失。
3. 必要的数据可以编辑，并实际驱动游戏，而不是代码另写一套布局和参数。
4. 被测试的版本就是交付版本；已知缺陷、未验证范围和需要裁决的事项明确可见。
5. 后续修改有版本和设计依据，不依赖模型恢复全部聊天历史。
6. 审计与返工可以停止；成本、耗时和维护负担可以解释。

不承诺任意 Idea、任意平台、任意风格都能全自动生成合格游戏；不承诺零缺陷；不把可运行、测试通过或 LLM 好评等同于好玩和精美。

八类专业工作仍然存在，但不再默认变成八份长文档、八个固定 Agent 或八个交接阶段。

## 2. 改造前已确认的约束（历史定位，不代表当前执行方式）

以下记录变更前事实，仅用于确定迁移位置，不把旧流程当作正确答案。

| 已确认事实 | 实施含义 |
| --- | --- |
| `project-delivery.ts` 当前执行 author → review → resources → content → implementation → acceptance，并维护八文档基线 | 要改变实际派工、推进和完成判断，不能只改提示词 |
| `project-conversation.ts` 按上述阶段提供文档、工具、格式和任务输入 | 新路线需要对应修改上下文构建、能力开放及续跑；不能继续注入旧阶段要求 |
| `project-content-authority.ts` 对固定八文档及其 handoff 计算来源版本 | 新项目的数据来源不能再依赖八文档齐全；旧项目版本关系不能被静默改写 |
| `runtime-acceptance.ts` 能检查报告结构、来源版本、证据文件与声明覆盖；其中部分结果仍由 Agent 填写 | 保留版本与结构检查，但不能把它当作观察真实性或语义完整性的证明 |
| `preview-test-recording.ts` 保存浏览器事件、环境和截图，并明确不判断玩法 | 复用记录能力；录制成功不等于场景执行成功或玩法合格 |
| `game-content-consumer.ts` 提供解析、加载、坐标与布局等工具，明确不是游戏引擎 | 不能假定已有完整运行底座；先验证可复用实现，必要时补一个范围明确的适配实现 |
| `ui-layout-inspection.ts` 的遮挡检查依赖 protected / occluder 标记；UI 审计的部分覆盖依赖作者填写尺寸和节点信息 | 新路线必须检查输入和覆盖，不能继续依赖模型主动选全对象 |
| 已有编辑器、资源清单、内容格式、预览、会话、模型配置及用量记录 | 优先复用，不把本次改造扩大成整个平台重写 |

已观察到的系统级问题包括：重复翻译设计、遗漏检查对象、正文 Review 漏检、完成声明缺少对应证据，以及长上下文反复携带导致消耗放大。

高上下文可能增加执行风险，但目前不能据此断言所有语义错误都由上下文长度造成。减少上下文是成本与执行改进，不是可靠性证明。

## 3. 总体设计

生产路线：

**Idea 与必要澄清 → 制作说明和短任务清单 → 代表性整合可玩样板 → 完成首发内容 → 实际验收与版本交付。**

这是成果顺序，不是要求新建五套调度器或五次固定模型会话。

- 小型游戏的代表性版本可以就是完整一局，在原项目上继续完善，不额外生成一个原型项目。
- 核心活动有疑问时先用必要表现验证，再把该路径的操作、UI、美术、必要音频及反馈整合到可沿用的首发处理；不把仍有必要占位的粗模当作完成的质量样板。
- 重大技术或玩法疑问需要小实验时才安排，不强制每个项目都先研究所有平台能力。
- 数值、场景、UI、资源和代码围绕可玩功能一起完成，不再等待所有文档齐全后才开始整合。
- 新主路线没有强制的整批文档 Inspect / Revision / Verify 循环。
- 语义咨询和专业 Review 可以发生，但只用于具体问题，不独自签发合格结论。

### 3.1 首批支持范围

实施建议先验证：单人、2D、浏览器小游戏，无联网对战、账号后端和复杂外部服务。

这是首批新路线的验证范围，不自动撤销既有产品的其他平台能力。第一步需核对当前可复用技术，选定一种运行组合；不预建多个引擎适配器。

超出已验证范围的 Idea：明确提示限制，提出有损范围的替代方案并获得授权，否则停止该请求。不能无提示地换题，也不能自动回退旧路线后宣称质量已有保障。

首批范围和最终默认入口，需要在上线前明确确认；本文不把尚未验证的范围写成现有产品承诺。

### 3.2 系统责任

| 部分 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| BGS 项目宿主 | 原始请求、项目身份、任务范围、版本、取消恢复、实际工具结果和交付状态 | 替模型理解全部自由文本、证明审美与趣味性 |
| 制作协调任务 | 确定必要决策、安排功能工作、协调依赖、报告未决项 | 凭摘要宣布整合成功、替专业责任人悄悄修改要求 |
| 制作任务 | 完成有边界的设计、数据、资源和代码工作 | 重新定义用户目标、以自检 PASS 代替实际证据 |
| 检查工具 | 检查明确输入、执行可观察场景、保存结果 | 推断没有表达的设计意图、把截图存在认作画面合格 |
| 有权裁决者 | 处理范围改变、关键设计争议和无法可靠自动判断的质量问题 | 每个小任务都审批、为自动检查填补虚假的结论 |

这些是职责，不是新增固定 Agent 编制。先让单个制作执行任务完成一个功能；只在真实独立工作出现时委派，并限制共享文件并发改动。

## 4. 设计依据和项目产物

### 4.1 唯一必要的说明：游戏制作说明

建议新项目保存为 `docs/GAME_BRIEF.md`，不限定长度，但禁止把原八份文档机械拼进去。

必要内容：

- 用户目标、核心体验、首发范围及明确不做的内容。
- 玩家与游玩情境、活动价值／趣味来源、一局中的变化与回报；区分确认要求与作者工作假设。有限、平静或教学体验同样可以成立，不强制重玩、成长、惩罚或挑战。
- 操作、动作结果、成功失败、必要状态转换与恢复行为。
- 必要界面和关键玩法场景；数量与项目实际需要一致。
- 目标设备、输入方式、显示条件及适配要求。
- 视觉、声音与反馈方向；引用必要的实际样板或参考。
- 关键实现约束、已核实能力及尚未验证的假设。
- 可观察的交付条件、已知限制和需要何时关闭的未决项。

存在影响核心体验的疑问时，在现有章节说明最小代表性可玩情境及能支持／反驳它的观察，优先用同一项目的可玩版本检验，再铺开内容。规则正确、运行正确、玩家理解和享受是不同结论；没有玩家证据时保留体验假设为未验证，不另设默认调研门槛，不用 Bot 或模型好评补成通过。此要求与方法已进入任务 Prompt 和现有 Skills；真实生成效果仍需后续授权测试，不能由文本落盘证明。

区分用户明确要求、制作方选定方案和待验证假设。一般细节允许采用记录下来的默认方案；改变核心玩法、首发范围或平台时需要有权确认。

每个关键交付条件写明“条件/动作 → 预期结果 → 检查方式”，使用稳定编号供任务和结果引用。编号仅用于追踪，不建立全局 Decision Taxonomy，也不把全部自然语言转换成 Schema。

说明负责意图和规则；具体数值、布局及资源信息引用实际项目文件，不维护第二份可运行参数表。

### 4.2 数值、场景、UI 等直接形成可消费产物

| 工作 | 必要规划 | 项目产物 | 必要验证 |
| --- | --- | --- | --- |
| 数值 | 初值、单位、计算关系、合法范围、调优目标 | 项目实际数值配置；复杂计算按需附脚本或简短说明 | 计算和边界检查；节奏、难度通过试玩判断 |
| 场景 | 出生点、目标、路线、障碍、相机、可见性和空间关系 | 实际 Scene 数据；占位资源只能用于中间版本 | 加载、空间计算、实际画面、移动/碰撞/目标可达性 |
| UI/UX | 页面、内容、导航、交互状态、布局、适配和视觉方向 | 实际 UI 数据；实际文字及必要状态样本；视觉参考 | 覆盖、布局、真实字体测量、完整渲染与交互 |
| 美术 | 风格、语义辨识、图层、必要资产及质量样板 | 参考样板、正式资源和对应绑定 | 解码/规格/绑定检查，实际画面审看 |
| 音频 | 事件、开始/停止、状态变化、并发、静音及音量行为 | 简单项目用实际音频映射配置，复杂项目补专项说明 | 资源加载、事件行为和实听；未听不宣称听感验证 |
| 资源 | 必需项、用途、来源、规格和已批准回退 | 现有资源清单及实际文件/可执行生成产物 | 引用、可用性、许可和目标环境加载 |
| 实现 | 实际数据消费、行为和生命周期 | 项目代码及必要测试 | 构建、真实运行、行为与数据消费验证 |

继续使用现有 `content/index.json`、Scene/UI/VFX 格式及 `assets/asset-manifest.json`。数值和玩法配置按现有格式边界独立保存，不塞进只允许 Scene/UI/VFX 的注册表。

UI 在实现其功能前就生成可检查的真实数据，不先制作一套人工 HTML 再声称代表 JSON。Scene 同理。预览必须加载当前项目的实际文件、资源和字体，并显示项目/版本身份。

最先生产代表性体验所需数据和资源，而不是一次完成全部内容再开始运行。占位、未接行为和未验证资源必须明确可见，最终必要内容不能以占位交付。

### 4.3 说明、数据和代码的权威关系

- 用户确认的要求优先；制作说明记录当前设计意图。
- 数据拥有具体参数和静态布局；代码真实消费数据并执行行为。
- 格式说明规定平台表达能力，不替代玩法和美术设计。
- 游戏设计负责玩法和范围；技术、美术、UI、音频各自负责专业方案。技术提出不可行证据，不直接改玩法；音频不决定持久化技术。
- 发现意图与实现不一致，不能把实现现状反向写成需求以取得通过。
- 必要决定缺失时，明确谁有权补充、影响什么；暂停受影响工作，不阻断无关任务。

职责定义集中在任务/角色 Prompt。Skill 只保留专业方法、检查经验和工具用法，不再重复定义一套阶段权限。

## 5. 运行底座：先验证，不假定已有

### 5.1 为什么需要这一项

当前消费工具不是完整游戏引擎。如果每个游戏仍由模型重新编写 JSON 解释、坐标转换、字体、输入和页面生命周期，取消文档不会解决实现偏差。

最简单的处理不是造新引擎，而是选定一种已有运行组合，验证它对当前内容的实际消费。如果已有实现可复用，修正明确缺口；没有时，仅补首批支持范围必需的一套运行适配。

### 5.2 首批必需能力

- 正确加载资源及注册内容，错误能定位到文件/节点/资源，不能静默丢弃不支持的组件。
- Scene 和 UI 使用编辑器的共享坐标、布局及相机语义；运行与预览不能维护两套计算。
- 渲染必要的图形、文字、图标和层级；实际字体加载完成后测量。
- 输入、页面切换、暂停、重开、音量与清理有可复用实现，允许游戏连接自己的规则。
- 数据变更在运行中产生对应变化，不只做到 JSON 请求成功。

不实现通用 ECS、新物理引擎、任意引擎适配、通用可视化脚本语言或全类型模板库。复杂物理、动画等先使用选定技术的成熟能力；遇到真实需求再判断是否扩展。

### 5.3 先行验证

用系统测试夹具验证数据加载、坐标、字体、资源、页面切换和数据消费，不修改历史 BGS 游戏产物。

测试夹具需能在隔离副本中改变一个数值、一个 UI 布局和一个 Scene 位置，观察实际结果改变。不能只检查代码是否调用解析函数。

此项失败时停止扩展新主路线；否则新的制作流程仍建立在未经证实的运行基础上。

## 6. 任务执行方式

### 6.1 按功能交付

短任务清单按“完整操作与结果”组织，例如一个目标达成后的结算与恢复功能，而不是“写 UI 文档”“写音频文档”。

一个工作任务至少给出：

- 本次目标和适用的制作说明条目。
- 必须读取的实际输入文件；区分确认要求和建议。
- 允许修改的范围及与其他任务的依赖。
- 本次实际产物及检查要求。
- 已知缺口和不能自行决定的事项。

优先复用现有任务清单能力，不新建工作流 DSL、队列服务或长篇强制 handoff。

协调任务必须整合实际输出；委派任务的“完成”或“PASS”摘要不是整合证据。未知内容允许继续查阅，不以省 Token 为由截断必要数据后宣称完整读取。

### 6.2 专业 Skill

- 任务 Prompt 明确对应工作开始前调用具名 Skill：Brief 的规则、视觉、UI、声音、操作、反馈、空间及初值决策使用相关方法；保存说明后做面向实现者的设计核对并规划短路径。制作使用计划执行，验收使用试玩检查和完成证据；不一次读取所有专业资料。目录可见或提到名字不等于实际调用。
- 当前上下文已经加载的方法不重复加载，引用只读当前所需；缺失或加载失败说明影响，不伪称已使用。普通提问不因保存的生产阶段而触发制作技能或制作续跑。
- 改造已有 `game-design-check`，使其用于具体设计疑问、变更影响和实际产物检查，而不是默认八文档通关仪式。
- 删除新路线中的八文档强制阅读、固定作者名单和重复自检证明要求。
- Skill 使用与实际有效性分别记录；“调用了 Skill”不能作为产物合格的证据。
- 20 个内置 Skill 的合并核对见 `.beegame/skills/builtinskills/README.md`：保留不同专业方法，将基础体验定位集中到默认调用的系统设计入口，创意指导不再重复；删除两份内容完全相同且入口已覆盖的 XR 通用参考。没有新增 Skill、职责层、质量评分或 Review 循环。

## 7. 验收设计：检查对象不能靠模型自选完整

### 7.1 覆盖范围有两个来源

1. 制作说明中的项目交付条件：用于确定游戏特有行为和预期结果。
2. 宿主维护的通用检查与实际项目清单：用于检查构建、资源、注册内容、页面、布局、目标设备和生命周期等确定项。

通用检查对象从实际注册表、节点、路由/状态绑定和支持范围取得，不从作者“我检查了这些”取得。注册内容与实际发布引用需互相核对；必需页面没有生成，也不能因为清单里没有它就算通过。

自由文本要求仍有理解遗漏风险。结构化关键交付条件可以提高可见性，但程序只能验证登记和执行，不能保证登记已经涵盖所有设计意图。复杂的新机制或争议需要裁决，不宣称通用检查解决全部语义问题。

### 7.2 检查与证据的边界

| 类型 | 处理方式 | 缺少依据时 |
| --- | --- | --- |
| 格式、引用、文件、单位、计算边界 | 执行对应确定性检查，保存真实结果 | 缺输入/不支持为未验证；明确违规则失败 |
| 启动、操作、状态切换、胜负、重开 | 在实际运行环境执行明确场景，比较设计预期和实际结果 | 场景未执行或观察不足为未验证 |
| UI/Scene 几何与文字 | 枚举适用的内容、状态、显示条件；用共享算法及真实字体检查 | 尺寸、状态、字体或对象不完整则不签发完整布局通过 |
| 数据消费 | 隔离副本中的受控变更、运行观察及适用的回归测试 | 只读取 JSON 为不足证据 |
| 美感、辨识度、手感、声音和节奏 | 实际画面/试玩/实听，加专业审看；模型可提供意见 | 未有可靠审看为未验证，不用自评填空 |

测试场景的预期来自设计，而不是从当前游戏行为反推；新增游戏特有测试不能由写代码的模型随意降低条件后通过。

### 7.3 UI/Scene 空间问题的现实处理

首批运行路线优先支持明确的游戏区、HUD 区和模态覆盖关系。复用既有布局、相机和组合能力，让运行和检查使用同一份区域分配。

- 非覆盖式 HUD 必须与游戏区分配一致，检查全部实际边界，不等模型给每个面板补 `occluder` 标记。
- 模态覆盖属于有意遮挡，其适用状态和输入阻断需要明确，不把所有矩形相交判成 Bug。
- 漏写必要尺寸、游戏区或组合关系，报告输入/覆盖缺失；不返回“全布局合格”。
- 文字检查覆盖实际标签和可到达的动态值边界，使用最终字体；字体未加载或样本缺失不推断通过。
- 任意自由叠层、复杂遮罩、3D 投影等不能靠一条通用规则确定意图。首批若无法可靠检查，应明确限制或转专业审看，不硬写推断算法。

此项针对遗漏标记造成的通用失效，不包含某个测试游戏的坐标、名称、字体或正确答案。

### 7.4 可观察性不是验收作弊入口

浏览器/宿主可保存实际输入、页面环境、网络/异常和画面。对 Canvas 玩法，必要时提供小范围只读状态观察，用于计数、规则和生命周期测试。

状态字段是辅助证据，不是游戏质量真值：不能仅看到代码返回 `won: true` 就认定胜利可见且规则正确。还要核对用户操作、对应画面或独立规则结果。测试钩子不允许替代正式交互或在交付版本改变规则。

优先复用现有预览测试能力；只补首批测试所需的有限观察，不建立通用遥测总线。

### 7.5 谁可以写通过结论

- 工具产生的检查结果由实际执行写入并绑定版本；Agent 可以解释，不能用一段文字覆盖失败。
- Agent 填写的观察、未知项和结论保留其来源；报告格式正确不能证明观察真实。
- LLM Review 意见必须有原文/实际产物依据、具体影响和关闭条件，才能驱动返工；润色偏好不阻断交付。
- 系统区分“可运行/可试玩”“已列自动检查通过”和“交付要求已验证”，不统一显示为合格。
- 必要交付条件失败或未验证时，不标记完整交付通过。可以提供明确标注的预览，但不能改称最终成品。
- 高质量视觉和体验若缺少可靠自动判断，必须依赖专业审看或经过审定的有限样板。样板仍不能证明游戏手感；不要求用户每次投票好不好看，但不能取消必要质量判断。

在当前能力下，完全自由创作与完全自动质量保证不能同时作为承诺。若产品坚持无人介入，需要进一步限制支持范围和创作自由，并诚实说明仍存在的漏检风险。

### 7.6 修复与停止

区分产品缺陷、设计缺口、测试驱动缺陷和环境不可用，不能把工具失效统统算游戏错误。

每个已定位问题进行集中修复和相关复测。若修复后仍失败且没有新的定位证据，停止自动重复，重新分析或请求裁决；不得把次数上限当作通过条件。

只扩大到实际受影响的回归范围。无法关闭的关键问题阻断对应交付，记录原因和可选处理；不靠增加 Reviewer、无限重试或新付费实验维持“进展”。

## 8. 修改、版本与恢复

### 8.1 版本依据

交付版本同时关联：制作说明、资源/内容、代码、实际发布构建及对应验收结果。复用现有工作区/文件摘要和测试产物绑定，不另建一套版本服务。

- 制作说明修改提升文档版本，记录变更原因；没有改说明的纯 Bug 修复不虚增说明版本。
- 每次可交付结果具有不同项目版本；实际测试构建也要绑定，不能只绑定源码。
- 任务状态、交接和测试机器记录留在宿主既有状态/证据位置，不写进设计正文。
- Git 若可用于生产项目，则作为代码历史工具；不能假定所有用户项目都有 Git，非 Git 项目复用既有快照/摘要能力。

### 8.2 用户修改

1. 对照最后交付版本判断：需求改变、实现缺陷，还是参数/体验调整。
2. 需求改变更新制作说明；具体参数、布局、资源修改以对应数据为准。
3. 实现缺陷恢复设计要求，不修改要求来掩盖错误。
4. 检查相关资源、数据、代码和测试，重新验收受影响部分。
5. 保存新版本及已知限制；不重新启动八文档生产。

影响范围不确定时采用保守的关联回归，不让模型声称“不受影响”后跳过必要检查。

### 8.3 取消与续跑

使用现有会话和项目持久化：保存当前任务、实际输出和未解决项。恢复时先检查文件版本与证据是否仍有效；旧预览地址、旧摘要和旧 PASS 不能直接复用。

历史用户输入、附件、执行日志和原生摘要保留；BGS 不按制作阶段清空或重启模型历史，也不清空读文件缓存。平台上下文通过原生项目元数据进入已有 isMeta 消息，用 origin 明确标记来源；提供当前平台事实时只替换此前同来源的事实消息，原始日志仍留存。不能凭文字前缀删除用户内容；无来源标记的旧输入及原生摘要保守保留，不能承诺其中不存在旧任务信息。历史压缩交给原生机制，不额外制造压缩边界。

## 9. Token 与耗时控制

先跑通实际交付，再判断成本是否可接受；不以降低成本为由跳过必要设计、资源和运行验证。

| 已观察到的浪费来源 | 新路线处理 | 防止副作用 |
| --- | --- | --- |
| 整批文档前置检查、尚未存在文件造成返工 | 检查当前功能必需输入；未到期输出不报缺失 | 已到期的必需内容不能借此逃过检查 |
| 多次小调用重复取得相同结果 | 同版本相关检查合并执行、复用未失效证据 | 数据/代码/环境改变必须使相关结果失效 |
| 广泛环境探测、源码排查和格式读取 | 宿主提供已知命令、工作目录和所需格式；未知问题再定向调查 | 不封锁真实诊断，不伪造平台能力 |
| 累积历史导致小动作携带大上下文 | 更新当前平台事实，退出重复派工和额外执行指令；历史管理交给原生机制 | 不强制清空历史，不用模型摘要代替原始需求，不假装截断读取完整；仍可能有长上下文成本 |
| 按文档交接后再重复翻译实现 | 同一功能内直接修改真实数据和代码 | 仍检查数据消费与设计一致性 |
| 报告/交接手工填格式导致重复修复 | 工具记录确定事实，任务只补解释和未决项 | 记录自动化不等于验收自动化 |

逐次模型请求记录：项目/任务、调用次数、普通输入、缓存读/写、输出、最大输入上下文、工具失败与重试、用时。关联正常制作、诊断、修复、复测；不再只汇总“总 Token”。

金额只使用实际计费数据。接口不可读时报告 Token 和计费未知，不推算一个虚假的 Credit 总额。

不承诺固定百分比降耗。首轮形成端到端基线，再设有依据的时间/费用目标；耗时应包含人工审看和恢复成本。测试经授权开始前，约定次数与停止条件，不能因尚未通过而自动追加。

## 10. 保留、替换和退出范围

| 处理 | 范围 |
| --- | --- |
| 保留并验证 | 用户请求/项目身份、存储与会话、权限/计费、资源管理、内容 Schema、编辑器共享几何、预览/测试浏览器、实际证据及版本绑定 |
| 替换新项目主入口 | 固定八文档 author/review 前置，资源→内容→实现的全量等待，基于作者摘要的推进，固定角色派工与八文档 Prompt 注入 |
| 调整依赖 | 内容来源版本、交付报告覆盖、任务上下文、专业 Skill、项目进度与产物展示 |
| 退出新主路线 | 强制八份 handoff 索引、整批 Inspect/Revision/Verify、作者重复自检作为通关证明、文档名称决定产物来源 |
| 暂留兼容 | 旧状态只读辨识与显式迁移；不再恢复旧执行链。历史文档和运行证据保持原样 |
| 明确不做 | 清空历史项目、通用 Decision Taxonomy/Ownership Auditor、新工作流框架、泛化引擎、复杂质量评分系统、无依据的多 Agent 编制 |

“删除旧机制”只针对失去用途且无兼容消费者的系统代码和指令，不删除历史产物，不把大范围清理包装成实现必要步骤。

## 12. 分批实施顺序

以下是工程改造顺序，不是再给每个游戏增加六个生产阶段。

### P0：验证基础与边界

- 核对真实创建/派工/恢复/发布入口，列出现有模式依赖；只查相关范围。
- 验证一种首批运行组合能消费 Scene/UI、资源和数值，形成小型系统夹具。
- 确认视觉质量如何获得可靠审看、首批支持范围和无法自动处理事项。
- 用本规划逐项评估新增复杂度；若基础不成立，修最小缺口或缩小范围，不先改整个调度。

完成条件：数据消费、完整渲染和关键生命周期在目标环境有实际结果；支持/不支持与质量判断责任明确。能力测试不冒充游戏生产验收。

### P1：制作说明与功能任务接入

- 新项目能保存制作说明、关键交付条件和现有任务清单。
- 项目状态使用明确的新格式版本辨识路线；旧状态不会自动进入新路线。
- 一个功能任务可以连接必要数据/资源/代码，保留相关原始需求。
- 修改内容来源、格式 materialization 和权限开放，解除新项目八文档硬依赖。

完成条件：不创建八文档也能合法启动一个功能任务；缺少当前必要要求仍会明确阻断；旧项目读取/取消/恢复测试通过。

### P2：代表性整合可玩样板

- 在同一项目内完成一局或一段代表性体验，包含真实数据、UI、Scene、数值、输入、可沿用的视觉处理及必要音频/反馈。玩法先行验证与表现整合仍属于同一个可玩阶段。
- 资源可以逐功能补齐，未完成状态不能被伪装成正式资源完成。
- 不让实现 Agent 另造一套布局和参数；修复共享运行适配的真实缺口。

完成条件：从用户入口实际进入玩法、产生结果并恢复；数据可编辑且驱动结果；UI/Scene 真实组合可见，必要声音与反馈实际接入。宿主核对本阶段选定的交付条件及当前来源/构建/证据；专业体验判断保留其证据边界。此项仍不是最终游戏交付。

### P3：实际检查与完整交付

- 宿主从项目实际输入构建通用检查对象，检查覆盖缺失。
- 执行项目特有行为检查，保存来源、场景、观察和版本；区分声明与工具事实。
- 修补布局漏标、字体未测、假消费等通用失效；失败时不得自动推进。
- 完成正式资源、全部首发内容、目标设备适配及必要专业审看。

完成条件：通过失败注入证明系统会阻断已支持的错误和缺证据情况；实际交付结果有当前构建证据。不能以增加测试数量代替此条件。

### P4：修改、恢复与前端呈现

- 用户改需求/改参数/修 Bug 均从已有版本继续，不重新生成全套文档。
- 文档与项目版本更新、旧证据失效和受影响回归可用。
- 取消、恢复、过时预览和不完整用量等问题不会被显示成完成。
- 前端显示当前游戏版本、实际检查范围、未决项和交付性质。

完成条件：完成一次真实变更和一次中断续跑；结果、版本和成本可追踪；无关正确工作被保留。

### P5：真实验收、切换默认与清理

- 按下节授权流程进行不同 Idea 的端到端生产，不人工修测试产物。
- 本地开发分支使用新入口；真实验收通过后才适合正式上线。旧项目保留原状态，显式迁移后从新制作说明开始，不自动重新生成或宣称旧产物通过。
- 删除无消费者的旧代码/Prompt，更新说明；兼容逻辑保留到实际消费者退出。

完成条件：核心交付、修改、恢复和成本均有证据；达到停止条件时暂停扩展，不默认追加付费重试。失败时可以保留开发入口继续定位，但不能把退回旧路线称为新方案已成功。

## 13. 系统验收方案

### 13.1 本地回归：先证明会拒绝错误

使用通用系统夹具，不向作者预填正确游戏方案。

- 缺必要要求、页面、注册文件、资源或目标设备检查：不允许完整交付 PASS。
- 去掉布局遮挡标记、漏检查尺寸、缺真实字体或动态文字边界：覆盖不足不能显示全布局通过。
- 非覆盖 HUD 侵入实际游戏区、有意模态覆盖、不同相机/尺寸：检查能区分适用关系。
- 有 JSON 请求但运行仍用硬编码位置/参数：数据消费检查能检出。
- 构建后改数据/资源/代码、使用旧截图或旧发布产物：关联证据失效。
- 测试驱动失败或浏览器不可用：标记检查问题/未验证，不能冒充产品通过或产品缺陷。
- Agent 声明 PASS、证据不存在或工具已失败：主会话不能宣布完整交付。
- 非法路径、越权修改、取消后后台工作及恢复冲突：原有安全边界不退化。
- 原项目模式识别、读取和取消保持可用；旧生产续跑被明确阻断，迁移必须显式进行，不恢复被移除的执行链。

删除标记等失败注入作用于系统测试夹具或隔离测试副本，不改历史/正式 BGS 项目产物。

### 13.2 真实生产验收：小批不同 Idea

P0—P4 满足前置条件后，另行获得本轮付费授权。首批建议最多三个不同 Idea，各覆盖：

1. 实时操作与完整一局，主要检查输入、节奏、结束和恢复。
2. 离散/回合规则，主要检查状态、数值和 UI 操作一致性。
3. 空间或关卡规则，主要检查 Scene、相机、UI 组合和目标可达性。

实际题目在系统版本冻结后确定，不把正确坐标、具体事件或上一案例修复答案写入 Prompt。首批结束后再保留一个未参与调优的不同 Idea 做外推检查；不在本批自动追加。

每个项目检查：原始要求符合度、全部必要数据/资源、真实可玩过程、视觉和音频结果、交付构建、未验证项、用量和耗时。其中一个项目再进行用户需求修改，并测试中断续跑。

同一已修问题的复测用于证明局部修复；不同 Idea 用于检查迁移性，两者不能互相替代。三个案例全通过也不能证明任意游戏稳定。

发现共享运行、检查覆盖或交付状态的阻断问题，先停止后续同类付费运行，修系统并做本地回归。个别游戏设计争议交给有权者，不改成系统特判。

### 13.3 发布判断

必需条件：

- 已验证范围内可完成真实游戏，而非停在文档通过或中间预览。
- 下游不用重新猜关键玩法和界面行为，实际数据被消费。
- 已支持的确定性缺陷与缺证据情况能够阻断；未知范围被披露。
- 审美、手感等必要质量判断有真实依据，不靠模型自评签字。
- 用户修改、版本和恢复能工作。
- 用量记录覆盖各任务与修复/复测；无未经授权追加运行；成本和耗时经实际评估可接受。

不以八文档齐全、Reviewer PASS、比旧版更快、测试数量增加或回滚旧流程作为新系统发布标准。

## 14. 主要风险和处理

| 风险 | 处理 |
| --- | --- |
| 简短说明遗漏关键设计 | 必要规则/界面/交付条件前置；缺决策不让实现猜；自由文本语义仍承认残余风险 |
| 运行底座不能表达设计 | 先做能力验证；明确支持范围；补具体缺口或请求调整，不造通用引擎 |
| 自动检查覆盖不完整 | 宿主枚举实际对象、核对必需项和失败注入；不靠作者声明完整 |
| 测试与实现一起误解需求 | 预期引用设计；通用测试由系统维护；特殊/争议要求需要专业或有权确认 |
| 取消八文档后美术/音频设计流失 | 保留专业工作和实际参考/配置；在代表性体验中整合，不拖到结尾补装饰 |
| 自由视觉生成不稳定 | 使用经过审定的有限样板或真实专业审看；明确不能自动证明的部分 |
| 成本转移到运行测试/人工 | 统计完整生产周期；定向回归和有效证据复用；不只报文档 Token 降低 |
| 两套路线长期并存 | 新项目明确版本；旧项目最小兼容；消费者退出后删失效代码，不建通用双引擎框架 |
| 简化导致越权或伪成功 | 保留安全、版本与失败阻断；简化的是无效交接，不是必要正确性 |

当前离线验证：系统及原生进程回归 67 通过；用量代理 13 通过；真实 CLI 接本机假模型 2 通过。真实 CLI 证明格式命令的管道可执行、两种格式读取的约 10KB 输出不受已删除的专用限额影响、超过 40 次迭代仍可完成后续任务；阶段切换后旧平台派工退出而原生回复保留。服务端 TypeScript 与 CLI 构建通过。这些是系统行为证据，不是完整游戏生产或实际成本验收。

代价与剩余风险：保留原生历史可能增加长任务上下文；移除额外截止不保证任务自行结束，人工 Stop 必须可用；格式自由读取也可能增加单次输入。当前清理不能证明模型误判、无效排查或游戏质量已经解决，本轮没有开启付费生成。

## 21 专业规划与整合样板调整

当前四个阶段保持 `brief → playable → production → acceptance`。本次解决两个实际缺口：专业方法主要在制作时才被要求；可玩阶段仅凭成果声明和结构检查就可进入制作，没有样板范围的运行依据。

| 调整 | 已实现行为 | 仍不能证明 |
| --- | --- | --- |
| 专业规划前移 | Brief 决策时明确相关具名 Skill；设计核对和实现规划在原任务内进行，不新增作者/Reviewer 派工 | 实际作者必然调用、正确应用方法，或审读必然找到全部语义问题 |
| 样板范围 | Brief 的 `Playable` 从现有 Delivery IDs 选取，必须引用有效条目且包含运行检查；旧 Brief 可读，但新样板推进不能猜测缺失的选择 | 作者选取的路径和条目足以覆盖所有关键体验 |
| 实际运行依据 | `.beegame/delivery/playable.json` 复用验收结构，只验选定条件及已注册内容消费；缺失、失败、模拟代替实际运行或来源/构建/证据过期都停止推进 | 记录中的观察真实、游戏确实有趣或精美 |
| 版本绑定 | 共用只读 checker 输出来源与文件字节快照，之后核对快照；构建输出即使不计入源码版本也不能静默换版 | 重新计算快照意味着重新测试；哈希只是身份，不是测试 |
| 功能制作 | 样板路径先整合操作、UI、资源、声音、反馈和恢复，后续按完整玩家行为扩展并检查受影响消费者 | 要求写入 Prompt/Skill 就能保证制作效果或节省成本 |
| 专业意见 | 复用有权者 `/quality-review` 操作，`scope: sample` 单独记录样板意见，不推进阶段、不授予发布资格、不成为新增必经人工关卡 | 一次样板认可能代表最终首发；历史意见能代表已改动的当前游戏 |
| 验收展示 | 区分阶段、运行记录、作者体验观察、未验证项、样板意见和最终放行；刷新结果不调用模型 | 展示完整就是自动质量保证 |

`verification.quality` 保存体验观察及未验证项，区别于必要行为的 `knownIssues/unverified`。没有玩家、观看或实听证据，不改写成体验 PASS；必要功能失败也不能移进体验限制来绕过验收。最终仍检查全部 Delivery 条件、首发屏幕和目标尺寸，保留原有权限与最终质量决定。

新增范围选择是为了避免样板被整批首发要求拦住；新增快照是为了避免把旧观察重新绑定到已变化的源码、构建或证据。复用既有报告、版本计算和 checker，不增加决策分类系统、趣味评分、独立原型、审批引擎、循环审计或执行次数上限。专业 Skills 只补规划、执行和体验检查方法，已有美术/UI/音频/手感方法不再重复堆叠。

此次只修改系统与合成夹具，没有人工改写 BGS 游戏，也未启动付费生成。离线核对覆盖无证据不推进、范围区分、过期失效、数据消费、权限和样板意见不能发布；真实产出品质、专业方法实际采用情况、Token 与耗时收益仍需另行授权，用不同 Idea 验证。历史报告和第 17—20 节记录保留原时点事实，不改写成新方案已通过。

本次相关服务端回归 94 通过、0 失败；3 项需显式启用的真实浏览器检查跳过。验收面板及协作展示 48 通过；服务端/前端类型检查、4 个修改方法的 Skill 校验及差异空白检查通过。模拟报告只证明受测系统行为，不冒充实际游玩证据。当前运行服务和原生 CLI 包未重启/重建；进入新方案真实测试前需同步构建并安全切换服务，不能把仍运行旧代码的项目当作新方案样本。
