# 项目对话与交付流程分离

## 目标

“修复按钮文字”“玩家速度调快”“为什么画面不对”是现有项目的一次对话，不是重新交付整个游戏。

## 实现边界

- HTTP 入口负责身份、项目归属、附件、请求 ID 和并发互斥。
- `project-conversation.ts` 将原始输入交给项目主会话，不创建 implementation worker，不添加影响分析阶段。
- Session Manager 负责流式事件、权限、计费、停止及原生会话恢复。同一项目连续请求复用 Claude Code 会话；语言变更只重启传输并恢复原生 UUID。
- Agent 自行决定调查范围、工具、委派与修改顺序。涉及玩法/数值需求时，同步相关文档和实现；不把文档永久锁成只读，也不强制整套文档重写。是否允许修改仍以用户请求和原生权限为准。
- 资源、生图、Preview 能力按需查阅；能力文件不包含原需求的扩大改写。测试浏览器清理不关闭用户的项目 Preview。
- 原工作流仍负责用户明确启动的构建/继续交付及整体验收。它不能与项目对话同时修改同一工作区。

## 消息与结果

- 用户原文只记录一次。网络重发按 `clientMessageId` 幂等，不按文本去重。
- 内部 `workflow_worker` 指令保留在审计 transcript，但不进入 Chat。历史 journal 只过滤显示，不重写文件或编号。
- 普通请求使用原生最终结果，不要求额外 `runtime-*.json`，不把一次回复当作验收通过。
- 修改不会重置已完成任务、重建资源或重跑文档阶段。已有整体验收结论与当前文件不符时，仅撤销该结论，等待显式复验。交付门禁仍检查实际文件和证据。
- Chat 的继续操作恢复对话；显式 workflow resume/retry 才恢复交付。

## 无费用验收

使用临时工作区和模拟 runtime 验证：原文传递、附件、连续请求/重启恢复、语言切换、网络重发、停止、忙碌拒绝、历史与实时内部消息过滤、请求/交付状态隔离、验收失效但任务不重置。

本次回归：后端 143 项、前端消息转换 22 项通过；前后端 TypeScript 检查通过。未调用真实模型，未修改示例项目，未重启现有服务。

真实模型对需求范围和文档同步的判断不由这些测试保证。上线后可由用户分别测试：仅诊断 UI、修复单个按钮、修改移动速度、调整玩法；检查实际改动与必要验证，不以“少调用工具”代替正确性。不承诺未经实测的耗时节省比例。
