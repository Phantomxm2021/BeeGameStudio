# 项目 Agent 与交付状态

## 目标

一个项目由同一个原生 Agent 会话承接原始目标和后续对话。“修复按钮文字”“玩家速度调快”“为什么画面不对”不会启动新的交付阶段或重跑已完成内容。

## 实现边界

- HTTP 入口负责身份、项目归属、附件、请求 ID 和并发互斥。
- `project-conversation.ts` 将原始输入交给项目主会话，不创建 implementation worker，不添加影响分析阶段。
- Session Manager 负责流式事件、权限、计费、停止及原生会话恢复。同一项目连续请求复用 Claude Code 会话；语言变更只重启传输并恢复原生 UUID。
- Agent 自行决定调查范围、工具、委派与修改顺序。涉及玩法/数值需求时，同步相关文档和实现；不把文档永久锁成只读，也不强制整套文档重写。是否允许修改仍以用户请求和原生权限为准。
- 资源、生图、Preview 能力按需查阅；能力文件不包含原需求的扩大改写。测试浏览器清理不关闭用户的项目 Preview。
- 新项目不创建旧阶段 `run.json`，也不启动阶段 worker 或 checklist drafting。主机保存原始目标、当前交付里程碑、暂停状态与当前版本的验收收据；除下述依赖写作分组和一次独立联合 Review/Revision 外，Agent 自行选择实现方法与验证方式。
- 旧阶段控制器及其生产入口已移除。磁盘上的旧 run 仅作历史记录，不驱动项目请求、继续、停止、排队或 Chat 上下文，也不与原生交付状态双写。

## 消息与结果

### Author 分批交接

同一个项目会话按五批完成文档草稿：

1. GDD：撰写范围、规则和完成条件，保存后供后续专业作者使用；此时仍是未审草稿。
2. 技术基线、美术、音频：建立后续作者需要的约束与方向，技术消费细节留待最终补全。
3. 关卡、数值：协调实际空间与数量规则。
4. UI：依据已交付专业决策完成操作、布局与界面反馈。
5. 技术补全、资产计划：对照具体设计完成运行时消费与资源规格。

GDD 由主 Agent 撰写；后续专业文档沿用原生写作角色和文档局部上下文。技术基线、美术、音频可并行，关卡后接数值、资源计划后接技术补全，遵循实际依赖。撰写分组不再意味着每组必须审查，也不把八文档塞进一个长上下文。作者使用适用 Skills，负责必要决策及基本保存/引用正确性；简单项目允许简短文档，不为凑章节或数据表扩展游戏。主机不创建额外项目 Session。

专业作者通过本轮私有 stdin 元数据取得文档局部上下文及 `project-author.ts` 中的职责，预加载相应写作 Skill，继承项目当前模型、原生权限和取消机制。作者读取原始简报、已保存草稿和真正相关的源定义；运行时交接实际结果，不追加主模型“再总结一次”的回合。异步任务等待同一任务完成，不重复生成；工具或 Skill 缺失、权限拒绝、执行失败或取消均停止，不改由主 Agent 代写。派出和 Skill 加载保证执行路径，不保证语义质量。

主机保存当前撰写批次。GDD 仍需本轮明确的 `complete` 结论；后续批次需实际调度的原生作者成功完成，并核对本批与前序草稿存在。普通聊天结束、空结果、失败或取消不能冒充交付。前四批完成后继续下一撰写批次，最后一批完成后才进入一次覆盖八文档的联合 Review。`designDrafts` 只记录未审稿件的字节、版本与证据，用于保护当前作者范围之外的草稿；它不是审查基线，不能供制作阶段放行。联合审查通过才建立 `designBaseline`。旧中间 Review 或部分已审基线不能静默转为新流程下的通过状态；需要明确处置，真实历史产物不自动改写。

每个正式 Review 步骤由运行时直接派出新上下文的原生 `bgs-design-review` 角色，不由主模型决定是否执行或用作者阶段的旧审查替代，不恢复作者、不分派逐文档 Reviewer、不由主会话重复审稿。该角色继承当前模型，通过原生 `skills` 预加载 `game-design-check`；运行时从同一 Skill 的 `references/document-checks.md` 直接加载本轮文档及已记录问题关联源的专业方法到角色输入，不依赖模型主动调用 Read，不把方法复制维护进职责 Prompt。相关节缺失就停止；其他专业资料仍按实际依赖读取。私有元数据传入原始任务上下文、当前步骤、准确回执路径和可编辑文件范围；协调者不另写一份预测结论。Skill 只提供方法，职责来自角色/任务 Prompt，放行规则由主机执行。缺失 Skill、任务文件或任务路径越出真实工作区时停止，不静默降级。加载与完整读取记录不证明语义合格；Reviewer 的 complete 只表示步骤执行完毕，不是最终交付认证。

### 文档交付：可消费基线，非零缺陷承诺

验收目标是下游能工作、不必猜关键答案。八文档各自保留专业决策权，GDD 只对核心玩法和范围有权威。趣味性、最终平衡、最终画面与听感留给实际制作验证；可选润色不阻断交付。

正文保留设计规则和必要表格。`.beegame/design-handoffs/<文档名>.json` 收敛为实际消费者需要的最小索引：输出 ID、实际章节、可观察验收期待的章节与方法，以及必要证据引用。删除状态、声音行为、数值、资源规格、输入映射、readiness 和 pending 等镜像/台账；这些决定由正文唯一表达。程序检查索引、明确引用和证据字节，实际资源/Content/runtime 仍走各自校验。程序不再宣称通过重复表格验证了规则、覆盖或专业职责。

Review 原始任务输入附带当前范围的输出/验收/证据指针，来自实际侧车而非作者摘要，不含无须审读的哈希/版本镜像。Reviewer 仍读取真实正文、相关源证据并判断期待的意义和覆盖；只有具体未解决问题才重读侧车，不逐份复查宿主已检查的元数据。坏索引保留既有确定性修订路径，不伪造指针。作者不在宿主升版及同组写作完成前运行整批 `--design-handoff`；原生专业作者权限拒绝该过早入口，合同 help 和相关局部计算仍可用。

新索引使用 `version:2`。主机仅在获得有效交付结果的授权写边界维护文档头版本、索引 `documentVersion` 和证据哈希；实际修订升版，未改不升，不要求模型双写。只读检查不会改稿。基线仍绑定正文、索引及证据；正式 Content 和运行验收仍绑定真实源版本，不能拿设计数据本身充当运行结果。旧 v1 索引只读兼容其实际消费字段，不再检查退役镜像，也不因此重新认证旧项目。内嵌 handoff 仍需明确迁移，不能悄悄重写真实产物。

已保存草稿的普通索引、引用和证据问题交给这一次联合 Review，不增加逐批修复关卡；缺稿、原生执行失败、越界路径或真实写入失败仍立即停止。主机只处理本轮事先捕获且实际获准编辑的文档；普通提问、失败/空回合，以及状态已被其他操作改变的过期结果都不能触发升版或推进。

尚未确定的专业输入在相关正文说明负责人和影响，不伪造已交付答案，也不在每份索引复制一份状态台账。联合 Review 检查制作必需决策是否明确、彼此一致；真实未决项进入现有问题回执，不能用 follow-up 标签放行已经依赖它的工作。

关键平台事实需要实际合同、资料或能力观测，并保留来源。合同值可按 JSON pointer 验证，观测需包含实际检查及结果，不能只有 PASS。程序生成哈希只绑定字节，不生成通过观测，也不证明来源权威或事实充分成立。无依据且影响制作的假设仍需明确处置；常规设计不为凑证明材料建立临时仿真。

主机将现有 review 里程碑改为有限的三个步骤，而非让同一个模型自行宣布循环结束：

| 步骤 | 执行内容 | 可写范围 | 结束条件 |
| --- | --- | --- | --- |
| inspect | 联合读取全部已保存设计及相关源，列影响制作的具体问题 | 本轮回执 | 无阻断项则结合程序检查释放；可纠正问题进入一次 revise；需裁决/补证据则停止 |
| revise | 一次集中修订已记录的源定义和受影响消费者 | 授权文档、最小索引、正文明确引用的既有计算文件、本轮回执 | 主机完成版本/哈希维护；不得自行关闭问题；程序检查仍失败则停止，否则进入 verify |
| verify | 只核对问题、修订及关联要求 | 本轮回执 | 每项已记录问题有关闭依据或明确保留；仍阻断则停止，不再自动 revise |

原生工具权限实际约束上述范围；禁止任意 shell 写入及另派 Reviewer。Hook 自动批准也必须经过权限检查。32 个原生执行回合是执行保护上限，不是审计轮次或合格分数。缺回执、错步骤、只读源版本漂移、无效数据、无源位置、漏报旧问题、修订者自证关闭或降级逃避阻断均不能释放。

已经用于支撑关键结论的计算，源定义改变后不能继续冒充有效证据；必要时通过既有工具修订和重算受影响部分。只授权已有、非符号链接、被受影响文档明确引用的具体文件，不授予整个目录或运行时代码权限。Inspect／Verify 保持只读，不执行项目代码；服务器不代跑模型或改写观测。普通规划不要求每份文档有计算文件、附录或模拟器；无法在现有证据和授权范围内解决关键问题时停止并说明原因。

数值助手对八份设计文档的源身份仅排除唯一合法的 Version 元数据行，并在输出标明 Hash scope；计算读取相同的正文范围，模型代码及其他源文件仍绑定原始字节。这避免自动升版造成无意义重算，不豁免实际正文或模型改动。运行验收仍绑定完整正文及索引字节。

每个问题记录实际源章节、具体下游影响、关闭条件、负责人和 neededBefore；纯可选改进使用 null。Verifier 可以更新剩余影响描述，但不能改写问题身份、范围、负责人、严重性、关闭条件和截止阶段；Revise 原样移交发现项。问题和关闭依据保存在现有 delivery state，不另建台账。到期的必要决策不能以 follow-up 标签通过；争议停止受影响的自动交付，不重复付费重审。

放行保存文档/证据快照、版本和已知限制。下游开始前及完成后检查基线；初始作者只可按排定职责补全设计，其他基线变更需要明确的受影响修订请求。不把八文档全重跑。旧 follow-up 继续保留，但不会因为新的局部请求而一起取得编辑权限。设计版本变化后，正式 Content 的 documentRevision 必须重绑定；涉及美术、音频、资源计划时先核对受影响资源，再进入 Content，否则直接进入 Content，复用仍有效数据与资源。不能拿新文档配旧 Content 直接回到实现。可通过以下已认证项目接口查看和处理升级项：

- `GET /api/projects/:id/design-review`：当前步骤/问题、版本基线、问题与关闭历史。
- `POST /api/projects/:id/design-resolution`：`{instruction, mode:"revise"|"verify", findings:[原问题或有实际源位置的变更问题], start?:boolean}`。指令是明确负责人/用户决定或补证据要求，不是通过声明；不能改写已记录问题。仅重新启动指定受影响修订/核对，仍需实际关闭依据。默认不启动模型；`start:true` 才执行该请求。当前 turn 运行中时拒绝修改。
- 旧项目没有新基线时，不能自动进入依赖阶段；准备必要源引用后，使用 `mode:"inspect"` 明确审查全部设计并建立首次基线。不能对已有基线用 inspect 掩盖无限全量重审。旧正文、历史运行验收证据不改写或删除，也不自动获得新的文档认证。已完成项目变更设计后仍需处理受影响的资源/Content，并重新实现和实际验收。

确定项由程序查，事实靠实际证据，语义由有限 Review 辅助，关键争议由明确责任方裁决。上述运行约束不承诺绝对没有语义漏检；其作用是让检查和返工有边界、结论有依据、待决风险不能隐含转嫁给下游。

2026-10-04 落盘核对：相关 22 个测试文件共 264 项离线回归通过，覆盖有限审修、实际工具权限、引用/证据、跨批依赖、基线变更、原生交接与项目接口；原生 SDK 路径使用模拟模型，不是付费模型产出的质量验收。服务端类型检查、检查 Skill 校验及 diff 空白检查通过。全仓类型检查仍有既存的 sceneContentAdapter 模块引用与旧测试类型错误，未作为本轮无关修复范围。本轮未修改真实生成项目或启动付费测试。

每批作者只接收自己的职责和相关前序依据。联合 Review 后八文档成为制作基线；正式 Scene/UI 是实际数据源，后续验证该数据及其运行时消费。发现设计缺陷应报告证据并处理受影响部分，不能通过改文档迁就实现。Review 的限范围编辑和停止条件仍由程序执行。

八文档的详细写作要求集中在 `project-author.ts`，只随所属批次发送，不在总指令或 Skills 中再复制一套。GDD 定义玩家承诺、首版范围和核心玩法契约：语义动作、玩法后果、核心状态及胜负条件，不统管全部玩家可见行为。关卡落实空间、取景与生成约束；数值定义参数、公式与调优；美术定义视觉身份及世界反馈组合；技术拥有运行时执行、模块协作和数据消费；UI 拥有操作映射、页面交互、布局适配、参考/最小宿主尺寸及界面动效；音频定义声音行为；资源计划拥有生产规格和资源组织。

用户明确要求和真实平台约束跨专业生效；作者方案的权威限于其责任范围，不因先写入 GDD 而扩大。GDD 未获用户指定时不预填专业参数、尺寸或缩放政策，只明确待决事项及负责文档。Author/Review 内由负责角色形成专业决定，整合角色同步源定义与受影响引用；主 Agent 协调交付，不替所有专业拍板。涉及已确认要求或约定范围变化时请求用户决定。Review 后仍保护既有基线，后续阶段发现问题按原有边界报告，不自动回退或擅自改文档。

所有作者批次共用决策归属要求：写作时区分用户/平台约束、已交付责任方决定、本职待决事项和其他专业待决事项；引用需要不授权代填专业默认值。按决策主题判断归属，区分玩法规则或范围与实现它的参数、操作映射、表现和技术方案，表格或示例中的细节也受同一边界约束。作者交付实际草稿及未决影响，独立 Review/Revision 承担正式越权、遗漏、矛盾、依赖及声明检查与修订复查；主会话只协调交接。文件存在、引用有效及“已检查”声明不等于内容正确，不新增检查报告或审批阶段。

委派时提供原始简报、当前项目上下文输入路径和相关源文件，接收者据此读取适用的用户/平台要求，不把协调者摘要当作唯一约束来源。交接前对照相同输入核对实际保存文件。临时上下文仅是本轮输入，不成为文档的持久引用权威。

这些要求规定设计结果，不规定写作方法或章节模板：按确认范围适用、共享规则只保留一个权威定义、不虚构已完成的运行验证。数值计算不等于试玩平衡已验证；资源计划不提前生成素材或猜测图集裁切坐标；UI 与场景必须共同解决游戏视图、HUD 和操作区的空间分配。此次细化不增加批次、评审或 Session。

界面切换与动效由现有 `game-ui-ux-designer` 深化：处理动作生效与视觉完成的区别、注意力与空间连续性、输入/焦点、重复或中断及减少动态效果。新增 `game-feel-designer` 负责操作响应、动作节奏与跨动画/特效/镜头/声音的游玩反馈和冲击力，不要求每个游戏使用震屏、顿帧或粒子。结果仍落入现有八文档：美术定义世界动作与反馈组合，UI 定义界面动效，数值定义动作/模拟参数，音频定义声音行为，技术消费实际事件与生命周期，资产计划汇总所需资源。适用职责调用相关 Skill，不新增文档或批次；Author-2 的美术作者预加载该 Skill，其他阶段不据此固定代理阵容。规划不等于真实手感已验证。

质量验收仍关注规则一致、布局可行、后续设计返工，以及真实总耗时和 token，不能以批次运行完毕代替。
