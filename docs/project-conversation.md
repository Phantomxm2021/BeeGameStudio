# 项目 Agent 与交付状态

## 目标

一个项目由同一个原生 Agent 会话承接原始目标和后续对话。“修复按钮文字”“玩家速度调快”“为什么画面不对”不会启动新的交付阶段或重跑已完成内容。

## 实现边界

- HTTP 入口负责身份、项目归属、附件、请求 ID 和并发互斥。
- `project-conversation.ts` 将原始输入交给项目主会话，不创建 implementation worker，不添加影响分析阶段。
- Session Manager 负责流式事件、权限、计费、停止及原生会话恢复。同一项目连续请求复用 Claude Code 会话；语言变更只重启传输并恢复原生 UUID。
- Agent 自行决定调查范围、工具、委派与修改顺序。涉及玩法/数值需求时，同步相关文档和实现；不把文档永久锁成只读，也不强制整套文档重写。是否允许修改仍以用户请求和原生权限为准。
- 资源、生图、Preview 能力按需查阅；能力文件不包含原需求的扩大改写。测试浏览器清理不关闭用户的项目 Preview。
- 新项目不创建旧阶段 `run.json`，也不启动阶段 worker 或 checklist drafting。主机保存原始目标、当前交付里程碑、暂停状态与当前版本的验收收据；Agent 自行决定工作顺序、是否委派及如何验证。
- 旧阶段控制器及其生产入口已移除。磁盘上的旧 run 仅作历史记录，不驱动项目请求、继续、停止、排队或 Chat 上下文，也不与原生交付状态双写。

## 消息与结果

### Author 分批交接

同一个项目会话按四批完成文档草稿：

1. GDD：范围、规则和完成条件。
2. 关卡、数值、美术、技术设计：共同落实空间与可行性。
3. UI、音频设计：依据前面的设计完成界面与反馈。
4. 资产计划：汇总已确定的资源需求。

Author 指令要求依赖明确的独立工作使用子代理并行，具体拆分和角色由 Agent 决定。主 Agent 确定 GDD；第二批协调关卡与数值，让美术、技术并行；第三批并行 UI 与音频；最后统一汇总资产。每批按职责检查并调用适用 Skills，已加载且适用的指导可以复用。主机不创建额外项目 Session，不固定代理人数。

主机保存当前批次，成功回合结束且本批及前序文件存在时交接下一批。这个检查只确认交接文件，不能证明设计合格。中断与重启保留当前批次；同批错误重试不重复发送完整指令。四批之后只进入一次统一 Review/Revision，不为每批增加评审。

每批只提供本批职责与前序依据；Agent 自行选择工具、Skills、子代理和批内顺序，Author 期间可以修订先前草稿。Scene/UI JSON 的数据权威从第一批明确。Review 后八文档成为实现与验收基线；后续阶段发现设计缺陷应报告证据，不能通过改文档迁就实现结果。这是交付职责说明，不是文件沙箱，也未新增自动回退评审。

八文档的详细写作要求集中在 `project-author.ts`，只随所属批次发送，不在总指令或 Skills 中再复制一套。GDD 完整定义玩家行为与状态；关卡落实空间、取景与生成约束；数值验证规则可计算且可行；美术定义可执行的视觉语言；技术明确模块协作和数据消费；UI 覆盖每页布局、空间不足与交互反馈；音频定义触发、停止与叠加；资源计划将这些设计转为有用途和规格的资源需求。

这些要求规定设计结果，不规定写作方法或章节模板：按确认范围适用、共享规则只保留一个权威定义、不虚构已完成的运行验证。数值计算不等于试玩平衡已验证；资源计划不提前生成素材或猜测图集裁切坐标；UI 与场景必须共同解决游戏视图、HUD 和操作区的空间分配。此次细化不增加批次、评审或 Session。

质量验收仍关注规则一致、布局可行、后续设计返工，以及真实总耗时和 token，不能以批次运行完毕代替。

### UI / Scene 空间计算（2026-09-30）

2026-10-01 的实测发现：局部 HUD 与相机分别通过，不代表新增的全屏适配规则成立。现有计算器支持 `--layout-draft ui-file host-width host-height --game-view node-id --camera camera-file`，从同一份完整 UI 草稿取得游戏区域及宿主偏移，再复用现有相机算法。设计或修订改变布局时，更新该草稿并复算受影响尺寸，文档引用对应输入及结果；不再手工维护另一份相机区域尺寸。该命令仍只读，不新增阶段、验收门禁或自动付费回合，也不验证审美、文字排版、3D 对象可见性及 XR 舒适度。

后续修正：技术文档只说明加载、转换与消费，引用 UI 的屏幕分配和 Scene 的世界/取景要求，不重复维护具体矩形、视口分配或验收偏移值。Agent 声明构图、排列、间距、内边距及控件尺寸约束，现有 Yoga 计算最终矩形；最小容纳空间用包含最小控件尺寸的自动容器计算，不另写心算表。每个已规划页面和弹窗均有计算输入或共享构图引用，正式 Review 核对这些输入与最终声明，覆盖参考、最小支持和布局切换边界。补充只读 `outsideContentArea` 诊断：流式子节点侵占父容器内边距也会报告，绝对定位覆盖层明确退出该检查。不新增算法、阶段、自动修复或机器设计 PASS。此后真实模型验证使用全新隔离项目，不继续修改此前测试游戏。

移除测试期间追加的逐文档自检记录、检查子代理安排和修订后独立检查要求；保留一次正式 Review/Revision。Agent 仍可自主协作，但 BGS 不指定审计代理、额外检查轮次或报告。已保存的测试日志与产物只是历史证据，不进入新项目指令。

UI_UX_SPEC 唯一定义布局选择条件和屏幕空间分配；LEVEL_SCENE_DESIGN 定义世界、取景与玩法必须可见的范围，引用 UI 的分配，不另写一套阈值。竖屏、横屏、空间受限时可以选择不同布局；是否悬浮由游戏决定，暂时没有物体的区域不等于可以覆盖的安全区。

Author 中的 Scene/UI 批次、Review/Revision、Content 和 Implementation 直接收到项目内计算入口；恢复旧会话时也刷新入口。使用只读 `check-content.mjs --layout-draft 文件 宽 高` 计算 UI 容器及 2D Scene；`--camera-draft 文件 宽 高` 复用已有的正交/透视镜头取景计算；已登记内容使用 `--layout`。规划草稿不依赖 Manifest、内容索引或游戏实现。先算 UI，再将游戏显示区域的实际宽高交给 Scene，并保留宿主偏移。相关设计段落记录输入引用与简明结果，不增加审计报告或机器 PASS 门禁。后续内容/实现只恢复已评审约定，不因计算失败自行改写设计基线。

计算命令在容器计算前初始化现有 Yoga 算法。矩形与取景计算不证明未测字体、玩法遮挡、3D 物体可见性或 XR 舒适性；XR 使用设备投影，不能用平面窗口适配替代。正式评审修订空间决策后，重算受影响布局并同步引用，不要求另找检查代理。

### 阶段指令交接审计

内容阶段负责把已评审设计落实为可编辑数据，并简述哪些动态行为、反馈和引用仍需运行代码接入；格式通过不等于设计覆盖或可玩。坐标、组件和 Tilemap 规则由现有内容契约提供，阶段指令不另抄示例，不要求新增清单或报告。发现设计矛盾或格式不能表达需求时明确报告，不静默省略。

用户明确改变设计时先修订受影响基线，再实现该变更；恢复既有设计的缺陷修复不要求改文档。程序化资源的生成产物或生成器应实际可用，但数据/运行时表达的简单图形不必提前建成独立资源框架。验收首次交接提供报告契约，同阶段自动续接只指向当前上下文中的契约，不重复插入字段规则。以上仅调整指令与交接，不改变阶段、Session 或自动续跑逻辑。

### 验收报告提交前检查

验收回合提供只读 `check-acceptance.mjs` 命令，复用交付端的 `readRuntimeAcceptanceReport`，核对报告、真实内容引用、适用绑定检查及证据/构建文件。不再使用只检查字段组合的另一套实现。命令不启动浏览器、不修改项目、不登记验收、不发布；通过仅说明记录通过机器校验，不证明报告中的观察真实或美术/玩法合格。最终门禁仍检查当前版本身份。

评审与实现不能以原生回合正常退出代替完成结论。Agent 在该回合独有的临时结果文件写 `complete` 或 `blocked`（下一行简述原因），BGS 只据此交接，不判断其工作方法或聊天措辞。缺失、无效或阻塞结论不自动推进；旧回合结果不复用，普通用户回合若已明确完成也无需再重复该阶段。

持久 CLI 的结果必须先归属到请求：原生 `user` replay 的 UUID 确认当前请求已被消费；确认前的旧子任务通知结果不得结束当前回合。回执前的流式片段暂存，旧结果到达即丢弃其片段，当前回执到达才交给当前回合。CLI 结果附带命令 `request_id`，覆盖首次回复/回执前的模型错误。只有所属回合真正结束后，才清理其权限、工具入口与临时交接文件；不增加模型续跑或限制子代理。

2026-09-29 回归：复现旧音频通知在新评审请求前结束的时序，使用 stdio 子进程贯穿 SessionManager 与阶段交接，确认只收到真正的评审结果、权限回调仍有效、最终才清理上下文。真实 CLI 使用本地模拟模型验证委派、读取/写入、本地命令和上游错误，无付费调用；与接续、报告、发布及 Preview 回归合计 116 项通过。另修复上游错误仅在 `result` 字段时被替换成通用失败提示的问题。本次未自动恢复或修改真实测试游戏。

验收处理统一依据诊断类别：报告格式与内容引用错误均为 `report-invalid`，沿用已有的一次新诊断反馈，未变化不再自动续跑；验证不足、实际失败或 Agent 报告阻塞不会作为格式修复重试。预检明确返回 `publishReadiness: not-checked`；发布接口返回阻塞层 `report`、`acceptance-record`、`delivery`、`revision` 或 `ready`，防止把报告校验通过误当成当前版本已可发布。

诊断分类为报告无效、验证不足、游戏验收未通过；保留具体原因供 Agent 自主纠正或补测。校验分类不增加自动续跑或改变已有阶段推进规则。已有证据仅在对应实现未变化且仍有效时复用。检查器仅在验收回合提供，回合结束清理。

### 共享浏览器测试依赖

服务器依赖固定版本 `playwright-core`，随正常依赖安装提供，游戏无需添加测试依赖。项目执行环境的 `BEEGAME_PLAYWRIGHT_MODULE` 是该包 ESM 入口的文件 URL；仅对包的真实目录开放只读权限，不开放 BGS 源码或整个 node_modules。Node 脚本可用 `await import(process.env.BEEGAME_PLAYWRIGHT_MODULE)`，再用 `chromium.connectOverCDP(endpoint)` 连接 Preview API `POST /browser` 返回的地址。使用现有隔离、静音、随能力关闭的浏览器，不读取个人浏览器配置。

已有测试 Chromium 优先复用；新主机在服务器包目录运行 `bun run test:browser:install`，只安装 Chromium Headless Shell，或配置 `BEEGAME_TEST_BROWSER_EXECUTABLE` 指向已验证的可执行文件。安装是主机配置步骤，不由每个游戏重复下载。Agent 自行安装的工具仍使用项目缓存；共享浏览器由宿主启动，不需要向 Agent 开放宿主浏览器缓存。共享客户端通过 CDP 的功能范围需由真实连接、交互和截图测试验证，不宣称具备所有 Playwright 原生协议功能。

### 会话交互

- 用户原文只记录一次。网络重发按 `clientMessageId` 幂等，不按文本去重。
- 内部续做指令和历史 worker 指令保留在审计 transcript，但不进入 Chat；不改写历史事件或编号。
- 普通请求使用原生最终结果，不要求额外 `runtime-*.json`，不把一次回复当作验收通过。
- 修改不会重置已完成任务、重建资源或重跑文档阶段。未交付时的新里程碑或新增校验信息由同一原生会话接续，不凭旧阶段记录派遣其他 Agent；用户明确停止后不自动续做。
- Agent 提交 `.beegame/delivery/acceptance.json`，主机仅在报告、证据、构建输出与源码版本均新鲜时记录交付收据。发布门禁再次核对这些字节；Chat 中的 `passed` 不等于交付通过。
- 完整交付的 `passed` 还要求在实际目标运行环境验证约定范围；模拟渲染只能作诊断。首版范围内有已知问题或未验证要求时，报告为 `failed` 或 `blocked`，不能用 `passed` 抵消。Scene/UI/VFX 注册表不接收通用玩法配置，项目自有共享数值数据由游戏自行加载，不能在文档里承诺一个不受支持的内容类型。
- “继续”恢复同一 Agent 和原目标；并发继续只认可当前运行中的一轮。旧 `workflow/retry` 不用于新项目。

## 无费用验收

临时项目与模拟 runner 验证：新项目只启动一个主 Agent、不生成旧阶段 run、后续对话不重复显示用户消息、停止/继续和 queue/steer 维持同一会话、旧 run 不能重新派遣 worker、源文件/证据/构建改动使发布验收失效。离线测试不代表真实模型交付、浏览器游玩或耗时验收；不调用模型、不修改示例项目。

直接 CLI 与 BGS 的耗时/质量对照必须使用同一份已确认需求和首版范围；不能将仅含一句创意且允许 Agent 自行扩张的 CLI 项目，与已限制为小型首版的 BGS 项目直接比较。
