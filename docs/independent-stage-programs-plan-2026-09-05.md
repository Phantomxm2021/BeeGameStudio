## 1. 必须成立的依赖关系

合法方向：

现有编排 → 某阶段 public 入口 → 该阶段 private 实现。
阶段结束 → 公开结果 → 现有编排 → 下一阶段 public 入口。
各阶段 → 认证模块 / 计费模块等基础能力的公开入口 → 该基础模块自己的私有实现。

禁止方向：

- 阶段 → 编排实现，或把内部操作作为回调交给编排完成。
- 阶段 A → 阶段 B 的 public 或 private 代码；阶段之间由编排交接数据，不直接调用。
- 多阶段 → 共同的项目 dispatcher、controller、transition、store、session adapter、业务校验器或公共阶段 SDK。
- 编排/UI → 阶段私有任务、checkpoint、worker 回调、事实库、修订批次或恢复实现。

共享数据约定不是共享实现。各模块维护自己的契约解析及验证；不建立公共运行内核或统一业务 parser。编排可导入各阶段公开入口及公开类型，不得因此导入私有流程。禁止通过依赖、动态 import、路径别名、符号链接、全局单例或内部服务代理绕过边界。

可使用语言标准库、操作系统、外部模型服务及基础模块的公开 API。只有阶段专属执行实现归入该阶段；认证、计费等通用能力按各自所有者封装，不在各阶段保留副本，也不复制整个包含所有阶段分支的大内核。基础模块不得反向调度阶段、接纳 worker 终态或修改阶段 checkpoint。

认证、计费是正常模块依赖，不是对隔离规则的临时豁免。禁止的是越过公开边界及共享阶段内核，不是禁止合法模块复用。旧 session-manager/dispatcher 不能仅改名为“基础服务”继续承担三阶段业务。

## 2. 不变范围与保证边界

八文档业务保持不变：提示、文档契约、依赖调度、模型策略、正文生成、内部完成及重试语义冻结。不重生成、不恢复暂停项目。

八文档尚未完成独立，必须作为 P1 正式迁移，不能只增加外层接口。当前 controller、dispatcher、transition、run-store、recovery、session adapter 和展示入口中属于作者的执行职责及传递依赖，全部归入作者模块私有实现；编排不能继续替作者派发、接纳终态、持久化或恢复。

“保持不变”限定为业务规则和可观察行为不变，不是冻结耦合代码位置或免除隔离。允许为完整剥离移动、拆分和接线，必要项目代码副本由作者独占；不得通过包装器继续调用旧全局执行链。若确需改变作者业务策略而非代码归属，停止并单独请求决定。

Reviewer/Revision 的审计、修订业务尽量原样迁移。保留业务效果和安全保证，不要求保留原全局状态字段、函数调用序列和跨模块事务。

隔离保证：公开契约和资源访问约束不变时，修改模块内部逻辑，不应要求修改上游、下游或编排代码，也不能直接修改其状态。

这不意味着任意错误都不会产生影响：输出错误会影响消费结果，接口语义变更必须迁移契约，同进程崩溃/OOM也不由代码封装保证隔离。本次不以“零故障传播”作虚假承诺，也不因此扩大为进程隔离工程。

## 4. 公开接口：数据而不是流程

每阶段可提供自己的 start、resume、stop、getResult 公开操作；名称是设计示意，不引入所有阶段必须实现的共享基类。

- start：接收项目身份、调用 ID、明确版本的输入及本阶段配置；返回不透明运行句柄，最终形成公开结果。
- resume：只接收句柄和明确授权的续行请求；内部选择重放、继续任务或报告需要处理。
- stop：接收句柄和停止请求 ID；由模块完成内部停止及持久化，返回公开确认。编排不能自行遍历/中断其 worker。
- getResult：通过句柄读取粗粒度运行状态或最终结果；无结果时明确 running/stopped/needs_action，不读日志猜测完成。

阶段自己持有内部执行循环、并发、重试、会话回收、终态接纳和恢复。不向编排返回“下一内部任务”“请执行此 worker”“请写入此状态”等内部工作指令。
术语约束：“内部终态接纳”指模块接收并处理自己的 worker 结果；“编排结果确认”仅指确认模块已经发布的最终公开结果。编排不能直接接收原始 worker 终态或替模块完成内部提交。
允许提供可选的只读展示摘要；编排不得用摘要决定内部调度。业务数据在最终结果交接，控制面仅暴露必要状态和句柄。

阶段业务输入输出必须是可复制的数据值或绑定版本的只读产物引用，不能返回私有对象、函数、store、可变引用或完整 DeliveryRun。基础模块依赖可以通过其正式 public 入口或类型受限的公开客户端提供，不等于允许注入任意业务回调。公开操作错误只表达调用无效、执行失败、停止或需要用户处理，不泄漏可供编排操作的内部任务结构。

## 5. 交接数据与兼容性

不强制 ZIP、包目录或跨进程文件交换。可以是公开数据对象或现有产物的不可变快照引用；大文档不必重复序列化进对象。所谓“包”仅指完整、自洽的交接数据集合。

公共约定至少明确：

- 协议版本、生产模块、调用/运行身份、唯一结果 ID；
- 项目身份、输入版本与摘要、结果文件及摘要；
- 阶段特有的结果种类和相应必填字段；
- 引用必须可独立读取，不需要生产模块的数据库、会话或任务结构。

文档结果：八文档清单、内容版本/摘要及完成依据。
审计结果：被审计版本、问题 ID、位置、证据、依据、预期条件、允许修复范围和需人工裁决项。
修复结果：基础文档和输入问题的摘要、候选 ID/摘要、完整候选版本、差异、逐项修复声明和未解决事项。修复声明不是审计通过。
复核结果：绑定指定候选及问题版本，给出通过/剩余问题/needs_action。

各消费者在自己的边界验证输入。采用共同的协议样例和反例测试数据，而不共用生产校验代码。
增加字段、删除字段、改变含义分别定义兼容规则；破坏性变更必须升级契约并显式调整编排映射和消费者，不伪装成内部改动。
必须区分格式兼容与语义正确：模块输出仍需本模块测试和下游契约验收。

## 6. 产物和状态的写入权

每模块拥有私有状态命名空间和工作区；不共用可变运行对象、锁对象、单例配置或状态文件。输入只读，输出在完整提交后发布；私有临时文件不成为交接结果。
模块不能修改进程级环境、cwd或其他模块配置来控制执行。路径白名单、文件身份、跨模块写入拒绝纳入测试。

八文档首份交接结果由作者模块在完成内部提交后通过 public 出口发布，只读导出清单与摘要；不是编排读取内部检查点后拼装。冻结样本来源、文件清单和完成依据在 P0 固定；Reviewer 不读取作者私有状态。若现有完成信号不足，不以扫描“文件都存在”冒充完成。

Revision 输出新候选，不覆盖作者原始输入。Reviewer 读取候选副本并发布审计结果，不写候选正文。
通过结果交给现有编排后，下游消费绑定的通过版本。若平台必须使用 canonical 路径，在现有编排侧设置范围受限的产物交接映射：只复制已通过的公开版本，不计算审计/修订业务，不回写作者任务。映射的原子提交与恢复由该交接操作拥有，不另建业务阶段或共享执行内核。

## 7. 现有编排的续接边界

不建立第二套编排入口；在当前入口中移除阶段内部职责，保留串联。现有 controller/dispatch/store 等文件不能凭名称继续认定为编排或公共设施，须逐项按所有权处理。

编排可持久化自己的链路记录：调用 ID、阶段身份、不透明句柄、输入摘要、已接纳结果 ID、下一阶段调用身份和整链停止状态。
这些是交接状态，不包含任何内部任务/checkpoint。模块运行状态与编排链路状态分别恢复，不使用跨模块事务。

必须定义并测试：

- 阶段已完成但编排未接纳就崩溃：按原句柄查询同一最终结果，重复接纳幂等。
- 编排已决定启动下游但确认丢失：使用同一调用身份重试公开 start，不重复开启业务运行。
- 用户停止与终态并发：先持久化整链停止意图，再请求模块 stop；可保留已完成结果，但禁止自动启动下游，直到显式继续。
- 模块停止超时：编排保持停止请求/需要处理状态，不伪造停止成功，不启动下游，不自行修改内部检查点。
- 候选 A 已被 B 取代：A 的迟到结果不能替换当前指定交接版本。
- 不兼容输入、部分输出或过期结果：拒绝交接，不通过修改上下游私有状态“修复”。

## 8. 文档修复闭环的业务保持

Reviewer → issues_found → 编排 → Revision → candidate_ready → 编排 → Reviewer 复核。
Reviewer passed → 编排 → Checklist；needs_action → 停止等待处理。
不新增轮数上限、降级放行或自动放弃。

Reviewer 拥有内容审计与复核，Revision 拥有修改完整性和修复实施。
原流程中的同轮失败重试、仅修失败文档、已通过部分保留、问题连续性及最终发布绑定必须形成行为对照表。通过正式问题/候选/变更结果表达需要传递的事实，不暴露 frozenTaskIds、revisionBundles 等内部结构。
复核后继续修复时，以显式公共数据提供原基础与保留候选的绑定；若原算法需要的依据缺失，应补结果契约，不能跨模块读取私有事实库。
编排只映射公开结论，不决定修哪些文档、如何冻结或何时内容合格。

“业务等价”对照问题集、允许修改范围、保留字节、失败升级条件与发布可见性；不要求复制旧全局事务和事件序列。无法等价保持的业务变化必须单列并先确认。

实现审计/验收返修也通过问题结果交接给实现模块，不由编排重置其内部任务。

6. 结果正确：错误内容并不因格式合法而获准通过；通过本模块规则测试与端到端证据检查。
